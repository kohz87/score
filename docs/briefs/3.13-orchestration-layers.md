# Orchestration layers: oracle, advisor, helpers, forks (3.13 – 3.16)

Owner, 2026-10-27: "how can we achieve something like the screenshot in concept.md? … how we can orchestrate the tasks
like that" → **"All four, step by step"** (decision 150). The concept: a lead does the work; a swarm of cheap helpers
searches, greps and audits; an advisor on a strong model is consulted only at checkpoints; an oracle runs the tests; many
tiny decisions are voted on by cheap models and only split votes reach the lead. Score already has the lead ("lead
decides" jobs), parallel steps and the timeline. This note designs the four missing layers, in the order they ship.

## 3.13 The oracle: a check step that runs a command

**What.** A job (a "lead decides" job, or a recipe) may have a **check**: a command run in a workspace, whose exit code is
the verdict. `0` passes; anything else fails. It is ground truth, not a model's opinion.

**Who sets it: only the person.** In Start a job ("Before it finishes, run …") or as a recipe node. The lead can *run* it
(`orch.check`, no arguments) and read its result; it can never write, change or add a command. Agents' text never reaches
a command line.

**The command.** Entered as one line and split into an argument array by a strict splitter (spaces, single and double
quotes, backslash; no `$`, backticks, globs, pipes, `;`, `&&`, redirection: those are refused with a message, or the
person writes `bash -lc '…'` explicitly, which is then visibly a shell). Run with `execFile` semantics, never a shell string.
Up to 64 arguments, 4 KiB in all.

**Where.** A workspace folder the person picks, checked by the Workspace tab's root policy (`checkRoot`): a coding agent's
workspace or another allowed root. Never Score's or Hermes's homes.

**How it runs.**
- As the Score user, in its own process group (the supervised-unit backend when the computer has it, as coding runs do),
  with the terminal's six-variable environment (HOME, USER, LANG, PATH, TERM=dumb, SHELL) plus `CI=1`.
- Timeout 10 min by default, at most 60; stopped with SIGTERM then SIGKILL; Stop on the job stops it.
- Output: the last 64 KiB of stdout+stderr kept, redacted (`redact()`), shown to the person and (its last 8 KiB) to the lead.
- One check at a time per job.

**The finish rule.** `orch.finish({ outcome: 'success' })` is refused (`check_required`) unless the latest check run
**passed** and started **after the last step attempt ended** (no stale pass). `partial` and `failed` need no pass: an
honest finish is always possible. The person can still close it: **"Finish without a passing check"** on the job is a
decision surface (`data-protected`), recorded on the timeline.

**Recipes.** A new node kind `check` (`{ argv, workspace, timeoutSec }`) whose outcome feeds branches like an agent node's
(`outcome is succeeded/failed`); a recipe can loop back to a fixing step.

**Records and restarts.** `orc_checks` rows (id, orchestration, argv hash, started/ended, exit code, outcome, output tail).
A check is a side effect: started and ended are journaled. A check running when Score stops is killed with its group at
start-up and marked `interrupted` (not a pass); the lead runs it again.

**Confirmation.** Starting a job or recipe that carries a check needs the security password or passkey (the Terminal's
fresh-auth rule), because it runs a command on the computer.

## 3.14 The advisor: a strong model on call

**What.** Start a job may name an **advisor** (any agent that can take work, usually a strong model). Score consults it
by itself at three checkpoints, and stays silent otherwise:
1. **Before the plan:** after the lead's `orch.plan`, before its first `orch.assign`.
2. **Same failure twice:** when a step's attempts fail twice with the same failure (normalised text), or the check fails
   twice in a row.
3. **Before done:** when the lead calls `orch.finish(success)` (after the check passed): finishing waits for the advice.

**What it sees.** A bounded digest: the goal, the plan, each step's instruction and result summary (outside content,
quoted), the last check result, and the checkpoint's reason. At most 32 KiB. It answers in at most 1,200 characters.

**How it acts.** Advice only, never a veto. It is delivered into the lead's next turn as "Advisor: …"; at "before done"
the lead gets one more turn to act on it and may then finish anyway (the timeline shows both). The advisor's turns run
read-only (a Hermes run with no tools beyond reading; a coding agent at read-only permission) and count against the job's
budget. The timeline shows each consult (checkpoint, tokens, the advice).

## 3.15 Helpers: a swarm on a cheap model

**What.** Start a job may name **helpers**: one or more agents (usually cheap models) and how many may run at once. The
lead's `orch.assign` gains an optional `role`: `search` (map where things are), `grep` (find call sites), `audit` (check a
diff), each with a short built-in instruction that asks for a compact, structured result. Helper steps run in parallel up
to the helpers' own limit, outside the main step limit, read-only by default.

## 3.16 Forks: votes on small decisions (experimental)

**What.** A new lead tool `orch.vote({ question, options, k })` (2–6 options, k ≤ 7): Score asks k quick helper turns the
same multiple-choice question with the lead's short context; they answer with one option. If one option has at least 70% of
the votes, the answer is **sharp** and returned as the choice; otherwise **split**, and the lead decides. The timeline shows
the vote and its shares ("which file → src/hooks.ts 0.86"). Costs are bounded by k and tiny prompts; each vote counts against
the budget.

## Adversarial review (lead, 2026-10-27; Codex is on another project)

| # | Risk | Answer in the design |
|---|---|---|
| 1 | The lead or a step injects a command into the check | Only the person sets the argv; `orch.check` takes no arguments; agent text never reaches argv. |
| 2 | A shell sneaks in through the command line | Strict splitter refuses shell syntax; no shell unless the person writes one explicitly and visibly. |
| 3 | The check escapes its folder or reads secrets | Root policy as the Workspace tab; six-variable environment; output redacted; no Score/Hermes homes. |
| 4 | A stolen session runs commands | Starting a job with a check needs the security password or passkey, like the Terminal. |
| 5 | A stale pass lets a broken change finish | A pass counts only if it started after the last step attempt ended. |
| 6 | A stuck or endless check | Timeout (≤ 60 min), process-group kill, Stop stops it, one at a time. |
| 7 | A restart mid-check counts as passed | Killed at start-up, `interrupted`, never a pass. |
| 8 | The person can't finish when tests are broken for an unrelated reason | Partial/failed finishes are always allowed; "Finish without a passing check" is a recorded, protected decision. |
| 9 | Prompt injection from step outputs into the advisor | Step results reach the advisor quoted as outside content; its advice is advice, never a command or veto. |
| 10 | Advisor loops or runaway cost | Three fixed checkpoints, each at most once per trigger; counted in the budget; read-only turns. |
| 11 | Helpers or votes multiply cost | Helper concurrency and vote k are bounded; every turn is budgeted; votes refuse when the budget can't cover k turns. |
| 12 | Vote manipulation by a poisoned context | Votes only pick among the lead's own options; a split goes back to the lead; nothing is executed by a vote. |
