# Task 5.12: Send chat image attachments to agents (owner request, 2026-10-08)

Follow `AGENTS.md` exactly (licensing; Hermes access only under `apps/server/src/hermes/`; zod at every edge; spawn rules;
never read credential files). No new dependencies. Don't commit. Run `pnpm lint`, `pnpm format:check`, `pnpm typecheck`,

## Goal

Images a person attaches to a chat message (message parts `{ kind: 'image', mediaId }`, PNG/JPEG/WebP/GIF in the media
store) reach the agent with the message. Today `routing-dispatch.ts` starts runs with text only.

## Verified Hermes behaviour (0.21.5, read-only source at ~/.hermes/hermes-agent)

- `POST /v1/runs` takes `input` as a string OR a list; with a list it uses `input[-1].content`
  (`gateway/platforms/api_server_runs.py` ~650) and passes it to `agent.run_conversation(user_message=…)`, which accepts
  list content (`agent/conversation_loop.py`, `native_turn_images`).
- Content parts: `{ type: 'text', text }` and `{ type: 'image_url', image_url: { url: 'data:image/png;base64,…' } }`
  (`api_server.py` `_normalize_multimodal_content` documents the accepted shapes; data:image URLs are allowed).
- The gateway refuses request bodies over 10,000,000 bytes (`MAX_REQUEST_BYTES`).

## Design

1. **Which images:** only a hop-0 turn (the person's own message) carries images: the `image` parts of
   `message_runs.parent_message_id`. Hand-offs between agents carry none.
2. **Port:** `HermesPort.startRun` gains optional `images?: string[]` (media ids, in message order). The live adapter
   receives an `imageReader(mediaId) → { contentType, bytes } | null` dependency (wired in `start-server.ts` from the
   `MediaStore`), so `hermes/` never imports the media store. The fake adapter accepts `images` and mentions their count
   in its reply ("I can see 1 image.") so e2e can assert it.
3. **Intent payload:** the durable command intent stores the media ids, never the bytes (they're read when the request is
   sent, including on crash retry). The idempotency comparison includes the ids.
4. **Request:** with images, `input` becomes `[{ role: 'user', content: [{ type: 'text', text }, …image_url parts] }]`.
   Budget: total raw image bytes ≤ 6 MB per message (base64 ≈ ×4/3 keeps the body under Hermes's 10 MB with the
   text); images that don't fit, or whose media item is gone, are skipped and the text gets a short note appended:
   "(2 attached images could not be sent: too large)" / "(… no longer available)".
5. **Redaction:** images are the person's own input like their text (sent verbatim, decided in 1.11a); nothing about the
   bytes is logged or stored beyond the existing media store.
6. Contract: no endpoint change; document in `docs/API-CONTRACT.md` §5 (messages) that image attachments are sent to the
   addressed agents' runs. USER-GUIDE: one line.

## Done when

Server tests: a hop-0 run with two image parts sends the list input with both images (live gateway fake, assert body
shape and base64), hand-off turns send none, an over-budget set sends what fits plus the note, a missing media item is
skipped with the note, the intent payload holds ids only and a crash retry re-reads the bytes. Fake e2e: attach an image
in Chat, the reply says it can see 1 image. `pnpm check` green.
