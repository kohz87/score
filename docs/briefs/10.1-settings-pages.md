# 10.1 — Settings as pages

Owner (2026-10-19): "for settings, can we use navigation page instead of 1 whole column scroll down, it's mostly because
model, connections, especially logs extending too long".

## Goal
Settings stops being one long column. The left section list from `docs/design/settings.png` (and the standalone HTML in
`docs/design/html/`) becomes real navigation: each section is its own page, only that section's card(s) on the right.

## Done when
1. **Routes.** `/settings/:section` for every section in `SettingsPage.tsx`'s list: `models` (Models and keys: providers
   + the chosen-models list), `connections`, `rules`, `look`, `notifications`, `knowledge`, `shares`, `advanced`,
   `backup`, `logs`, `about`, plus `remote-access` when the transport is remote and `terminal` when the terminal section
   has anything to show (follow what the components render today). `/settings` shows the first section (redirect,
   replace). An unknown section shows the first one. `/settings/look/customize…` (the Customizer) is unchanged.
2. **Old links.** `/settings#<id>` (bookmarks, boot caches, the ways back) redirects to `/settings/<id>`, keeping any
   query (e.g. `?look=safe`). Update every in-app link that uses an anchor (`LookRuntime.tsx`, `ReportsPage.tsx`,
   `PermissionsTab.tsx`, `Customizer.tsx`, the palette, Needs-you items, toasts, docs) to the page URL.
3. **Navigation.** Desktop: the left list uses router links with `aria-current="page"` on the current section, styled
   as the design's selected white pill; the "Settings for one agent live on their page in Team." note stays. Phone: the
   existing Section picker shows the current section and navigates. Moving between sections scrolls to the top and
   moves focus sensibly (the section's heading), so keyboard and screen-reader users land in the new content.
   The Hermes version banner shows above every section. The document title names the section.
4. **Palette.** ⌘K lists each section ("Settings: Logs", …) besides plain Settings; the chat-first and Customizer
   palettes keep their reduced lists (Settings stays reachable).
5. **Protection unchanged.** Every protected surface and decision in Settings (Remote access, rules, the Look reset,
   the Settings link) keeps its marking; `protected.test.ts` inventory and the themes e2e still pass. The ways back that
   point into Settings land on the Look page.
6. **Tests.** Unit tests for the routing and the hash redirect; e2e: navigate every section by click, keyboard and
   phone picker; old anchor redirect; back/forward. Update e2e specs that relied on one long page. Visual baselines for
   Settings (visual, responsive, packs-visual, themes-builtin-visual, layout specs) are updated — list them and check
   each diff shows the intended page. Refresh the README Settings screenshot (`pnpm screenshots`, neutral team).
7. Docs: USER-GUIDE Settings section, API-CONTRACT only if a URL the server knows changes (it shouldn't: check the
   server serves the SPA for `/settings/*`).

## Constraints
Follow AGENTS.md (design rules: take spacing and colours from the design HTML). No new dependencies. Don't edit
docs/ARCHITECTURE.md. Commit per step with `git add <paths>`. Targeted tests while building; one full `pnpm check` and
one full `pnpm e2e` at the end.
