# 10.6 — Big files in Knowledge

Owner (2026-10-19): "the knowledge limit is 25mb". Knowledge must take files up to 256 MB. Branch
`task/10.6-knowledge-large` is built on `task/10.3-staged-zip` (staged zips, finished and reviewed): keep its behaviour.

## Contract (lead, on this branch; don't edit)
`docs/API-CONTRACT.md` › Knowledge › "Documents and zips" and the upload bullet: 256 MB per file; text read, indexed and
previewed only up to 25 MB (`KnowledgeTextStatusSchema` gains `too_large`); unzip: 1 GB unpacked in total, 256 MB per
extracted file, other zip rules unchanged; staged zips: at most 8 / 1 GB.

## Done when (from docs/PLAN.md 10.6)
- A 100 MB upload (`PUT /api/knowledge/files/*`), a 100 MB zip's preview + unzip (also through `files-from-staged`) and
  a 100 MB download (`GET /api/knowledge/files/*`) work in tests.
- The server doesn't hold a big file in memory more than once per request: no extra copies; the download streams from
  disk (no `readFile` of the whole file); hashing of big files streams.
- A file over 25 MB is stored with `textStatus: 'too_large'`, is never sent to the text worker (PDF/DOCX) and isn't read
  for indexing; re-indexing and the vault watcher treat it the same. Files ≤ 25 MB behave exactly as now.
- The web: `MAX_UPLOAD_BYTES` 256 MB with the messages that name it; a document with `too_large` says "Too large to
  preview (over 25 MB). Download it to open it." where the preview/text would be.

## Where (find the rest)
- `apps/server/src/knowledge/doc-types.ts` `MAX_FILE_BYTES` is used for three different things: the upload cap, the
  read cap for indexing/hashing/preview, and the per-entry cap in `extract-worker.ts`. Split it into named limits
  (e.g. `MAX_STORE_BYTES` 256 MB, `MAX_TEXT_BYTES` 25 MB) and go through every use (`vault.ts`, `documents.ts`,
  `extract-worker.ts`, `http/knowledge.ts` body limit) deciding which one applies.
- `apps/server/src/knowledge/extract.ts` `maxTotalBytes` → 1 GB; check the unzip worker writes entries without holding
  the whole unpacked total in memory (stream or write per entry), and its resource limits fit a 256 MB entry.
- `apps/server/src/knowledge/staging.ts` `STAGING_MAX_BYTES` → 1 GB (its tests use their own small cap).
- Hashing for change detection (`hashContent` over `readContainedBuffer`) must stream for big files, keeping the
  containment checks (no symlinks, inside the vault) the current reader has.
- Git: documents over 10 MB are already not versioned; keep that.
- `apps/web/src/routes/knowledge/knowledge-files.ts` `MAX_UPLOAD_BYTES`, the messages, and `DocumentWorkspace.tsx`.

## Tests (failing first)
Server: 100 MB upload/preview/unzip/staged/download (generate the bytes in the test; zips with stored entries so they
are fast), `too_large` status and no worker call (spy), 256 MB + 1 → 413, a zip whose total exceeds 1 GB by its
declared sizes is `413 zip_limits` without inflating it, memory: assert the download path uses a stream (e.g. the reply
payload is a stream). Web: limit message, the `too_large` text. Keep test run time reasonable (no 256 MB buffers unless
one test truly needs it; tests may lower limits through options where the code allows).
