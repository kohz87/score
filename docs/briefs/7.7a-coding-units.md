# 7.7a Coding runs as supervised systemd user units (stage 1 of 7.7; design v4, for re-review)

Owner 2026-10-11: 7.7 "full, in stages" (decision 65). Reviews: v1 `docs/reviews/2026-10-11-7.7a-design-review.md`,
v2 `docs/reviews/2026-10-12-7.7a-design-rereview.md`, v3 `docs/reviews/2026-10-12-7.7a-v3-review.md` (cited [n] = v3
finding n). v3's model stays (decision 66: an attached supervisor; a run never outlives Score's connection; no output on
disk). v4 makes each protocol point exact. Fix batch Y (merged) already signals the fallback through pidfds, group
signals via `PIDFD_SIGNAL_PROCESS_GROUP` [7].

## Guarantee
Score proves every process **in the run's cgroup** ended. Work handed to another user service, scheduler or daemon is
outside the proof (stated in consent text and the user guide). Antigravity is Chat-only; its prompt travels in argv
(`-p`), which other local accounts can read through the process list on a default `/proc`: the Team note says so [14].

## 1. Unit, supervisor, signals [4, 8, 11]
- `systemd-run --user --no-ask-password --expand-environment=no --unit=<name> --description="Score coding run"
  --property=Type=exec --property=ExitType=main --property=KillMode=mixed --property=KillSignal=SIGINT
  --property=TimeoutStopSec=<2×grace + 5s> --property=FinalKillSignal=SIGKILL --property=SendSIGKILL=yes
  --property=RuntimeMaxSec=<remaining turn time + 2×grace + 5s> --property=TasksAccounting=yes
  --property=StandardInput=null --property=StandardOutput=null --property=StandardError=null
  --property=UnsetEnvironment=<deny list> --setenv=PATH=<fixed> --setenv=HOME=<home> --setenv=LANG=C.UTF-8
  -- <absolute node> --no-warnings <supervisor.mjs> <spec path>`.
- **The supervisor is the unit's main process and stays alive until its own cgroup holds nothing but itself** (it
  polls `cgroup.procs` of its cgroup and `cgroup.events`). With `ExitType=main`, when it exits — normally, on a crash, or
  killed — systemd stops the unit and the final SIGKILL reaches **every** remaining process of the cgroup, regardless of
  ancestry or `setsid` [4]. On socket loss it stops the CLI tree (INT → TERM → KILL, one grace each) and then exits;
  any survivor is killed by systemd's stop. Disconnect cleanup is bounded by `2×grace + 5s`.
- **One escalation owner** [11]: the supervisor. `KillMode=mixed` sends systemd's SIGINT to the supervisor only (no
  duplicate INT to the CLI); the supervisor escalates INT → TERM → KILL to the CLI tree; systemd's SIGKILL to the whole
  cgroup comes only after `TimeoutStopSec`, which covers both intervals plus flushing. The stop cause (user, deadline,
  quota, socket loss, Score shutdown) is persisted for released runs.
- **Clocks** [11]: the turn's deadline is wall time (contract), enforced by the supervisor against the persisted
  deadline; `RuntimeMaxSec` (monotonic) is only the backstop. One deadline per turn, shared across launch attempts.
- **Startup environment** [8]: the deny list always includes, whether or not the manager exports them, `LD_PRELOAD`,
  `LD_LIBRARY_PATH`, `LD_AUDIT`, `NODE_OPTIONS`, `NODE_PATH`, `NODE_REPL_EXTERNAL_MODULE`, `NODE_EXTRA_CA_CERTS`,
  `NODE_ICU_DATA`, `UV_THREADPOOL_SIZE`, `PYTHON*`, plus every other name the manager exports at launch **except**
  PATH/HOME/LANG (which are set explicitly and never listed, since `UnsetEnvironment` applies last). Node is invoked by
  absolute path with no ambient flags. The CLI's environment is built by the supervisor from the spec (replace, never
  merge). A real-systemd test sets harmless sentinel variables (including `NODE_OPTIONS=--require …`) in the manager
  and proves neither the supervisor nor the CLI sees them.

## 2. Installation identity and the journal [3, 12]
- **Installation id**: a random id created at first start in `$SCORE_HOME/installation.json` together with the home's
  real path. If the recorded path differs from the current one (a copied home), Score refuses coding admission until the
  person confirms it is a move or creates a new installation id.
- **Journal per installation**: `<journal dir>/<installation id>/journal.ndjson` plus a **stable sidecar lock**
  (`<…>/lock`, the same O_EXCL + pid/start-time lock as the password store) held for every read-for-decision, tail repair,
  append, sequence allocation and compaction (compaction renames the journal, never the lock) [12]. The legacy
  path-scoped journal is migrated under that lock on first start: its records for this home are copied, the legacy file
  stays as a read-only witness consulted by reconciliation; restore markers move with them. Orchestration writers move
  to the same journal in the same change, so they get the lock too.
- **Coding records** carry: launch id, run id, turn id, generation, phase, revoked flag, release possibility, invocation
  identity, proof, disposition, waiver. **Reconciliation compares this full state**, not just phase [3]. Each launch's
  latest record is kept forever as a compact **tombstone** (never compacted away); the database stores the journal's
  checkpoint sequence, and a database whose checkpoint is behind the journal (an older backup) fences coding admission
  until reconciled; every execution the journal witnessed becomes permanently unsendable before admission resumes.

## 3. Phases, with one ordering point [1, 2]
Phases: `authorised` → `requested` → `armed` → `releasing` → `released` → `ended` → `settled`, each journaled
(fsynced) **before** the external effect it permits.
- `requested` before `systemd-run`. `armed` when Score has verified the supervisor's identity (§5).
- **The ordering point** [1]: release and revocation are one compare-and-set in a database transaction under the
  journal lock: `releasing` is written only if the launch is `armed`, not revoked, and the run's authorisation still
  holds (re-evaluated inside that transaction); the journal `releasing` record is fsynced; only then is `go` sent.
  Revocation is the same CAS from `authorised|requested|armed` to `revoked`; if `releasing` already won, revocation is a
  Stop of a possibly-executing run (never "never ran").
- **Receipts live outside the home** [2]: the supervisor writes `released` (before it spawns the CLI) and `ended` into
  `<journal dir>/<installation id>/launches/<launch id>/`, so restoring the home can't remove them. Directory creation
  order: installation dir and `launches/` created once at setup and synced (each parent fsynced); per-launch directory
  created and its parent fsynced before `requested`; each receipt written `O_EXCL`, fsynced, directory fsynced. Any write,
  sync or read error ⇒ fail closed (the launch is "may have executed").
- **No-launch** is proven only by: journal `revoked` (CAS won before `releasing`), or no `releasing` record at all; never
  by a missing receipt alone. A present `released` receipt means "may have executed", not success.
- The database (WAL `synchronous=NORMAL`) may lag after a power loss; the journal is authoritative for phases, and
  recovery rebuilds missing rows from it.

## 4. Wire protocol [5, 10, 15]
- Socket: `$XDG_RUNTIME_DIR/score/<installation8>.sock` (short path; length checked at start; directory 0700); stale
  socket removed only while holding the installation lock; a live foreign listener ⇒ refuse. Readiness (listener up) is
  part of the capability check.
- Versioned frames (JSON lines, each ≤ 64 KB): `hello{v, launch, token, generation}` → Score `welcome` / `reject`;
  `ready{pid, start, invocation, cgroup}`; Score `go` / `cancel` / `stop`; `out{stream, seq, data}`;
  `eof{stream, lastSeq}`; `exit{code, signal}`; `end{}`; Score `ack-end` → the supervisor then exits (normal terminal
  close). Any other close is socket loss.
- Tokens are single-use, bound to installation + launch + generation + spec hash + Score incarnation, consumed
  atomically on `hello`; a second connection for the same launch is rejected; tokens never logged.
- **Backpressure and bounds** [10]: the supervisor pauses reading the CLI's pipes while the socket buffer is above a high
  mark (the CLI blocks on write); per-stream and per-run byte caps and Score's receive queue caps; on overflow, read
  error or unexpected `end`/`error`, the run is stopped and its result made ineligible. Control frames are handled
  independently of output draining. On Score shutdown accepted sockets are destroyed explicitly (not `server.close()`
  alone) after `stop` is sent.
- **Completeness** [5]: Score accepts a terminal outcome only after it has parsed and durably processed every `out`
  record up to each stream's `eof.lastSeq`; any ingest/translation failure makes the result ineligible (the current
  swallowed-error path in `service.ts` is removed).

## 5. Identity verification [9, 13]
Before `armed`, Score compares the supervisor's claims with independent sources: `systemctl --user show <unit>`
(`MainPID`, `InvocationID`, `ControlGroup`, `ActiveState`) and `/proc/<pid>/stat` start time and `/proc/<pid>/cgroup`.
Any mismatch ⇒ revoke and stop the unit. **Manager incarnation** = the user manager's PID and start time, read from the
system manager (`systemctl show user@<uid>.service -p MainPID`) and `/proc`. It is rechecked on every inventory, proof
and stop: a different incarnation with the unit missing ⇒ outcome from receipts + the recorded cgroup only, never from
missing metadata; transport/permission errors ≠ absence; reset/cleanup acts only on the exact name **and** matching
InvocationID [13].

## 6. Proof, disposition, eligibility (unchanged from v3) and acceptance [6]
- Ended proof: the recorded cgroup absent or `populated 0`, no pending unit job, identity checks passing; boot change ⇒
  ended.
- `completed` with an eligible result requires **all**: normal terminal close (`ack-end` exchanged), every stream's
  `eof` processed, CLI exit 0 without signal, no stop cause, ended proof, and the driver rule for the **pinned CLI
  version** (versions outside the tested table ⇒ no eligible result for executor-owned runs):
  - Claude Code: a `result` event with explicit `subtype: "success"`, explicit `is_error: false`, string `result`
    non-empty; defaults never imply success.
  - Codex: every `agent_message` validated (a rejected or malformed one invalidates authority for the turn); the final
    reply is the last validated `agent_message` before `turn.completed`; any dropped record in the turn ⇒ none.
  - Antigravity (Chat only): `status === "SUCCESS"` and a non-empty `response`; the response wins over commentary.
  - The current exit-zero/commentary fallback in `service.ts` is removed.
- Chat hand-offs and plans use only the eligible authoritative reply (v3 §5).

## 7. Fallback [7]
Without the unit backend: Chat uses the process-group backend (W/X/Y: pidfd signals, fence, Release), with its weaker
lifetime stated in Settings › Coding ("runs may outlive Score until their time limit; Score stops them on restart");
executor workers (stages 2–3) are refused. Both backends are reconciled before admission; the backend is stored per
launch and never switched for an uncertain launch.

## Done when
Fake-boundary tests plus an opt-in real-systemd suite (harmless CLIs) for: the release/revoke CAS race both ways;
crash at each phase boundary (journal vs DB vs receipts, home restored to before `releasing`); supervisor killed after
`go` with a `setsid` survivor (killed by systemd's stop); socket loss; signal sequence INT → TERM → KILL without
duplicates; manager sentinel variables never seen; token replay/second connection rejected; identity mismatch revoked;
manager cold restart with the unit gone (receipts decide); backpressure and caps; completeness with an ingest failure;
driver acceptance tables (malformed Codex final, Claude defaults, Antigravity status); copied home refused; legacy
journal migration; socket path too long; both backends reconciled after an upgrade.
