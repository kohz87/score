# 7.7a Coding runs as supervised systemd user units (stage 1 of 7.7; design v2, for re-review)

Owner 2026-10-11: 7.7 "full, in stages" (decision 65). v1 of this stage was blocked
(`docs/reviews/2026-10-11-7.7a-design-review.md`, 10 P1 / 10 P2). v2 keeps the systemd cgroup as the job identity and
adds a **trusted Score supervisor inside every unit** plus launch records in the **external execution journal**.
Findings are cited as [n].

## Guarantee, stated precisely [18]
Score proves that every process **in the run's cgroup** has ended. Work a tool hands to *another* user service, a
scheduler or a daemon is outside that proof; this residual same-user risk is stated in the consent text (7.7b) and in
the user guide. Antigravity (which advertises scheduling/subagents and needs its prompt in argv [16]) stays a Chat-only
coding agent; stage 2/3 workers are Claude Code and Codex.

## 1. The unit [1, 16, 17, 20]
`systemd-run --user --no-ask-password --expand-environment=no --unit=<name> --description="Score coding run"
--property=Type=exec --property=ExitType=cgroup --property=RuntimeMaxSec=<s> --property=TimeoutStopSec=<grace>
--property=KillMode=control-group --property=KillSignal=SIGINT --property=FinalKillSignal=SIGKILL
--property=SendSIGKILL=yes --property=TasksAccounting=yes --property=MemoryAccounting=yes
--property=StandardInput=null --property=StandardOutput=null --property=StandardError=null
--working-directory=<launch dir> -- <node> <supervisor.mjs> <spec path>`
- `Type=exec`: the start call returns only after the supervisor executed [20]. `ExitType=cgroup`: the unit stays active
  (and `RuntimeMaxSec` keeps counting) until the **whole cgroup** is empty, not just the main process [1].
- No `RemainAfterExit`. Retention of the outcome is the supervisor's receipts (§3), not unit state [12].
- Signals: SIGINT (today's first signal; the supervisor forwards INT→TERM→KILL to the CLI on Score's existing grace),
  then systemd's TERM/KILL with explicit timeouts [17]. The deadline uses `RuntimeMaxSec` (monotonic: suspend doesn't
  count) **and** the supervisor's own wall-clock check against the persisted turn deadline (realtime) [17].
- `--expand-environment=no`, neutral description, `--` before argv [16]. The CLI's argv and environment are not on the
  `systemd-run` command line at all: they are in the spec file.

## 2. The supervisor (`apps/server/src/runtimes/coding/supervisor.mjs`, Node built-ins only) [7, 8, 9, 13, 14]
- Reads the **spec** (0600 JSON in the launch directory): executable, argv, the exact environment, workspace, limits,
  turn deadline, redaction rules version. Spawns the CLI with **exactly** that environment (`env` replaced, not merged;
  `LD_*`/`NODE_OPTIONS` etc. absent) [9]. The supervisor's own unit environment is minimal (`--setenv` only `PATH`,
  `HOME`, `LANG`; everything else unset with `UnsetEnvironment=` for the manager's imported variables) [9].
- Pipes the CLI's stdout/stderr through Score's **redactor** (the same rules as `redact.ts`, shipped as an erasable-
  syntax module the supervisor imports) **before** anything is written [7].
- Writes **numbered, immutable segment files** (`out-0001.jsonl`, `err-0001.log`; ≤ 4 MB each; never truncated or
  rotated in place), each record on a line boundary; `fsync` per segment close and per receipt; directory `fsync` on
  create [13, 14]. Quotas: per-launch stdout/stderr and an aggregate across launches (Settings › Coding, default
  256 MB); on exhaustion it stops the CLI's process tree and writes an `exhausted` receipt, keeping a reserve for
  receipts [8].
- Writes **receipts** (`receipts.jsonl`, fsynced): `started` (supervisor pid, InvocationID from `$INVOCATION_ID`,
  cgroup path from `/proc/self/cgroup`, boot id), `cli-exited` (code, signal), `leftovers` (descendants still alive
  after the CLI exited), `stop-requested` (cause: user | deadline | quota | shutdown), `ended` (written only after
  `cgroup.events` shows `populated 0` for every child cgroup it can see except itself — it waits for its own descendants,
  then exits; the unit's final state is checked by Score, §4).
- The launch directory is created by Score with `mkdir` 0700 in `$SCORE_HOME/coding/launches/<id>/`, files created
  `O_EXCL` 0600, symlinks refused [7].

## 3. Durable phases, journaled outside the database [3, 4, 11, 13, 15]
The external execution journal (`domain/orchestration/journal.ts`, already outside Score's home and restore-proof) gains
coding records: `launch-requested`, `stop-requested`, `settled` tombstone. Order:
1. DB transaction: `coding_launches` row `authorised` (launch id, run id, backend `unit`, installation id, spec hash).
2. Journal `launch-requested` (fsynced) — **from here execution may have happened** [3].
3. Final synchronous authorisation (Chat: not stopped; 7.7b extends it); if refused → journal `settled(no-launch)` and
   never call systemd [3].
4. `systemd-run` (with a timeout); record the unit's `InvocationID`, cgroup and manager incarnation (§4) in the row.
5. On end: Score drains the segments (§5), commits the terminal result with its proof, journals `settled`, then removes
   the launch directory after retention.
Recovery compares journal ↔ database ↔ live units ↔ launch directories before admitting any coding turn. A journal
`launch-requested` without a database row (restored DB) fences coding admission and shows a review item [4]. Missing
units are **never** a no-launch receipt [3, 11]: only "journaled `settled(no-launch)`" or "no `launch-requested` at all".

## 4. Identity and the user manager [11, 15, 20]
- Unit name `score-<installationId8>-c-<launchId>.service` (server-minted, `[a-z0-9-]`, validated from every boundary,
  exact names only, never globs or prefix operations) [15].
- Bound to: installation id, `InvocationID`, cgroup path, boot id, and the **manager incarnation** (the user manager's
  `ActiveEnterTimestampMonotonic` + its PID). A different incarnation without a matching unit ⇒ the outcome comes from the
  supervisor's receipts and the cgroup path (is it populated?) — never "never started" [11].
- The backend (unit | process-group fallback) is stored per launch and never changes for an uncertain launch; both
  inventories (units and `coding_processes`) are reconciled before admission [20].

## 5. Ingesting the stream [5, 14]
- Score tails segments with fs watch + periodic stat, reading complete lines only; an incomplete trailing line waits.
- Every observation's ingest key is `(launch, segment, line index)`; on restart Score **reparses from segment 1** and
  relies on these keys for idempotency, so parser/translation state (tool pairing, `lossy`, final-result candidate) is
  rebuilt exactly, not resumed from an offset [5].
- A missing or shortened segment that was already ingested ⇒ `lossy` + gap noted; never silent [14]. After the end proof,
  Score drains every remaining complete line before terminalising [14].

## 6. Proof, disposition and eligibility are separate [2, 12, 19]
- **Ended proof** = the unit is inactive/failed **and** its cgroup is gone or `cgroup.events: populated 0` (recursive),
  with no pending job, **and** an `ended` receipt or, failing that, a verified empty/absent cgroup for the recorded path on
  the same boot [2]. `TasksCurrent` is advisory only (unknown ≠ 0) [2].
- Proof is monotonic and stored separately from **disposition** (completed/failed/cancelled/limit) and **result
  eligibility**. Late proof (after `unconfirmed`) closes obligations and lifts the fence but never revives a result or
  hand-offs [19]. A person's Release/Keep is an audited **waiver**, not proof, and keeps a tombstone with the unit identity
  so a still-live unit isn't later mistaken for a lost record [19].

## 7. Final reply authority [6]
- Claude Code: only a `result` event with `subtype: success`, `is_error: false` and non-empty `result` text.
- Codex: the last `agent_message` of the turn, validated (string text), with every potentially final message parsed
  (none dropped), followed by `turn.completed`; any dropped/malformed record in the turn ⇒ no authoritative reply.
- Antigravity (Chat only): the final `response` field is authoritative when present, else none.
- Streamed commentary is never used to build an authoritative result. Chat keeps showing the stream.

## 8. Fallback and requirements [20]
Capability check at start (and in Settings › Coding): user manager reachable, `Type=exec`/`ExitType=cgroup` accepted,
cgroup v2 with readable `cgroup.events`, linger on. Each failure is shown by name with its fix. Without the unit backend,
Chat uses the process-group backend (W/X/Y), stages 2–3 refuse coding workers.

## Done when
Fake `systemd-run`/`systemctl` boundary tests **and** an opt-in real-systemd suite (harmless `sh -c` CLIs) covering:
main exit with a `setsid` survivor and the deadline still enforced; failed unit with a surviving task not counted as
ended; crash after `launch-requested` before/after `systemd-run`; DB restore after collection (journal fences); cold
manager restart; Stop-then-crash before terminal commit; reparse-from-zero idempotency; partial line at EOF; offline
spool exhaustion; malformed Codex final; Claude result without text; environment sentinel from the manager not reaching
the CLI; secret redacted before disk; unit-name validation; both backends reconciled after an upgrade.
