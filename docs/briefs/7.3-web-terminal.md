# 7.3 Web terminal — design v1 (2026-10-09)

**Goal (PLAN 7.3):** a shell on the Score machine in the browser, for the owner only: paired browser, HTTPS only, security
design first. Use: quick `hermes` CLI work, looking at logs, git in a workspace, without leaving Score (phone included).

## Threat model

- Single owner (D7). Remote mode exposes Score on the LAN and the tailnet over HTTPS. A paired browser session is the
  only way in; a stolen or shared session cookie must not be enough on its own to get a shell.
- Agents run as the same OS user (accepted, D7.1 option a). The terminal therefore grants nothing an agent can't already
  do, but it must not become a new **remote** path for anyone who reaches the port, nor something an agent can drive
  through Score (agents have no browser session and bridge tokens can't call `/api/*`).
- Out of scope: protecting against a hostile same-user process; multi-user.

## Decisions

1. **Off by default.** `SCORE_TERMINAL=1` at start enables it (Settings shows how). Not reachable at all otherwise
   (routes not registered, not just refused).
2. **Second factor per terminal session.** Opening a terminal needs a paired session **and** a fresh security-password
   check or passkey assertion (5.23/5.28) made in the last 60 s; the server mints a one-time terminal ticket (random,
   hashed at rest, 60 s TTL, bound to the session id and origin). The WebSocket upgrade must present the ticket; a ticket
   opens exactly one terminal.
3. **Transport.** One WebSocket per terminal at `/api/terminal/ws`, HTTPS only (the dual listener refuses plain HTTP
   already), Origin checked against `SCORE_PUBLIC_ORIGINS`, `X-Score-Client` replaced by the ticket (browsers can't set
   headers on WebSocket upgrades). Dependency: `@fastify/websocket` (MIT) — the only new one; license check before adding.
   Frames: binary stdin/stdout; small JSON control frames for resize and exit.
4. **Process.** `node-pty`-free design: spawn `script -qfc "$SHELL -l" /dev/null` with argv arrays via `child_process.spawn`
   (util-linux `script` gives a real PTY without a native module); resize via `stty` on the PTY is not available that way,
   so the first version uses a fixed 120×36 and `COLUMNS/LINES`; native PTY (`node-pty`, MIT, native build) only if the
   owner accepts a native dependency (open question).
   Environment: a minimal allowlist (`HOME`, `USER`, `LANG`, `PATH`, `TERM=xterm-256color`, `SHELL`) — never Score's own
   environment (it holds `SCORE_*` secrets paths and the bridge port). Working directory: `$HOME`.
5. **Limits.** At most 2 terminals at once; idle timeout 15 min (no input or output), absolute 8 h; closing the tab,
   revoking the session, signing out, or Score stopping kills the process group (SIGHUP, then SIGKILL after 3 s).
6. **Audit.** Score logs open/close/kill with session id, peer address and duration — never keystrokes or output.
   Settings › Remote lists open terminals with a Close button.
7. **Web.** `xterm.js` (MIT) on a `/terminal` page; copy/paste, font JetBrains Mono, theme from tokens; on phones a key
   bar (Esc, Tab, Ctrl, arrows). The page states "This is a shell on the Score machine as <user>."
8. **Not in v1:** sharing a terminal, recording/replay, running as another user, terminals inside agent sandboxes.

## Contract

`POST /api/terminal/tickets` (paired + fresh password/passkey) → `{ ticket, expiresAt }`; `GET /api/terminal/ws?ticket=…`
(upgrade); `GET /api/terminal/sessions` and `DELETE /api/terminal/sessions/:id` (paired). Errors: `feature_disabled`,
`ticket_invalid`, `too_many_terminals`.

## Tests

Ticket rules (expiry, single use, session binding, origin), routes absent when disabled, environment allowlist, limits
and kill on revoke/stop, no keystrokes in logs; e2e: open a terminal in the fake mode, run `echo`, close.

## Open questions for review

- `script`-based PTY vs `node-pty` (native) — resize support vs dependency.
- Is a 60 s fresh second factor enough, or require it per terminal and every 30 min?
