# Task 5.33: Rewind a conversation: edit or delete rewinds the room and the agents' sessions

Owner 2026-10-09: "is it possible to reflect the changes on hermes agent itself as well? so what you see is what you
get?" — "undo is fine, since when we delete up the chain, the subsequent message need to be removed or hide as previous
iterations". Today (5.24 + lead fix): an edit removes the original and its reply chain from Score only; Delete removes one
message from Score only; agents' Hermes sessions keep every turn.

## Behaviour

1. **Edit** your message X, or **Delete** your message X: X and **every message after it in the room** become a
   _previous version_ of the conversation from that point. They are hidden from the room's normal view; at X's position a
   compact switcher shows "Version 2 of 2 · ‹ ›" (or "Previous version" for a delete) to view earlier versions read-only
   (greyed, no actions). The edit's correction starts the new version. Agent replies and hand-offs after X belong to the
   version they were in. Deleting an agent reply alone keeps today's Score-only Delete (with Undo).
2. **Agents' sessions are rewound** to just before X: for every agent whose Hermes session for this room has turns at
   or after X, rewind that session by exactly the number of its user turns that started at or after X. Hermes's own
   rewind is the gateway session store's `rewind_session(session_id, n)` (used by the `/undo` command in
   `gateway/slash_commands_session.py`; it soft-deletes the rows and the next turn rebuilds from active rows). Score may
   not write Hermes SQLite: the rewind must run inside Hermes through the **score_bridge plugin**, with the private call
   only in `hermes_private.py`, triggered by a new server→plugin command on the existing decision transport (or a sibling
   long-poll) and acknowledged with Hermes's result (`turns_undone`, `rewound_count`).
3. **Safety and honesty:**
   - Refuse (409, clear message) while any agent in the room is answering, while the room's work is paused with pending
     holds, or when the plugin/gateway can't be reached. Nothing is hidden in Score unless every needed rewind succeeded,
     or the owner explicitly chooses "Hide in Score only" after seeing which agents could not be rewound.
   - Count turns exactly from Score's own records (message_runs per agent, room session id `score-<room>-<agent>`, the
     compression lineage Score already follows in `hermes/live/recover.ts`). If a session was compressed after X, a rewind
     across the compression boundary is not attempted: report it and offer "Hide in Score only".
   - Long-term memory (MEMORY.md, skills, Knowledge notes) is not rewound; the confirmation says so.
   - Idempotent per (room, X, version) so a retried request never rewinds twice.
4. Contract first (§5): `POST /api/rooms/:id/messages/:messageId/rewind { mode: 'edit'|'delete', scoreOnly?: boolean }`
   → `{ version; rewound: { agentId; turnsUndone }[]; skipped: { agentId; reason }[] }` (the edit's new text then goes
   through the normal post with `edits`), message `version` fields and `GET /api/rooms/:id/versions/:anchorId`; events
   `room.version.created`. Migration **0036** for versions. Bridge contract §11 for the rewind command and its result.
5. Web: Edit and Delete on your own messages open a confirmation that lists what will happen (N messages hidden as the
   previous version; agents rewound: builder −2 turns…; memory not rewound); the version switcher; the 5.24/5.25 edit bar
   keeps working on top.
6. Tests: turn counting per agent (hand-offs, retries, edited corrections, compression boundary), plugin rewind with a
   fake session store (pytest), the command round trip, idempotency, refusal cases, version reads, web confirmation and
   switcher, e2e on the fake adapter (fake port simulates the rewind result). Live check only on test profile
   `scoretesta`.
