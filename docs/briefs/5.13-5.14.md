## 5.13 (from docs/PLAN.md)

Children linked to a paused brief, tasks assigned to a paused agent, and tasks created while the team is paused are held
too (parked on arrival, released with the pause). Context: `apps/server/src/http/task-holds.ts` (per-owner holds,
pending → held, `kanban schedule`, recovery after the adapter starts), `brief-control.ts`, `agent-pause.ts`,
`team-pause.ts`, `domain/briefs.ts` (`linkTasks`, child linking from the Kanban tailer). Codex audit wave 2 finding
"Tasks added after Pause escape its holds" (`~/.score/codex/audit-2026-10-08/wave2/tasks-flow.md`). Design: when a task is
linked to a paused brief, assigned to a paused agent, or created while the team is paused, record a pending hold for each
paused owner in the same transaction and park it through the existing hold path; plan start stays refused while paused.
Tests for each path, including a child created by a running step after Pause.

## 5.14 (from docs/PLAN.md)

Plan start is a durable operation (steps recorded before the CLI calls); startup finishes or reports it. Context:
`http/briefs.ts` (`startPlan`, step keys `plan:<messageId>:<index>`, per-step linking added today, keyed lock), the
task-create intents in `hermes/live/task-writes.ts`. Design: record the plan start (message id, brief id, steps) before
the first create; each step's outcome updates it; on startup (after the adapter starts, like hold recovery) unfinished
plan starts are resumed with the same step keys (idempotent) or marked failed with a visible notice in the room.
