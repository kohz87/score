# Task 5.17: Kanban attempts as runs — design v5 (2026-10-09)

v4 (`docs/reviews/2026-10-09-5.17-design-v4-codex.md`) was not approved: 6 high, 3 medium; the separate
`kanban_attempts` projection, opaque ids, transactional revisions, explicit unknowns, session-only spend, no Stop and the
5.17a-2 deferral were accepted. v5 keeps v4 (below) and **replaces or extends** the sections the review named. Where v5
and v4 differ, v5 wins.

## v5 amendments to 5.17a-1

### A. Watermarks, cursors and frozen evidence (v4 high 1)

- Persisted per history, updated **in the same transaction** as each accepted page: `event_alloc_mark` (from
  `sqlite_sequence` for `task_events`), `attempt_alloc_mark` (for `task_runs`), `event_cursor` (last processed event),
  `baseline_cursor` (last baselined attempt id), `fullpass_cursor`.
- Contradiction rule per sequence: an allocation mark **below its own saved mark** (not below a processing cursor). A
  missing `sqlite_sequence` row is valid only while its table is empty; a missing row with a non-empty table, or an
  unreadable sequence table, is "insufficient evidence".
- Undetectable restores are only those that preserve **both** saved allocation marks and all checked frozen evidence;
  the docs say exactly that.
- **Frozen evidence** is captured when first observed and never compared against later-cleared fields: claim lock as
  first seen, claim event (`source_status`, profile) when retained, worker pid + `worker_started_at` fingerprint. Hermes
  writers that later clear `claim_lock` (invariant recovery) or enrich unknown → known are **not** contradictions; only a
  frozen non-null value later seen with a _different_ non-null value is.

### B. Classification: indistinguishable means partial (v4 high 2)

- Synthetic exclusion only where evidence actually distinguishes the synthetic writer: the attempt was **first seen
  already closed**, has no positive evidence, matches the synthetic shape, **and** the task's retained events show the
  transition that synthesizes it with no preceding claim/start. Every other evidence-free row (including legacy backfill
  closed in the same second) is **partial**.
- "Previously observed open" is persisted; a row ever seen open is never later reclassified synthetic. Classification
  provenance (which evidence decided) is stored per attempt.
- Writer coverage fixtures: claim, complete, block, schedule, request_review, reclaim, `edit_task` synthesis,
  dangling-run recovery, dispatcher closure branches, legacy backfill with copied positive evidence, without evidence, and
  followed by same-second closure.

### C. Observation-loss boundaries and inert controls (v4 high 3)

- `observation_ended_at` is set — atomically with the gap and source state — when an open attempt **disappears**
  (task deleted/archived upstream, row gone), when its source is **paused** (insufficient evidence) or **unreadable**, and
  when its history closes. Consumers stop every interval there (dashed "no longer observed" tail, never counted after).
- While a source is paused or a task's qualification is unverified: routing, parking, release and hold recovery for those
  tasks are suspended (`task-holds` checks qualification before any `getTask`/action); Tasks shows why.
- If later confirmed evidence returns (same history verified), the boundary stays as recorded history; the attempt
  continues from the new observation with the gap retained.

### D. Restart-safe page identities (v4 high 4)

- Each captured read gets a **capture id** (UUID minted when the read is taken, persisted with the page in a
  `kanban_pages (capture_id, kind 'baseline'|'tail'|'sweep'|'fullpass', history_id, event_from, event_to, attempt_from,
attempt_to, captured_at)` row inside the page transaction). Observation identity = `kanban:<kind>:<capture_id>`. A
  retry of the same captured page reuses the id; a new read always gets a new id. No tick counters.
- Baseline, sweep and full-pass observations are submitted **without** an event-retirement floor (they are not event
  observations); tail pages carry the event floor as today. The durable `baseline_cursor` from v3 is kept (§A).

### E. Legacy links need affirmative proof (v4 high 5)

- A legacy numeric link maps **only** if at least one retained piece of affirmative evidence ties the old reference to the
  current attempt: (1) the legacy projection's saved activity contains that attempt's claim event id or start timestamp
  equal to the attempt's frozen `started_at`; or (2) the attempt's frozen claim profile and start minute match a legacy
  "claimed by" activity item for that task. Task id + numeric id alone (even on the same inode) is **unresolved**.
  Each allowed case has a fixture.
- Receipt invalidation keeps the execution barrier: a persisted idempotency receipt whose response references old ids is
  rewritten with the mapped/unresolved representation; the receipt itself (and its "already executed" status) is never
  deleted, so the mutation cannot run again — compressed receipts included.

### F. Qualified public references (v4 high 6)

- Public task references from attempts are **qualified**: `TaskRef { taskId; historyId; current: boolean }`. Only
  `current: true` references navigate to `/tasks/:id` or allow actions; historical ones open a read-only **attempt
  detail** (from `kanban_attempts` + a frozen task snapshot `task_snapshot JSON` stored with the attempt: title, status,
  assignee at last observation) and say "from an earlier copy of the board".
- Upgrade of existing associations (`brief_tasks`, `task_rooms`, review edges, holds): rows are assigned to the current
  history **only** if the task id exists in the current history at upgrade time with no contradiction; otherwise they stay
  unqualified and **inert** (displayed, never routed/parked/released).
- Kanban denials: until 5.17a-2, a denial resolves to a task only when that task is current and unambiguous; denial
  uniqueness gains `history_id`; unqualified denials never authorize task actions.

### G. Late relationship backfill (v4 medium 1)

- A separate **association pass** keyed `(history_id, brief_id, event_id)` in `kanban_associations` processes
  already-seen canonical events for newly linked tasks (review edges), without re-emitting task activity; it commits the
  relationship and its stream updates together and keeps durable progress. Fixture: late link with a crash mid-backfill.

### H. Complete consumer contracts (v4 medium 2)

- Exported union `WorkItem = { kind: 'run'; run: RunSummary } | { kind: 'attempt'; attempt: AttemptSummary }`; stream
  event **`attempt.updated`** carries `AttemptSummary` (contract §2), invalidating Flow/Now/Reports/Team queries that
  include attempts.
- Now: `checks[].verdict: 'passed' | 'changes_requested' | 'unknown'` replaces `ok` (web renders "unknown" neutrally);
  lane blocks gain `observationEndedAt` and `provenance: 'proven'|'partial'`; handoffs with an unknown agent endpoint are
  drawn to/from the Unattributed lane header; blocks carry `order: [startedAt, upstreamAttemptId]` and the client sorts by
  it (never by opaque id).
- Flow: `tools: string[] | null` (null = not observed); attempt cost is explicit `unknown`, so totals are partial.
- Reviewer role evidence = the claim event's `source_status = 'review'`; Hermes's completion outcome is `completed`; the
  verdict comes from the following review transition (`changes_requested` vs approval-to-done). Fixture covers Now, Flow,
  Reports (incl. trend and CSV), Team history, notifications and Stop rejection together.

### I. Bounded source work (v4 medium 3)

- Every source query is a bounded primary-key batch or a targeted read of Score-known ids: baseline/full-pass `WHERE id >
? ORDER BY id LIMIT 200`; open attempts by **Score's known open ids** (`WHERE id IN (…)` in batches of 200);
  recently closed by the ids touched by the last N tail events. No `ended_at` scans, no per-task all-attempt reads in the
  polling path (the old whole-board attempt read is removed).
- Schedule: tail every second; open-id refresh every 5 s; full pass continuous at ≤ 200 rows per 10 s with durable
  `fullpass_cursor` — old closed-row contradictions are detected within one full-pass cycle (documented latency).
- Oracles add: query plans (no table scans), eventless baseline pages in one capture batch, restart repeating ids,
  legacy writer ambiguity, paused/deleted interval bounds, reused-id ownership, late backfill, client ordering.

### J. Migration

Next free number at implementation (currently 0036); existing checksums untouched; `runs`, its STRICT table, indexes,
the `message_runs` foreign key and message/FTS triggers are untouched (asserted by the populated-upgrade fixture).

### v5.1 (lead review, `docs/reviews/2026-10-09-5.17-design-v5-lead.md`): approved for implementation

1. Legacy proof (§E) narrowed: only an activity item with the claim text, `at` equal to the frozen `started_at` second
   and `agentId` equal to the frozen claim profile maps a link; everything else is unresolved and shown as "an earlier
   attempt (details not kept)". Expect most legacy links to be unresolved.
2. Each capture is one read transaction covering `sqlite_sequence`, the min/max probes and the page rows.
3. `kanban_pages` rows are kept 7 days (hourly retention; never the latest page of an open capture).
4. `task_snapshot` redacted through `redactBounded`; title ≤ 300 chars; JSON ≤ 4 KB.
5. Now `checks[].ok` → `verdict` is contract + web only (checks are computed on read).
6. Pause release skips inert holds and reports them.
7. Extra fixtures: Hermes legacy-shape migration (new history); rows changing between a capture's queries.

# Design v4 (2026-10-09; amended by v5 above)

v3 (`docs/reviews/2026-10-09-5.17-design-v3-codex.md`) was not approved: 9 high, 3 medium. The split stays (5.17a-1
Kanban DB only; 5.17a-2 bridge provenance later; 5.17b Stop deferred). v4's main change: **Kanban attempts get their
own projection, separate from `runs`** — no rebuild of a populated table, no change to gateway run lifecycle guards, and
unknown attribution has a natural home. Consumers read attempts and runs through one domain function that returns an
explicit union.

## 5.17a-1 design v4

### 1. Sources, histories and the ambiguity policy (v3 high 1)

- `kanban_sources (id, path, board)`; `kanban_histories (id, source_id, opened_at, closed_at, reason)`.
- Evidence read every poll (read-only, cheap): `sqlite_sequence` high-water marks for `task_events` and `task_runs`
  (allocation counters, not retained maxima), the retained `MIN/MAX(id)` of both, file identity, and per known attempt the
  immutable tuple `(id, task_id, started_at, claim_lock-at-claim, claimed_profile)`.
- Classification per poll:
  - **normal maintenance**: retained maxima fall (GC, task deletion) but the allocation high-water marks are ≥ Score's
    checkpoint and no known attempt contradicts → same history; missing attempts are recorded as `deleted upstream`, not
    as a new history.
  - **contradiction** (allocation high-water below the checkpoint; a known attempt id with a different immutable tuple;
    a closed attempt seen open again — terminal→open regression) → close the history with a gap and open a new one.
  - **insufficient evidence** (file identity changed and the sample can't decide, or `sqlite_sequence` unreadable) →
    pause projection for that source, record a gap, show "Kanban history paused: the board database changed in a way
    Score can't verify" in Tasks, resume when evidence decides (or the owner chooses "treat as new board").
- A restore that also catches up past the checkpoint with unchanged tuples and no regression is **not detectable**; the
  docs say so; nothing promises otherwise.
- **Abandoned open attempts**: when a history closes, its still-open attempts get `observation_ended_at` (the moment
  observation stopped) — not an end time; consumers draw them up to that point with a dashed "no longer observed" tail and
  never count time after it.

### 2. Qualified ownership (v3 high 2)

- `task_projections` gains `source_id`, `history_id`. Every dependent association — `brief_tasks`, `task_rooms`, review
  edges, pause holds (`*_paused_tasks`), arrival holds — is written and read **with** the qualifying history; a task id
  from a closed history never resolves through a new history's projection. On history change: holds and room/brief links
  of the old history are kept for display but are inert (no parking, no routing); pending holds for the old history are
  dropped with a gap.
- Aggregates count an attempt once by `(source_id, history_id, attempt_id)` and exclude attempts marked
  `copied_from` (same tuple seen in an earlier history) so ancestral copies are not double counted.

### 3. Claim classification from the writers (v3 high 3)

- Positive evidence, persisted when first seen and never erased by later cleanup: `claim_lock` non-null on the row (Hermes's
  claim writer keeps it on close), a retained `claimed` event, an observed `worker_pid`, `worker_started_at`.
- **Proven**: any positive evidence. **Synthetic**: no positive evidence ever and the row matches the synthetic writer's
  shape (`started_at == ended_at`, `claim_lock` null, written by a transition: scheduled, blocked, completed,
  review_requested — outcome and summary text are **not** evidence). **Partial**: neither (e.g. legacy inflight
  backfill rows without a lock): shown with "provenance unknown", excluded from working-time totals, counted separately.
- The classifier is defined against every Hermes writer in `kanban_db.py` (claim, complete, block, schedule,
  request_review, reclaim, legacy backfill) with one fixture per writer.

### 4. A separate attempts projection (v3 high 4, 5, 6)

- `kanban_attempts (id 'kr_<uuid>' PK, source_id, history_id, attempt_id, task_id, profile NULL, role NULL,
status, closure_reason NULL, started_at, ended_at NULL, observation_ended_at NULL, evidence 'proven'|'partial',
claim_lock NULL, worker_pid NULL, worker_started_at NULL, summary NULL, error NULL, revision, content_hash,
copied_from NULL, deleted_upstream_at NULL)`, UNIQUE (source_id, history_id, attempt_id), STRICT. New tables only — the
  `runs` table, its indexes and foreign keys are untouched (no rebuild).
- Status: `running`, `completed`, `failed`, `blocked`, `review_handoff`, `changes_requested`, `ended_unknown`.
- **Kanban projection operation** (its own writer, not the gateway run upsert): accepts newer same-terminal content,
  refines `ended_unknown` → a known terminal, refuses terminal → open (that is a contradiction, §1). Revisions are
  allocated and hashes compared **inside** the writer transaction. "A→B→A" means three _observed snapshots_.

### 5. Contracts for unknowns (v3 high 5, medium 1)

- New contract type `AttemptSummary { id; kind: 'kanban'; agentId: AgentId | null; role: 'implementer'|'reviewer'|null;
status; closureReason: string | null; startedAt; endedAt: string | null; observationEndedAt: string | null; evidence;
taskId; tools: null; session: null; model: null }` — tools/session/model are **null = not observed** (never `[]`).
- Now: lanes gain an explicit `{ kind: 'unattributed' }` lane header (no fabricated AgentSummary) holding null-agent
  attempts. Reports: an `unattributed` bucket for counts and working time, separate from session-spend aggregation (which
  stays per session and is not invalidated by it). Flow: attempt rows with nullable agent; logs and Watch links for
  Kanban attempts are "not observed" (a general agent Watch link, when shown, is labelled "general activity"). Team
  history: attempts appear under their agent when known. Notifications for an unattributed attempt open the task, not a
  Watch URL. Stop on a Kanban attempt is rejected **before** any profile lookup (existing 501), gateway actions keep strict
  profile validation.

### 6. Verdicts, roles and ordering (v3 high 9)

- Review checks come only from exact persisted evidence: an attempt whose status is `changes_requested` is a rejection;
  `review_handoff` by the implementer is a request; an approval is a reviewer attempt whose closure reason is the
  approve transition (`completed` by the reviewer role with Hermes's approval outcome) — anything else is "unknown",
  never "passed". Role comes from the stored claim role, never the current assignee. Ordering everywhere (Now, Flow,
  history) is `(started_at, upstream attempt_id)` — never the opaque id. Fixture: same-second rejection, retry and
  approval, with reassignment and a null role.

### 7. One history-fenced ingestion coordinator (v3 high 7, medium 2)

- A single coordinator per source serializes baseline, tail and sweep reads (one in flight at a time) so an older
  snapshot never overwrites a newer one.
- Each page is one ingest observation with identity `kanban-page:<source>:<history>:<firstEventId>-<lastEventId>:<sweepTick>`;
  inside `apply` every constituent event is deduped by its own key in a `kanban_seen_events (history_id, event_id)` table
  and every attempt snapshot is compared by hash and revision in the same transaction; the checkpoint, attempt rows,
  task projections (with the history fence), review transitions (folded into the same page), gaps and stream events all
  commit together. In-memory baseline cursors advance only after commit.
- Reconciliation is **not** tied to the event checkpoint: sweeps read attempts directly and use their own observation
  identity (`kanban-sweep:<source>:<history>:<attempt>:<sweepTick>`) so retired event floors never suppress them.
- The task-projection revision guard is reset per **history**, not per file incarnation.
- Bounded source queries: baseline pages of ≤ 200 attempts by `id` (`WHERE id > ? ORDER BY id LIMIT 200`); open attempts
  every tick (`WHERE ended_at IS NULL`); recently closed: `WHERE ended_at >= now - 24h` (Hermes has no `updated_at`, so
  closed-row edits older than a day are caught by the daily full pass, paged); the existing whole-board reader is
  replaced by these paged queries for attempts.

### 8. Legacy numeric links (v3 high 8)

- A numeric link maps only when **all** retained independent evidence agrees: same task id, the current history's attempt
  with that numeric id, and that attempt's immutable tuple consistent with the projection's last saved activity (claim
  profile and start time when the legacy projection recorded them). Same filesystem incarnation alone never authorizes.
- Upgrade inputs are snapshotted into `kanban_upgrade_links (projection task_id, numeric_id, saved_evidence JSON)` by the
  migration before any reconciliation; work is resumable and idempotent; runs only while Hermes is readable (otherwise it
  waits, recorded in Tasks).
- `TaskDetail` gains `unresolvedRunLinks: { legacyId: string; reason: string }[]` (contract §7); cached `TaskDetail`
  responses and persisted idempotency receipts holding old ids are refreshed or invalidated.

### 9. Redaction and limits

Unchanged from v3: summary ≤ 8 KB, error ≤ 2 KB through `redactBounded`, metadata allowlist, closure reason bounded and
allowlisted; nothing from the bridge stored.

### 10. Acceptance fixtures with oracles

Each fixture states inputs, crash/restart points and the expected durable state: event GC (same history, no
duplicates); task deletion (deleted upstream, same history); in-place restore below the high-water (new history, gap);
restore that caught up (documented undetected); terminal→open regression (contradiction); copy onto a new inode (same
history); unreadable `sqlite_sequence` (paused, gap); one fixture per Hermes writer for classification incl. retained
lock with pruned claim event (proven) and legacy backfill (partial); populated database upgrade with active gateway runs
and message links (untouched); `ended_unknown` → `completed` refinement accepted, `completed` → open refused; A→B→A with
interleaved polls (three snapshots); multi-page baseline with a restart between pages and a source replacement mid-baseline;
failure injected inside the writer transaction and after commit (replay, no loss, no duplicates); sweep without new
events; numeric-link upgrade (mapped, unresolved, Hermes unavailable then available); same-second reject/retry/approve;
unattributed lane, bucket, notification and Stop rejection; redaction/byte limits.

## 5.17a-2 requirements (designed after 5.17a-1 ships)

v3's list plus: a distinct idempotent association operation after original ingest, atomic with pending resolution and
Watch frame updates (same frame sequence, update event); field ownership so Kanban snapshots never erase bridge-owned
fields (and terminal enrichment of closed attempts); profile/source-qualified session keys; Flow log and Now file
consumers updated; session-accounting completeness and window rules before any attempt cost attribution. 5.17a-1 already
persists the claim lock, claim-event and process evidence (§3) that 5.17a-2 will validate against.

## 5.17a-1 design

### 1. Sources and histories (finding 1, 13)

- A **source** is one Kanban board database: its resolved real path plus board slug, row in `kanban_sources (id, path,
board, first_seen)`. Score reads only the default board today; the table allows more later.
- A **history** is Score's own epoch for "one continuous lineage of that database": `kanban_histories (id, source_id,
opened_at, closed_at, reason)`. Filesystem identity (dev, inode, birth time) is recorded per history as an
  _observation_, never as proof.
- **Contradiction detection** opens a new history (and closes the old one with a reason and a recorded gap) when any of:
  (a) the max `task_events.id` is below Score's checkpoint (rollback or restore); (b) an attempt id Score already knows
  has different immutable fields (task id, `started_at`, claim profile) — the same id now means a different attempt;
  (c) the file identity changed **and** a sample of known attempts (up to 50, all of them if fewer) does not match.
  A copy of the same logical history onto a new inode (all sampled attempts match) keeps the history: no duplicate runs.
- Runs from a closed history stay (labelled "from an earlier copy of the board"); they are never re-attached.
- **No absolute restore guarantee is claimed**: ambiguous evidence is kept unassociated with a gap. If Hermes later offers
  an immutable database lineage id, it replaces detection.

### 2. Identity and task links (finding 1, 13)

- A Kanban run has an opaque id `kr_<uuid>`; `kanban_attempt_runs (run_id PK, source_id, history_id, attempt_id,
task_id, claimed_profile NULL, role NULL, evidence, revision, content_hash, first_seen)` with UNIQUE (source_id,
  history_id, attempt_id).
- Task relationships are **source-qualified**: `kanban_task_runs (source_id, history_id, task_id, run_id)`. The existing
  `task_projections` (keyed by upstream task id, current board) is unchanged; `TaskDetail.runIds` lists the current
  history's `kr_` ids.

### 3. What becomes a run (finding 4, 6)

- **Synthetic** (never a run): `started_at = ended_at`, no PID ever observed, outcome in Hermes's transition-only set
  (scheduled, blocked-by-transition, archived…) and no retained claim event or worker summary.
- **Proven claimed**: a retained `claimed` event for that attempt, or a PID/claim lock observed by Score, or a worker
  outcome (completed, failed, review handoff, requested changes, crashed, timed out).
- **Anything else** (claim events pruned, no worker evidence, but not clearly synthetic) becomes a run with
  `evidence: 'partial'` and a recorded gap — never silently dropped, never presented as proven.

### 4. Unknown agent and unknown end (finding 4)

- Migration recreates `runs` with `profile` NULLable (table rebuild in one transaction, data copied, indexes recreated,
  old checksums untouched) and adds status `ended_unknown`.
- Contract: `RunSummary.agentId: AgentId | null`; status adds `'ended_unknown'` (terminal). Every terminal set, parser,
  filter and label is updated: Now puts null-agent attempts in an "Unattributed" lane; Team history shows "Ended
  (unknown)"; Reports counts them under "Unknown agent". A later observation may refine `ended_unknown` to a known terminal
  outcome without reopening execution.

### 5. Revisions and reconciliation (finding 5)

- Task events are observations with identity `kanban-event:<source>:<history>:<event id>`.
- Attempt rows are observed by **reconciliation snapshots** with a persisted monotonic `revision`: a read computes a
  content hash over every projected field; if it differs from the stored hash, revision + 1 and the observation identity is
  `kanban-attempt:<source>:<history>:<attempt>:r<revision>`. A → B → A therefore yields three revisions, never a
  dedupe of the third.
- Sweeps: every tick for open attempts; closed attempts changed in the last 24 h every minute; a slow paged full pass
  daily (closed rows can change silently, e.g. PID cleanup). ARCHITECTURE D2.3's revision example is corrected.

### 6. One atomic writer step (finding 6)

- The Kanban tailer reads one page (≤ 500 events, then the attempts they touch) and submits **one** ingest observation
  whose transaction writes: sources/histories, attempt runs, run rows, task links, gaps, derived stream events and the
  checkpoint. A crash before commit replays the page; after commit nothing is lost.
- **Historical baseline** on first start (and after a new history): paged by attempt id, resumable through a
  `kanban_baseline (history_id, last_attempt_id, done)` cursor, each page one transaction.

### 7. Upgrade of numeric run links (finding 13)

- The SQL migration only creates tables and one `kanban_upgrade_work` row. The adapter does the work when Hermes is
  readable: for each projection with numeric run ids, match within the projection's recorded incarnation and the current
  history; a match maps to the `kr_` id; anything else becomes a `legacy_unresolved` link with a gap (shown as "an earlier
  attempt that could not be matched"). Resumable, idempotent; cached `TaskDetail` responses are refreshed.

### 8. Lifecycle and consumers (finding 9–12 kept, 16)

- Open vs closed from `ended_at`; terminal status from outcome; the **raw closure reason** is stored separately, bounded
  (≤ 200 chars, allowlisted values or "other"), redacted. Review verdict, task acceptance and worker termination stay
  separate facts (5.17-pre2 rules).
- Now: one finite block per attempt from `started_at` to `ended_at`, gaps visible, never merged; a late approval from a
  surviving worker is separate evidence.
- Flow: attempts per task ordered `(started_at, attempt_id)`, implementer vs reviewer from the claim's role; attempt
  failure ≠ task failure.
- Reports: attempts count as runs and working time; spend stays session accounting only; attempt cost null.
- Team history: brief links through `kanban_task_runs` as well.
- **No Stop, no reclaim, no retry action** for Kanban attempts in 5.17a: Stop answers "unavailable for Kanban attempts"
  (existing 501 path); reclaim stays in Hermes.

### 9. Redaction and limits (finding 14, for the fields 5.17a-1 stores)

- `summary` ≤ 8 KB and `error` ≤ 2 KB through `redactBounded`; `metadata` reduced to an allowlist of provenance fields;
  closure reason bounded as above. Nothing from the bridge is stored by 5.17a-1.

### 10. Acceptance fixtures (finding 16)

Recorded/fake fixtures for: synthetic rows (not runs); pruned claim events (partial runs with a gap); same-second and
short-gap retries (separate blocks); A → B → A summaries (three revisions); in-place restore / rollback (new history,
gap, no duplicates); copy onto a new inode (same history); a recreated board reusing attempt ids (new history); unknown
profile and unknown end (null agent, `ended_unknown`, labels); requested changes (no passed review); crash between
reading and committing a page (replay, no loss, no duplicates); upgrade of numeric links (mapped and unresolved); Stop
answering "unavailable".

## 5.17a-2 requirements (designed after 5.17a-1 ships)

Immutable producer identity separate from per-hook execution role and explicit session lineage (helpers, compression
children; host-isolation mode → ownership unknown unless Hermes transports it; the private-API set added to the tested
bridge fingerprint); pending evidence keyed by validated source/history provenance from `HERMES_KANBAN_DB` (realpath) +
task + attempt + claim, resolved only against stored claim provenance, ambiguous evidence unassociated; observed model
history (not "actual model"); tool observations stored by producer/counter, paired only with a guaranteed invocation id;
Watch frames re-linked in place (same sequence) with an update event; one normalization path (plugin redaction, server
credential filters, scrub, limits) before both immediate projection and the pending store, with pending limits, orphan
expiry and gaps.

# Design history: v2 (not approved; kept for reference)

Owner request 2026-10-08. v1 was not approved by the adversarial review (`docs/reviews/2026-10-08-5.17-design-codex.md`,
Codex max: 1 critical, 15 high). This v2 follows that review's "corrected design I would approve". Hermes facts below are
from that review (verified against Hermes `e97923c`); file references point there.

## Scope and split

- **5.17-pre (independent bugs the review found; no new model):** Reports time categories overlap (an hour of working and
  of human waiting counts in both); Now merges same-agent retries across gaps (two 10-minute attempts 50 minutes apart
  became one 70-minute block); Flow sums known run costs and shows the partial sum as a total, picks runs by the task's
  _current_ assignee (the reviewer after `request-review`) and has no tie-breaker for same-second runs; Team history finds
  brief links only through `message_runs`; Stop on a non-gateway run sends it to the gateway Runs API.
- **5.17a (projection, read-only):** Kanban worker attempts become Score runs with exact provenance.
- **5.17b (Stop):** needs a Hermes operation fenced by board + attempt + claim that holds dispatch and verifies
  termination. Until Hermes has it, Score says Stop is unavailable for Kanban attempts (explicit, not a 409) and offers
  reclaim only as "retry this task". A proposal for Hermes is drafted in `docs/proposals/`.

## 5.17a design

### Identity

- A Score run for a Kanban attempt has an **opaque id** (`kr_<uuid>`), mapped in a new table
  `kanban_attempt_runs (run_id, source, history, attempt_id, task_id, profile, role, claimed_at, …)`:
  - `source` = the observed board database (root + board slug), `history` = the existing SQLite incarnation of that file
    (`hermes/live/sqlite.ts`), so a recreated/restored board never reuses a run id for a different attempt.
  - `attempt_id` = `task_runs.id`; unique `(source, history, attempt_id)`.
- `TaskDetail.runIds` lists these opaque ids. Existing numeric `runIds` in stored projections are backfilled on upgrade.

### What becomes a run

- Only **proven claimed attempts**: a `claimed` task event (or equivalent claim provenance) names the attempt. Hermes
  writes zero-duration synthetic `task_runs` rows for transitions on never-claimed tasks (`kanban_db.py:2093`); those
  stay task history and never become runs. A genuine claim that failed before spawning is a run (failed).
- `profile` comes from the claim; when Hermes left it null, the run keeps an unknown profile (never the current assignee
  or `default`).

### Source of changes

- The existing Kanban tailer's `task_events.id` cursor (no new timestamp cursor), with a bounded baseline and a periodic
  reconciliation sweep of open attempts (rows can change without events: summaries edited, PID evidence cleared).
- Observation identity covers **every projected field** (status/ended_at/outcome/summary hash/error hash/profile), so a
  later change is never deduplicated away.

### Lifecycle

- Open vs closed comes from `ended_at`, not `status`. Closed attempts map `outcome` to a terminal run status and keep
  the **raw closure reason** in a separate field (review handoff, requested changes, scheduled, stale worker, rate
  limited, reclaimed, …). Review handoff and requested changes are normal finishes; task acceptance is a task fact.
- `waiting_for_approval` only for an actual active approval pause of that attempt; `blocked` closes the attempt.
- An unknown outcome is shown as "ended (unknown)" with a recorded gap, never guessed.

### Worker provenance through the bridge

- Hermes injects `HERMES_KANBAN_TASK`, `HERMES_KANBAN_RUN_ID`, `HERMES_KANBAN_CLAIM_LOCK` and the board into workers
  (`kanban_db_dispatch.py:2888-2908`). The plugin reads them **per hook, through `hermes_private.py`**, together with the
  delegation context: a delegated helper or in-process cron run inherits the environment but does not own the claim
  (`agent/delegation_context.py`). Each event carries `{ board, attemptId, claimLock, role: 'worker' | 'helper' | 'other' }`.
- Bridge contract + schemas + spool format + producer registry gain these fields together; legacy producers stay
  unassociated (no heuristic matching; D4.4 forbids time-window correlation).

### Sessions, model, tools

- `on_session_start` gives the worker's session id and actual model; compression can rotate the session within one
  attempt. Table `kanban_attempt_sessions (run_id, session_id, role: root|helper|continuation, model, first_seen)`.
- Model = the observed one; historical attempts without evidence keep `model = null`.
- Tool occurrences are kept per producer counter (Hermes fallback tool-call ids repeat). Watch frames and tool evidence
  link to the attempt by exact provenance.

### Arrival order

- Bridge evidence can arrive before the tailer sees the attempt (and vice versa). Unmatched evidence is stored
  **already redacted** under its exact key `(source, history, attempt_id)` and resolved when the other side arrives.
  Enrichment after closure updates session/model/tools without reopening the lifecycle. Board snapshots never
  overwrite bridge-owned fields with defaults. Score-origin runs keep Runs API authority.

### Consumers

- **Flow:** attempts by role (implementer vs reviewer) from claim/review provenance, active attempt selected exactly,
  history ordered by `(claimed_at, attempt_id)`; attempt failure ≠ task failure.
- **Now:** an attempt is a finite block; retries are separate blocks (gaps visible).
- **Reports:** run counts and working intervals include attempts. Spend stays the single session-cost aggregation (each
  session counted once; 5.15 snapshots); attempts show attributed views of it, never added on top. Time categories are
  disjoint (5.17-pre).
- **Team history:** brief links through task relationships as well.

### Redaction and storage

- `summary`/`error` from Hermes: `redactBounded` before storing (8 KB / 2 KB); `metadata` reduced to an allowlist of
  provenance fields. Pending evidence is stored only after the plugin's forced redaction and the server's scrub.

### Migration and contract

- One migration at the next free number when 5.17a lands (after 0025): `kanban_attempt_runs`,
  `kanban_attempt_sessions`, `kanban_pending_evidence`, run `closure_reason`; upgrade backfills numeric `runIds`.
  Old migration checksums untouched.
- Contract: bridge hello/event provenance fields; `RunSummary` closure reason; `TaskDetail.runIds` values change
  meaning (opaque). Both adapters + fake fixtures updated together.

### Tests (done when)

Recorded/fake fixtures for: synthetic rows (not runs), repeated attempt ids across board recreation, same-second retries,
event reordering (evidence before attempt and after), session rotation by compression, helper vs worker attribution,
legacy producers, redaction of summaries/errors/metadata, Reports counting each session's spend once, disjoint time
categories, and the Stop path answering "unavailable" for Kanban attempts.

## 5.17b

Draft `docs/proposals/hermes-attempt-fenced-stop.md`: a Hermes CLI/API operation `kanban stop --attempt <id>
--claim <lock>` that refuses a different attempt, holds the task (no re-dispatch), terminates the verified worker
process (host + start fingerprint) and reports evidence. Score implements Stop against it once Hermes ships it.
