Owner request 2026-10-08 ("start on all the deferred tasks"), from Codex audit wave 2 (tasks-flow, high): a live task's
Kanban worker attempt never becomes a run. Flow shows the task working but its inspector has no run, model or tools; Now
has no block; Reports omits the attempt; Stop on that Flow node returns 409. `TaskDetail.runIds` holds stringified
numeric `task_runs.id` values that consumers look up in Score's `runs` table, which only holds gateway run ids.

## Facts (Hermes 0.21.5; to be verified by the design review)
- Each attempt is a row in the board's `kanban.db` `task_runs` (`hermes_cli/kanban_db.py` ~1080): `id` (autoincrement),
  `task_id`, `profile`, `status` (running | done | blocked | crashed | timed_out | failed | released), `worker_pid`,
  `worker_started_at`, `started_at`, `ended_at`, `outcome` (completed | blocked | crashed | timed_out | spawn_failed |
  gave_up | reclaimed), `summary`, `metadata`, `error`. Score already reads `kanban.db` read-only (tasks tailer).
- Workers run with `HERMES_KANBAN_TASK=<task id>` (`kanban_db_dispatch.py` ~2888); the Score bridge plugin inside a
  worker registers a producer with `kanban_task_id` (Score `producers.kanban_task_id`), so its tool calls and Watch
  frames already arrive tagged with the task.
- Stop: `hermes kanban reclaim [--reason] <task>` "releases an active worker claim on a running task". Whether it also
  terminates the worker process (or only frees the claim) must be verified.
- Score's `runs` table (migration 0005-ish) has `origin IN ('score','kanban','gateway','cron')`, `session_id`, `model`,
  `tools_used`, `output`, `error`, timestamps; ids are Hermes gateway run ids today.

## Proposed design
1. **Identity:** a Kanban attempt's run id is `kanban:<board>:<task_runs.id>` (namespaced; never collides with gateway
   ids). `TaskDetail.runIds` carries these ids (contract value change only; the field type is unchanged).
2. **Ingest:** the existing Kanban tailer also reads `task_runs` rows whose `id` or `ended_at`/`status` changed since its
   cursor (bounded batch), and submits one observation per change through the single ingest path (identity
   `kanban-run:<board>:<id>:<status>:<ended_at|''>`), upserting the `runs` row in the same transaction
   (origin `kanban`, profile, status mapped: running → running; done/completed → completed; blocked → waiting;
   crashed/timed_out/failed/spawn_failed/gave_up → failed; released/reclaimed → cancelled; summary → `output`, error →
   `error`, both redacted and bounded). Model: the task's model override, else the profile's model at start.
3. **Tools and Watch:** bridge events from a producer with `kanban_task_id = T` during an attempt's window are attributed
   to that attempt's run id (tool calls → `tools_used`, Watch frames → `run_id`).
4. **Consumers:** Flow inspector, Now lanes and Reports read these runs like any other (Reports counts their working
   intervals; spend comes from the session when one is known, else unknown).
5. **Stop:** Flow/Task Stop on a `kanban:` run calls `hermes kanban reclaim --reason "Stopped from Score" -- <task>`
   (human-guarded, idempotent) and verifies via `task_runs` that the attempt ended.
6. **Migration 0027:** only if needed (e.g. an index on `runs(origin, started_at)` or a `task_id` column); otherwise none.

## Questions for the review
- Is `task_runs.id` stable per board, and is `<board>` needed in the id (Score reads one board today)?
- Does `reclaim` stop the worker, or only release the claim? If only the claim, what is the correct stop?
- Can a worker's session id be derived (for spend and transcript), or only the producer link?
- Ordering/races between the tailer's attempt rows and bridge events that arrive first.
- Anything here that would mislabel a gateway/Score run or break existing run lifecycles.
