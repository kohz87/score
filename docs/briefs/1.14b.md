## Task (from docs/PLAN.md)
**1.14b Approvals ledger + delivery outbox**
- Goal: operations with phases; `approval_deliveries` outbox (`intent → delivering → applied | not_pending | failed |
  unknown`); attribution only on confirmed delivery; `/api/approvals*` (H); origin dedupe (D4).
- Done when: tests cover a double decision (409), an answer from another surface first (`not_pending` → "answered
  elsewhere", never deny), a Score crash between intent and apply, guardian escalation linking, and a non-actionable

Kanban grants (D4.3) and the plugin side of gateway approvals (exact `requestId` capture, settle callbacks, the
decision poller) are **not** in this task (1.13b/1.13c). This task builds the server ledger they plug into, and

## Hermes facts this design relies on (verified in `../reference/hermes-agent` and the spike)
- Score-started runs: the run SSE emits `approval.request {command, description, pattern_key, pattern_keys,
  allow_session, allow_permanent, request_id, choices}`. The approval session key **is the run id**
  (`api_server_runs.py: approval_session_key`). `POST /v1/runs/{id}/approval {choice, request_id}` → 200
  `{resolved: n}`; 409 `approval_not_pending` or `approval_not_active` when nothing is pending (both mean
  `not_pending`). `approval.responded {choice, request_id, resolved}` is emitted **only** for answers through that
  endpoint.
- Hooks (any process with the plugin): `pre_approval_request(command, description, pattern_key, pattern_keys,
  session_key, surface, [coalesced=True], [request_id, request_digest for transports])`; `post_approval_response(…same,
  choice)`, where `choice ∈ once|session|always|deny|timeout|cancelled|notify_failed|smart_approve|smart_deny` (smart
  adds `decided_by='aux_llm'`). The guardian ("smart" mode) fires `pre_approval_request` with `surface='smart'`; on
  approve/deny it fires the post hook; on **escalate it fires no post hook**, and the human prompt that follows fires
  a fresh `pre_approval_request` with the human surface. Coalesced followers fire `pre_approval_request` with
  `coalesced=True` and adopt their leader's outcome.
- Hooks carry no actor. Only a confirmed delivery proves Score answered.

## Design (from the lead; follow it)

### Migration `apps/server/migrations/0005_approvals.sql`
```sql
CREATE TABLE approvals (
  id TEXT PRIMARY KEY,                       -- random uuid
  origin TEXT NOT NULL CHECK (origin IN ('score-run','gateway','kanban')),
  profile TEXT NOT NULL,
  session_key TEXT NOT NULL,                 -- Hermes approval session key (= run id for Score-started runs)
  run_id TEXT,                               -- Score-started run, when origin = 'score-run'
  request_id TEXT,                           -- exact Hermes target; NULL → never actionable
  producer_id TEXT,                          -- bridge producer that reported it (gateway delivery target)
  surface TEXT NOT NULL,                     -- 'run-sse' | 'smart' | 'cli' | gateway surface | 'transport:<name>'
  leader_id TEXT REFERENCES approvals(id),   -- coalesced follower → its leader
  command TEXT NOT NULL,                     -- redacted, ≤ 2 KB
  command_digest TEXT,
  description TEXT NOT NULL,                 -- redacted, ≤ 2 KB
  pattern_keys TEXT NOT NULL,                -- JSON array of strings
  choices TEXT NOT NULL,                     -- JSON array of ApprovalChoice
  phase TEXT NOT NULL CHECK (phase IN ('guardian_evaluating','human_pending','decided','executed','blocked','withdrawn','expired')),
  status TEXT NOT NULL CHECK (status IN ('pending','approved','denied','expired','withdrawn','unknown')),
  guardian_verdict TEXT CHECK (guardian_verdict IN ('approve','deny','escalate')),
  decision_choice TEXT CHECK (decision_choice IN ('once','session','always','deny')),
  decision_by TEXT CHECK (decision_by IN ('you','guardian','elsewhere','timeout','rule')),
  decided_at TEXT,
  blocking TEXT,
  created_at TEXT NOT NULL,
  expires_at TEXT,
  updated_at TEXT NOT NULL,
  version INTEGER NOT NULL DEFAULT 0
) STRICT;
CREATE UNIQUE INDEX approvals_target ON approvals(profile, session_key, request_id) WHERE request_id IS NOT NULL;
CREATE INDEX approvals_session ON approvals(profile, session_key, phase);
CREATE INDEX approvals_created ON approvals(created_at, id);
CREATE TABLE approval_deliveries (
  id TEXT PRIMARY KEY,                       -- random uuid
  approval_id TEXT NOT NULL UNIQUE REFERENCES approvals(id),  -- at most one decision per approval
  choice TEXT NOT NULL CHECK (choice IN ('once','session','always','deny')),
  note TEXT,                                 -- redacted, ≤ 500 chars; Score-side only, never sent to Hermes
  route TEXT NOT NULL CHECK (route IN ('port','bridge')),
  producer_id TEXT,                          -- route = 'bridge': the only producer allowed to lease it
  state TEXT NOT NULL CHECK (state IN ('intent','delivering','applied','not_pending','failed','unknown')),
  attempts INTEGER NOT NULL DEFAULT 0,
  lease_until INTEGER,                       -- epoch ms, route = 'bridge'
  error TEXT,                                -- short code, never upstream text
  created_at TEXT NOT NULL,
  updated_at TEXT NOT NULL
) STRICT;
CREATE INDEX approval_deliveries_open ON approval_deliveries(state, route, producer_id);
```

### Domain module `apps/server/src/domain/approvals.ts`
Synchronous functions over `DatabaseSync`, called from ingest `apply` callbacks (so ledger changes commit
atomically with the observation) and from the decision route. Each returns the `DomainEventDraft`s to emit:
`approval.requested` when an operation is created, `approval.updated` on any visible change. Map rows to the contract
`Approval` (`agentId = profile`, `title` = the description's first line ≤ 120 chars or the first pattern key,
`cwd: null`, `refs` = `[{kind:'run', runId}]` when `run_id` is set, `delivery` from the delivery row or `'none'`,
`decision` from the decision columns or null, `actionable` computed as below). All row updates go through
`guardedUpsert`/version checks so a stale observation never moves a terminal phase backwards.

**Phases.** `guardian_evaluating → human_pending → decided → (executed | blocked)`; `withdrawn` and `expired` are
terminal from `guardian_evaluating`/`human_pending`. `decided` may still change `decision_by` (see attribution), but
never its `phase` backwards.

**Actionable** (computed on read, stored nowhere): `phase = 'human_pending'` and `request_id IS NOT NULL` and
`leader_id IS NULL` and no delivery row exists and the origin's route is available: `score-run` → the run row is
Score-started and in `queued|running|waiting_for_approval` and the compatibility gate does not disable
`score-runs`; `gateway` → `producer_id` is set, that producer was told `enabled.gatewayApprovals = true` at its last
hello (store this flag on the producer row; add the column in 0005 with `ALTER TABLE producers ADD COLUMN
gateway_approvals INTEGER NOT NULL DEFAULT 0`, set by hello), was seen in the last 2 minutes, and the gate does not
disable `gateway-approvals`; `kanban` → false in this task. Fake mode: actionable comes from the scenario.

**Creation and matching (origin dedupe).** One operation per flagged action:
1. Run SSE `approval.request` (live translate): the canonical producer for Score-started runs. Key
   `(profile, session_key = run_id, request_id)`. If an operation with that key exists, enrich it. Otherwise, **link
   an escalation**: the newest operation in the same `(profile, session_key)` with `phase = 'guardian_evaluating'`,
   equal `pattern_keys` and `created_at` within 10 minutes becomes this operation (set `request_id`, `surface =
   'run-sse'`, `phase = 'human_pending'`, `guardian_verdict = 'escalate'`). Otherwise create it (`origin =
   'score-run'`, choices from the event's `choices`).
2. Bridge `pre_approval_request` (1.14a's approval-hook path; keep inserting `approval_signals` as the raw audit):
   - `surface = 'smart'` → create `phase = 'guardian_evaluating'`, `status = 'pending'`, no `request_id`, origin
     `score-run` if `session_key` is a Score-started run id else `gateway`.
   - `coalesced = true` → find the leader: the newest operation in `(profile, session_key)` with equal `command` and
     `pattern_keys` in `human_pending`. Create a follower with `leader_id` (never actionable). No leader found →
     create a view-only operation (no `request_id`).
   - Human surface with `session_key` = a Score-started run id → **never create**; the run SSE is canonical. Enrich
     the operation found by `(profile, session_key, request_id)` when the payload has `requestId`/`request_id`;
     otherwise the unique open operation in that session with equal `pattern_keys` (if not unique, do nothing).
     If the SSE event hasn't arrived yet, record nothing beyond the signal; escalation linking still happens when
     the SSE event arrives (rule 1).
   - Any other human surface → escalation link as in rule 1 (same session, `guardian_evaluating`, equal
     `pattern_keys`, ≤ 10 min) or create `origin = 'gateway'`, `producer_id` = the reporting producer, `request_id`
     from the payload (`requestId` from 1.13b, or `request_id` on transport surfaces; else NULL → view-only).
     Choices: `['once','session','always','deny']` minus `session`/`always` when the payload says they aren't allowed
     (default all four).
3. Resolution signals (all idempotent; first terminal signal wins for `phase`/`status`; attribution may upgrade):
   - SSE `approval.responded {choice, request_id}` → the operation by `(profile, run_id, request_id)` → `decided`,
     `status` approved (once/session/always) or denied, `decision_choice`. `decision_by` per attribution below.
   - Bridge `post_approval_response`: `smart_approve`/`smart_deny` → the `guardian_evaluating` operation (same
     session, equal `pattern_keys`, newest) → `decided`, `decision_by = 'guardian'`, `guardian_verdict`,
     `decision_choice` once/deny. Human choices → match like the pre hook (request id first, else the unique open
     operation in the session with equal `pattern_keys` and `command`) → `decided`. `timeout` → `expired`
     (`decision_by = 'timeout'`, `status = 'expired'`). `cancelled`/`notify_failed` → `withdrawn`.
   - Bridge `approval.settled {requestId, reason}` (from 1.13b; handle it now): `resolved` → `decided` with
     `status = 'unknown'` unless already decided (the post hook fills the choice); `timeout` → `expired`; anything
     else → `withdrawn`.
   - A run reaching a terminal status → its `guardian_evaluating`/`human_pending` operations become `withdrawn`.
   - Followers mirror their leader's terminal phase/status/decision whenever the leader changes (decision_by
     `'elsewhere'` for followers unless the leader's is `'guardian'`).
4. Expiry: a periodic sweep (wired with the existing retention timer in `start-server.ts`) moves
   `human_pending`/`guardian_evaluating` operations past `expires_at` to `expired`. `expires_at` = the event's own
   expiry if Hermes provides one, else `created_at + 1 h`.

**Attribution.** `decision_by = 'you'` **only** when this operation's delivery is `applied`. When a resolution signal
arrives first (possible: Hermes fires the post hook before Score receives the delivery result), set `'elsewhere'`;
when the delivery later becomes `applied` with the **same** choice, upgrade to `'you'`. If the applied delivery's
choice differs from the recorded decision, keep the recorded decision and set the delivery to `unknown`
(inconsistent evidence). `not_pending` is never a denial: the operation keeps whatever the signals say, and the UI
shows "answered elsewhere" (`delivery = 'not_pending'`).

### Decision API (`apps/server/src/http/approvals.ts`, contract §6)
- `GET /api/approvals?status=pending|all&agent=&cursor=` (S): `pending` = phase `guardian_evaluating` or
  `human_pending`. Order `created_at DESC, id DESC`; page 50; `cursor` = opaque base64url of `(created_at, id)`;
  `asOfSeq` = the event log's current max seq read in the same transaction. Followers are included (the UI groups
  them). Validate query params with zod (400 on bad cursor).
- `POST /api/approvals/:approvalId/decision {choice, note?}` (H: the existing human guard and CSRF). One
  transaction: load the operation (404 if missing); `403 feature_disabled` if the gate disables its origin; `409
  conflict` with the current `Approval` in `details` if it isn't actionable or a delivery already exists; `400
  validation_error` if `choice` isn't in its `choices`. Insert the delivery (`state = 'intent'`, `route = 'bridge'`
  with the operation's `producer_id` for live gateway operations, else `'port'`), emit `approval.updated`, return
  `202` with the `Approval` (`delivery: 'intent'`). Then wake the dispatcher. A concurrent second decision hits the
  `UNIQUE(approval_id)` constraint → 409 (test it).

### Delivery
- **Port route** (`domain/approval-outbox.ts`): a dispatcher claims `intent` rows (→ `delivering`, `attempts + 1`,
  committed before the external call), then calls `port.deliverDecision({ approvalId, origin, profile, runId,
  requestId, choice })`. Change the `HermesPort.deliverDecision` request type accordingly (keep the
  `'applied'|'not_pending'|'failed'` result). Live: `gateway.submitApproval(profile, {runId, choice, requestId},
  generation)` with the credential generation from the `runs` row; treat 409 `approval_not_active` like
  `approval_not_pending`; transient errors (transport, 5xx, 429) → back to `intent` with backoff (1 s, 5 s, 30 s;
  at most 4 attempts, never past `expires_at`), then `failed`; other 4xx → `failed`. Fake: unchanged behaviour,
  keyed by `approvalId`. Outcome in one transaction: delivery state + operation update (attribution, phase) +
  `approval.updated`.
- **Crash recovery**: at startup, port-route rows in `delivering` were possibly applied. Retry once with the same
  exact target: `applied` → `applied`; `not_pending` → `unknown` (Score may have applied it before the crash); an
  error → `unknown`. Rows in `intent` are delivered normally.
- **Bridge route** (contract §11):
  - `GET /bridge/v1/decisions?wait=0..30` (producer token): returns up to 20 deliveries with `route = 'bridge'`,
    `producer_id` = this producer, and `state = 'intent'` or (`delivering` with `lease_until` past). Claiming sets
    `delivering`, `attempts + 1`, `lease_until = now + 30 s`. With nothing to return, wait up to `wait` seconds,
    woken by an in-process notifier when a delivery for this producer is inserted; close cleanly on server shutdown
    and client disconnect. Items: `{ deliveryId, leaseUntil, sessionKey, requestId, choice, reason: null }`.
  - `POST /bridge/v1/decisions/:deliveryId/ack {outcome, resolved, error?}` → 204. Only the producer the delivery
    belongs to (else 404, same body as unknown ids). `applied` (requires `resolved ≥ 1`) → `applied`;
    `not_pending` → `not_pending` on the first attempt, `unknown` on a later one (an earlier lease may have applied
    it); `failed` → `failed`. Acks for a terminal delivery are idempotent 204s with no change.
  - A lease that expires with `attempts ≥ 3` → `unknown`. A delivery whose producer hasn't been seen for 2 minutes
    while `intent` → `failed` (error `producer_gone`).

### Fake mode
The fake scenario's approvals must go through the same ledger so `/api/approvals` and the decision route behave the
same in e2e: the fake port's `approval.requested` steps upsert operations through the domain module (origin, choices,
actionable and ids from the scenario; `request_id` = the scenario approval id; `route = 'port'`), and fake decisions
flow through the outbox and `port.deliverDecision`. Keep the existing fake e2e behaviour working.

## Done when
1. **Double decision** → the second gets 409 with the current `Approval`; a concurrent pair → exactly one 202.
2. **Answered elsewhere first**: a resolution signal arrives, then our delivery returns `not_pending` → the operation
   shows the signal's decision with `decision_by = 'elsewhere'`, `delivery = 'not_pending'`, never a Score denial;
   and the reverse order (signal after `applied`, and signal before `applied`) ends with `decision_by = 'you'`.
3. **Crash between intent and apply**: rows left in `intent` are delivered after restart; rows left in `delivering`
   are retried once and end `applied` or `unknown` (never `not_pending`).
4. **Guardian escalation linking**: smart pre hook → operation in `guardian_evaluating`; then the human prompt (both
   the run-SSE path and the gateway hook path) links to the **same** operation id; smart approve/deny without
   escalation ends `decision_by = 'guardian'`.
5. **Non-actionable cards reject decisions** (409): no `request_id`, a coalesced follower, an inactive run, a gone
   producer, a disabled feature (403), a guardian-phase operation.
6. Origin dedupe: the recorded L4A run produces exactly one operation even when matching bridge hooks for the same
   `session_key = run_id` also arrive (both orders).
7. Bridge decisions: lease, ack, lease expiry, the attempt rules for `not_pending`, producer isolation (another
   producer can't see or ack it), long-poll wake-up and timeout, and shutdown.
8. `pnpm --filter @score/server test`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check` pass; existing e2e flows still
   pass in fake mode (the lead runs `pnpm e2e`).
