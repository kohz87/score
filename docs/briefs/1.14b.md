## Hermes facts this design relies on (verified in `../reference/hermes-agent` at e97923c3 and by the design review)
- Score-started runs: the run SSE emits `approval.request {command, description, pattern_key, pattern_keys,
  allow_session, allow_permanent, request_id, choices}`; **no `tool_call_id`**. The approval session key **is the run
  id**. `POST /v1/runs/{id}/approval {choice, request_id}` → 200 `{resolved: n}`; 409 `approval_not_pending` or
  `approval_not_active` when nothing is pending (both mean `not_pending`). `approval.responded {choice, request_id,
  resolved}` is emitted only for answers through that endpoint.
- **Every approval hook carries the active `tool_call_id`, `turn_id` and `session_id`** (`approval_context.py:
  _fire_approval_hook`), plus `command, description, pattern_key, pattern_keys, session_key, surface` and
  optionally `coalesced=True` (followers) or `request_id, request_digest` (transport surfaces; those ids belong to the
  transport, not the gateway queue). `post_approval_response` adds `choice ∈ once|session|always|deny|timeout|
  cancelled|notify_failed|smart_approve|smart_deny|transport_*` (smart adds `decided_by='aux_llm'`).
- Guardian ("smart"): `pre` with `surface='smart'`; approve/deny fire a post hook; **escalate fires none**, and the
  human prompt that follows fires a fresh `pre` for the **same tool call**. A human may override a guardian
  **deny** (`approval.py:761`): then a human prompt follows the smart-deny post hook, with choices `once|deny`.
- Coalesced followers: Hermes picks the first matching queue entry as leader; a leader answered `once` sends the
  follower to a fresh prompt (a new non-coalesced `pre` for the follower's tool call).
- Hooks carry no human actor. Only a confirmed delivery proves Score answered.

## Design (from the lead; revised after the max design review — see docs/reviews/2026-10-07-1.14b-design-adversarial.md
and ARCHITECTURE D4.4)

### Principles
1. **Exact keys only.** A row is found by `request_id` (run SSE; hook payload `requestId`, which the producer
   guarantees exact — contract §11) or by `(producer incarnation, tool_call_id)` for hook stages. Never by pattern
   keys, command text, time windows or "the only open one".
2. **Stages are rows; links are explicit.** A guardian stage and the human stage it escalates into are separate rows
   linked by `linked_to`; rows are never merged.
3. **Order-independent.** Every bridge approval signal is stored (`approval_signals`, from 1.14a) with its keys and a
   `matched_approval_id`. When a row is created or gains a key, unmatched signals with that key are replayed in
   counter order. When a signal matches nothing, it is kept and nothing is guessed.
4. **Evidence ranks.** Closure (settle-like, timeout, run end, tool completion) can be refined later by decision
   evidence (a known choice). A known choice is never overwritten by weaker evidence.

### Domain module `apps/server/src/domain/approvals.ts`
Synchronous functions over `DatabaseSync`, called from ingest `apply` callbacks (ledger changes commit atomically
with the observation) and from the decision route. They return `DomainEventDraft`s: `approval.requested` on row
creation, `approval.updated` on any visible change. Row → contract `Approval`: `agentId = profile`, `title` = the
description's first line ≤ 120 chars or the first pattern key, `cwd: null`, `linkedTo = linked_to`, `refs` =
`[{kind:'run', runId}]` when `run_id` is set, `delivery` from the delivery row or `'none'`, `decision` from the
decision columns or null, `actionable` as below. Updates are version-guarded and never move a phase backwards except
the explicit transitions listed here.

**Phases.** Guardian stage: `guardian_evaluating → decided` (smart approve/deny) or `→ escalated` (a human stage
for the same tool call appears; also from `decided` after a smart deny, because a human may override it). Human
stage: `human_pending → decided → executed | blocked`. Both: `→ withdrawn | expired` from an open phase.

**Actionable** (computed on read): `stage = 'human'`, `phase = 'human_pending'`, `request_id IS NOT NULL`,
`coalesced = 0`, `target_kind ∈ ('run_request','gateway_request')`, and no delivery row exists **or** the existing
delivery is `failed` without `maybe_applied` (retry, see below); plus the route is available: `run_request` → the run
row is Score-started and in `queued|running|waiting_for_approval` and the gate doesn't disable `score-runs`;
`gateway_request` → `producer_id` set, `producers.gateway_approvals = 1`, last seen within 2 minutes, gate doesn't
disable `gateway-approvals`. Fake mode: actionable comes from the scenario.

**Events → rows.** Let a *hook key* be `(producer incarnation, tool_call_id)` (absent when `tool_call_id` is empty).
1. Run SSE `approval.request` (live translate): find or create the row keyed `(profile, session_key = run_id,
   request_id)`: `origin 'score-run'`, `stage 'human'`, `target_kind 'run_request'`, `surface 'run-sse'`, choices
   from the event. Then replay unmatched signals with that `request_id`.
2. Bridge `pre_approval_request`:
   - `surface = 'smart'` → create a guardian row (hook key; `origin` = `score-run` if `session_key` is a
     Score-started run id else `gateway`; `target_kind 'none'`).
   - `surface` starts with `transport:` → create a view-only human row (hook key; `target_kind 'none'`; its
     `request_id` belongs to the transport and is **not** stored as `request_id`).
   - otherwise (a human prompt): if the payload has `requestId`, find or create the row keyed by
     `(profile, session_key, requestId)` and attach the hook key to it (a Score-run row created by the SSE gains its
     hook key here; that is the dedupe). Without `requestId`: if `session_key` is a Score-started run id, **create
     nothing** (the SSE row is canonical; keep the signal unmatched); else create a view-only gateway human row with
     the hook key. `coalesced = true` → a view-only row (`coalesced = 1`); no leader is guessed. A later
     non-coalesced `pre` for the same hook key upgrades that row in place (the follower's fresh prompt after a `once`).
     A gateway row with `requestId` gets `target_kind 'gateway_request'` and `producer_id` = the reporting producer.
     Choices: `['once','session','always','deny']` minus `session`/`always` when the payload disallows them.
   - **Escalation link:** whenever a human row gains a hook key, a guardian row with the **same hook key** in
     `guardian_evaluating`, or `decided` with verdict `deny`, becomes `escalated` with `linked_to` = the human row
     (`guardian_verdict` stays as it was, or `escalate` when it had none). Exact key, nothing else.
   - A second human `pre` for a hook key whose human row is still open and not coalesced: close the old row
     (`withdrawn`, `status 'unknown'`, `closed_reason 'superseded'`) and create the new one; gates are sequential
     per tool call.
3. Bridge `post_approval_response`: match by `requestId` if present, else by hook key (newest human row for that
   key; for `smart_*`, the guardian row for that key). `smart_approve`/`smart_deny` → guardian row `decided`,
   `decision_by 'guardian'`, `guardian_verdict`, `decision_choice` once/deny. Human choices → `decided`, status
   approved/denied, `decision_choice`, attribution below. `timeout`/`transport_timeout` → `expired` (`decision_by
   'timeout'`). `cancelled`/`notify_failed`/other `transport_*` → `withdrawn`. Matching does **not** require the row
   to be open: a post arriving after a closure refines it (principle 4).
4. Run SSE `approval.responded {choice, request_id}` → the row by `(profile, run_id, request_id)` → `decided` (same
   rules).
5. Closure without a known choice: the run reaches a terminal status → its open rows → `withdrawn`
   (`closed_reason 'run_ended'`); a bridge `post_tool_call` for a hook key → open guardian rows for it → `escalated`
   if a human row exists for it, else `decided` with status `unknown`; open human rows → `withdrawn`
   (`tool_completed`), and `decided` human rows → `executed` (tool status ok) or `blocked` (blocked/error).
6. Expiry sweep (with the existing retention timer): open rows past `expires_at` → `expired` (`closed_reason
   'expired'`). `expires_at` = Hermes's expiry if given, else `created_at + 1 h`.

**Attribution.** `decision_by = 'you'` only when this row's delivery is `applied`. A choice signal arriving first sets
`'elsewhere'`; a later `applied` delivery with the **same** choice upgrades it to `'you'`. An `applied` delivery whose
choice differs from a recorded choice → keep the recorded decision, delivery `unknown`. `not_pending` is never a
denial: the row keeps what its signals say; the UI shows "answered elsewhere" (`delivery 'not_pending'`).

### Decision API (`apps/server/src/http/approvals.ts`, contract §6)
- `GET /api/approvals?status=pending|all&agent=&cursor=` (S): `pending` = phase `guardian_evaluating` or
  `human_pending`. Order `created_at DESC, id DESC`; page 50; `cursor` = opaque base64url of `(created_at, id)`;
  `asOfSeq` = the event log's max seq read in the same transaction. Zod-validate params (400 on a bad cursor).
- `POST /api/approvals/:approvalId/decision {choice, note?}` (H: human guard + CSRF). One transaction: 404 if
  missing; 403 `feature_disabled` if the gate disables its route; 409 `conflict` with the current `Approval` in
  `details` unless actionable; 400 `validation_error` if `choice ∉ choices`. With no delivery: insert one
  (`intent`; `route 'bridge'` + `producer_id` for `gateway_request`, else `'port'`). **Retry**: if the delivery is
  `failed` and `maybe_applied = 0`, the same request with the **same** choice resets it to `intent` (a different
  choice → 409). Emit `approval.updated`; return 202 with the `Approval`; wake the dispatcher. A concurrent second
  decision hits `UNIQUE(approval_id)` → 409 (test it).

### Delivery
- **Port route** (`domain/approval-outbox.ts`): the dispatcher claims due `intent` rows (→ `delivering`,
  `attempts + 1`, committed before the call), then calls `port.deliverDecision({ approvalId, origin, profile, runId,
  requestId, choice })` (change the `HermesPort.deliverDecision` request type; keep the result type). Live:
  `gateway.submitApproval(profile, {runId, choice, requestId}, generation)` with the `runs` row's credential
  generation; add `approval_not_active` to the not-pending codes. Classify each attempt:
  - connection refused / DNS / TLS before sending → **not sent**: back to `intent` with backoff (1 s, 5 s, 30 s).
  - timeout, reset after sending, 5xx, 429 → **maybe sent**: set `maybe_applied = 1`, back to `intent` with backoff.
  - 200 → `applied`. 409 not pending → `not_pending` if `maybe_applied = 0`, else `unknown`. Other 4xx → `failed`.
  - At most 4 attempts and never past `expires_at`; then `failed` if `maybe_applied = 0`, else `unknown`.
  Each outcome is one transaction: delivery + row (attribution, phase) + `approval.updated`.
- **Crash recovery** at startup: port rows in `delivering` get `maybe_applied = 1` and go back to `intent` (the
  rules above then end them `applied` or `unknown`, never `not_pending`).
- **Bridge route** (contract §11):
  - `GET /bridge/v1/decisions?wait=0..30` (producer token): claims up to 20 deliveries with `route 'bridge'`,
    `producer_id` = this producer, and `state 'intent'` or (`delivering` with `lease_until` past); skip and fail
    (`expired`) any whose row is no longer actionable or past `expires_at`. Claiming sets `delivering`, `attempts +
    1`, a new random `lease_id`, `lease_until = now + 30 s`, and `maybe_applied = 1` (once leased, the plugin may
    apply it). With nothing to return, wait up to `wait` seconds, woken by an in-process notifier keyed by producer;
    end cleanly on server shutdown and client disconnect. Polls and acks update `producers.last_seen_at`.
  - `POST /bridge/v1/decisions/:deliveryId/ack {leaseId, outcome, resolved, error?}` → 204. Wrong producer or
    unknown id → 404 (same body). `applied` (schema requires `resolved === 1`): accepted for **any** lease of this
    delivery, even late; it moves `delivering`/`unknown`/`failed` to `applied` (strong evidence). `not_pending` and
    `failed` are accepted only for the **current** `lease_id` and state `delivering` (else 204, no change):
    `not_pending` → `not_pending` if this is attempt 1, else `unknown`; `failed` → back to `intent` while attempts <
    3, else `unknown`.
  - **Delivery sweep** (every 10 s): `delivering` bridge rows whose lease expired and whose producer hasn't been seen
    for 2 minutes → `unknown`; `intent` rows whose producer is gone → `failed` (`producer_gone`; never sent); rows
    whose approval closed or expired → `failed` if `intent`, `unknown` if `delivering`.

## Done when
1. **Double decision** → the second gets 409 with the current `Approval`; a concurrent pair → exactly one 202.
2. **Answered elsewhere first**: a resolution signal arrives, then our delivery returns `not_pending` → the operation
   shows the signal's decision with `decision_by = 'elsewhere'`, `delivery = 'not_pending'`, never a Score denial;
   and the reverse order (signal after `applied`, and signal before `applied`) ends with `decision_by = 'you'`.
3. **Crash between intent and apply**: rows left in `intent` are delivered after restart; rows left in `delivering`
   end `applied` or `unknown` (never `not_pending`). A lost HTTP response followed by a 409 ends `unknown`, never
   "answered elsewhere". A definitively failed delivery (never sent) can be retried with the same choice only.
4. **Guardian escalation linking** by exact hook key: smart pre → guardian row; human prompt for the same tool call
   (gateway path, and the Score-run path where the SSE arrives before **and** after the hooks) → guardian row
   `escalated` with `linkedTo` = the human row; smart deny then a human override → the same link; smart approve/deny
   without escalation ends `decision_by = 'guardian'`. **Adversarial cases from the review**: two smart evaluations
   back to back for different commands never cross-link; two identical commands pending in the same session stay
   two rows; a coalesced follower stays view-only and is upgraded in place by its fresh prompt after a leader `once`;
   a post arriving after a settle-like closure refines the decision; an unmatched signal is replayed when its key
   appears.
5. **Non-actionable cards reject decisions** (409): no `request_id`, a coalesced follower, an inactive run, a gone
   producer, a disabled feature (403), a guardian-phase operation.
6. Origin dedupe: the recorded L4A run produces exactly one operation even when matching bridge hooks for the same
   `session_key = run_id` also arrive (both orders).
7. Bridge decisions: lease ids (a stale negative ack is ignored; a late `applied` refines `unknown`), lease expiry
   and the delivery sweep (no delivery stays `delivering` forever), the attempt rules for `not_pending`, producer
   isolation (another producer can't see or ack it), polls refreshing liveness, long-poll wake-up and timeout, and
   shutdown.
8. `pnpm --filter @score/server test`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check` pass; existing e2e flows still
   pass in fake mode (the lead runs `pnpm e2e`).
