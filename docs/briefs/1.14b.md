## Hermes facts this design relies on (verified in `../reference/hermes-agent` at e97923c3 and by the design review)

- Score-started runs: the run SSE emits `approval.request {command, description, pattern_key, pattern_keys,
allow_session, allow_permanent, request_id, choices}`; **no `tool_call_id`**. The approval session key **is the run
  id**. `POST /v1/runs/{id}/approval {choice, request_id}` → 200 `{resolved: n}`; 409 `approval_not_pending` or
  `approval_not_active` when nothing is pending (both mean `not_pending`). `approval.responded {choice, request_id,
resolved}` is emitted only for answers through that endpoint.
- **Every approval hook carries the active `tool_call_id`, `turn_id` and `session_id`** (`approval_context.py:
_fire_approval_hook`), plus `command, description, pattern_key, pattern_keys, session_key, surface` and
  optionally `coalesced=True` (followers) or `request_id, request_digest` (transport surfaces; those ids belong to the
  transport, not the gateway queue). `post_approval_response` adds `choice ∈ once|session|always|deny|timeout|
cancelled|notify_failed|smart_approve|smart_deny|transport_*` (smart adds `decided_by='aux_llm'`).
- Guardian ("smart"): `pre` with `surface='smart'`; approve/deny fire a post hook; **escalate fires none**, and the
  human prompt that follows fires a fresh `pre` for the **same tool call**. A human may override a guardian
  **deny** (`approval.py:761`): then a human prompt follows the smart-deny post hook, with choices `once|deny`.
- Coalesced followers: Hermes picks the first matching queue entry as leader; a leader answered `once` sends the
  follower to a fresh prompt (a new non-coalesced `pre` for the follower's tool call).
- Hooks carry no human actor. Only a confirmed delivery proves Score answered.

## Design (from the lead; revised after the max design review — see docs/reviews/2026-10-07-1.14b-design-adversarial.md

and ARCHITECTURE D4.4)

### Principles (after two design reviews: docs/reviews/2026-10-07-1.14b-design-adversarial.md and …-followup.md)

1. **Exact keys only.** A human or guardian stage is found by: `request_id` (run SSE; a hook's `requestId`, which the
   producer guarantees exact), `transport_request_id` (transport surfaces), or the **producer-minted gate id**
   `(producer_incarnation, gate_id)`. Hermes's `tool_call_id` is **not** unique; store it, never key on it. No pattern,
   command-text or time-window matching; no "only open one" fallback.
2. **Stages are rows; links are explicit.** Guardian and human stages are separate rows, linked by `linked_to` from the
   plugin's `linkedGateId`. Rows are never merged.
3. **Order-independent.** Every bridge approval signal is stored (`approval_signals`) with its keys and a
   `matched_approval_id`. When a row is created or gains a key, unmatched signals with that key are replayed in
   producer counter order.
4. **Evidence, then phase.** Decision evidence (a known choice and who made it), closure evidence (timeout,
   cancellation, run end) and completion evidence (the tool's outcome) are stored in separate columns; the phase and
   status are **recomputed** from them after every change, so arrival order can't change the result. A known choice
   always beats closure; completion turns `decided` into `executed`/`blocked`.

### Plugin: gate ids (`hermes-plugin/score_bridge/`, in scope for this task)

In the hook wrappers (capture time, hook thread; keep the 1.13a budgets and fail-open rules):

- Per thread (`threading.local`), keep a small stack of open gates `{gate_id, surface, command_digest_or_snapshot_key,
pattern_keys}` and the last closed guardian gate of the current tool call.
- `pre_approval_request`: mint `gate_id = uuid4().hex`; if this is a human surface and the top of this thread's stack is
  an open `smart` gate (escalation), or the last closed guardian gate in this thread ended `smart_deny` and no other
  gate opened since (override), set `linkedGateId` to that guardian gate and pop it. Push the new gate. Add `gateId`,
  `linkedGateId`, and for `surface` starting `transport:` the payload's `request_id` as `transportRequestId` (remove
  `request_id` from the payload so it can't be mistaken for a gateway id).
- `post_approval_response`: pop the newest open gate in this thread with the same surface family (smart vs human) and
  attach its `gateId` (and `transportRequestId`). No open gate → `gateId: null` (the server keeps it unmatched).
- A human `pre` while the top open gate in this thread is a **coalesced follower**: Hermes sends the follower to a fresh
  prompt after its leader's `once` without a post hook (`approval_gateway_wait.py:_await_coalesced_leader`), so pop the
  follower and add `supersedesGateId` = its gate id.
- Bounded: at most 16 open gates per thread (drop the oldest), cleared on fork (1.13a reset).
- Tests: pre/post pairing in one thread; two threads interleaving identical commands stay distinct; smart → escalate →
  human links; smart deny → human override links; coalesced follower then fresh prompt; transport id moved.

### Domain module `apps/server/src/domain/approvals.ts`

Synchronous functions over `DatabaseSync`, called from ingest `apply` callbacks (ledger changes commit atomically
with the observation) and from the decision route; they return `DomainEventDraft`s: `approval.requested` when a
**visible** row is created (or a hidden row becomes visible), `approval.updated` on any visible change. Row →
contract `Approval`: `agentId = profile`, `title` = the description's first line ≤ 120 chars or the first pattern key,
`cwd: null`, `linkedTo` = `linked_to` only when the target row is visible (else null), `refs` = `[{kind:'run',
runId}]` when `run_id` is set, `delivery` from the delivery row or `'none'`, `decision` from the decision columns or
null, `actionable` as below. Hidden rows never appear in the API or the stream.

**Derivation** (one pure function from evidence to `{phase, status}`; test it table-driven):

- Guardian stage: `linked_to` set → `escalated`; else a guardian verdict approve/deny → `decided` (approved/denied,
  `decision_by 'guardian'`); else closure → `withdrawn`/`expired`; else `guardian_evaluating`.
- Human stage: a decision choice → `decided` (approved/denied), then `tool_outcome` ok → `executed`, blocked/error →
  `blocked`; else closure `timeout`/`expired` → `expired`; other closure → `withdrawn` (status `withdrawn`, or `unknown`
  for `superseded`/`run_ended` when a delivery is `delivering`/`unknown`); else `human_pending`.

**Actionable** (computed on read; permission to **submit** a decision): visible, `stage 'human'`, phase
`human_pending`, `request_id IS NOT NULL`, `coalesced = 0`, `target_kind ∈ ('run_request','gateway_request')`, the
route is available (`run_request` → run row Score-started and `queued|running|waiting_for_approval`, gate allows
`score-runs`; `gateway_request` → `producer_id` set, `producers.gateway_approvals = 1`, seen within 2 minutes, gate
allows `gateway-approvals`), and either no delivery row exists or the delivery is `failed` with `maybe_applied = 0`.
**Deliverability** (eligibility to deliver an existing decision) is separate: the row is still `human_pending` and
not past `expires_at`, and the delivery's producer (bridge) is the row's producer.

**Events → rows.**

1. Run SSE `approval.request` → find or create the visible row keyed `(profile, session_key = run_id, request_id)`:
   `origin 'score-run'`, `stage 'human'`, `target_kind 'run_request'`, `surface 'run-sse'`, choices from the event.
   Replay unmatched signals with that `request_id`.
2. Bridge `pre_approval_request` (with `gateId`; without one → keep the signal unmatched, create nothing):
   - `surface 'smart'` → guardian row keyed by gate id (`origin` = `score-run` if `session_key` is a Score-started run
     id else `gateway`; `target_kind 'none'`; visible).
   - `transport:*` → visible human row keyed by gate id, `target_kind 'transport'`, `transport_request_id` set
     (view-only).
   - Human prompt with `requestId` → find or create the row by `(profile, session_key, requestId)` and attach the gate
     key (a Score-run SSE row gains its gate here: dedupe). Gateway rows get `target_kind 'gateway_request'` and
     `producer_id` = the reporting producer.
   - Human prompt without `requestId`: Score-run session → a **hidden** human row keyed by gate id (`visible = 0`);
     otherwise a visible view-only gateway row (`target_kind 'none'`). `coalesced = true` → view-only
     (`coalesced = 1`).
   - `supersedesGateId` (the plugin's report that this fresh prompt replaces a coalesced follower in the same thread,
     after its leader answered `once`; Hermes fires no post hook for that follower) → close that follower row with
     closure `superseded`.
   - `linkedGateId` → set the guardian row's `linked_to` = this human row (if the guardian row is missing, keep the
     link in the signal and apply it when it appears).
   - Choices: `['once','session','always','deny']` minus `session`/`always` when the payload disallows them; after a
     guardian deny, `['once','deny']`.
3. Bridge `post_approval_response` → the row by `gateId` (else `transportRequestId`, else `requestId`); unmatched →
   kept. `smart_approve`/`smart_deny` → `guardian_verdict`, `decision_choice` once/deny, `decision_by 'guardian'`.
   Human choices → decision evidence (attribution below). `timeout`/`transport_timeout` → closure `timeout`.
   `cancelled`/`notify_failed`/other `transport_*` → closure with that reason.
4. Run SSE `approval.responded {choice, request_id}` → decision evidence on the row by request id.
5. Run terminal status → closure `run_ended` on its open rows. Bridge `post_tool_call` → `tool_outcome` on rows whose
   gate belongs to the same producer and `tool_call_id` **and** that are the newest human row for that pair (tool
   outcome is informational: it only turns `decided` into `executed`/`blocked`, never decides anything).
6. Expiry sweep (with the existing retention timer): open rows past `expires_at` → closure `expired`.
   `expires_at` = Hermes's expiry if given, else `created_at + 1 h`.

**Attribution.** `decision_by = 'you'` only when this row's delivery is `applied`. A choice signal arriving first sets
`'elsewhere'`; a later `applied` delivery with the **same** choice upgrades it to `'you'`. An `applied` delivery
whose choice differs from the recorded one → keep the recorded decision, delivery `unknown`. `not_pending` is never a
denial.

### Decision API (`apps/server/src/http/approvals.ts`, contract §6)

- `GET /api/approvals?status=pending|all&agent=&cursor=` (S): visible rows only; `pending` = phase
  `guardian_evaluating` or `human_pending`. Order `created_at DESC, id DESC`; page 50; `cursor` = opaque base64url of
  `(created_at, id)`; `asOfSeq` = the event log's max seq read in the same transaction. Zod-validate params.
- `POST /api/approvals/:approvalId/decision {choice, note?}` (H: human guard + CSRF). One transaction: 404 if
  missing or hidden; 403 `feature_disabled` if the gate disables its route; 409 `conflict` with the current
  `Approval` in `details` unless actionable; 400 `validation_error` if `choice ∉ choices`. No delivery → insert one
  (`intent`; `route 'bridge'` + `producer_id` for `gateway_request`, else `'port'`). **Retry**: delivery `failed` with
  `maybe_applied = 0` and the **same** choice → back to `intent`, `cycle + 1`, `cycle_attempts = 0` (a different
  choice → 409). Emit `approval.updated`; 202 with the `Approval`; wake the dispatcher. Concurrent second decision →
  `UNIQUE(approval_id)` → 409.

### Delivery

**Monotone uncertainty:** once `maybe_applied = 1`, every terminal classification other than `applied` is `unknown`
(never `failed` or `not_pending`). **Positive receipts win:** a verified `applied` moves the delivery to `applied`
from any state.

- **Port route** (`domain/approval-outbox.ts`): claim due `intent` rows that are deliverable (else `failed`/`unknown`
  per monotone rule, error `not_deliverable`) → `delivering`, `cycle_attempts + 1`, committed before the call; then
  `port.deliverDecision({ approvalId, origin, profile, runId, requestId, choice })` (change the request type; keep
  the result type; the live port returns `applied` only when `resolved === 1`, and `failed` with a `maybe_applied`
  hint is expressed by throwing a typed error the outbox classifies). Live: `gateway.submitApproval(profile, {runId,
choice, requestId}, generation)` with the `runs` row's credential generation; add `approval_not_active` to the
  not-pending codes. Classification: not sent (connection refused, DNS, TLS before sending) → `intent` with backoff
  (1 s, 5 s, 30 s); maybe sent (timeout, reset after sending, 5xx, 429) → `maybe_applied = 1`, `intent` with backoff;
  200 with `resolved === 1` → `applied`; 409 not pending → `not_pending` (or `unknown` if `maybe_applied`); other 4xx →
  `failed` (or `unknown`). Budget: 4 attempts per cycle and never past `expires_at`; then `failed` (or `unknown`).
  Each outcome: delivery + row (attribution, derivation) + `approval.updated` in one transaction.
- **Crash recovery** at startup: port rows in `delivering` → `maybe_applied = 1`, back to `intent`.
- **Bridge route** (contract §11):
  - `GET /bridge/v1/decisions?wait=0..30` (producer token): claims up to 20 deliverable deliveries with `route
'bridge'`, `producer_id` = this producer, and `state 'intent'` or (`delivering` with `lease_until` past). Claim:
    `delivering`, `cycle_attempts + 1`, a new random `lease_id` (also inserted into `approval_delivery_leases`),
    `lease_until = now + 30 s`, `maybe_applied = 1`. Non-deliverable claims → terminal per the monotone rule (error
    `not_deliverable`). With nothing to return, wait up to `wait` seconds, woken by an in-process notifier keyed by
    producer; end cleanly on shutdown and client disconnect. Polls and acks update `producers.last_seen_at`.
  - `POST /bridge/v1/decisions/:deliveryId/ack {leaseId, outcome, resolved, error?}` → 204. Wrong producer, unknown
    id, or a `leaseId` never issued for this delivery → 404 (same body). `applied` (schema: `resolved === 1`) from
    **any** issued lease and any state → `applied`. `not_pending`/`failed` count only for the **current** lease while
    `delivering` (else 204, no change): `not_pending` → `not_pending` if `cycle_attempts = 1` and this is the only lease
    of the cycle, else `unknown`; `failed` → back to `intent` while `cycle_attempts < 3`, else `unknown`.
  - **Delivery sweep** (every 10 s): `delivering` rows whose lease expired and whose producer hasn't been seen for 2
    minutes → `unknown`; `intent` rows that are no longer deliverable → terminal per the monotone rule.

## Done when

1. **Double decision** → the second gets 409 with the current `Approval`; a concurrent pair → exactly one 202.
2. **Answered elsewhere first**: a resolution signal arrives, then our delivery returns `not_pending` → the operation
   shows the signal's decision with `decision_by = 'elsewhere'`, `delivery = 'not_pending'`, never a Score denial;
   and the reverse order (signal after `applied`, and signal before `applied`) ends with `decision_by = 'you'`.
3. **Crash between intent and apply**: rows left in `intent` are delivered after restart; rows left in `delivering`
   end `applied` or `unknown` (never `not_pending`). A lost HTTP response followed by a 409 ends `unknown`, never
   "answered elsewhere". A definitively failed delivery (never sent) can be retried with the same choice only.
4. **Guardian escalation linking** by exact gate ids (plugin `linkedGateId`): smart pre → guardian row; the human prompt that follows in the same thread
   (gateway path, and the Score-run path where the SSE arrives before **and** after the hooks) → guardian row
   `escalated` with `linkedTo` = the human row; smart deny then a human override → the same link; smart approve/deny
   without escalation ends `decision_by = 'guardian'`. **Adversarial cases from the review**: two smart evaluations
   back to back for different commands never cross-link; two identical commands pending in the same session stay
   two rows; a coalesced follower stays view-only and is upgraded in place by its fresh prompt after a leader `once`;
   a post arriving after a settle-like closure refines the decision; an unmatched signal is replayed when its key
   appears.
5. **Non-actionable cards reject decisions** (409): no `request_id`, a coalesced follower, an inactive run, a gone
   producer, a disabled feature (403), a guardian-phase operation.
6. Origin dedupe: the recorded L4A run produces exactly one operation even when matching bridge hooks for the same
   `session_key = run_id` also arrive (both orders).
7. Bridge decisions: lease ids (a stale negative ack is ignored; a late `applied` refines `unknown`), lease expiry
   and the delivery sweep (no delivery stays `delivering` forever), the attempt rules for `not_pending`, producer
   isolation (another producer can't see or ack it), polls refreshing liveness, long-poll wake-up and timeout, and
   shutdown.
8. `pnpm --filter @score/server test`, `pnpm typecheck`, `pnpm lint`, `pnpm format:check` pass; existing e2e flows still
   pass in fake mode (the lead runs `pnpm e2e`).
