# 3.8.0 Recipes: archive, and delete with runs (owner, 2026-10-27, decision 142)

Owner pasted the refusal "This recipe has runs, so it can't be deleted. Delete is only for recipes nothing has run."
and chose **Both**: Archive by default for a recipe with runs, plus "Delete with runs" for when it must go.

## Done when
1. **Archive.** A recipe can be archived and unarchived. Archived recipes:
   - are hidden from the Recipes list by default, which gets an **Archived** filter (or a toggle) to show them, with
     **Unarchive** on each;
   - are not offered in Start a job's recipe choices (`BoldStartJob.tsx`, its recipe list);
   - keep their runs: past runs still open (Runs list, Threads) exactly as now.
   An archived recipe can still be opened from a run link; its page says "Archived" and offers Unarchive.
2. **Delete stays** for a recipe nothing has run (unchanged behaviour, no confirm text change needed).
3. **Delete with runs**, for a recipe that has runs, under Archive (a quieter, destructive action):
   - a confirmation dialog: says how many runs will be deleted and that it can't be undone; the person types the
     recipe's name to enable the button;
   - refused (409, plain message) while any run of it is still going (not finished/released): "A run of this recipe is
     still going. Stop it first.";
   - deletes every run of the recipe the same way deleting the run's room does today: call `deleteRoom` from
     `apps/server/src/domain/room-delete.ts` for each run's room (`orchestrations.room_id` of each `wf_runs` row of the
     workflow) in ONE transaction, then the versions and the definition. deleteRoom prunes the run's records and (3.7.12)
     the team-room job that started it. Return/emit every event deleteRoom returns plus a workflow-removed signal the web
     list reacts to (see contract below).
4. The Recipes list, Start a job, and the run list update live (stream events), no reload needed.

## Contract (update docs/API-CONTRACT.md §15 Workflows first, then packages/contract, then both sides)
- Migration `0097_workflow_archive.sql`: `ALTER TABLE workflow_definitions ADD COLUMN archived_at TEXT;` (0096 is taken).
- `WorkflowSummary` (whatever `GET /api/workflows` returns per item) gains `archivedAt: string | null`.
- `POST /api/workflows/:id/archive` → the summary; `POST /api/workflows/:id/unarchive` → the summary. Human-guarded
  like the other mutations (`mutation` options in apps/server/src/http/workflows.ts).
- `POST /api/workflows/:id/delete-with-runs` body `{ confirm: string }` (must equal the recipe's name, else 400) →
  `{ deletedRuns: number }`; 409 `run_active` while a run is going; 404 unknown.
- `GET /api/workflows` keeps returning all (archived included, flagged), so the web filters; check every web consumer
  of that list and filter archived out where a recipe is *offered* (Start a job), keep it where a past run *names* it.
- If the web keeps the workflows list via a stream query, emit an event on archive/unarchive/delete (follow how
  workflows changes are announced today; if they are not streamed, invalidate the TanStack query after the mutation).
