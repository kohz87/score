# 4.0 — Chats, a Knowledge page, shared workspaces (design note, draft for the owner)

Owner, 2026-11-03: "job, room, runs and threads are still confusing … 1. dedicated page for knowledge, 2. centralize
workspace then assign agents … (so one may assign multiple workspaces), 3. combine job, threads, run and room into
chatroom (each chatroom has an owner like a WhatsApp or Telegram group … owner assigns work with function and role using
/command or @ command …), a messaging-app interface with ample space."

Today (research map, 2026-11-03): a **room** (team room, chosen teams, one direct room per agent, hidden run rooms) holds
**jobs** (each with its own Hermes sessions, state, budgets, holder); a job's **thread** opens in the side panel; a **run**
(recipe or lead-decides) has its own hidden room plus a linked team-room job, created in two calls; one-to-ones are jobs
in a direct room; Knowledge lives in the side panel's Library; each agent has exactly one folder (a Hermes profile's
`terminal.cwd`, or a coding agent's `workspace`).

## The model: one thing, the chat
- **A chat is a room.** Group chats (the team chat, any chat you make with chosen members) and direct chats (one per
  agent). Each group chat has an **owner, its leader agent** (`rooms.lead_agent_id`, which exists) and members. The chat
  list is the app's left column, newest activity first, like a messenger.
- **Topics replace jobs and threads in the UI.** A chat is one continuous conversation. `/new <title>` (or the person's
  first message after a topic is done) starts a **topic**: a divider in the stream ("New topic: Activity feed"), fresh
  agent sessions, its own state (working / waiting on you / done). Under the hood a topic is today's job (same table,
  same sessions, same budgets), so nothing is migrated and no agent loses its history. The old job tabs and the side-panel
  thread go away: the chat itself is the thread, full width.
- **Runs are things you start in a chat.** `/run <recipe>` (or `/run` and pick) starts a recipe or a lead-decides run as a
  new topic in this chat; its progress is a live card in the stream (steps, who's on what, needs-you). The run's own
  hidden room stays an internal detail. Creating the run and its topic becomes one server call (today two, not atomic).
- **Work is given by talking.** `@builder …` hands that message to builder (as today's To chips). The leader gets
  everything not addressed. Commands (`/` opens a palette with descriptions):
  `/new <title>` new topic · `/run <recipe>` start a recipe · `/assign @agent <task>` a Hermes task · `/lead @agent` change
  the owner · `/add @agent`, `/remove @agent` members · `/workspace <name>` the chat's workspace · `/rename`, `/done`,
  `/reopen` the topic · `/model`, `/usage`, `/compress` as today. Every button that does one of these stays too.
- **Agents still hand off with their tools** (exchanges): an agent writing "@reviewer" in prose doesn't start work, as
  today (decision 116); only people's @mentions and commands assign.

## Knowledge page
**Knowledge** in the top bar: `/b/knowledge`, the Library's notes, documents, search and folders at full width (same
routes, same components, laid out as a page). The side panel's Library becomes a quick picker for linking a note into a
message.

## Shared workspaces
A **Workspaces** page (Settings › Workspaces, linked from each agent): you create workspaces (a name and a folder) and
tick which agents may work in each. An agent can be in several. A chat can be set to one workspace (`/workspace` or its
info panel); an agent working in that chat works there, if it's assigned to it. New tables `workspaces` and
`workspace_agents`, `rooms.workspace_id`. Coding agents: Score sets the folder per turn (it starts them). Hermes agents:
**open question to verify** whether a turn can take its own working folder through Hermes' API; if not, the agent's
profile folder is switched before a turn only when no other turn of that agent runs (or Hermes agents keep one folder
and workspaces apply to coding agents first).

## Phases (each its own release, mock-up first)
1. Knowledge page (small, web only).
2. Shared workspaces (server + web; coding agents first, Hermes per the answer above).
3. Chats: the messenger layout, topics in the stream, the command palette, `/run` in one call, the info panel (members,
   owner, workspace). Old deep links (`?job=`, `?run=`, `?with=`) redirect to the chat and topic.

## Risks (for the adversarial review before phase 3)
Job-scoped budgets and the one-turn-per-agent rule stay as they are (topics are jobs). The run's two-call start becomes
one transaction. Deep links and the side-panel modes need redirects. Search, shares and summaries keep job ids (topics).
Hermes session keys are untouched.
