# 10.4 — Upload progress everywhere

Owner (2026-10-19): "also include upload progress for big files". Knowledge file uploads (1.9.5, `UploadProgressPanel`
in `routes/knowledge/UploadFlow.tsx`) and pet packs (1.10.0, `PackUploadProgress` in `routes/team/PetPackSection.tsx`)
already show progress through `apiUpload` (`apps/web/src/data/api.ts`: XHR with `upload.onprogress`; takes a `Blob` or a
`FormData` and extra headers). Every other upload sends with `fetch` and shows nothing until it finishes.

## Done when (from docs/PLAN.md 10.4)
Each of these shows a live percentage and megabytes while sending ("Uploading · 42% · 84.0 MB of 200.0 MB"), then a
named step while the server works, then the result — with unit tests that drive XHR progress events:
1. **Team › Import agent** (`routes/team/ImportAgent.tsx`, `POST agents/imports`, up to 200 MB) → after sending:
   "Checking the archive…".
2. **Chat attachments** (`routes/chat/Composer.tsx` `upload()`, `POST media`) → per file in the attachment tray, e.g.
   a chip "report.pdf · 42%" that becomes the attachment; several files each show their own. After sending: "Checking…".
3. **Workspace upload** (`routes/team/workspace-queries.ts` `upload`, used by `WorkspaceTab.tsx`) → in the tab, per file.
4. **Theme zip install** (`themes/customizer/api.ts` `installThemeZip`, used by the Customizer and Settings › Look
   import) → "Uploading · …", then "Installing…".
5. **Knowledge editor images** (`routes/knowledge/EditorToolbar.tsx`): if its insert uploads without progress, pass
   `onProgress` to the existing `uploadBlob` and show it in the toolbar's status. Don't touch `UploadFlow.tsx`,
   `knowledge-files.ts` or `KnowledgePage.tsx` (another builder is changing them for 10.3).

## How
- Make one shared component, `components/UploadProgress.tsx` (`role="status"`, the text above, a `<progress>` with value
  while sending and indeterminate after; names in a short form), and use it in all five places and in
  `PetPackSection.tsx` (replacing `PackUploadProgress`). Leave Knowledge's `UploadProgressPanel` alone (10.3).
- Move each upload to `apiUpload`, keeping its exact method, headers (`content-type`, `Idempotency-Key`, `If-Match`) and
  error handling; extend `apiUpload` only if a method other than PUT is needed (it must then take the method as an
  option; existing callers unchanged). Errors must stay `ApiError` with the same status and code as `apiFetch` gives.
- No server changes, no contract changes.
- Tests failing first: per place, a unit test that fires progress events (the test setup's `xhr-via-fetch` shim in
  `apps/web/src/test/` routes XHR through the fetch mocks; extend the shim if it can't emit progress) and checks the
  text, then the named step, then the result; error paths (413/415/409) still show their current messages. One e2e:
  agent import of a generated archive shows "Checking the archive…" or a percentage before the inspection appears.
