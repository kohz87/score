# 7.2 Coding agents as team members — design v1 (2026-10-09)

**Goal (PLAN 7.2):** Claude Code, Codex CLI and OpenCode take part in rooms next to Hermes agents: you can @mention
them, hand work to them, see their tool use in the thread, Stop them, and see them in Now/Flow/Reports.

## Boundary
A second runtime adapter, parallel to `hermes/`: `apps/server/src/runtimes/coding/` with one driver per CLI
(`claude.ts`, `codex.ts`, `opencode.ts`). Nothing else imports CLI names, flags or event shapes (same rule as D2.1). The
domain sees a `CodingAgent` with `{ id, name, runtime: 'claude-code'|'codex'|'opencode', workspace, permission,
model? }` and the same `startRun/stopRun/stream` port shape Hermes runs use, so rooms, routing, Now, Flow, Reports and
Watch need only a `runtime` field, not new paths.

## Running
- **Headless, one process per turn**, argv arrays only:
  - Claude Code: `claude -p --output-format stream-json --verbose --permission-mode <mode> [--model M]
    [--resume <session>]` with the turn input on stdin; cwd = the agent's workspace.
  - Codex: `codex exec --json -s <sandbox> -C <workspace> [-m M] [resume <id>]` with the prompt on stdin.
  - OpenCode: `opencode run --format json …` (not installed here; driver ships disabled until the owner installs it).
- **Sessions:** each (room, agent) keeps the CLI's own session id so the next turn resumes it (like Score's
  `score-<room>-<agent>` Hermes sessions). Rewind (5.33) is "not available" for coding agents in v1.
- **Permissions:** chosen per agent in Score: `read-only` | `workspace-write` (default) | `full` (needs the security
  password to select). Mapped to each CLI's own sandbox/permission flags; Score never answers the CLIs' interactive
  permission prompts in v1 (headless modes run with the chosen fixed policy; anything outside it is refused by the CLI).
- **Workspace:** a folder under the same root policy as 6.1 (no `$HOME`, no `~/.hermes`, no `~/.score`); default
  `~/score-workspaces/<agent-id>`; git badge reused.
- **Credentials:** the CLIs use their own logins (the owner's subscriptions/keys in their own config). Score never reads,
  copies or passes credentials; the child environment is an allowlist plus the CLI's own config dirs implied by `HOME`.
- **Limits:** one turn per coding agent at a time (queue like Hermes turns), max wall time per turn (default 30 min),
  Stop = SIGINT, then SIGTERM after 5 s, then SIGKILL; output capped and redacted (D6) before storing.

## Events → Score
Each driver parses its CLI's JSON stream into Score's run model: text deltas, tool calls (name, args preview, result
status), file edits (path, +/−), usage and cost when the CLI reports it, final status. Unknown events are counted and
dropped, never stored raw. Watch frames come from the same parsed events (D6), so replay works.

## Product
- Team › Add agent gets a "Coding agent" choice (runtime, name, glyph/colour, workspace, permission, model).
- Rooms: coding agents can be members, are @mentionable, take hand-offs; plan-first and `/assign` treat them like any
  agent. Kanban tasks: v1 can't claim Hermes Kanban tasks (no Hermes worker), only room work.
- Reports: spend from the CLI's reported usage; marked "estimated" when the CLI reports tokens without cost.

## Security
These CLIs execute code. Default `workspace-write` in their own sandboxes; `full` needs the security password and
shows a warning. Score runs them as the same OS user (same accepted limit as D7.1). Prompt injection from room text is
the main risk: a coding agent only sees the turn input Score sends (room context + the message), never other agents'
secrets, and its output is shown, not executed by Score.
