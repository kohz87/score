# 7.7 Coding agents as orchestration and workflow workers (design v2, for re-review)

Owner 2026-10-11 asked for coding agents as orchestration workers. v1 was blocked by the adversarial review
(`docs/reviews/2026-10-11-7.7-design-review.md`, 12 P1 + 6 P2). Fix batch W (merged, migration 0054) already made
today's runtime truthful: process groups are tied to boot id + start time (`killRecordedGroup` → `gone | alive |
unobservable`), a record is deleted only with proof and in the same transaction as the terminal result, a run whose
group isn't proven gone ends with `terminal_source = 'unconfirmed'` (not evidence) and fences the agent, `stopRun`
returns `stopped | not_running | unconfirmed`, and the resume fallback can't run the CLI twice. v2 builds on that.
Numbers in [brackets] are the review findings each rule answers.

## Scope
Claude Code and Codex may take **worker** steps in orchestrations and workflows. The lead stays a Hermes agent.
**Antigravity is not a worker in this version** [17]: it advertises scheduling and subagents that outlive its process
group, so group termination can't prove its work ended. Full-access coding agents are never workers [5].

## 1. One port, one executor [16]
`start-server.ts` builds the composite port (`withCodingAgents`) exactly once and passes the same object to the
`Orchestrator` (which also runs workflow planning, transactionally) and to `buildApp`, which stops wrapping it again.
`assertHermesOnly` becomes `assertWorkerSupported(agent, role, frozenPolicy)`.

## 2. Frozen worker policy [5, 14, 17]
At run start (orchestration create / workflow start) Score snapshots, per allowed coding worker: runtime, CLI version,
permission level, resolved workspace, and its **effective reach** (a driver-computed description: readable roots, tool
list, deny rules, network). It is stored with the run and journaled with the admission. Before every launch (§4) the
current agent is compared with the snapshot: any change (level, workspace, CLI version, tools) blocks the step as
"agent changed" and uses the existing remap/re-approval flow; it never launches with the new settings. `full` is
refused at start and at launch. Readiness is typed (`ready | not_installed | version_untested | level_unverified |
changed`); preflight shows it per worker.

## 3. Consent [17]
The start dialog lists each coding worker with its frozen reach in plain words and the risk it means ("Codex can read
any file your user can, including keys, and could be asked to send them in a reply"), and asks for one acknowledgement
that **accepts the risk** (it doesn't claim confinement). The server requires `acknowledgeCodingReach: true` whenever
any worker's driver reports reach beyond its workspace; stored in the run history. 7.5's orchestration acknowledgement
stays as well. Driver fixes found by the review ship with 7.7: Claude Code deny rules also cover `Grep`/`Glob` (and any
read-capable tool), not only `Read`/`Edit`.

## 4. Launch: durable phase, release barrier, revocable authorisation [3, 6, 15]
- **Durable launch row before spawn.** In the executor's dispatch transaction (where `send_started` is journaled) a
  `coding_launches` row is written: run id, attempt id, owner (`orchestration` | `workflow`, planner kind), frozen
  policy hash, state `authorised`.
- **Launcher with a release barrier.** The CLI is started through a tiny Score launcher (`node launcher.mjs`, detached,
  its own group) that waits on an inherited pipe for one "go" byte before starting the CLI as its child. Score records
  the launcher's pid/pgid/boot/start time durably (W), **then** sends "go". If Score dies before "go", the pipe closes
  and the launcher exits without starting the CLI: a provable no-launch. The launch row records `released_at` in the
  same transaction as the process record. Missing `released_at` ⇒ never executed; present ⇒ executed (identity known).
- **Revocable authorisation.** A queued coding turn owned by an executor carries an `authorise()` callback. Immediately
  before writing "go" (same tick) the runtime calls it; the executor answers from its own state synchronously: the
  attempt is still `running` (not stopped, abandoned, cancelled), the run isn't stopping/paused/fenced, the run deadline
  hasn't passed, the worker policy still matches, the coding limits (§8) allow it. Any "no" ⇒ the launcher is told to
  exit, the launch row ends `revoked` (proof: never executed), and the attempt follows the no-dispatch path (§9).
  Stop therefore revokes a queued turn even before the executor's owed Stop is delivered.

## 5. Sessions [8, 9]
Executor-owned coding turns always start a **fresh CLI session** per attempt (new session id, never `--resume`), never
read or write Chat's (room, agent) session cache, and the W5 resume fallback is disabled for them. Retries, replacements
and remaps get new sessions. A workflow room released to Chat keeps Chat's own cache untouched.

## 6. Evidence [1, 2, 13]
- An executor-owned coding run is **evidence** only when the runtime records `terminal_source = 'runtime'`, which it
  does only when the group is proven gone (W) — never NULL. `isEvidence` for coding runs requires `'runtime'`.
- Disposition is separate from proof: `completed`/`failed` + proof ⇒ result accepted (failed ⇒ retry policy);
  `cancelled` + proof ⇒ execution obligations closed, no result, not auto-retried ("stopped, confirmed"); `unconfirmed`
  or no proof ⇒ attempt `unknown`, obligations kept, the agent fenced (W2) until the group is proven gone. A later proof
  for an `unconfirmed` run is recorded as **late evidence** (as today for abandoned attempts): it closes obligations but
  never makes the old result consumable.
- Restart: `CodingRuntime.recover()` for executor-owned launches: `released_at` missing ⇒ `failed` + `'runtime'`
  ("didn't start"), a proven no-launch; group `gone` ⇒ `failed` + `'runtime'` ("Score restarted while this ran") ⇒ a
  failed try under the retry policy; `alive`/`unobservable` ⇒ `unconfirmed` (fenced, retried in the background).

## 7. Stop [7]
The executor uses W's `StopOutcome`: it stamps `stop_acknowledged_at` only on `stopped`/`not_running`; `unconfirmed`
keeps the obligation and is retried with backoff. Delivery is asynchronous: one slow Stop never blocks the pump or
other Stops; shutdown waits on the tracked stop jobs with the existing barrier.

## 8. Spend and coding limits [11, 12]
- Unknown cost keeps today's rule: it **pauses** the run ("spend unknown") unless the person accepted unknown cost at
  start — now offered per coding runtime ("Accept unknown cost for Codex steps in this run"), journaled with the
  admission like the existing unknown-spend acceptance. Hermes uncertainty is accepted separately. No "quota, not money"
  claim. Claude Code's cost is recorded as `estimated` (as the code does), counted as provisional.
- **Coding limits**, set at start and journaled: `codingSteps` (default 10) and `codingMinutes` (default 60, summed
  worker wall time). At authorisation (§4) a launch **debits one step and reserves** `min(remaining minutes, per-turn
  cap)`; the turn's wall-clock limit is that reservation (not a fresh 30 minutes); at proof of end the reservation is
  settled to the measured time. Debits and reservations are rows keyed by launch id, so restart reconstructs them
  without double charging; an unconfirmed launch keeps its reservation. No per-step deadline is promised (7.1 removed
  it); the run deadline applies at authorisation and during execution.

## 9. No-launch refusals vs failures [14]
A launch revoked or refused before "go" (readiness changed, policy mismatch, CLI missing) is a **proven no-dispatch**:
it goes through 7.1's bounded refusal-generation machinery (reusable, journaled), not a logical retry. Only a released
launch can consume a try.

## 10. Results [10]
Drivers expose an authoritative `finalReply` only from the CLI's own final-result event (Claude Code: the `result`
event; Codex: the turn's final agent message on `turn.completed`; streamed commentary never counts). Its complete
sanitized text is recorded with `recordRunResult` (the workflow result limit, before any display truncation) in the same
transaction as the terminal proof. No authoritative final reply ⇒ the step fails ("no final answer"), and no verdict is
parsed. Files changed stay in the worker's workspace; the result may link them as `workspace://`.

## 11. Storage [18]
The coding translator charges executor-owned thinking/tool observations through `chargeObservation` at its writer and
drops ordinary observations when the run's allowance is exhausted, keeping Stop and obligation evidence.

## 12. UI
Coding workers show their CLI badge in diagrams, logs and the run's agent list; 5.39 status lines work as in Chat;
preflight shows typed readiness; the start dialogs add the reach acknowledgement, unknown-cost acceptance per runtime
and the coding limits; a blocked "agent changed" step offers remap.

## Out of scope
Coding agents as leads; Antigravity as a worker; approvals inside CLIs; moving files between workspaces.

## Done when
Tests with fake drivers and harmless child processes (the launcher included): dispatch → proven completion → result
accepted; Stop while queued (revoked, never executed), during launch, while running (`stopped`/`unconfirmed`);
restart before "go", after "go" with the group gone, with a survivor; policy change while queued blocks; `full`
refused; consent and unknown-cost acceptance required; coding limits debit/reserve/settle across a restart; final
reply missing ⇒ no verdict; storage charging; workflow with a coding step and a retry getting a fresh session.
`pnpm check`; e2e for the start dialogs and a coding step in an orchestration and a workflow.
