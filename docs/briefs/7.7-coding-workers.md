# 7.7 Coding agents as orchestration and workflow workers (design v1, for adversarial review)

Owner 2026-10-11: "if we reject coding-agent, that means we cannot use it for orchestration? wouldn't that weaken the
function by a lot?" Today (1.0.2) orchestrations and workflows refuse coding agents (`assertHermesOnly`,
`domain/orchestration/supported-agents.ts`, audit S2-009) because the executors hold the raw Hermes port. This task lets
Claude Code, Codex and Antigravity take **worker** steps. The orchestration lead stays a Hermes agent (it plans through
Score's orchestrator tools, which live in Hermes).

## What exists (facts from the code)
- Coding turns are `runs` rows (`runtime != 'hermes'`) written by `CodingRuntime` (`runtimes/coding/service.ts`); they end
  `completed | failed | cancelled | interrupted`, with `terminal_source` NULL. The orchestrator's evidence rule
  (`isEvidence`: completed/failed and not `recovered`) would therefore accept them unchanged.
- `withCodingAgents(port, coding)` (`runtimes/coding/port.ts`) routes `startRun`/`stopRun` by agent; only `buildApp`
  uses it. `Orchestrator` and the workflow executor are built in `start-server.ts` with the raw Hermes port.
- After 1.0.2 (batch R) a coding run is supervised as a **process group**: `done` settles only when the group is empty;
  Stop and the wall-clock limit reach descendants; the durable `coding_processes` row stays until the group is gone; on
  start, `recover()` kills every recorded group (pid + start time) and then marks open coding runs `interrupted`.
- Coding agents run one turn at a time per agent (a queue), resume a CLI session per (room, agent), report cost as
  `reported | estimated | unknown` (Codex: unknown; Antigravity: tokens without cost; Claude Code: reported).
- Permission levels: read-only, workspace-write, full (full needs the security password at creation). Codex can read
  every file the user can at every level; Claude Code has deny rules; Antigravity is sandboxed below full.

## Design
1. **One execution port.** `start-server.ts` builds the coding runtime before the executors and passes the same
   capability-aware port (`withCodingAgents`) to `Orchestrator` and the workflow executor. `assertHermesOnly` becomes
   `assertWorkerSupported(agent, role)`: the **lead** must be Hermes; a **worker** may be Hermes or coding, subject to 2.
2. **Who may be a worker.** Read-only and workspace-write coding agents only. **Full-access coding agents are refused as
   unattended workers** (`422 unsupported_agent`, "Full-access coding agents can't take steps without you; lower its
   level or use it in Chat") — an LLM lead writing instructions for an unsandboxed CLI is too much reach. A coding agent
   whose CLI is `not_installed`/`not_supported`/unverified for its level fails preflight like an offline Hermes agent.
3. **Explicit consent per run.** The start dialogs (orchestration and workflow) list each coding worker with its read
   reach in one line (same text as the Team note) and require one tick: "I understand Codex can read any file my user
   can while it works on these steps". The server requires `acknowledgeCodingReach: true` when any allowed worker is a
   coding agent whose driver `requiresReadAck(level)`; stored in the run's history.
4. **Dispatch.** Unchanged journal discipline: `send_started` is journaled before `port.startRun`. For a coding worker
   the request carries `owner: 'orchestration' | 'workflow'`, `turnId`, the rendered input and **a session key of
   (orchestration or workflow run, agent)** so one CLI session spans that run's steps for that agent (resume), never the
   agent's Chat rooms. No capability is minted for workers (leads only, as today).
5. **Queueing.** A coding agent busy in Chat makes the step wait in the coding queue; the attempt is `running` once
   admitted by the executor and the run row is `queued`. The run's wall-clock and the step's deadline both apply; Stop
   from the run removes a queued coding turn before it launches (batch R guarantees no spawn after stop).
6. **Evidence and restart.** A coding run that ends `completed`/`failed` is evidence (process group gone). On restart,
   `CodingRuntime.recover()` already proves each recorded group dead before marking `interrupted`; it will record that
   proof (`terminal_source = 'runtime'`, status `failed`, error "Score restarted while this ran"), so the attempt ends
   as a **failed try** (retry policy applies) instead of `unknown` with stop obligations. A run with no process row
   (never spawned) is `failed` with "didn't start" — also proof, nothing ran. `cancelled` by the user stays as today.
7. **Stop.** `port.stopRun` → `CodingRuntime.stopRun` → group stop; acknowledgement = group gone (stronger than Hermes'
   stop ack). Abandon ("stop waiting for") remains available but should rarely be needed.
8. **Results.** The step result is the CLI's final reply text (bounded like Hermes output, redacted). Files the agent
   changed stay in its workspace; the result mentions them as `workspace://` links when the driver reports them.
9. **Spend.** Coding CLIs mostly bill the owner's subscription quota, not per-token money. Policy: `reported` cost counts
   against the run's money budget as today; `estimated` counts as provisional; `unknown` **does not trip the
   "spend unknown" pause** for coding workers (it would on every Codex step) but is shown as "Codex: quota, not money" in
   the budget panel, and coding steps count against a new per-run **coding limit**: max coding steps (default 10) and
   max coding minutes (default 60), set in the start dialog. Hermes workers keep today's rule.
10. **Workflows.** The editor offers coding agents in the agent-step palette (marked with their CLI), the same
    consent/full-access rules apply at start, and the remap flow treats a coding agent like any other agent.
11. **UI.** Coding workers show their CLI badge in diagrams, logs and the run's agent list; status lines (5.39) work as
    in Chat; Watch links to the coding run's replay.

## Out of scope
- Coding agents as **leads**. Approvals inside coding CLIs (they run non-interactively by level). Moving files between
  agents' workspaces.

## Risks for the reviewer
- Prompt injection: a lead (LLM) composes instructions for a CLI that can read secrets (Codex). Mitigations: 2 and 3,
  output redaction, and results bounded. Is consent per run enough?
- Session key per (run, agent): could a resumed CLI session carry content between runs? (No: key includes the run.)
- Recovery change (6) alters `interrupted` → `failed` for coding runs started by executors only; Chat keeps
  `interrupted` with its "next message resumes it" note. Confirm the executors can't double-count a retried try.
- Spend policy (9): is excluding `unknown` from the pause safe with the coding limit as the guard?
- Concurrency: one CLI turn per agent; a workflow join waiting on two steps for the same coding agent serialises.

## Done when
Tests (fake coding runtime, harmless child processes, fake Hermes): dispatch to a coding worker and result accepted;
Stop before and during launch; restart with a live group → failed try, group gone, retried; full-access refused;
consent required; coding limit trips; workflow with a coding step; preflight shows CLI states. `pnpm check`, e2e for the
start dialogs and a coding step in a run.
