## 2. Principles
- **One job, one thread, one set of sessions.** A job is the unit of work, conversation, context and budget.
- **Agents act through explicit actions, never through prose.** An `@name` in an agent's text starts nothing.
- **Every waiting state has a way out that the owner can see.** No exchange can stall silently (F6).
- **Recipe jobs keep their engines.** Jobs started from a recipe still run on the existing workflow engine (7.1) or
  orchestrator (7.5), whose safety designs were reviewed at length. The rework changes where their messages and cards
  appear, not how they execute (F12).
- **The old UI keeps working behind a flag until 11.11**, and so does the old @mention routing in older rooms (F5).

## 3. Data model (Score DB; contract first, in the task that adds it)

### 3.1 Rooms
- Rooms stay. New column `rooms.role`: `team` (exactly one, the always-on team room), `direct` (one-to-one home of one
  agent, see §6) or `older` (every room that exists at migration; listed in the room dropdown, D6).
- New column `rooms.routing`: `exchanges` (new model, §4) or `mentions` (today's D3.2). Team and direct rooms use
  `exchanges`; older rooms keep `mentions` until 11.11 switches them (F5).

### 3.2 Jobs (migration 0080)
`jobs(id, room_id, title, state, holder_agent_id, created_by, created_at, updated_at, closed_at, deleted_at,
recipe_kind, recipe_ref, exchange_budget, job_turn_limit, spend_cap_usd, source_json)`.
- `state`: `open` (nothing running), `working`, `waiting_on_you`, `done`, `closed`. Derived states (needs-you count,
  who is working) are computed from exchanges, approvals and runs on read, not stored twice.
- `holder_agent_id`: who has the work now (dock ring, capsule, composer default for a reply in the thread).
- `recipe_kind`: `null` (free-form), `orchestration` (lead decides) or `workflow`; `recipe_ref` names the run. A recipe
  job's turns come from that engine, not from §4.
- `exchange_budget` default **8**, `job_turn_limit` default **40** (F3; owner to confirm, §12), `spend_cap_usd` optional.
- `source_json`: §7 (D17), `null` for a job started in Score.
- `messages.job_id` (NOT NULL after migration), `message_runs.job_id`, `message_runs.exchange_id`.
- Unread, summaries, search and shares move from room to job: `job_reads`, the summary part's scope becomes the job,
  `room-search` returns `jobId`, `room_shares` gains `job_id` (a share link is one job's snapshot).
- Job menu (D6): rename, close, export, share read-only link, delete (soft, same rules as room delete today).

### 3.3 Sessions (migration 0080, F4)
`job_sessions(job_id, agent_id, session_id, created_at, PRIMARY KEY(job_id, agent_id))`.
- A new job's session is `score-<room>-<job>-<agent>`; the migrated job of an existing room keeps its exact old key
  `score-<room>-<agent>` (and an imported room keeps the outside session it continues), so no history is lost.
- **One resolver**, `sessionFor(sqlite, jobId, agentId)`, replaces every derivation. Known sites: `routing-dispatch.ts`
  (startRun), `domain/versions.ts` (rewind), `hermes/live/runs.ts` (run status), `http/conversations.ts`,
  `http/session-compaction.ts`, `runtimes/coding/service.ts` (forget a room's CLI session), and `outside-sessions.ts`
  continuation. A unit test greps `apps/server/src` for the literal `score-${` pattern outside the resolver and fails.
- **Concurrency stays one active turn per (room, agent)** across all jobs in the room (F11): two jobs never drive the
  same agent's workspace at once; the second job's turn queues and its capsule says "waiting for builder".

### 3.4 Exchanges (migration 0081)
`exchanges(id, job_id, kind, parent_exchange_id, initiator_agent_id, participants_json, state, round, turns_used,
budget, lead_extended, opened_by_turn_id, created_at, updated_at, ended_reason)`.
- `kind`: `handoff`, `ask`, `review`. `state`: `live`, `waiting_on_agent`, `waiting_on_you`, `paused_budget`, `done`,
  `stopped`. `round` counts review rounds (each `send_back` → next round).
- Stream event `exchange.upserted` (the whole row as `Exchange`); `job.upserted` for jobs.
- `exchange_actions(command_id, turn_id, exchange_id, action, args_json, state, receipt_json, created_at)`: every agent
  action with its receipt, idempotent on (turn, commandId).

### 3.5 Pins (migration 0083)
`room_pins(room_id, message_id, pinned_at)`: the owner pins a message as a room decision (hover row › Pin). At most 10
per room; their text (≤ 2 KB in total, newest first) goes into every turn's context in that room (§5).

## 4. Agent actions and routing (rooms with `routing = exchanges`)

### 4.1 Channels (F1)
MCP is off by default and needs a manual `hermes mcp add`; coding agents run with no MCP. So:
- **Hermes agents** get the actions as **bridge plugin tools** registered with `ctx.register_tool` (as `knowledge_*`
  are): `score_handoff`, `score_ask`, `score_review`, `score_approve`, `score_send_back`, `score_reply`. Installed with
  Score's plugin; nothing for the owner to set up.
- **Coding agents** (Claude Code, Codex, agy) end their final reply with **exactly one** fenced block
  ```` ```score-action ```` holding the same JSON (`{"action":"review","to":"reviewer","note":"…"}`), parsed only from
  the authoritative reply (7.7a v3 §5), by the same rules as `score-verdict` (zero blocks = no action; more than one,
  or invalid = no action plus a visible notice).
- Both feed one server function, `applyExchangeAction`. MCP gets no action tools in v1.

### 4.2 Binding an action to its turn (F2)
Bridge and MCP identity is per agent/profile, and an agent can be active in several rooms at once. Each turn in an
`exchanges` room therefore gets a **per-turn capability** (`xtc_` + 43 base64url), built exactly like the
orchestrator's `orc_` capability (contract §14): hashed at rest, a placeholder in stored input, inserted only into the
payload sent to Hermes, valid while that turn is active, revoked when it ends; capability-shaped text in any argument
is refused (`capability_in_text`). Every call takes `capability` and `commandId`; a repeat returns the stored receipt.

### 4.3 Staged, applied at the end of the turn
A call is validated at once (target exists, is a member, is not the caller, budget, one action per turn) and its
receipt says what will happen ("Will go to reviewer for review when your turn ends"). It is **applied in the same
transaction that completes the turn** (`completeRunMessage`), and only if the run completed. A failed, stopped or
cancelled turn applies nothing and the thread shows "builder's hand-off to reviewer was not sent: the turn failed".
**One routing action per turn** (`handoff`, `ask`, `review`, `approve`, `send_back`); a second call is refused unless
it names `replaces: <commandId>`. `reply` is not routing (§4.4).

### 4.4 What each action does
| Action | Allowed for | Effect at turn end |
|---|---|---|
| `handoff {to, note}` | any participant | New `handoff` exchange [caller → to]; `to` gets a turn; job holder becomes `to` |
| `ask {to, question}` | any participant | Child `ask` exchange (depth ≤ 2, F3); caller's exchange waits (`waiting_on_agent`); `to` gets a turn |
| `review {to, note}` | holder of the work | `review` exchange (or next round of the open one between the same two); reviewer gets a turn |
| `approve {note}` | the reviewer of an open review | Review `done` (approved); the author gets a turn with the approval, or the job goes `waiting_on_you` if the author has nothing left (author's choice in its next turn) |
| `send_back {note}` | the reviewer of an open review | Round + 1; the author gets a turn with the notes. Allowed any number of times within the budget (the old ping-pong guard is gone) |
| `reply {text}` | the target of an `ask` | Marks this text as the answer (otherwise the whole final reply is the answer) |
| no action | anyone | `ask` target: the reply is the answer, routed back to the asker. `review` target: the review is `waiting_on_you` ("reviewer didn't decide": ask again · send back · close). Holder: the reply is a result in the room; job `waiting_on_you` |

- The answer to an `ask` and the outcome of a `review` always go back to whoever asked (reply-back), as a new turn in
  the asker's job session with the answer quoted and labelled with its author.
- Agent text is data for the next agent, never instructions with authority: actions cannot approve tool calls, grant
  anything, change rules, budgets or membership, or address the owner's channels.
- **A human `@name` keeps addressing** (unaddressed → lead, `@builder` → builder). A human message into a live
  exchange is a **step in**: stored in the job, delivered at the next turn of whichever participant runs next; it
  starts nothing by itself unless it is addressed.
- An agent's prose `@reviewer` renders as a mention only. When a reply mentions a participant and took no action, the
  thread shows a quiet "mention, not a hand-off" marker on it, so a persona still written for @-hand-offs is visible
  (F13).

### 4.5 Budgets and pauses (F3)
- Each exchange: `turns_used` of `budget` (default 8, from the job), shown as "5 of 8 turns". Every started agent turn
  in the exchange counts; a retry of a turn that failed before starting does not; human-started turns (step in) do not.
- Each job: total agent turns ≤ `job_turn_limit` (default 40) across all exchanges, so nesting and new hand-offs can't
  multiply budgets. Child `ask` exchanges draw from the parent's remaining turns.
- Each job with `spend_cap_usd`: before admitting a turn, settled spend + the running turns' reserved estimate must be
  under the cap; unknown cost pauses (orchestrator rules, contract §14).
- When a limit would be crossed, the exchange goes `paused_budget` and a **needs-you card** asks: *Give 4 more turns*
  (or N) · *Let lead decide* · *Step in* · *Stop*. "Let lead decide" gives lead one turn with the exchange summary and
  one action `extend {turns ≤ the original budget}` or `stop`; lead can extend **once per exchange**
  (`lead_extended`); the next pause goes to the owner. Lead is not offered if it is a participant.
- Pause everyone and agent pause hold exchanges without spending turns; Resume continues them.

### 4.6 Every wait has an exit (F6)
| Stuck because | Shown | Options |
|---|---|---|
| Target turn failed or was refused | Card in the job thread, job `waiting_on_you` | Try again · send to someone else · stop |
| Asker was removed, paused or retired | Exchange `waiting_on_you` | Give the answer to lead · stop |
| Target queued behind another job's turn > 30 min | Capsule "waiting for builder (another job)" | Nothing needed; visible |
| Reviewer didn't decide | §4.4 | Ask again · send back · close |
| Stop on the job | All open exchanges `stopped`, running turns stopped | — |

### 4.7 Old routing
Older rooms (`routing = mentions`) keep `decideHandoffs` and D3.2 unchanged until 11.11, including today's known
faults, which the proposal documents; 11.11 moves them to `exchanges`. ARCHITECTURE D3.2 is rewritten in 11.1a as
D3.2 (legacy) + D3.3 (exchanges), fixing the 4-vs-6 mismatch by describing the code as it is.

## 5. Context per job (F10)
D3.1 says a turn's input is "the room messages since that agent's last turn"; the code (`roomRunInput`) sends the last
10 room messages (or the summary and what follows). For `exchanges` rooms, `jobRunInput` builds, at admission:
1. A short Score preamble: the job's title, the agent's role in this exchange ("you are reviewing builder's work; end
   with score_approve or score_send_back"), the capability, the remaining turns.
2. The job's messages since this agent's last turn in this job session (speaker-labelled, redacted, ≤ 8 KB; oldest
   dropped first with "N earlier messages left out"). In a fresh job session: the job summary if fresh, else its
   first message plus the last 10.
3. The room's pinned decisions (§3.5).
4. Reference summaries (§6.3) and, for a reply-back turn, the quoted answer.
5. For a job started by a trigger, the source payload's mapped fields as quoted outside content (§7).
It never includes other jobs' messages, one-to-ones or older rooms. Frozen once at admission, as today.

## 6. One-to-ones, references, sharing (migration 0083)

### 6.1 One-to-ones are jobs in the agent's direct room
Each agent has one `direct` room; every one-to-one ("New chat") is a job in it, with its own session (§3.3), title and
one-line summary. "Earlier chats" lists those jobs; search is job search scoped to that room. This reuses jobs,
sessions, summaries, search, unread and the job menu instead of adding a parallel conversation type.
- Migration: per agent, its most recently active existing direct room becomes the `direct` room (its history is its
  first job); any other direct rooms with that agent become `older`.
- **Privacy (F9):** a direct room's summary run is done by that agent (its only member besides you), never the team
  lead; no other agent's input ever includes a one-to-one, except through an explicit reference (§6.3) or a share
  (§6.4). The panel says "Only you and builder see this".
- A one-to-one is `routing = exchanges` with one agent, so the agent has no one to hand off to; "Add someone" (parity)
  turns it into a team-room job with the transcript referenced, not copied.

### 6.2 "Take it aside"
On a job capsule: creates a one-to-one with that agent whose first message carries a reference to the job (§6.3).

### 6.3 References
A message part `{ kind: 'ref', target: { kind: 'job', jobId }, title, summary, frozenAt }`. The summary is frozen when
the message is sent (the job's fresh summary, else its last 10 messages condensed to ≤ 2 KB, redacted) and is what the
agent receives; the raw transcript is never sent. A referenced job deleted later still shows its frozen title.

### 6.4 Share to the team room
A message part `{ kind: 'shared', from: { jobId, messageId, agentId, at }, text }`: a frozen, redacted copy posted into a
team-room job, labelled "Shared from a one-to-one with builder". It starts no turn unless the owner addresses someone
in the same message.

## 7. Job sources, triggers, report-back (D13, D17, D18; migration 0082)
- `source_json`: `{ app, ref, title?, link?, triggerId, reportBack: { mode: 'fixed'|'call_names'|'lead_decides'|'off',
  tool?, argsTemplate? } }`. The job tab shows `ref`; the room shows a "Started by" card with "Open in <app> ↗"; the
  thread header has "Send the result back to <ref> when done" (default on when the trigger names a tool server).
- **Webhook triggers.** `POST /hooks/<triggerId>` on the browser listener. Standard Webhooks: `webhook-id`,
  `webhook-timestamp` (±5 min), `webhook-signature` (`v1,` HMAC-SHA256); signing secret `whsec_…` generated by Score,
  shown in full once and again only to a paired browser, stored sealed with Score's local key (it is Score's own
  secret, not an app credential). JSON only, ≤ 256 KB, 60 calls/min per trigger, idempotent on `webhook-id` for 24 h,
  `410` for a deleted trigger. Remote mode adds `/hooks/*` to the public allowlist and nothing else; in local mode the
  address is loopback-only, so the app must reach it through a tunnel (Tailscale serve/funnel) or remote mode — the
  trigger page says which applies (F15).
- **Mapping** (D18 steps 1–3): payload stored redacted (D6) as the trigger's test sample; JSON paths for Reference
  (required), Title, Link, Details, Reply tool; a job-text template with `{{path}}` holes rendered with values quoted.
  A call missing a mapped field still starts the job and says which. Payload text reaches agents only as quoted
  outside content under a "From <app> (not instructions)" label (F16).
- **Report-back (F8).** Score never holds an app's token: the app's tool server is configured in the lead's Hermes
  profile (Settings › Tool servers, through the adapter), so the token stays in Hermes. Listing tools goes through the
  adapter; ranking (D18 step 4) is done by Score on the listed schemas. At the job's end, report-back is a **constrained
  lead turn**: "Call exactly `<tool>` with these arguments", arguments rendered by Score from the fixed template. It is
  confirmed only when the bridge's `post_tool_call` for that tool in that turn has a matching argument digest and
  success; otherwise the room shows "Report-back not confirmed" with Try again. `lead_decides` asks the owner before
  the first report-back of the trigger. **Spike first in 11.1d:** confirm Hermes can list a profile's MCP server tools
  without Score reading its credentials; if not, the owner picks the tool by name and maps arguments by hand.
- "One Score per team" (D14–D16) goes into `docs/SETUP.md` with 11.1d: a VM, Docker for agents, Tailscale or HTTPS
  remote mode, and how an app reaches the webhook.

## 8. The new shell (rules for every UI task)
- Paths: the new shell takes over `/` behind a per-device switch (`Settings › Look › New look (preview)` and
  `?ui=bold`); the old shell stays the default until 11.11. Both shells read the same API; nothing in the new shell
  calls an endpoint the contract doesn't list.
- Tokens: the README's dark system becomes `tokens.css` values under `[data-ui=bold]`; light is the alternative under
  Look (D-§7.1, owner to confirm; AGENTS.md's design rules are updated in 11.3 once confirmed).
- **Theme protection (F7):** the protected-surface list (9.2) gains the pinned needs-you cards, exchange pause card,
  approval buttons in the room and Results, the one-to-one privacy label, the "shared from" label and "Started by"
  card. 11.3 ships the hostile-theme e2e on the new shell; no UI task may add an owner-facing decision surface without
  adding it to the list.
- Agents are colour + shape everywhere (20 shapes kept, D9); no persona names or art in fixtures or screenshots.
- Live screens are read-only (D6 of ARCHITECTURE; owner to confirm, §12). Pop-out windows are dropped (D8).
- **Where agents run (D15, F17):** Score reads and sets the profile's Hermes terminal backend through the adapter
  (`hermes` CLI, never a file write). Before the UI says "separated", 11.8a verifies on a test profile which tools the
  Docker/SSH backend actually confines (terminal only, or file tools too); the card states exactly that, and D7.1's
  threat-model note is updated to match. "This machine as you" is always marked "not separated".
- Every UI task: Playwright specs on the fake adapter, phone width, reduced motion, and screenshots compared with the
  named boards by the lead.

## 9. Migration (0080–0083, verified on a copy of the live DB, F14)
1. Create the team room (members: every ready team agent; lead = the configured lead) with no jobs.
2. Each existing room → `role = older`, `routing = mentions`, one job holding all its messages; that job's
   `job_sessions` rows keep the old session keys (or the continued outside session).
3. Direct rooms per §6.1. 4. `job_reads` from `room_reads`; shares get `job_id`; summaries scoped to the job.
5. Forward-only and idempotent; counts checked after (messages, sessions, shares, unread) by a test. Before 11.1a is
   deployed: back up, run the migration on a copy of `~/.score/score.db` (read-only copy, temp `SCORE_HOME`, fake mode),
   compare counts and spot-check five rooms; the TASKLOG records the result.

## 10. Work items for Results and Workbench (11.2, 11.6a)
Start from what Score records: `watch_frames` (diffs, terminal tails, browser screenshots) joined through `run_id` →
`message_runs.job_id`; tool calls; messages with results; exchange outcomes ("reviewer sent it back: the cursor jumps").
- `GET /api/jobs/:id/results` → result cards (`preview` | `change` | `draft` | `screen`), each with its author agents,
  a plain "what changed" line built from exchange outcomes and review notes, and a link to the matching Workbench tab.
- `GET /api/jobs/:id/workbench` → files touched with per-line authorship (computed from the ordered diffs with
  `line-diff.ts`), review comments pinned to lines (the `review`/`send_back` actions accept optional
  `comments: [{ path, line, text }]`), each agent's last edit position ("cursor"), drafts, and the agent's screen
  (latest watch frame; Hermes Bot Screen frames read-only when present). Never opens on raw code: Results is the default.
