# 7.7b Coding agents as orchestration workers (design v1, for adversarial review)

Stage 2 of PLAN 7.7 (decision 65). Stage 1 (7.7a, v1.1.0) made every coding turn a supervised systemd unit with a
journaled launch, a release barrier, receipts and an eligibility verdict. This stage lets the orchestration executor
give **worker** steps to Claude Code and Codex agents. Workflows are stage 3 (7.7c). The overall design
`docs/briefs/7.7-coding-workers.md` (v2) is the source for the rules below; where 7.7a already provides a mechanism,
this design uses it instead of v2's (v2 §4's launcher is now 7.7a's unit, journal and release CAS).

## 0. What exists and is relied on
- **7.7a:** `CodingRuntime.startRun({agentId, input, turnId, sessionId?, model?})`; one launch per turn, journaled
  `requested → armed → releasing → released-seen → ended → settled`; `release(launchId, stillAuthorised)` decides
  release vs revoke as one CAS inside `journal.critical`; permanent tombstones; `turnWitnessed(turnId)` refuses a turn
  that may already have run; receipts outside the home; the verdict (`eligible` + the **eligible reply**, per the
  acceptance matrix); a finished result is held and redelivered until saved; the freeze (decisions 71–74).
- **Executor (W, X, 7.1):** `beginSend` journals `send_started` per attempt generation before the port is called;
  `startRun(..., owner: 'orchestration')`; `send_refused` makes a generation re-sendable; `StopOutcome`
  (`stopped | not_running | unconfirmed`) with the obligation kept on `unconfirmed`; `isEvidence(run)` excludes
  `recovered` and `unconfirmed`; late evidence never makes a result consumable; `assertHermesOnly` at create/plan.

## 1. Scope
- Workers: **Claude Code and Codex**, permission `read-only` or `workspace-write`. **Never `full`** (refused at create,
  plan and release). The lead stays a Hermes agent. Coding agents can't be leads.
- **Antigravity is not a worker** in this stage: it advertises scheduling and subagents that may outlive its run
  (v2 §Scope, review finding 17); whether the unit's cgroup contains all of that is not verified. Revisit separately.
- **Only on unit hosts.** A worker step needs the unit engine usable (`backend().kind === 'unit'`, no pause, no
  freeze). A host on the process-group engine refuses coding workers at create (`422 coding_workers_need_units`) —
  decision 69 keeps that engine only for Chat on hosts that never passed the unit check.
- Out of scope: workflows (7.7c), approvals inside CLIs, moving files between workspaces.

## 2. One port
`start-server.ts` builds the composite port (`withCodingAgents`) once and passes the same object to the executor and to
`buildApp` (which stops wrapping it). `assertHermesOnly` becomes `assertWorkerSupported(ids, team, role)`: Hermes
agents anywhere; coding agents only as workers, only Claude Code/Codex, only on unit hosts, never `full`.

## 3. Frozen worker policy (v2 §2)
At create, Score snapshots per allowed coding worker: runtime, CLI version, permission, resolved workspace (realpath,
identity) and the driver's **effective reach** (readable roots, tool list, deny rules, network). Stored with the
orchestration and journaled with the admission. At **release** (§5) the current agent is compared with the snapshot;
any change blocks the step as "agent changed" (existing remap/re-approval flow). Preflight shows typed readiness:
`ready | not_installed | version_untested | level_unverified | changed | paused | frozen | needs_units`.

## 4. Consent (v2 §3)
The start dialog lists each coding worker with its frozen reach in plain words and the risk ("Codex can read any file
your user can, including keys, and could be asked to put them in a reply") and asks for one acknowledgement that
**accepts** the risk. The server requires `acknowledgeCodingReach: true` when any worker's reach goes beyond its
workspace; stored in the run history. 7.5's orchestration acknowledgement stays.

## 5. Launch: the executor authorises the release
- `startRun` gains `owner: { kind: 'orchestration'; attemptId; generation; authorise(): AuthoriseAnswer }` and
  `maxTurnMs`. The turn id stays the attempt's `turn_id` (one per generation), so `turnWitnessed` and the launch
  tombstones apply unchanged.
- Order: executor `beginSend` journals `send_started` (generation g) → `startRun` → 7.7a journals `requested`, arms the
  unit → at the release CAS 7.7a calls `stillAuthorised = () => owner.authorise().ok`.
- `authorise()` is **synchronous and transaction-aware** (it runs inside `journal.critical`, and callers may already
  hold a DB transaction — the bug class found in the 7.7a verification): it reads, on the current handle, that the
  attempt is still `send_started`/`running` with generation g, the orchestration isn't stopping/paused/fenced/frozen,
  the run deadline hasn't passed, the policy snapshot matches (§3), and the coding limits allow it (§9). Lock order:
  journal critical section, then the DB read; `authorise()` never writes and never awaits.
- **Revoked** (any "no") ⇒ 7.7a's revoke tombstone (proof: never executed) ⇒ the executor records `send_refused` for
  generation g with the reason, and the attempt follows 7.1's bounded refusal machinery (§10). A Stop while the turn
  is queued therefore never executes it, even before the owed Stop is delivered.

## 6. Sessions (v2 §5)
Executor-owned turns start a **fresh CLI session** per attempt (never `--resume`, never Chat's (room, agent) session
cache), and 7.7a's resume-retry is disabled for them. Retries, replacements and remaps get new sessions.

## 7. Evidence and results
- A coding run is **evidence** only when 7.7a's verdict is final with proof of end (unit gone, receipts complete):
  `runs.terminal_source = 'runtime'`. Otherwise `'unconfirmed'` (attempt `unknown`, obligations kept).
- Mapping from 7.7a's outcome: eligible success ⇒ `completed` with the **eligible reply** as the result; proven failure
  ⇒ `failed` (a try under the retry policy); proven stop (person/deadline/limit) ⇒ `cancelled`, obligations closed, no
  result, not auto-retried; anything unproven ⇒ `unconfirmed`.
- The result is the **complete** eligible reply, recorded with `recordRunResult` (the workflow result limit, before any
  display cut) in the same transaction as the terminal state. No eligible reply ⇒ `failed` ("no final answer") and no
  verdict is parsed. Files changed stay in the worker's workspace; the result may link them as `workspace://`.
- A result held by 7.7a for redelivery is delivered once; the executor's reconciliation is idempotent on run id.

## 8. Stop
The executor's existing owed-Stop service applies: `stop_acknowledged_at` only on `stopped`/`not_running`;
`unconfirmed` keeps the obligation, retried with backoff; delivery is asynchronous (one slow Stop never blocks the pump).
While frozen the executor sends no Stops (FV); the coding runtime's own deadline and caps still stop runs it started
(decision 74).

## 9. Spend and coding limits (v2 §8)
- Unknown cost pauses the run ("spend unknown") unless the person accepted unknown cost **per coding runtime** at start
  ("Accept unknown cost for Codex steps in this run"), journaled with the admission. Claude Code's cost is `estimated`,
  counted as provisional.
- **Coding limits** set at start and journaled: `codingSteps` (default 10) and `codingMinutes` (default 60, summed
  wall time). At authorisation a launch **debits one step and reserves** `min(remaining minutes, 30)`; the turn's
  `maxTurnMs` is that reservation; at the verdict the reservation settles to the measured time. Debits and reservations
  are rows keyed by launch id (restart reconstructs them without double charging); an unconfirmed launch keeps its
  reservation. The debit is written in the executor's DB transaction **before** `startRun`; `authorise()` only checks.

## 10. Refusals vs failures (v2 §9)
Before release: `coding_paused`, `cli_not_installed`/`untested_version`, policy mismatch, frozen, revoked ⇒ a **proven
no-dispatch** (`send_refused`), through 7.1's bounded refusal-generation machinery. `turn_witnessed` is **not** a
refusal: the turn may have run ⇒ attempt `unknown`. Only a released launch consumes a try.

## 11. Restart
- Never released (journal shows no `releasing`) ⇒ proven no-dispatch for that generation.
- Released, verdict known and held ⇒ delivered as §7.
- Released, end not proven ⇒ `unconfirmed`, the agent fenced as in Chat, retried in the background by 7.7a.
- Frozen states (copy, lost journal) ⇒ nothing is dispatched or stopped until `reset-history` (decisions 71–74).

## 12. Storage (v2 §11)
The coding translator charges executor-owned thinking/tool observations through `chargeObservation` and drops ordinary
observations once the run's allowance is exhausted, keeping Stop and obligation evidence.

## 13. UI
Coding workers show their CLI badge in the Flow diagram, logs and the run's agent list; live status lines work as in
Chat; preflight shows typed readiness; the start dialog adds the reach acknowledgement, unknown-cost acceptance per
runtime and the coding limits; a blocked "agent changed" step offers remap.

## Contract changes
`POST /api/orchestrations` (and preflight) gain `acknowledgeCodingReach?`, `acceptUnknownCost?: RuntimeId[]`,
`codingLimits?: { steps; minutes }`; preflight returns per-worker readiness; new error codes `coding_workers_need_units`,
`acknowledgement_required` (reach). Contract doc first, then `packages/contract`, then both sides.

## Done when
Tests with fake drivers on the fake unit backend, plus the opt-in real-systemd suite with a harmless fake CLI:
- dispatch → release → eligible completion → result accepted (complete reply, no display cut);
- Stop while queued (revoked, never executed, `send_refused`), while releasing, while running (`stopped`/`unconfirmed`);
- restart before release, after release with the verdict held, with the end unproven;
- policy change while queued blocks at release; `full` refused; Antigravity refused; process-group host refused;
- consent and per-runtime unknown-cost acceptance required; coding limits debit/reserve/settle across a restart;
- no eligible reply ⇒ "no final answer", no verdict; `turn_witnessed` ⇒ `unknown`, not a refusal;
- `authorise()` called inside a caller's DB transaction works (no nested transaction);
- storage charging; a retry gets a fresh session.
