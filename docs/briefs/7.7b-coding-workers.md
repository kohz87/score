# 7.7b Coding agents as orchestration workers (design v6, accepted for building)

Stage 2 of PLAN 7.7 (decision 65). Stage 1 (7.7a, v1.1.0) made every coding turn on a unit-capable host a supervised systemd unit (process-group hosts
keep the 1.0.3 engine, without units or launch rows) [M9] with a
journaled launch, a release barrier, receipts and an eligibility verdict. This stage lets the orchestration executor
give **worker** steps to Claude Code and Codex agents. Workflows are stage 3 (7.7c).

## 0. What exists (corrected) [R 18, 7, 8]
- **7.7a:** `CodingRuntime.startRun({agentId, input, turnId, sessionId?, model?})`; the launch id is minted inside the
  unit backend; the journal folds `requested → armed → releasing → released-seen → ended → settled` with permanent
  tombstones and a folded `mayHaveExecuted`; `release(launchId, stillAuthorised)` returns `not_authorised` **without**
  writing a revoke (the revoke is a separate step); `turnWitnessed(turnId)` checks projected `unsendable = 1` launch
  rows: requested/armed launches return false, revoked ones true [N13]. Chat's qualified resume fallback may launch **twice** per turn. A success still pending
  at restart is downgraded to `interrupted`: its eligible reply is cleared, its pending output is kept for display
  (enforced by a test) [M9].
- **Orchestration states:** attempts are `created | send_started | running | terminated | unknown | refused |
  abandoned`; steps are `pending_gate | queued | admitted | succeeded | failed | unknown | cancelled | blocked |
  rejected | not_started` with a `disposition`. The journal's dispatch fold knows `send_started` (sent) and
  `send_refused` (re-sendable) per generation.
- **Executor:** one `turn_id` per **logical attempt** (not per generation); `beginSend` journals `send_started` for
  generation g; `recordRefusal` keeps the old run/turn linkage and counts consecutive/lifetime refusals; `isEvidence`
  requires a `completed`/`failed` run and excludes `recovered`/`unconfirmed` [M9]; evidence on an `unknown` attempt is consumed normally (only `abandoned`
  attempts get the non-consumable late-result path); owed Stops are delivered sequentially inside the pump, and a
  Hermes `void` counts as acknowledged; while frozen no Stop is sent at all; `recordRunResult` serves workflows only;
  orchestration results are the 8 KiB run output, falling back to message text and with failure errors appended
  [N13]; `assertHermesOnly` guards orchestrations **and** workflows. A run's runtime is in its launch row (`runs.origin`
  is `score` for every Score-started run) [N13].

## 1. Scope [R 16]
- Workers: **Claude Code and Codex**, permission `read-only` or `workspace-write`; never `full`. Lead stays Hermes.
- **Antigravity is not a worker** (v2 finding 17: scheduling and subagents that may outlive its run; not shown to be
  contained by the unit). Revisit separately.
- **Only on unit hosts** (`backend().kind === 'unit'`, not paused). Process-group hosts refuse coding workers at
  create (`422 coding_workers_need_units`).
- **Orchestrations only.** Workflows keep `assertHermesOnly` and its tests until 7.7c; the new guard
  `assertOrchestrationWorkers(ids, team)` is used only by orchestration create/plan/remap.

## 2. One port, routing by run [R 15, M1]
`start-server.ts` builds the composite port once and passes the same object to the executor and `buildApp`. Controls
(Stop, result reads) for a run route by the run's durable **`runs.runtime`** — the column **already exists** (migration
0047) and coding admission already writes it before queueing; the new work is routing controls through it [A3]; a coding run's launch row is only a recovery fallback when the run row is missing. Absence of a
launch row never means Hermes (a queued Chat turn, a process-group run). **Coding Stop with no run row [K4]:** the
coding runtime resolves launch evidence before answering; a recoverable, unproven launch is stopped through its
qualified launch identity and the answer is `unconfirmed` until no-execution or end proof exists — never `not_running`
just because the run row is missing. A coding agent **can't be removed** while any
of its runs is unresolved (launch not `settled`, `unconfirmed`, held group, or queued) — `409 agent_busy`.

## 3. Owned invocation: built from the frozen policy [R 2, 11, N3]
- At **preflight** Score computes, per allowed coding worker, a **worker policy**:
  - runtime; CLI executable identity (realpath, dev/ino, size, mtime, reported version); permission; workspace identity
    (realpath, dev/ino); the reach in plain words;
  - the **owned invocation**: the full argv minus the prompt, and the **environment**: the allow-list names and a hash
    of their values. The values are never stored in policy snapshots, the journal, run history or the UI (proxies may
    carry credentials); the only copy is 7.7a's private transient `spec.json` for the supervisor, with today's
    credential filtering [K5];
  - the **settings bytes** Score writes for the CLI (Claude Code's `--settings` file): Score generates them from the
    policy, so the bytes are known and hashed;
  - the **configuration sources** the CLI may still read, bound by **file identity only** (dev/ino, size, mtime, or
    "absent"), never by reading them: Claude Code user/project/local settings, managed settings, `CLAUDE.md` files in
    the workspace chain; Codex `$CODEX_HOME/config.toml` and profiles, project `.codex/`, managed config, `AGENTS.md`
    in the workspace chain. Credential files are never touched.
  Its canonical JSON hash is the **policy id**. Preflight returns `{ policyId, reach }` per worker.
- **Neutralised where the CLI allows it** (Claude Code: `--setting-sources` limited to Score's settings,
  `--strict-mcp-config` with no `--mcp-config`; Codex: `-c` overrides for sandbox, approval policy, MCP servers, shell
  environment policy, hooks/notify). Whatever stays readable is bound by identity above, so any change shows as "agent
  changed". A driver declares, per pinned CLI version, which sources it neutralises and which it binds; a source it can
  neither neutralise nor bind ⇒ `reach_unverifiable` ⇒ not ready. The builder verifies the list on the installed CLIs
  (help output and recorded fixtures; no prompts).
- `POST /api/orchestrations` must carry the `policyId` the person saw for each coding worker (`409 policy_changed`
  otherwise); stored with the orchestration and journaled with the admission.
- **Prepared, then authorised [M3].** Before arming, the runtime builds the supervisor spec (argv, environment,
  settings bytes, workspace, **expiry**) **from the stored policy** (never from the live agent row), re-reads every
  bound identity, and computes the spec's policy id; the spec is authenticated to the supervisor as today. At release
  `authorise()` checks the **prepared** spec: its policy id equals the stored one, and its prepared expiry is
  `≤ deadlineAt` as it stands now. **Inside the release critical section, immediately before `releasing`, it re-reads
  every external identity again** — executable, workspace, every bound configuration source, and the settings file
  Score wrote (its bytes must still hash to the prepared value; the file is Score's, mode 0600, in Score's own
  folder) [K1]. A mismatch (agent changed, deadline moved earlier, a file changed while the unit started) revokes the
  launch with a typed cause (§6) and the next generation prepares a new spec; nothing is updated in place. "Agent changed" ⇒ remap/re-approval with a **new
  policy id and new reach consent** (§12a).

## 4. Consent [v2 §3, R 11]
The start dialog lists each coding worker's reach in plain words and the risk, and asks for one acknowledgement that
accepts it; the server requires `acknowledgeCodingReach: { policyIds: [...] }` covering every worker whose reach goes
beyond its workspace. Stored in the run history. 7.5's acknowledgement stays. A remap or re-approval to a new policy id
needs its own acknowledgement of the new reach; an old acknowledgement never carries over [N10].

## 5. Identities per generation [R 3, N2]
- Each dispatch generation g of an attempt has its own **coding turn id** `"<attempt turn_id>:g<g>"` and **launch id**,
  minted by the executor in `beginSend`'s transaction and journaled with `send_started`. `startRun` accepts
  `owner: { kind: 'orchestration'; orchestrationId; attemptId; generation; launchId; policyId; deadlineAt; authorise }`;
  the backend uses that launch id.
- **Joins are by attempt and generation, not by turn id:** the room/owner message mapping, command intent, run handle,
  observation charging and callbacks carry `(attemptId, generation)`; `message_runs` and intents gain a `generation`
  column and attach by `(attempt, generation)`. The journal's `run_handle` record gains `generation`; verification and
  replay use only the **latest admitted generation's** handle and keep older handles as evidence (their launches stay
  witnessed; they are never attached).
- `beginSend` returns the **committed** attempt row; `recordHandle` accepts only the current generation.
- **Permanent owner [M4]:** the coding journal's `requested` record carries an immutable owner
  `{ orchestrationId, attemptId, generation }`, kept in the launch's folded state, its projection row and its tombstone
  through compaction. Counting and pruning use it, never database joins alone.
- One launch per generation: the resume fallback and any second launch are disabled for owned turns.
- **Bound:** at most 20 generations per attempt; past that the step is blocked "kept being held back" for the person
  (no automatic loop) [N12].

## 6. Release, authorisation and transactions [R 1, 4, 5, 12, N1, N7, N8, M2, M5]
- **Phases of an owned coding attempt:** `created` →(beginSend)→ `send_started` →(handle while queued or arming)→
  `running` →(release)→ executing. The common admission rules are one pure function; the phase guards differ:
  `beginSend` requires `created`; release requires `send_started` or `running` **for generation g, with this launch's
  handle or none yet**.
- **Transaction ownership.** `release` is never called inside a database transaction (asserted). Inside
  `journal.critical`: (1) `authorise()` in its own read transaction; (2) on yes the journal records `releasing`; (3) the
  projection commits; (4) only then `go`. On no: the revoke tombstone with its typed cause is written in the same
  critical section. No `go` before the owning commit; no DB transaction spans a journal append.
- **`authorise()`** = the common admission rules (not retired, no owed Stop, orchestration not
  stopping/finishing/paused/fenced/frozen, no agent or team hold, inputs not withdrawn, budget and unknown-cost
  acceptance) + the release guard + the prepared spec (§3) + the coding step limit (§8). It never writes, never awaits,
  and returns a **typed cause** on "no".
- **Proof of no execution:** that launch's revoke tombstone; or, when no launch of generation g was ever requested
  (the pre-minted launch id is absent from the coding journal), a refusal before arming. Anything else (projection
  failure, exception, `releasing` without outcome) is **uncertain** ⇒ attempt `unknown`.
- **Closing a generation without launch [M2].** Every proven no-launch writes one executor journal record
  `send_closed { attemptId, generation, cause }`. The dispatch fold treats it like `send_refused` (generation g closed,
  the attempt sendable as g+1) but it **never** touches refusal counters; verification and replay recognise it. Restart
  recovery writes it for a bare `send_started` whose pre-minted launch id never reached the coding journal (cause
  `restart`). A proven no-launch has **known-zero execution spend** (no unknown-cost provenance).
- **Every cause, mapped to real states [M5]:**

  | cause | attempt | step | counters | wakes when |
  |---|---|---|---|---|
  | `paused`, `frozen`, `hold`, `fenced`, `restart` | `send_closed` ⇒ `created` (g+1) | stays `admitted` | none | the hold lifts (next pump) |
  | `budget`, `unknown_cost` | `send_closed` ⇒ `created` (g+1) | `admitted`; orchestration `paused` with today's budget/spend pause reason | none | the person raises the budget or accepts the source |
  | `deadline` (past) | `terminated` | `cancelled`, disposition `deadline` | none | — (the orchestration's deadline flow) |
  | `deadline_changed` (prepared expiry now too late) | `send_closed` ⇒ `created` (g+1) | `admitted` | none | next pump (new spec) |
  | `stop`, `cancel`, `retired`, `owed_stop`, `inputs_withdrawn` | `terminated` | `cancelled`, disposition = cause | none | — |
  | `agent_changed` | `send_closed`, then **suspended** (see §12a) | `blocked`, disposition `agent_changed` | none | remap or re-approval (§12a) |
  | `limit` (coding steps) | `send_closed` ⇒ `created` | `blocked`, disposition `coding_limit` | none | the person raises `codingSteps` |
  | readiness (`cli_missing`, `untested_version`, `engine_paused`, `needs_units`, `reach_unverifiable`) | `send_refused` ⇒ back to `created` with 7.1's retry/wait fields; at the lifetime limit, 7.1's terminal outcome | 7.1's refusal flow | refusal streak +1 | 7.1's readiness wait [K3] |

  The refusal streak is reset **only by a qualified release** of that attempt, not by `recordHandle` [N7].

## 7. Evidence, late proof and results [R 7, 8, 10]
- Three separate facts per coding run: **end proof** (monotonic: none → proven), **disposition**
  (`completed | failed | cancelled | interrupted`), **result eligibility** (only 7.7a's eligible reply, only for the
  generation that is current when the proof arrives).
- An attempt is `running` → on proof + disposition: `completed`+eligible ⇒ result accepted; `failed`/`interrupted` ⇒ a
  failed try (retry policy); `cancelled` ⇒ obligations closed, no result, not retried. No proof ⇒ `unknown`,
  obligations kept, agent fenced.
- **Late proof** for an `unknown` (or `abandoned`) coding attempt closes obligations and settles accounting but its
  result is **permanently non-consumable** (a coding-specific path; the generic "evidence on unknown is consumed" path
  is not used for coding runs). 7.7a's unit reaping publishes executor reconciliation evidence when it records proof.
- **Restart keeps 7.7a's rule:** a success pending at restart is `interrupted` (its reply is not kept) ⇒ a failed try,
  "Score restarted before the answer was saved". No durable result envelope in this stage.
- **Result storage:** new `orc_attempts.result_text` (and `result_truncated`) written in the same transaction as the
  terminal state, sourced only from the eligible reply, before any display cut or Score annotation. Limit 32 KiB;
  longer ⇒ stored cut (§11). The executor
  feeds the lead `result_text`, never the 8 KiB run output, for coding workers.

## 8. Coding step limit and spend [R 6, 13, N5, N9, decision 75]
- One limit, set at start and journaled with the admission: `codingSteps` (default 10) = how many coding launches this
  orchestration may **release**. It is **derived from the coding journal**: inside the release
  critical section, count the folded launches whose permanent owner is this orchestration and whose
  `mayHaveExecuted` is true (`releasing` or later); revoked launches never count [M4]. Launch tombstones are permanent and survive
  compaction, so the count survives restores and compaction with no allocation, refund or settlement records. There is
  no minutes limit (decision 75): time is bounded by the run deadline (§9) and 7.7a's per-turn cap.
- **Spend:** a coding run's cost is recorded at its terminal state, as in Chat. A run that ends **without** a recorded
  cost (crash, supervisor death, lost usage) counts as **unknown cost** for its source. Unknown cost keeps provenance per
  source (`hermes`, `claude-code`, `codex`); the person may accept unknown cost per source at start or later
  (journaled); an unaccepted source with unknown cost pauses the run **when a dollar budget is set** (today's rule);
  without a budget nothing pauses. Claude Code's cost is `estimated`.

## 9. Stop and deadline [R 9, 14]
- Owed Stops become **tracked asynchronous jobs** (one per attempt, retried with backoff); the pump never awaits them;
  shutdown drains them with the existing barrier. Acknowledgement: coding ⇒ only `stopped`/`not_running`; Hermes keeps
  today's `void` = acknowledged.
- **Decision 74 extends to executor-owned runs:** while frozen, an owed Stop for a coding run **this process launched**
  and is connected to is delivered; Stops for recovered/inherited runs still wait.
- **Deadline [N4]:** `startRun` carries the orchestration's absolute `deadlineAt`. At release the supervisor's expiry is
  `min(now + 7.7a's per-turn cap, deadlineAt)`, validated (an expiry already past ⇒ revoked as "deadline"). A deadline
  moved earlier while queued or arming is caught by `authorise()` at release; while running, the executor owes a Stop
  for coding attempts past the new deadline.
- **Expiry at spawn [A2]:** the supervisor checks the absolute expiry in its `go` handler immediately before spawning the
  CLI; an expired `go` doesn't spawn (the supervisor reports `expired`). Once `releasing` is durable, the launch keeps
  `mayHaveExecuted` and its step charge (no manufactured revocation); the attempt ends as a proven no-run only if the
  supervisor's receipts prove it never spawned, otherwise per §10. Tested with delayed commit and delayed `go` delivery.
- **Shutdown [N11]:** executor close stops scheduling Stop retries, waits for in-flight Stop deliveries up to 5 s and
  leaves unresolved Stops durably owed; then the coding runtime closes; ingest and the database stay open until both
  have committed their receipts.

## 10. Restart matrix [N8]
| what the journal and database show for generation g | executor outcome |
|---|---|
| `send_started` and a refusal receipt | the receipt's class (§6) |
| `send_started` only, pre-minted launch id not in the coding journal | `send_closed` (cause `restart`) ⇒ `created` (g+1) |
| launch `requested`/`armed`, never `releasing` | 7.7a revokes it at recovery (tombstone, cause `restart`) ⇒ `send_closed` ⇒ `created` |
| revoke tombstone | the class of its cause (§6) |
| `releasing`, outcome unknown | `unknown`, agent fenced; late proof per §7 |
| released, verdict `completed` held but not committed | `interrupted` ⇒ failed try (7.7a rule) |
| released, result already committed to the attempt | nothing (idempotent on run id and generation) |
| released, proven failure / stop | failed try / `cancelled` |
| released, end unproven | `unknown`, agent fenced; late proof per §7 |
| frozen home | nothing until `reset-history` |

A released launch without a handle is `unknown`; Stop routing uses the launch row.

## 11. Storage and pruning [R 17, N6, N12, M7, M8]
- **Coding launch rows and their journal tombstones are never pruned** (as in Chat).
- **Pruning enumerates by identity, not turn id:** for each attempt, every generation's run (by `(attempt,
  generation)` joins and launch owners), command intent, message mapping, thinking/tool rows and result; deleted
  atomically with the attempt rows, keeping launch projections and tombstones.
- **Proven-unlaunched payloads are dropped:** when a generation is closed by `send_closed` or a revoke tombstone, its
  command intent's input is replaced by its hash (never sent, so nothing needs the text again for recovery); only the
  current generation and launched generations keep their input.
- **Reserve:** a coding worker item reserves `72 KiB + 32 KiB (result) + 32 KiB (one retained input)` plus 2 KiB per
  generation (≤ 20), independent of the ordinary observation pool, so its terminal state, proof, refusal receipt and
  Stop always fit. Policy snapshots (≤ 4 KiB each) are charged at create. Admissions are charged like observations.
- `result_text` is limited to **32 KiB** (cut at a character boundary, `result_truncated = 1`, and the lead is told).
- The coding translator charges executor-owned observations through `chargeObservation` and drops ordinary ones when
  the allowance is exhausted, keeping Stop and obligation evidence.

## 12a. Remap and re-approval to a new policy [M6]
- A step blocked `agent_changed` offers **"Use the new settings"**: a policy-only remap of the **same** agent (no
  incarnation change needed). Validation: the agent is the step's worker, its current policy id differs from the
  stored one, it is ready, and the request carries the new `policyId` and (when its reach goes beyond its workspace) an
  acknowledgement of that policy id. The resulting mapping `{ attemptStep, agentId, policyId }` is journaled with the
  decision and verified after restore.
- Step gates (approval payloads) include the worker's policy id; a gate approved for an old policy id doesn't cover the
  new one: the step goes back to `pending_gate` for a fresh approval.
- **One attempt per step, suspended while blocked [K2]:** the `agent_changed` attempt is closed (`send_closed`) and
  marked **suspended** (a new attempt flag): dispatch selection skips suspended attempts and they don't occupy a
  concurrency slot. After the remap (and, if needed, the fresh gate approval) the **same** attempt is unsuspended and
  re-admitted through normal admission, which now also requires the step's current gate, payload and policy id; the
  release check requires them too. No replacement attempt is created, so the step keeps exactly one active attempt.
- **One reservation owner [A1]:** the suspended attempt keeps its budget reservation through suspension, re-gating and
  re-admission; while a step has a suspended attempt, the budget sum excludes the step's own estimate (no double count
  in `pending_gate`/`queued`). Tested with a tight budget across a restart.
- Remap to a **different** agent keeps today's rules plus the new agent's policy id and consent.
