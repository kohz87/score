# 7.7c Coding agents in workflows (design v2, for re-review)

Stage 3 of PLAN 7.7 (decision 65). Stage 2 (7.7b, v1.2.0/1.2.1) made Claude Code and Codex orchestration **workers**:
frozen worker policy and policy id, consent by policy id, per-generation identities, release authorised by the
executor's one admission function, proof of no execution, the cause table, coding step limit from the launch journal,
unknown cost per source, `result_text`, per-step policy remap with suspended-attempt re-admission, gates bound to policy
ids, the coding storage partition. A workflow run **is** an orchestration (`planner = 'workflow'`) on the same executor,
attempts, journal and release path; this stage opens the workflow doors onto that machinery and adds what is
workflow-specific. Reference: `docs/briefs/7.7b-coding-workers.md` (v6), decisions 69–77.
v1 was blocked (`docs/reviews/2026-10-14-7.7c-design-review.md`, 1 P1, 7 P2, 2 P3; [W n]). W9 was a live 7.7b bug, fixed
in v1.2.1 (owned runs no longer write Chat's session cache).

## 0. What exists (verified by review 1)
- Workflow save and preflight/start call `assertHermesOnly` (`http/workflows.ts:77,83`, `executor.ts:1171`); Validate
  (`http/workflows.ts:65`) runs the graph-only `validateDefinition`.
- `WorkflowRunCreate`: `agentMap` (incarnations), `gatePolicy` (`gates-only`), `budgetUsd`, `deadlineAt`,
  `unknownSpend: 'pause' | 'continue'`, `maxConcurrentSteps` (≤ 3), `stepEstimateUsd`, `rerunOf`.
- Assignment gates (every-step) go through `decideGate` (`executor.ts:1307`) with payloads built by the workflow
  planner (`planner.ts:598`); `decideNodeGate` handles graph `gate` nodes, which have no agent.
- The planner clears a blocked node's `step_id` and may assign a replacement (`planner.ts:298`).
- `tryAgain` resets refusal counters on the existing attempt (`workflows/decisions.ts:195`); the executor caps
  generations at 20 per attempt.
- `remapWorkflow` replaces the incarnation of the **same agent id** and rejects an unchanged incarnation
  (`workflows/decisions.ts:231`); the 7.7b policy-remap endpoint requires a lead orchestration (`executor.ts:1077`).
- Verdicts are parsed from the complete reply (`verdict.ts:58`) into `wf_results`, joined via `message_runs.run_id`.
- Workflow live views report the start-time `unknownSpend` and have no coding items (`views.ts:576`,
  `WorkflowNeedsYouSchema`).

## 1. Scope and validation [W7, W8]
- Claude Code and Codex agents may be the agent of a **step node** (read-only or workspace-write; never `full`), on
  unit hosts only (7.7b §1). Antigravity/OpenCode are refused. Graph `gate` nodes have no agent and are unaffected.
- **One runtime validation**, `validateWorkflowAgents(definition, team, facts)`, returns structured issues
  (`coding_agent_unsupported`, `coding_permission_full`, `coding_workers_need_units`) and is used by **Validate**, save,
  new versions and preflight/start, next to the graph validation. Readiness (CLI installed, version, policy) is
  **never** part of a definition or its hash; it is checked at preflight/start only.
- **Zero coding workers:** a workflow with no coding step node sends and stores **no** coding fields (no policies, no
  `codingSteps`, no reach acknowledgement, no coding storage partition). The existing Hermes-only and gate-only paths are
  unchanged; regression tests for both.

## 2. Policy, consent and the run dialog [W6]
- **Preflight** returns per coding agent `{ readiness, policyId, reach, reachBeyondWorkspace }` (7.7b `buildPolicy`).
- **Start** carries `codingPolicies`, `acknowledgeCodingReach: { policyIds }` and `codingSteps` (default = the number of
  coding step nodes × (1 + the node's retry allowance), capped at the 7.7b maximum); `409 policy_changed` /
  `409 reach_not_acknowledged` as in 7.7b. `agentMap` keeps its incarnation check.
- **Unknown cost:** `unknownSpend: 'continue'` accepts every source; `'pause'` plus the new optional
  `acceptUnknownCost: Source[]` accepts those sources. Journaled with the admission; later changes go through the
  workflow limits decision (§6) with 7.7b's scoped add/remove.
- **Rerun** shows the current policy ids and asks for the acknowledgement again; nothing carries over.

## 3. Results and verdicts [W10]
- The verdict is parsed from the **raw eligible reply** (`TerminalInfo.reply`, the CLI's own validated final answer)
  before any storage cut, display fallback or Score annotation — never from `result_text`'s 32 KiB copy. The parser
  keeps today's rule for Hermes replies (whole reply). Bound: an eligible reply over the verdict input limit (256 KiB)
  fails the node "answer too long to read a verdict" (no prefix parsing).
- The `wf_results` row joins by `(attempt, generation)` (7.7b §5). No eligible reply ⇒ no row ⇒ the node fails "no
  final answer". Late proof / `interrupted` / `unknown` never give a verdict (7.7b §7).

## 4. Nodes, blocks and decisions [W1, W2, W3, W4]
- **A blocked coding node keeps its step [W1].** When a node's step is blocked `agent_changed` or `coding_limit`
  (attempt suspended, 7.7b), the planner does **not** clear the node's `step_id` and never assigns a replacement; the
  node→step→suspended-attempt binding is durable. Only the matching decision (policy remap, raising the limit) re-admits
  **that** attempt. Other blocked dispositions keep today's planner behaviour.
- **Assignment gates [W2]:** the workflow planner puts the node agent's `policyId` into every assignment gate payload
  it creates; re-approval after a policy remap creates a fresh payload with the new id; admission and release require
  the gate's id to match (the 7.7b rule). Graph gate nodes have no agent and no policy binding.
- **Policy-only remap for a node [W3]:** new
  `POST /api/workflow-runs/:runId/nodes/:nodeId/policy-remap { revision, policyId, acknowledgeCodingReach? }`:
  the node's agent unchanged, its current policy reported by preflight; uses 7.7b's per-step mapping and suspended
  re-admission; journaled and verified after restore. **Remap to a different agent** keeps today's workflow remap
  semantics (same agent id, new incarnation); switching a node between Hermes and coding agents is **not** offered in
  this stage (the v1 promise is removed).
- **Try again [W4]:** creates a **fresh attempt** for the node (new attempt id, its own generations) instead of resetting
  counters on the old one; the old attempt stays as history. Bounded by the workflow's existing attempt budget
  (`attempts_max`) and storage (§5).
- **Retry** creates the next attempt through the normal path (fresh CLI session, policy checked at release, coding step
  counted).

## 5. Storage [W5]
- The coding partition is set at creation: `codingSteps × CODING_ITEM_EXTRA_BYTES` (7.7b's constant, which covers
  input, result copies, retained reply, run output and generation records), plus a `wf_results` copy per coding attempt
  (32 KiB output + verdict) inside the same item allowance — computed from constants. Ordinary observations can't spend
  it (7.7b F1).
- Raising `codingSteps` grows the partition by the items beyond those already reserved (7.7b F2), or is refused.

## 6. Live views and decisions [W6]
- `WorkflowNeedsYou` gains `coding_agent_changed { nodeId, agentId, newPolicyId, reach }` and `coding_limit {
  used, limit }`; summary/detail gain `coding: { codingSteps, used, acceptedSources, unknownSpend }` (the **effective**
  current authorisation, not the start-time snapshot).
- The workflow limits decision accepts `codingSteps?` and scoped `acceptUnknownCost` add/remove (7.7b's
  `LimitsDecision` shape), journaled and verified after restore.
- The web reuses 7.7b's decision cards and `RunDecisions` with the workflow's `coding` block; the live workflow view
  shows the CLI badge on coding nodes.

## 7. Rooms and sessions [W9]
Owned workflow coding runs never read or write Chat's session cache (fixed for all owned runs in v1.2.1); the run keeps
its own session id on its run row; releasing the workflow room to Chat doesn't clear Chat's cache.

## Contract changes
`WorkflowRunCreate` gains `codingPolicies?`, `acknowledgeCodingReach?`, `acceptUnknownCost?`, `codingSteps?` (all
omitted when the workflow has no coding step node); `WorkflowPreflight` gains `workers[]`; Validate/save return the
structured runtime issues; `WorkflowNeedsYou` and the summary/detail `coding` block; the node policy-remap endpoint; the
workflow limits decision fields. Contract doc first, then `packages/contract`, then both sides.
