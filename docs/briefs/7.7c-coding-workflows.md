# 7.7c Coding agents in workflows (design v1, for adversarial review)

Stage 3 of PLAN 7.7 (decision 65). Stage 2 (7.7b, v1.2.0) made Claude Code and Codex orchestration **workers**:
frozen worker policy and policy id, consent by policy id, per-generation identities, release authorised by the
executor's one admission function, proof of no execution, the cause table, coding step limit from the launch journal,
unknown cost per source, `result_text`, policy-only remap, gates bound to policy ids, coding storage reserve. A workflow
run **is** an orchestration (`planner = 'workflow'`) driven by the same executor, attempts, journal and release path, so
this stage opens the workflow doors onto that machinery and adds what is workflow-specific. Design and code of 7.7b are
the reference: `docs/briefs/7.7b-coding-workers.md` (v6) and decisions 69–77.

## 0. What exists (to verify)
- Workflow save and preflight/start call `assertHermesOnly` (`http/workflows.ts:77,83`, `executor.ts:1171`).
- `WorkflowRunCreate` carries `agentMap` (incarnations the page showed), `gatePolicy` (`gates-only` default),
  `budgetUsd`, `deadlineAt`, `unknownSpend: 'pause' | 'continue'`, `maxConcurrentSteps` (≤ 3), `stepEstimateUsd`,
  `rerunOf`.
- Workflow node results: `recordRunResult(runId, fullReply)` parses a verdict from the full reply into `wf_results`,
  joined through `message_runs.run_id` → attempt (workflow step attempts only).
- Node decisions: `retryNode`, `tryAgain`, `remapWorkflow`, `decideNodeGate` (`domain/workflows/decisions.ts`).
- A workflow room released to Chat keeps Chat's own session cache (7.7 v2 §5).

## 1. Scope
- Claude Code and Codex agents may be the agent of a workflow **step node** (read-only or workspace-write; never
  `full`), on unit hosts only — exactly 7.7b §1's worker rules. Antigravity and OpenCode stay refused.
- Nothing else in a workflow definition may name a coding agent (no coding agent as a planner/lead-like role, if any
  exists in the definition language; verify).
- `assertHermesOnly` is removed from workflows and replaced by `assertWorkflowWorkers(definition, team, facts)`
  (step nodes only; same refusals and codes as 7.7b: `unsupported_agent`, `coding_workers_need_units`).

## 2. Policy, consent and the run dialog
- **Preflight** (`GET /api/workflow-runs/preflight`) returns per coding agent `{ readiness, policyId, reach,
  reachBeyondWorkspace }` like 7.7b (same `buildPolicy`, stat-only, environment hash).
- **Start** (`POST /api/workflow-runs`) carries `codingPolicies`, `acknowledgeCodingReach: { policyIds }`, and
  `codingSteps` (default: the number of coding step nodes, capped at the 7.7b maximum); `409 policy_changed` /
  `409 reach_not_acknowledged` as in 7.7b. `agentMap` keeps its incarnation check; the policy id is checked in addition.
- **Unknown cost:** the workflow's `unknownSpend` stays (`continue` accepts every source, like 7.7b's legacy
  `acceptUnknownSpend`); new optional `acceptUnknownCost: Source[]` for per-source acceptance; when both are given,
  `continue` wins. Decided at start and journaled with the admission like 7.7b.
- **Rerun** (`rerunOf`) never inherits an old acknowledgement: the rerun shows the current policy ids and asks again.

## 3. Results and verdicts
- For a coding run, `recordRunResult` receives **only the eligible reply** (7.7a acceptance; the same text as
  7.7b's `result_text`, before any display cut or annotation), and joins by `(attempt, generation)` (7.7b §5), never by
  a logical turn id. No eligible reply ⇒ no `wf_results` row ⇒ the node fails "no final answer" (no verdict parsed).
- The verdict parser is unchanged; its input size limit applies to the eligible reply as to a Hermes reply.
- Late proof / `interrupted` / `unknown` follow 7.7b §7: never a consumable result, never a verdict.

## 4. Node decisions
- `retryNode` and `tryAgain` create the next attempt/generation through the normal path: fresh CLI session, policy
  checked at release, step limit counted.
- `remapWorkflow` to or from a coding agent carries the new agent's policy id and its reach acknowledgement (7.7b §12a);
  a **policy-only remap** of a blocked `agent_changed` node uses 7.7b's per-step mapping and suspended-attempt
  re-admission.
- `decideNodeGate`: gate payloads include the node agent's policy id; a gate approved for an old policy id doesn't cover
  the new one (7.7b).

## 5. Rooms and sessions
- Workflow coding steps never read or write Chat's (room, agent) session cache; releasing the workflow room to Chat
  leaves Chat's cache untouched (a later Chat message to that coding agent starts its own session).

## 6. Editor and UI
- The workflow editor's agent picker offers Claude Code and Codex agents for step nodes (with the CLI badge) and
  disables Antigravity/OpenCode with the reason; the definition validator gives the same reason.
- The workflow run dialog adds the reach section, one acknowledgement, per-source unknown cost (shown only if
  `unknownSpend = pause`), and the coding step limit — reusing 7.7b's components.
- The live workflow view (5.39) shows the CLI badge on coding nodes and the "Use the new settings" / "Raise the limit"
  cards from 7.7b.

## 7. Storage
The workflow item reserve gains 7.7b's coding item allocation for each coding step node (computed from the same
constants), and `wf_results` copies of a coding reply are charged.

## Contract changes
`WorkflowRunCreate` gains `codingPolicies?`, `acknowledgeCodingReach?`, `acceptUnknownCost?`, `codingSteps?`;
`WorkflowPreflight` gains `workers[]`; workflow save errors gain `unsupported_agent` reasons for coding agents in
non-step positions and `coding_workers_need_units`. Contract doc first, then `packages/contract`, then both sides.

## Done when
Fake drivers on the fake unit backend (as 7.7b), plus the opt-in systemd suite:
- a workflow with a Claude Code step node and a Codex step node runs to completion; each verdict comes from the CLI's
  eligible reply; no eligible reply ⇒ node fails, no verdict;
- save/preflight/start refuse Antigravity, `full`, coding agents outside step nodes, process-group hosts;
- start requires policy ids and the reach acknowledgement; a rerun asks again;
- retry / try again use fresh sessions and new generations; a policy-only remap and a gate re-approval work on nodes;
- the workflow room released to Chat leaves Chat's session cache untouched;
- storage reserve and charging; `unknownSpend` and per-source acceptance interplay;
- e2e (fake mode): the editor offers coding agents for step nodes, the run dialog shows reach and acknowledgement, a
  live workflow view shows the badge.
`pnpm check`; the live check (owner approval) as for 7.7b.
