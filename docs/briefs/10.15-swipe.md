# 10.15 — Swipe retry with true swapping (design v1)

Owner (2026-10-20): "the retry in chat isn't like swipe? so it toggle left and right between iteration?" → "build it
with true swapping and swipe everywhere".

Today **Retry** (`POST /api/rooms/:roomId/messages/:messageId/retry`, contract §5) appends a second reply below the
first; both stay in the thread and in the agent's session (it "saw" the first answer when writing the second). The
"‹ n / m ›" pager in Chat belongs to *edited person messages* (PLAN 5.33 rewind versions), read-only.

## What the owner gets
- **Retry regenerates into the same place.** An agent reply gets "‹ 2 / 3 ›"; the arrows flip between its
  *alternatives* in place. Retry adds a new alternative and shows it.
- **Every alternative is written from the same context**: before regenerating, the agent's session is rewound past the
  reply, so alternative 2 never saw alternative 1.
- **True swapping:** the alternative left showing is what the agent remembers. Flipping to another alternative swaps
  the agent's last turn in its session to that alternative, so the next message continues from it.
- **Everywhere:** rooms and direct rooms, any agent, with the limits below stated in the UI, never silently.

## Scope and limits (v1)
1. **Only the room's latest reply-turn can be swiped.** A *reply-turn* is one agent's reply to one person message. When
   anything newer exists in the room (a person message, another agent's reply, a hand-off, a tool card), the turn's
   alternatives freeze on the selected one: the arrows still show the others read-only ("‹ 1 / 3 › viewed only").
   Group rooms: two agents answering the same person message each have their own turn; each is swipeable only while
   nothing newer than *it* exists (in practice the last one to finish).
2. **Hermes agents:** full swapping through the bridge (below).
3. **Coding agents** (Claude Code, Codex, Antigravity): their conversation lives in the CLI's own session, which Score
   can only resume, not rewind or edit. v1 rule: an alternative for a coding agent starts a **fresh CLI session forked
   from the session as it was before the turn** where the CLI supports forking at a recorded point; the selected
   alternative's session id becomes the agent's session for the room, so swapping is true. Where a CLI can't fork at
   that point, Retry is **unavailable for that agent with the reason** ("Codex can't restart from before this reply").
   The build verifies per CLI (Claude Code `--resume <id> --fork-session` against a session id recorded *before* the
   turn; Codex/Antigravity: research, recorded fixtures) and ships the rule per runtime.
4. **Not in orchestration or workflow rooms** (their steps are journaled executions; a reply there is a step result):
   Retry stays unavailable with the reason, as today.
5. **Side effects are not undone.** If an alternative ran tools (commands, file edits, messages to channels), those
   effects stay when you swap away from it. The alternative shows "ran tools" and Retry on such a turn asks once:
   "This reply ran tools; their effects stay. Regenerate anyway?" Approvals an alternative raised that are still
   pending are withdrawn when it stops being selected (through the ledger's existing withdraw path).

## Score data model
- New table `message_alternatives`: `turn_id` (the first reply's message id, stable), `message_id`, `index` (1…n),
  `selected` (exactly one per turn), `created_at`, `hermes_rows` (JSON: the Hermes `message_uid`s of that alternative's
  rows in the agent's session, captured by the bridge), `cli_session_id` (coding agents), `ran_tools` (bool).
  Migration: next free number. Existing replies are single-alternative turns lazily (no backfill needed: a reply with no
  row is a turn of 1).
- Non-selected alternatives are **hidden from normal reads** exactly like deleted messages (`deleted_at` +
  `alternative_of`), so search, room summaries (7.4a), memory notes, exports, context meters, the stage, Knowledge
  saves and the agent tools see only the selected one. Switching selection un-hides one and hides the other in one
  transaction.
- Contract: `Message.alternatives?: { turnId; index; count; swipeable: boolean; reason: string | null }` on agent
  replies (absent = 1 of 1, swipeable per rules); `GET /api/rooms/:roomId/turns/:turnId/alternatives` →
  `{ items: Message[] }` (all, read-only); `POST …/messages/:messageId/retry` → `202 { messageId, turnId, index }`
  (regenerates into the turn); `POST /api/rooms/:roomId/turns/:turnId/select` `{ index, ifSelected }` → `200
  { selected: Message }` (`409 stale` if `ifSelected` changed, `409 not_swipeable` with the reason, `409 conflict` while
  the agent answers anything in the room). Stream: `message.updated`/`message.deleted` as today plus
  `turn.alternatives.updated { roomId; turnId; count; selectedIndex }`.

## Hermes side (bridge, `score_bridge`, private calls only in `hermes_private.py`)
New bridge commands (contract §11), each idempotent per command id, bounded by `expires_at`, refused while the
session has a running turn or holds a turn lease / compression lock:
- `capture_turn { sessionId, since }` → the live rows after the last user turn at or after `since`
  (`message_uid`s and roles, never content): Score stores them as the selected alternative's `hermes_rows` before any
  regenerate.
- **Regenerate** = the existing `rewind` of exactly that one user turn (soft-archive, `RewindTargetUnavailableError`
  → refuse), then Score re-sends the same person input through the normal dispatch path (pause, approvals,
  attachments, one-turn queue apply). The new alternative's rows are captured when its run completes.
- `swap_turn { sessionId, fromUids, toUids }` → in one `replace_messages(..., archive_dropped=True,
  reject_active_turn_lease=True)`: the live transcript with the suffix `fromUids` replaced by the archived rows
  `toUids` (read with `include_inactive=True`, re-inserted as live rows with the same content). Refuses when the live
  suffix isn't exactly `fromUids` (someone else wrote to the session), when any `toUids` row is missing, or across a
  compression boundary (like rewind). Returns the new live uids.
- Redaction (D6) applies to anything the bridge returns; the bridge never returns message content to Score.

## Web
Agent replies show "‹ i / n ›" next to the existing message actions when `alternatives.count > 1` or Retry was
used; arrows (and ←/→ when the reply has focus) select; the swap shows "Switching…" until the server confirms, and
reverts with the reason on refusal. Frozen turns show the arrows as view-only with a tooltip. Retry's confirmation
for tool-running turns as above. The stage/header moods treat a regenerating turn like any reply.

## Questions for the adversarial review
Is "latest reply-turn only" the right boundary in group rooms with hand-offs? Is re-inserting archived rows through
`replace_messages` safe against Hermes's own compaction, memory flush and transcript drains? What breaks if the gateway
restarts mid-swap, or Score crashes between the Hermes swap and its own selection commit (which side is the truth,
how is it reconciled)? Do summaries, FTS, read receipts, approvals, Watch frames and orchestration hand-offs that point
at a non-selected alternative behave? Is the coding-agent fork rule sound for each CLI, and what if a CLI's session
store expires the pre-turn session?
