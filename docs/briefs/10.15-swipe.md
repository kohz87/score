# 10.15 — Swipe retry (design v3: the safe part) and synced delete of the latest turn

Owner (2026-10-20): swipe retry with true swapping everywhere, and deletes that also reach the agent's memory. The v1
design (true swapping through transcript replacement) was **not approved** by the adversarial review
(`docs/reviews/2026-10-20-10.15-swipe-design-codex.md`): Hermes has no atomic, expected-state transcript operation, so
swapping or removing arbitrary rows can archive unseen rows, splice rows of the wrong alternative, or be undone by a
pending transcript drain. The owner chose: **build the part Hermes supports safely now, and draft a Hermes proposal**
(`docs/proposals/hermes-transcript-cas.md`) for true swapping and arbitrary deletes later.

## What the owner gets in v2
1. **Retry regenerates into the same place** as alternatives "‹ i / n ›" on the reply. Each alternative of a Hermes
   agent is written from the **same context**: Score rewinds the agent's session past the turn with Hermes's own
   rewind (the PLAN 5.33 path: `rewind` bridge command, soft-archive, counted and verified turns) and re-dispatches the
   **frozen admission input** of the original turn (text, attachments, recipients as admitted).
2. **The conversation continues from the newest alternative.** The arrows show older ones read-only with the line
   "Viewing 1 of 3 — the agent remembers 3 (the newest)". Nothing lets the screen and the agent disagree: the newest is
   the turn's message for the thread, search, summaries, exports and every agent tool; older ones are hidden from
   normal reads and listed only by the alternatives endpoint.
3. **Coding agents** (no verified pre-turn fork): Retry still adds an alternative in the same place, written by the
   CLI continuing its session (it saw the earlier answer). The alternative is labelled "Written after the earlier
   answer: Claude Code can't restart from before it". Their sessions are never forked or reset by this feature, and the
   unknown-session fallback never applies to a Retry.
4. **Delete that reaches the agent** (latest turn only): deleting an agent reply offers, when the turn is the room's
   latest and eligible, **"Delete question and reply — the agent forgets both"**, which is the existing rewind with
   `mode: 'delete'` on the person's message (5.33: hides the message and everything after it and rewinds every agent
   that answered). Today's **"Delete reply in Score only"** stays for any reply, with the existing explanation. Hermes
   can't remove a reply while keeping its question; the dialog says so.

## Eligibility (regenerate and the synced delete)
Refuse with the reason — never partially — unless **all** hold:
- The room isn't an orchestration or workflow room.
- The turn is the room's **latest causal work**: no newer message of any author, no queued or running work in the
  room (one-turn queue, hand-off reservations, summary admissions whose frozen input includes this reply,
  `message_runs` not terminal), and no pending approval raised by this turn that has been answered
  (`unknown`/possibly-applied delivery outcomes count as consumed). Checked in the same transaction that writes the
  operation record and the room hold, and again at dispatch.
- For Hermes agents: the rewind preconditions of 5.33 pass for exactly this turn, extended with the review's findings:
  the turn is a single Hermes user turn (no `/steer`, no merged/repaired user turns between the person message and the
  end of the reply), the session's turn count matches Score's records (`message_runs`), the session isn't in a
  compressed segment, and the bridge reports **no pending transcript writes for the session** (new read-only bridge
  probe `transcript_pending { sessionId }` → `{ pending: number }` through `hermes_private.py`, using Hermes's own
  drain state; unknown → refuse).
- The agent isn't paused and the team isn't paused.

## Durability: one persisted operation per Retry
New table `turn_operations` (`id`, `room_id`, `turn_id`, `kind: 'regenerate'|'forget'`, `phase:
'planned'|'rewound'|'dispatched'|'done'|'failed'|'unresolved'`, `alternative_index`, `rewind_command_id`, `run_id`,
`error`, timestamps). Order, each step committed before the next effect:
1. Eligibility + operation `planned` + a **room hold** (existing hold mechanism) in one transaction.
2. Bridge `rewind` (idempotent per command id) → on success `rewound`; on a definite refusal → `failed`, hold released,
   nothing changed; on an unknown outcome → `unresolved` (hold kept, Settings and the room say so; Score re-asks the
   bridge for the command result on the next start and resolves to `rewound` or `failed` from Hermes's verified turn
   count, never by expiry alone).
3. Dispatch the frozen input as a new alternative's run → `dispatched`; the run's terminal state → `done` (the new
   alternative becomes the newest) or `failed` (Stop, error): the failed alternative stays visible as the newest with
   its error, exactly like any failed reply today; the earlier alternatives stay read-only. The rewind is not undone
   (Hermes's soft-archive is the record; the turn now holds the failed attempt, as a normal failed reply would).
4. On Score start: operations in `rewound` are dispatched (the hold kept them from interleaving); `unresolved` are
   reconciled as in 2; the hold is released only at `done`/`failed`.
`kind: 'forget'` runs the existing 5.33 rewind operation (already durable and idempotent) under the same hold.

## Data model and contract
- `message_alternatives` (`turn_id`, `message_id`, `index`, `created_at`, `context: 'same'|'after_previous'`,
  `ran_tools`): the newest index is the turn's live message; older ones get **their own hidden marker**
  (`alternative_hidden_at`), separate from `deleted_at` and room-version membership, so a room version or an explicit
  delete never un-hides, and un-hiding never clears a delete. Migration: next free number.
- `Message.alternatives?: { turnId; index; count; context: 'same' | 'after_previous'; viewOnly: true }` on agent
  replies with more than one alternative.
- `POST …/messages/:messageId/retry` → `202 { messageId, turnId, index }` when the turn is eligible; `409
  not_eligible { reason }` otherwise (the reasons above in plain words). `GET /api/rooms/:roomId/turns/:turnId/
  alternatives?asOfSeq` → `{ asOfSeq; items: Message[] }` (read-only).
- Stream: the new alternative arrives as the normal reply events; the turn's previous newest gets
  `message.updated { alternativeHiddenAt }` then `turn.alternatives.updated { roomId; turnId; count; newestMessageId;
  newest: Message }` carrying the complete newest message, so a client that only had the old one replaces it
  (review P2 #10).
- Run approvals, Watch frames and Reports keep every real execution, linked to its alternative. Memory or Knowledge
  writes an alternative made **persist** (stated in the Retry confirmation when the turn ran tools: "This reply ran
  tools or saved notes; those stay.").

## Web
"‹ i / n ›" on replies with alternatives; ←/→ when focused; older alternatives render read-only with the "Viewing i of
n — the agent remembers n" line and a "Back to the newest" link. Retry on an eligible turn regenerates in place; on an
ineligible one the button is disabled with the reason as its description. The delete dialog shows the two choices
above when the synced one is eligible, and only the Score-only one (with the reason) when it isn't.

## Hermes proposal (separate document)
`docs/proposals/hermes-transcript-cas.md`, unsent draft for the owner: an atomic, expected-state transcript operation
(replace an exact contiguous block given the expected pre-turn prefix digests and transcript generation, no
common-prefix matching, full row payloads preserved, refusing while transcript writes are pending, steer-aware turn
boundaries), which would enable true swapping and deleting any reply.

## Questions for the adversarial review
Is "latest causal work" checked completely (queues, hand-offs, summaries, approvals) and serialised against room
writes? Is the operation journal sufficient across a Score or gateway restart at every phase? Does reusing 5.33's
rewind for regeneration inherit its guarantees, and are the added preconditions (single Hermes user turn, no pending
writes) checkable with Hermes's existing APIs? Is the alternatives visibility model independent of deletes and
versions in every read path?

## v3 changes (answers to the v2 review, `docs/reviews/2026-10-20-10.15-swipe-design-v2-codex.md`)
These rules override the v2 text above where they differ.

**R1 — Recovery for every phase (v2 P1 #1).** `turn_operations` also stores the resolved Hermes `session_id`, the
**expected source turn** (the person message's Hermes user-row uid and the uids of the turn's live rows, read through
the bridge at planning), a stable `command_id` and `admission_id`, and the linked run intent. Holds created by an
operation have **no expiry**: they live until the operation is terminal. On start, before routing or intent recovery,
every non-terminal operation is reconciled by reading the session's live rows through the bridge (read-only):
`planned` → if the expected source rows are still live, the rewind didn't happen → re-run step 2 with the same
`command_id`; if they are archived and nothing newer is live, it did → `rewound`; anything else → `unresolved`.
`rewound` → dispatch with the stored `admission_id` (idempotent through the existing run-intent path; an intent that
already exists is adopted, not duplicated). `dispatched` → normal run recovery decides `done`/`failed`.
`unresolved` keeps the hold and is shown in the room and Settings with "Resolve" (re-check) and "Release" (lead:
release after the person reviewed the agent). Coding agents have no rewind phase: `planned` → `dispatched` → terminal.

**R2 — Preconditions checked atomically with the rewind (v2 P1 #2).** The bridge's rewind for a Retry becomes a new
command `rewind_turn { sessionId, expected: { userUid, liveUids } }` implemented in `hermes_private.py`: under Hermes's
transcript drain lock it (a) refuses if any pending transcript write for the session exists in memory queues, disk
spools or reroutes (all three read through Hermes's own objects; if any can't be inspected on this Hermes version, the
command is unavailable and Retry says so), (b) refuses unless the live user turn ending the transcript is exactly
`userUid` with the live rows `liveUids` after it and no steer/merged user row among them, (c) refuses on a compressed
segment, then (d) calls Hermes's own `rewind_user_turn` for that one turn, whose active-row/lease checks run in the same
transaction. No turn count is recomputed. A refusal before (d) is "nothing changed"; a failure in or after (d) is
`unresolved` until reconciled by R1.

**R3 — Synced delete only with one Hermes respondent (v2 P1 #3).** "Delete question and reply — the agent forgets
both" is offered only when exactly one Hermes agent answered that person message and no coding agent did; it uses
`rewind_turn` under the same journal (`kind: 'forget'`). Otherwise only the Score-only delete is offered, with the
reason.

**R4 — A complete fence (v2 P2 #4).** While an operation holds a room, these refuse with `409 held` inside their own
write transactions: posting, editing or deleting messages, rewind, plan start, summary create/edit/regenerate,
compaction, hand-off reservation and dispatch of anything but the operation's own admission (the dispatcher admits a
held room's work only when it carries the holding operation's `admission_id`). A persisted plan start that consumed
the reply makes the turn permanently ineligible.

**R5 — Turn accounting (v2 P2 #5).** A logical turn id (the first reply's id) is separate from per-attempt admission
ids. At the verified `rewound` checkpoint the previous attempt's `message_runs` row is marked `transcript_retired_at`
(its execution, approvals and costs stay); rewind counting (`versions.ts`) counts only non-retired turns. An attempt
that failed before Hermes persisted its user turn is recorded as such and never counted.

**R6 — Exact admission material (v2 P2 #6).** At first admission Score stores the final input representation it sent
(text, the attachment selection with media ids and content hashes, omission notes). Media referenced by a stored
admission is retained (not cleaned up) while its turn has alternatives or could get one. Retry verifies every piece is
present **before** the rewind and refuses if not. Coding Retries store the required resume id and a continuity flag; a
missing session refuses — the fresh-session fallback never applies.

**R7 — One visibility predicate (v2 P2 #7).** `visibleMessage := deleted_at IS NULL AND alternative_hidden_at IS NULL`,
used by agent context, summaries, search (the FTS triggers also fire on `alternative_hidden_at`), exports, Now, unread
counts, MCP previews and new shares. Historical reads (versions, the alternatives endpoint) use their own predicates and
show explicit deletes as deleted. Existing frozen shares are kept and marked "changed since shared". Integration tests:
repeated Retry, delete, rewind/version reads and reload.
