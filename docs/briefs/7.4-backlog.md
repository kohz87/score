# 7.4 Backlog — design v1 (2026-10-09)

Four independent items (PLAN 7.4). Each can ship alone; order: 7.4b, 7.4a, 7.4d, 7.4c.

## 7.4a Long rooms summarise themselves
**Goal:** a room whose context grows past a token threshold gets a summary so agents keep the thread without the whole
history. **Design:** Score never edits Hermes sessions for this. When the room's routed context for an agent (what
Score sends as "Room context") exceeds a threshold (default 12k tokens, Settings › Chat, off by default), Score asks the
room's lead agent for a summary with a fixed instruction, stores it as a `summary` message part (visible, labelled
"Summary of earlier messages", editable by the person), and from then on sends "summary + messages after it" as room
context. Costs model tokens, so: opt-in per room, the summary run is a normal run (shows in Flow/Reports), and the
person can regenerate or delete it. **Not:** Hermes `/compress` (session-level, not available through the API).
**Contract:** `MessagePart` `summary { coversUntil; text }`; `POST /api/rooms/:id/summary` (mutation); room setting
`autoSummary { enabled; thresholdTokens }`. **Risks:** a summary dropping an instruction — shown to the person, editable.

## 7.4b Pop-out window per agent
**Goal:** one agent's live view in its own small browser window. **Design:** route `/agents/:id/pop` with a compact
layout: the agent's lane (Now), current run (Flow node detail), its direct chat composer, Stop. Opened with
`window.open` (named per agent so a second click focuses it); same session cookie; no new server routes. Works as an
installed PWA window too. **Tests:** web unit + e2e opening the route directly.

## 7.4c Journey graph
**Goal:** see how the team changed over time: tasks done, memories added, skills created, per agent. **Design:**
read-only Reports tab "Journey": a time axis with one row per agent; marks for tasks completed (Score's task
projection), knowledge notes written (Score vault log), skills and memory changes. Skills/memory come from Hermes files
the adapter already reads for Team (`SOUL.md`, skills list, memory file mtimes) — no content, only counts and names, and
only through `hermes/`. New `GET /api/reports/journey?from&to` returning `{ agents: [{ id, events: [{ at, kind, label,
ref }] }] }` (bounded: 2,000 events, newest first). **Risk:** inferring memory changes from mtimes is coarse; label it
"memory changed".

## 7.4d Score as an MCP tool server for its agents
**Goal:** agents use Score through MCP (rooms, tasks, knowledge) instead of plugin-only tools. **Design:** Score serves
MCP over streamable HTTP on the **loopback bridge listener only** (`/bridge/mcp`, never the browser port). Each Hermes
profile gets its own MCP entry through `hermes mcp add` (argv, via the adapter, with the owner's OK per profile — it
writes Hermes config) pointing at that URL with a per-profile bearer token that Score stores hashed and the CLI stores in
Hermes's own MCP config. Tools (v1): `rooms.list`, `rooms.post` (as the calling agent, into rooms it is a member of),
`tasks.list`, `tasks.comment`, `knowledge.search/read/write` (same limits and switches as 6.4). Identity comes from the
token, never from tool arguments. No tool approves anything, reads other agents' sessions, or changes settings.
**Dependency:** an MCP server SDK (`@modelcontextprotocol/sdk`, MIT) — license check first. **Risk:** prompt-injected
agents posting to rooms: rate limits (30 posts/hour/agent), posts are marked as agent-authored, and the switch is per
agent and off by default.
