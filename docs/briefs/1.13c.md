## Hermes facts (verified in `../reference/hermes-agent` e97923c3 and spike L5)
- A Kanban worker runs `chat -q` with `HERMES_KANBAN_TASK=<task id>` and `HERMES_KANBAN_RUN_ID=<current_run_id>`
  (`hermes_cli/kanban_db_dispatch.py:2888-2909`). Unattended mode denies a dangerous terminal command **instantly**,
  with **no** approval hooks: `tools/approval.py:_unattended_deny` → `detect_dangerous_command(command)`; if dangerous
  and not `_is_permanently_approved(pattern_key)` → blocked. In single-query mode the block result also carries
  `pattern_key` and `description`. The tool result reaches `post_tool_call` as JSON text whose top-level `status` is
  `error` and nested `result` has `"status": "blocked"` and an `error` starting `BLOCKED: Command flagged as dangerous`.
- After the pattern check, **Tirith** still runs (`check_command_security`), so a granted command can still be blocked.
- `approve_permanent(pattern_key)` adds to the in-memory permanent set (`_permanent_set()`, under `tools.approval._lock`,
  a plain `threading.Lock`); there is **no remove function**. Persisting is a separate `save_permanent_allowlist` step
  that must never be called. `_is_permanently_approved` checks aliases (`_approval_key_aliases`).
- `pre_tool_call` fires before the tool's guard check on the normal (sequential) path; spike L5 granted this way.
- **Terminal batches** (`agent/terminal_approval_batch.py`): when the model emits several terminal calls in one turn,
  each slot's `prepare()` runs `_check_all_guards` **during preparation, before that call's `pre_tool_call`**, in a
  context where `agent.terminal_approval_batch._slot` is set. A grant active during another slot's preparation could
  approve a different command with the same pattern.
- CLI: `hermes kanban unblock --reason <text> <task_id>` (records the reason as a comment, then unblocks);
  `hermes kanban comment --author <name> <task_id> <text>`.

## Design (from the lead; follow it)

### Feature flag
Off by default. Server config `SCORE_KANBAN_GRANTS=1` (zod, in `config.ts`) **and** the compatibility gate not
disabling `kanban-grants` → hello returns `enabled.kanbanGrants = true` for producers with a `kanbanTaskId` and
`isolation === 'in_process'` and the private APIs below resolved. Otherwise Kanban denials still become **view-only**
approvals (diagnostics) and nothing is redeemable.

### Plugin (`hermes-plugin/score_bridge/grants.py` + `hermes_private.py`)
1. **Private boundary** additions (each fail-closed: missing internals → feature unavailable):
   `detect_dangerous(command) -> (bool, pattern_key|None)`; `is_permanently_approved(pattern_key) -> bool`;
   `add_permanent(pattern_key)` (calls `approve_permanent`); `discard_permanent(pattern_key)` (under
   `tools.approval._lock` acquired with a 50 ms timeout, `_permanent_set().discard(pattern_key)`; returns False if the
   lock wasn't acquired); `in_terminal_batch() -> bool` (`agent.terminal_approval_batch._slot.get() is not None`; any
   doubt → True). Report these in `privateApis`.
2. **Denial report** (on the hook thread inside the existing `post_tool_call` capture, kanban worker only, i.e.
   `HERMES_KANBAN_TASK` set): decode the nested result JSON; the denial is **verified** only if the tool is the
   terminal tool, nested `status == "blocked"`, its `error` starts with `BLOCKED: Command flagged as dangerous`, and
   `detect_dangerous(raw command)` returns dangerous with the same `pattern_key` as the result (when the result has
   one). Then add `kanbanDenial: { patternKey, commandDigest, taskId, runId }` (runId from `HERMES_KANBAN_RUN_ID`, an
   integer) to the payload. Any other block → no `kanbanDenial` (the server keeps it as a diagnostic).
3. **Redeem** (on the hook thread inside `pre_tool_call`, synchronously, bounded): only if `enabled.kanbanGrants` for
   this producer, the tool is the terminal tool, the raw command is dangerous per `detect_dangerous`, the pattern is
   **not** already permanently approved, `in_terminal_batch()` is False, and **no other tool call is in flight** in
   this process (a process-wide in-flight set of `tool_call_id`s maintained by `pre_tool_call`/`post_tool_call`,
   bounded at 256; any doubt → in flight). Then `POST /bridge/v1/grants/redeem {taskId, taskRunId, commandDigest,
   toolCallId}` with a 1 s total timeout. On `200 {grantId, patternKey}`: require `patternKey` == the local pattern;
   `add_permanent(patternKey)`; record the active grant `{grantId, patternKey, toolCallId, added: True}`. Any error →
   no grant.
4. **Revoke**: while a grant is active, any other `pre_tool_call` in the process (different `tool_call_id`) first
   discards the pattern and marks the grant revoked (consume `revoked`, sent asynchronously by the sender thread).
5. **Consume**: at the grant call's `post_tool_call`, discard the pattern **before** anything else, then consume
   `{toolCallId, outcome}`: `executed` if the result isn't blocked, `blocked` if it is (e.g. Tirith). Consume calls go
   through a small queue on the sender thread with retries (they must not block hooks). If `discard_permanent` fails
   (lock timeout), retry from the sender thread until it succeeds; log an error code.
6. Fork: clear the active grant and in-flight set in the child (the child never inherits a grant); `at exit`/unload:
   discard any active pattern.
7. Never call `save_permanent_allowlist` or write config.

### Server
- **Migration `0006_grants.sql`**:
  ```sql
  CREATE TABLE kanban_grants (
    id TEXT PRIMARY KEY,
    approval_id TEXT NOT NULL UNIQUE REFERENCES approvals(id),
    profile TEXT NOT NULL,
    task_id TEXT NOT NULL,
    eligible_after_run_id INTEGER NOT NULL,   -- the blocked attempt; only a later run may redeem
    command_digest TEXT NOT NULL,
    pattern_key TEXT NOT NULL,
    state TEXT NOT NULL CHECK (state IN ('staged','redeemed','consumed','revoked','expired','unknown')),
    outcome TEXT CHECK (outcome IN ('executed','blocked','revoked')),
    producer_id TEXT, tool_call_id TEXT,      -- bound at redeem
    expires_at TEXT NOT NULL,                 -- staged + 2 h
    redeemed_at TEXT, consumed_at TEXT,
    created_at TEXT NOT NULL, updated_at TEXT NOT NULL
  ) STRICT;
  CREATE INDEX kanban_grants_task ON kanban_grants(task_id, state);
  CREATE UNIQUE INDEX approvals_kanban_denial ON approvals(kanban_task_id, kanban_run_id, command_digest)
    WHERE target_kind = 'kanban_grant';
  ```
- **Approval from a denial** (`domain/grants.ts`, called from the bridge translate for `post_tool_call` with
  `kanbanDenial`, inside the ingest transaction): the producer's `kanban_task_id` must equal `kanbanDenial.taskId`.
  Create (or find by the unique index) a visible row: `origin 'kanban'`, `stage 'human'`, `target_kind
  'kanban_grant'`, `kanban_task_id`, `kanban_run_id = runId`, `command`/`command_digest`/`pattern_keys` from the
  event, `choices ['once','deny']` ("always" lives in Settings later), `surface 'kanban'`, `expires_at = created + 2 h`.
- **Actionable** (extend 1.14b's rule for `kanban_grant`): the feature flag and gate are on; reading `kanban.db`
  (read-only, existing readers): the task is `blocked`, its `current_run_id` equals `kanban_run_id` or its latest run is
  that run (no newer attempt), its assignee equals the row's profile, and it is not in `triage`; no delivery exists.
- **Decision** (route `'kanban'`: add it to `approval_deliveries.route` in 0006 via a table rebuild, or a new
  `kanban_decisions` table if a rebuild is awkward; explain your choice):
  - `once`: in one transaction insert the grant (`staged`, `eligible_after_run_id = kanban_run_id`, expiry 2 h) and the
    delivery `intent`. The dispatcher revalidates the task (as for actionable, plus `task_events` max id unchanged
    since the approval was created — store it on creation), then runs `hermes kanban unblock --reason "Approved once in
    Score: <redacted command, ≤ 200 chars>" <task_id>` via a new `hermes/live/cli.ts` (`execFile`, args array, 30 s
    timeout, `HERMES_HOME` from config, stdout/stderr never stored, exit code only). Exit 0 → delivery `applied`
    (`decision_by 'you'`); revalidation fails → delivery `failed` and the grant `expired`; CLI error → `failed` with
    `maybe_applied` per the 1.14b monotone rule (an unblock may have happened: re-read the task; if it's no longer
    blocked, treat as applied).
  - `deny`: `hermes kanban comment --author score <task_id> "Denied in Score: …"`; the task stays blocked; delivery
    `applied` on exit 0.
- **Redeem** `POST /bridge/v1/grants/redeem` (producer token; the token's `kanban_task_id` must equal `taskId`, else
  404 `no_grant` with the same body as a missing grant): find a `staged` grant for the task with the same
  `command_digest`; 409 `not_eligible` if expired, `taskRunId <= eligible_after_run_id`, or not staged; else `redeemed`,
  bound to producer and `toolCallId`, in one transaction; respond `{grantId, patternKey}`. Exactly one redeem can win
  (version check).
- **Consume** `POST /bridge/v1/grants/:grantId/consume {toolCallId, outcome}` → 204: only the producer and tool call
  that redeemed it; `executed|blocked` → `consumed` with outcome; `revoked` → `revoked`. Idempotent for the same
  outcome; the approval row gets `tool_outcome`.
- **Sweeps** (with the existing timers): `staged` past `expires_at` → `expired`; `redeemed` without consume for 10
  minutes, or whose producer hasn't been seen for 2 minutes → `unknown` (needs a human; the approval shows it);
  a task now in `triage` or archived → its `staged` grants `expired`.
- Contract: these endpoints already exist in §11; add `BridgeGrantRedeemResponseSchema` if missing, mirroring §11
  exactly. Don't change §11's shapes.
