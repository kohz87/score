## Hermes facts (verified, including the design review's corrections)

- Kanban workers run `chat -q` with `HERMES_KANBAN_TASK=<task id>` and `HERMES_KANBAN_RUN_ID=<current run id>`.
- Unattended mode denies a dangerous terminal command instantly with **no** approval hooks. The `post_tool_call` event's
  envelope has `status: error`; its `result` is JSON **text** that decodes directly to an object with
  `"status": "blocked"` and an `error` starting `BLOCKED: Command flagged as dangerous`. The terminal denial **drops**
  `pattern_key`/`description`, so recompute with `tools.approval_detection.detect_dangerous_command(command)` →
  `(is_dangerous, pattern_key, description)` on the **raw** command from the tool args.
- Tirith blocks (`check_command_security`) and `execute_code` denials have different texts: they are not verified
  denials.
- CLI: `hermes kanban unblock --reason <text> <task_id>` (records the reason as a comment, then unblocks; fails when the
  task isn't blocked/scheduled); `hermes kanban comment --author <name> <task_id> <text>`. Use `-p <profile>` only if
  the existing live code does for kanban (kanban.db is shared; check `apps/server/src/hermes/live/paths.ts`).

## Design (from the lead; follow it)

1. **Plugin** (`hermes_private.detect_dangerous(command)` + capture in the existing `post_tool_call` path, hook thread,
   bounded, fail-open): only when `HERMES_KANBAN_TASK` is set and the tool is the terminal tool; decode the result JSON
   (≤ 16 KB, else skip); verified iff decoded `status == "blocked"`, `error` starts with the text above, and
   `detect_dangerous(raw command)` says dangerous. Add `kanbanDenial: {patternKey, commandDigest, taskId, runId}`
   (`runId` = int from `HERMES_KANBAN_RUN_ID` or null) to the payload. Anything else → no field.
2. **Server card** (`domain/kanban-denials.ts`, called from the bridge translate for `post_tool_call` with a valid
   `kanbanDenial`, inside the ingest transaction; zod-validate the field): the producer's `kanban_task_id` must equal
   `taskId` (else ignore + metric). Create (or find) a visible approval row: `origin 'kanban'`, `stage 'human'`,
   `target_kind 'none'`, `kanban_task_id`, `kanban_run_id`, `command` (redacted), `command_digest`, `pattern_keys
[patternKey]`, `choices []`, `surface 'kanban'`, `description` = "Blocked in unattended mode: Hermes asks nobody
   for dangerous commands in Kanban workers.", `blocking` = "Task <id> is blocked", `refs [{kind:'task', taskId}]`,
   `expires_at` = null (closed by the task, not by time). Dedupe with a unique index on `(kanban_task_id,
kanban_run_id, command_digest) WHERE origin = 'kanban'` (migration `0006_kanban_denials.sql`). `actionable` is
   always false for these rows (no decision endpoint use; 409 as today).
3. **Closure**: a periodic check (the existing retention/sweep timer, live mode only) reads `kanban.db` read-only via
   the existing readers for tasks with open kanban rows; when the task is no longer `blocked` (unblocked, running, done,
   archived, triage), close the row with `closed_reason 'task_moved'` (status `withdrawn`). Add `task_moved` wherever
   closure reasons are enumerated.
4. **CLI runner** `apps/server/src/hermes/live/cli.ts`: `runHermes(args: string[], {timeoutMs})` → `{exitCode}` via
   `execFile('hermes', args, {timeout, env: minimal env + HERMES_HOME from config, maxBuffer small})`; never store or
   log stdout/stderr (log only the exit code and the verb); reject args containing NUL. Unit-test with an injected fake.
5. **Task actions** `POST /api/tasks/:taskId/actions` (contract §7 revised; `apps/server/src/http/tasks.ts`; H: human
   guard + CSRF like the approvals decision route): body zod `{action, text?}` (text ≤ 2,000 chars, required for
   `comment`, optional reason for `unblock`). Only `comment` and `unblock`; other actions → `501 not_implemented`.
   Through a new `HermesPort.taskAction({taskId, action, text})` → `{hermesStatus}`:
   - live: validate `taskId` format; read the task from `kanban.db` (404 if missing); `unblock` requires status
     `blocked` (else 409 with the current status); run `hermes kanban unblock --reason <text or "Unblocked in
Score"> <taskId>` or `hermes kanban comment --author score <taskId> <text>`; non-zero exit → re-read the task: for
     `unblock`, if it's no longer blocked return 409 `conflict` ("state changed"), else 502 `hermes_unavailable`; then
     re-read and return `{taskId, action, hermesStatus}`.
   - fake: keep an in-memory status per scenario task; same semantics.
     Redact `text` before it is passed to the CLI only for the exact gateway key (as 1.11a does for run input); never log
     it.
6. Remove any leftover grant code paths/flags (`kanbanGrants` stays in hello as `false`, reserved).
