# Task 3.13: Remote access mode (DRAFT design, pending adversarial review)

Owner decision (2026-10-08): reach Score from another machine over a private network (Tailscale/WireGuard) **and**
a plain LAN address. Today Score listens on 127.0.0.1 only; GETs and the SSE stream need no pairing (only mutations go
through `humanGuard`), the web origin is fixed (`SCORE_WEB_ORIGIN`), and Vite's dev server proxies /api.

## Draft design
- **Opt-in**: `SCORE_REMOTE=1` plus `SCORE_HOST=<address>` (a specific interface address, never 0.0.0.0 by default;
  `SCORE_HOST=0.0.0.0` only with an explicit `SCORE_REMOTE_ANY=1`). Loopback behaviour unchanged when off.
- **Pairing for everything** when remote is on: every /api route and /api/stream require a paired session cookie
  (except the pairing endpoints and a minimal status), for loopback clients too (simpler, no IP trust).
- **Host/Origin allowlist**: requests must carry a Host in an allowlist (configured addresses + loopback) to stop DNS
  rebinding; mutations keep the CSRF + Origin checks with the allowlist of web origins.
- **Pairing token delivery**: printed on the server console only (as today); single-use, short TTL; rate-limited pairing
  attempts; sessions revocable from Settings (list of paired browsers with last-seen).
- **TLS**: optional `SCORE_TLS_CERT`/`SCORE_TLS_KEY` (owner's certificate, e.g. Tailscale cert); cookies `Secure` when TLS;
  a persistent banner in the app and a console warning when serving plain HTTP beyond loopback.
- **Serving**: production-style serving of the built web app from Fastify for remote use (no Vite dev server exposed);
  or document that dev mode stays loopback-only.
- **Bridge endpoints** (hermes-plugin → server) stay loopback-only regardless.

## Questions for the review
Anything readable or actionable without pairing in remote mode (stream, media, health, static assets, error pages)?
Cookie flags/SameSite over plain HTTP on a LAN; session fixation; pairing brute force; DNS rebinding; CORS; the
bridge endpoints; WebSocket/SSE auth; Vite dev server exposure; what a LAN attacker can do with a sniffed cookie and
how to limit it (bind cookie to client address? short idle timeout?). Minimal safe design for each.
