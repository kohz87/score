# Task 3.12: Profile management (DRAFT design, pending adversarial review)

Owner request (2026-10-08): "the score should allow me to create and manage the profile". Team page: Add agent, rename,
edit description, delete. Hermes 0.21.5 CLI: `hermes profile create <name> [--clone | --clone-from SRC | --clone-all]
[--description D] [--no-alias] [--no-skills]`, `profile rename OLD NEW`, `profile describe`, `profile delete -y NAME`,
`profile export NAME -o FILE`, `profile import`, `plugins install|adopt|enable`, `gateway start|stop|status`.

## Draft design
- **Create** (H): name (Hermes profile-name rules), role/description, start from blank / clone config+SOUL+skills from an
  existing agent (`--clone-from`, never `--clone-all`, never `--clone-channels`), model, color+shape (Score's own
  agent_style). Steps, recorded as an idempotent intent with per-step state so a failure can resume or roll back:
  1. `hermes profile create <name> [--clone-from SRC] --description D --no-alias`.
  2. Fresh per-profile API key (Score generates it; `hermes -p <name> config set API_SERVER_KEY <key>`; copy kept in
     `~/.score/hermes-keys/<name>` 0600). A clone copies the source's `.env`, so the key MUST be replaced.
  3. Bridge plugin: install/enable `score_bridge` for the profile (mechanism to be decided by this review: Hermes
     `plugins` verbs vs a link in `<profile>/plugins/` — the latter is a file write outside D2.6).
  4. Model: `config set model.default/provider` (existing 2.16 path).
  5. Gateway: start the profile's API server so Score can drive it (mechanism per Hermes: service vs `gateway run`).
  6. Score refreshes profiles; agent.upserted.
- **Rename** (H): `hermes profile rename OLD NEW`; Score migrates its own rows (agent_style, rooms membership, overrides,
  key file) in one transaction after the CLI succeeds.
- **Describe** (H): `hermes profile describe NAME --set …` (check verb).
- **Delete** (H): typed-name confirmation; refuse the default profile and any profile with running work; first
  `hermes profile export NAME -o ~/.score/profile-backups/<name>-<ts>.tar.gz` (must succeed), then stop its gateway,
  then `profile delete -y NAME`; Score archives its rows (messages stay, agent shown as "removed").
- Live tests only on throwaway test profiles (never the owner's real ones).

## Questions for the review
Which Hermes facts above are wrong? Is the clone path safe (what else does `--clone-from` copy: secrets, bot tokens,
allowlists, memories, sessions)? Plugin install mechanism within the D2.6 rule? Export contents (does it include
.env secrets? where may Score store it)? Rename side effects (identity migration, running gateway, kanban assignees)?
Partial-failure handling and idempotency. Anything that lets a click do more than the person confirmed.
