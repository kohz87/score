## Flow
1. **Watching** (state `running`, no `control`): "Read-only" pill and a **Take over…** button.
2. **Confirm** (inline light card, `data-protected`): the three bullet points from the mock-up, the security password
   field, **Take over**, "Use a passkey instead", Cancel. Take over posts `POST /api/agents/:id/bot-screen/take-over`
   `{ password }` (with the usual idempotency key and web-client header, as other password posts do, e.g. the Hermes
   update start). A session already unlocked (Remote access and security unlocked in the last 5 min) may send no
   password: try without first only if the security status says unlocked; otherwise ask. "Use a passkey instead" runs the
   same passkey unlock the Remote access and security lock uses, then posts take-over without a password. Errors in
   plain words from the response (`409` busy/not running, `503`/`502`).
3. **In control** (`status.control` present): red frame around the screen, red "You have control" pill
   (`data-protected`), **Hand back to builder**, the idle countdown, **Type text…**, a **Ctrl+Alt+…** menu (Ctrl+C,
   Ctrl+V, Ctrl+L, Ctrl+A, Alt+Tab, Esc, Enter) and **Full screen** (`requestFullscreen` on the screen box). While in
   control poll the status and frame faster (about every 400 ms).
4. **Handed back** / **lost** / **someone else**: a status line as in the mock-up; `state: 'human'` without `control`
   reads "Someone else took over in the Hermes app…" (screen hidden).

## Input (the part to get exactly right)
- The screen image (`<img>` of the frame) sits in a focusable box (`tabIndex=0`, `role="application"`,
  `aria-label="builder's desktop: you have control"`). Keyboard input is captured only while that box has focus
  ("Click the screen to type into it"); clicking outside stops it.
- **Keys** → X11 keysyms, `keydown` = `down: true`, `keyup` = `down: false`, `preventDefault` both:
  printable `event.key` of one character: U+0020–U+007E and U+00A0–U+00FF → the code point; any other code point →
  `0x01000000 + codePoint`. Named keys: Enter ff0d, Backspace ff08, Tab ff09, Escape ff1b, Delete ffff, Insert ff63,
  Home ff50, End ff57, PageUp ff55, PageDown ff56, ArrowLeft ff51, ArrowUp ff52, ArrowRight ff53, ArrowDown ff54,
  F1–F12 ffbe–ffc9, Shift ffe1, Control ffe3, Alt ffe9, Meta ffeb, CapsLock ffe5, ContextMenu ff67. Anything else:
  ignore. Put the mapping in a pure module with unit tests.
- **Pointer**: position in screen pixels = `floor((clientX − rect.left) × width / rect.width)` (same for y), clamped.
  Button mask: left 1, middle 2, right 4; wheel up = 8, wheel down = 16, each sent as press then release. Move events
  only while a button is down or at most every 50 ms otherwise. Prevent the context menu on the box.
- **Phone**: tap = left click; press and hold (≥ 500 ms) = right click; one-finger drag = wheel scroll; a **Keyboard**
  button focuses a visually hidden text input whose `input` events are sent as key presses (and Backspace).
- **Type text…**: a small field; Send types each character as a down+up pair.
- **Batching**: collect events and `POST …/bot-screen/input` every 50 ms (max 200 per post). **Never retry a batch**;
  a `409` means control is gone: stop sending, refetch the status, show the lost state.
- **Heartbeat** `POST …/heartbeat` every 10 s while in control. **Hand back** on the button, on `pagehide`, and on
  `visibilitychange` to hidden (use `fetch(..., { keepalive: true })` with the web-client header; `sendBeacon` can't
  set it), and when the component unmounts.
- **Idle countdown**: 5:00 after the last input this page sent (local clock, reset on each sent batch), not from the
  server's timestamps.
- Never log or store typed text or events (no console logging, no localStorage).
