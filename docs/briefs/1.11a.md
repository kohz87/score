**Migration `apps/server/migrations/0003_runs.sql`** (exactly this):

  score_turn_id TEXT UNIQUE,
  credential_generation INTEGER,

  model TEXT,
  started_at TEXT NOT NULL,
  ended_at TEXT,
  input_tokens INTEGER,
  output_tokens INTEGER,
  cost_usd REAL,
  last_seq INTEGER,                  -- last upstream run-SSE seq applied
  tools_used TEXT NOT NULL DEFAULT '[]',
  output TEXT,                       -- redacted, ≤ 8 KB
  error TEXT,                        -- redacted, ≤ 2 KB

  updated_at TEXT NOT NULL

CREATE INDEX runs_profile_status ON runs(profile, status);
CREATE TABLE tool_calls (
  run_id TEXT NOT NULL,
  seq INTEGER NOT NULL,              -- upstream seq of tool.started

**Credentials** (`hermes/live/credentials.ts`): `readKey(scoreHome, profile)` reads
`<scoreHome>/hermes-keys/<profile>`, refusing a file whose mode allows group or other access (must be 0600/0400) or
whose owner isn't the current user. It returns the trimmed key and a `keySha256`. `ensureGeneration(db, profile,
keySha256)`: inserts generation 1, keeps the generation if the sha is unchanged, increments if it changed. A missing
key file → typed `CredentialsUnavailable` (the profile shows "credentials unavailable"). Never log or return the key
outside the HTTP client.

**Gateway client** (`hermes/live/gateway.ts`), base URL from config `SCORE_HERMES_URL` (default
`http://127.0.0.1:8642`; put the default inside the adapter like the Hermes home). Every call goes to
`/p/<profile>/…` with `Authorization: Bearer <key>` (profile validated by `ProfileNameSchema`; for `default`, use the
unprefixed path):

- `startRun({ profile, input, sessionId?, model? }, idempotencyKey)` → `POST /v1/runs` with `Idempotency-Key`;
  returns `{ runId, replayed }` (202 body `{ run_id, status, replayed }`).
- `getRun(profile, runId)` → `GET /v1/runs/<id>` (body fields per the spike: `status`, `created_at`, `updated_at`,
  `session_id`, `model`, `output`, `error`, `last_event`, `usage?`).
- `stopRun`, `steerRun(input)`, `submitApproval({ runId, choice, requestId? })` → POST endpoints. Map 409
  `approval_not_pending` to `'not_pending'`.
- `capabilities(profile)` → `GET /v1/capabilities`; `health()` → `GET /v1/health` (no auth).
- `runEvents(profile, runId, lastEventId?)` → `connectSse(...)` from `sse-client.ts`.
- All bodies zod-validated. Timeouts: 10 s for JSON calls. Errors: typed `HermesHttpError(status, code)` without
  bodies that could echo secrets.

**Command intents** (`hermes/live/intents.ts`), using the existing `command_intents` table: `startRunIntent` writes an
intent (`kind: 'start_run'`, `idempotency_key = turnId`, payload without the key) **before** calling Hermes, then
marks it `accepted` (with `result = run_id`) or `failed`/`unknown`. `recoverIntents()` on startup re-sends `pending`,
`sent` and `unknown` start-run intents with the **same** Idempotency-Key. Hermes replays the original run
(`replayed: true`), so a crash between sending and recording never creates a second run.

**Run following + translate** (`hermes/live/runs.ts`, `hermes/live/translate.ts`): after `startRun`, follow the
run's SSE with `resumableSse`. Each upstream event becomes one `Observation`:

- `source: 'run-sse:<profile>'`, `identity: 'sse:<runId>:<seq>'`,
  `checkpoint: { scope: 'run:<runId>', position: seq, incarnation: '<profile>:g<credentialGeneration>' }`.
- `apply` updates projections with `guardedUpsert` (lifecycle `queued → running → waiting_for_approval →
completed | failed | cancelled | interrupted`; terminal states final; `versionColumn: 'version'`) and returns
  drafts:
  - `tool.started` → insert a `tool_calls` row (status `running`, redacted preview) and a `log.line` (kind `tool`).
  - `tool.completed` → complete the **latest running** `tool_calls` row with the same `tool` in that run (the run
    SSE has no tool_call_id; tools in one run are sequential), with status `ok`/`error`, `duration_ms` and a redacted
    `result_preview`; also a `log.line`.
  - `approval.request` → `run.status = waiting_for_approval` + `log.line` (kind `approval`). The approvals ledger
    arrives in task 1.14, so don't create approvals here; keep the raw request in a comment-free, redacted
    `log.line` text.
  - `approval.responded` → status back to `running`.
  - `message.delta`, `message.interim`, `reasoning.available` → no projection change for now (rooms come in Phase 2);
    return no drafts, but still ingest the observation so the checkpoint advances.
  - `run.completed | failed | cancelled | interrupted` → terminal status, `ended_at`, tokens from `usage`, redacted
    `output`/`error`.
  - Every change to `runs` also emits `run.updated` with the contract `RunSummary` built from the projection
    (`agentId` = profile, `toolsUsed` from distinct tools, `gaps` from the `gaps` table for that run).
  - Unknown upstream event names → counted in a metric and ingested with no drafts (never fatal).
- **Recovery** (D2.4): if the SSE ends without `: stream closed`, `resumableSse` gives up, or it gets a permanent
  4xx (404 after a gateway restart), switch to polling `getRun` every 2 s until terminal (max 30 min). Insert a
  `gaps` row (`source = 'run-sse:<profile>'`, `run_id`, from = last applied event time, to = now, `reason`), emit
  `gap.recorded`, and apply the terminal status from the polled run as one observation
  (`identity: 'run_status:<runId>@<status>'`).
- Runs not started by Score aren't followed here (the bridge covers them later).

**Redaction** (`apps/server/src/redact.ts`, D6 layer 2, used by translate): replace secret-shaped substrings with
`[redacted]` **before** truncation. Bearer tokens, `sk-…`/`sk-or-…` style keys, `ghp_`/`github_pat_` tokens, AWS
access keys (`AKIA…`), `-----BEGIN … PRIVATE KEY-----` blocks, `password=`/`token=`/`api_key=`/`secret=` values in
query strings, env-style assignments and JSON, and generic 32+ char base64url/hex runs following
`key|token|secret|password` labels. Pure function with table-driven tests.

**LivePort** (`hermes/live/live-port.ts`) now implements `startRun` (via intents + following), `stopRun`, and
`status()` from `health` + `capabilities` (cached 30 s) plus the profiles served (from
`<hermesHome>/gateway_state.json` `served_profiles`, read-only, zod-validated; it holds no secrets). `listAgents()`
returns one `AgentSummary` per served profile that has a key file (`served: true`), with neutral default styles by
index (lead/builder/reviewer/designer palette order) until Score-owned agent styles exist. `deliverDecision` stays
unimplemented (1.14). `start(sink)` runs `recoverIntents()` and re-follows non-terminal Score-started runs from
`runs.last_seq`.

## ARCHITECTURE D2.3–D2.6

**D2.3 Canonical producers and stable identities.**

| Domain fact               | Canonical source                                     | Others (enrich/reconcile only)                                         | Stable identity                                          |
| ------------------------- | ---------------------------------------------------- | ---------------------------------------------------------------------- | -------------------------------------------------------- |
| Tool call lifecycle       | Bridge `pre/post_tool_call` (`tool_call_id`)         | `state.db` rows (`tool_call_id`), run SSE `tool.*` (no `tool_call_id`) | `(profile, session_id, tool_call_id)`                    |
| Score-started run status  | Runs API (`GET /v1/runs/{id}` + SSE terminal events) | bridge session hooks                                                   | Hermes `run_id`                                          |
| Run text/reasoning stream | run SSE `message.*` / `reasoning.available`          | bridge `on_interim_message`                                            | `(run_id, seq)`                                          |
| Approval (Score run)      | run SSE `approval.request` (has `request_id`)        | bridge approval hooks                                                  | `(profile, session_key, request_id)`                     |
| Approval (gateway)        | bridge (exact `request_id`, D4)                      | —                                                                      | `(profile, session_key, request_id)`                     |
| Kanban task state         | `kanban.db` `tasks` + `task_events` (append-only)    | bridge `on_kanban_*`                                                   | `task_events.id`, `task_runs.id`                         |
| Session messages          | `state.db` `messages`                                | bridge                                                                 | `(profile, db_incarnation, messages.id)` + `message_uid` |

**Observation identity ≠ entity identity** (from the 1.4a review). The ingest key `(source, identity)` names one
immutable _observation_, not the entity it's about. Each source namespaces its keys by kind, so different tables can
never collide:

- Immutable redeliveries use the upstream event's own ID: `task_event:<id>`, `sse:<run_id>:<seq>`,
  `bridge:<incarnation>:<counter>`.
- Observations of **mutable** state add a revision: `task_run:<id>@<status>:<ended_at>`,
  `message:<uid>@<active>:<compacted>`, `run_status:<run_id>@<status>`. A changed entity therefore produces a new
  observation, not a dropped duplicate.

Projections key on the entity ID. Their `versionColumn` guard (`guardedUpsert`) rejects stale writes. A producer
that sees a conflicting payload for an immutable key logs it as a source fault; it doesn't overwrite.

Bridge events carry `(producer_incarnation, counter)`; the unique ingest key makes re-delivery harmless.
**Terminal-state guards:** a delayed observation can't move a finished run, approval or tool call back to an
earlier state. Upstream cursors are persisted per source: SSE `seq` per run, `task_events.id`, `messages.id` per
DB incarnation, bridge counters per producer.

**D2.4 Recovery per source.**

- **Run SSE**: resume with `Last-Event-ID`. On `replay.truncated` or a gateway restart, poll `GET /v1/runs/{id}`,
  reconcile tools and messages from `state.db`, and record a visible **gap interval** on the run.
  `run.queued`/`run.started` are **not** emitted by the Runs API, so lifecycle starts from Score's own dispatch
  record plus status polling.
- **Bridge**: a bounded on-disk **spool** per producer (`~/.score/spool/`, size-capped, oldest dropped, with a
  drop counter) when Score is unreachable. It drains on reconnect, and dropped ranges become gap intervals.
- **kanban.db**: tail `task_events` by `id` (append-only). Re-read `tasks` rows touched by new events.
- **state.db** (per profile): ingest new rows by `messages.id` > checkpoint, scoped to a DB incarnation
  (file identity + `state_meta`). Hermes inserts carried/cloned rows with **older timestamps** and orders by ID,
  so timestamps are never a cursor. Edits, `active`/`compacted` flips, rewinds and compaction create or change rows
  without new IDs, so a periodic **session reconciliation** compares logical identities (`message_uid`,
  `tool_call_uid`) for sessions active in the last N hours. Fixtures cover rewind, compaction, carried timestamps
  and restore.

**D2.5 Per-profile wiring and credentials.** Every profile has its own `state.db` and its own `API_SERVER_KEY`
(SPIKE L3). Score stores keys in `~/.score/hermes-keys/<profile>` (0600) with a **credential generation**. Run
mappings record the generation they were admitted under, because Hermes scopes run ownership by profile + key.

- **Adoption** of an existing profile is explicit (owner action).
- **Rotation** = stop new admissions for that profile → drain its runs and approvals → rekey → bump the generation.
- A **missing key** marks the profile "credentials unavailable" and is never silently regenerated. Runs admitted
  under a lost key are uncontrollable, and the UI says so.

**D2.6 Writes.** Hermes SQLite is never written.

- **CLI or gateway API** (`execFile`, argument arrays, timeouts, parsed output) for Kanban, config, profiles,
  skills and cron. Every Hermes-side create goes through a **command intent** (outbox, D5) with a stable
  idempotency key (`Idempotency-Key` on `/v1/runs`, `--idempotency-key` on `kanban create`). After a crash, Score
  reconciles acceptance before retrying or attaching results.
- **Exception: `SOUL.md` and `AGENTS.md`** in a profile directory. No CLI command edits them (`hermes profile`
  has none). The adapter writes exactly these two files: path-checked inside `<profile home>`, etag = sha256 of the
  current content, write temp + fsync + rename. Never `.env`, `auth.json`, `config.yaml` or anything else.

## ARCHITECTURE D6

### D6. Watch = event replay, not remote desktop

- Frames come from the bridge's `pre/post_tool_call` (terminal command + output tail, file path + unified diff from
  patch/write args, browser screenshots or artifact refs) and from interim/reasoning text. They are stored per
  session in `watch_frames` (64 KB per terminal chunk; images in `~/.score/media/` with a quota). Scrub = `seq` order.
- **Mandatory redaction (two layers).** Hermes hooks pass **raw** args and results (`model_tools.py:680`), and
  gateway approval text is redacted only if the user hasn't disabled redaction. So:
  1. the bridge runs `redact_sensitive_text(…, force=True)` on every command, argument and result **before
     truncation and before serialization**;
  2. the server runs its own secret-pattern pass before durable storage.

  Correlation uses digests computed in the plugin on raw text, never stored raw text. Fixtures include
  secret-bearing commands and outputs for every producer.

- "Take control" is **out of scope for v1**. v1 offers "Pause <agent>" and "Open in terminal" (copies the
  `hermes -p … --resume` command).
