## Task (from docs/PLAN.md)

**1.4c Ingest-key retirement** · Codex (added after the 1.4a review)

- Goal: keep `ingest_keys` from growing forever without re-enabling duplicates. Per source, retire keys strictly below a durable acknowledged floor: the checkpoint position for monotonic sources; for bridge producers, the incarnation's acked counter after the producer is gone for longer than the spool lifetime. Keep a per-source floor row so anything at or below the floor is still rejected as a duplicate.
- Files: `apps/server/src/hub/retire.ts`, migration if a floor table is needed, tests
- Done when: after retirement, redelivery at or below the floor is still rejected; keys above the floor are untouched; retirement runs in bounded batches.
- Test: `pnpm --filter @score/server test -- retire`

## Design (from the lead; follow it exactly)

**Why.** `ingest_keys` dedupes observations by `(source, identity)` and grows forever. Deleting old keys naively would
let a late redelivery be applied twice. So keys are retired only below a durable **floor**, and the floor itself
keeps rejecting anything at or below it.

**Migration `apps/server/migrations/0002_ingest_floors.sql`** (exactly this; migrations are immutable once applied):

```sql
ALTER TABLE ingest_keys ADD COLUMN scope TEXT;
ALTER TABLE ingest_keys ADD COLUMN incarnation TEXT;
ALTER TABLE ingest_keys ADD COLUMN position INTEGER;
CREATE INDEX ingest_keys_position ON ingest_keys(source, scope, incarnation, position) WHERE position IS NOT NULL;
CREATE TABLE ingest_floors (
  source TEXT NOT NULL,
  scope TEXT NOT NULL,
  incarnation TEXT NOT NULL,        -- '' stands for a NULL incarnation (PK columns can't be NULL meaningfully)
  floor INTEGER NOT NULL,           -- every observation with position <= floor is a duplicate
  updated_at TEXT NOT NULL,
  PRIMARY KEY (source, scope, incarnation)
) STRICT;
```

**Ingest changes (`ingest.ts`)**:

- When an observation carries a `checkpoint`, store its `scope`, `incarnation` and `position` on the new
  `ingest_keys` row.
- Before inserting the key: if the observation has a checkpoint and `ingest_floors` has a row for
  `(source, scope, incarnation ?? '')` with `floor >= position`, treat it as a **duplicate** (same behaviour as an
  existing key: no apply, no events, checkpoint advance rules unchanged). This check must be in the same
  transaction as the insert.

**Retirement (`apps/server/src/hub/retire.ts`)**:
`retireIngestKeys(db, { keepPositions = 10_000, batchSize = 5_000 })`:

- For each `ingest_checkpoints` row `(source, scope, cursor, incarnation)`: target floor
  `T = cursor - keepPositions`. Skip if `T < 0` or `T <= current floor`.
- **Never retire past a failure hold.** The ingest instance's in-memory holds mean "position X failed and must
  stay re-appliable". Expose `heldPositions(source, scope): number[]` from the `Ingest` and lower T to
  `min(T, minHeld - 1)`. The checkpoint can't pass a hold anyway, but make it explicit and tested.
- In batches (each batch its own `db.tx`): delete `ingest_keys` rows for that source, scope and incarnation with
  `position <= T` (`LIMIT batchSize` via `rowid IN (SELECT ...)`). After the last batch, upsert
  `ingest_floors(..., floor = T)`. The floor must never decrease. If the process stops between batches, re-running
  is safe (idempotent).
- Rows with a NULL `position` (observations without a checkpoint) are **never** retired here.
- Keys of other incarnations of the same source and scope stay until a separate decision (out of scope). Retire
  only for the checkpoint's current incarnation.
- Return `{ retired: number, floors: number }` for logging.
- Schedule it from the existing hourly retention timer in `src/index.ts` (after `pruneEvents`), with errors logged.

**Observation identity ≠ entity identity** (from the 1.4a review). The ingest key `(source, identity)` names one
immutable _observation_, not the entity it's about. Each source namespaces its keys by kind, so different tables can
never collide:

- Immutable redeliveries use the upstream event's own ID: `task_event:<id>`, `sse:<run_id>:<seq>`,
  `bridge:<incarnation>:<counter>`.
- Observations of **mutable** state add a revision: `task_run:<id>@<status>:<ended_at>`,
  `message:<uid>@<active>:<compacted>`, `run_status:<run_id>@<status>`. A changed entity therefore produces a new
  observation, not a dropped duplicate.

Projections key on the entity ID. Their `versionColumn` guard (`guardedUpsert`) rejects stale writes. A producer
that sees a conflicting payload for an immutable key logs it as a source fault; it doesn't overwrite.

Bridge events carry `(producer_incarnation, counter)`; the unique ingest key makes re-delivery harmless.
**Terminal-state guards:** a delayed observation can't move a finished run, approval or tool call back to an
earlier state. Upstream cursors are persisted per source: SSE `seq` per run, `task_events.id`, `messages.id` per
DB incarnation, bridge counters per producer.
