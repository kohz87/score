# Brief 5.17a-1: Kanban attempts projection — stage 1 (core)

**Design:** `docs/briefs/5.17.md` — v5 (top), v5.1 amendments, and v4 §1–§10 where v5 does not replace them. The
design is approved (lead review `docs/reviews/2026-10-09-5.17-design-v5-lead.md`). Where this brief and the design
disagree, ask; don't guess.

## Stage 1 scope (this brief)

Server only, no web and no contract changes except new internal types. Build the projection, its ingestion and its
recovery rules, with the acceptance fixtures; consumers (Now, Flow, Reports, Team, notifications, `attempt.updated`,
`TaskRef`, `checks[].verdict`) are **stage 2** and must not change yet.

1. **Migration `0039_kanban_attempts.sql`** (0036–0038 are taken by 5.31, 5.30 and 5.32): `kanban_sources`,
   `kanban_histories` (with `event_alloc_mark`, `attempt_alloc_mark`, `event_cursor`, `baseline_cursor`,
   `fullpass_cursor`, state `active|paused|closed`, reason), `kanban_attempts` (v4 §4 columns plus `first_seen_open`,
   frozen evidence columns, `classification_basis`, `task_snapshot`, `observation_ended_at`, `deleted_upstream_at`),
   `kanban_pages`, `kanban_seen_events`, `kanban_associations`, `kanban_upgrade_links`. STRICT tables; `runs`,
   `message_runs` and the message/FTS triggers untouched.
2. **Reader** (`apps/server/src/hermes/live/kanban-attempts/`): bounded queries only (v5 §I): baseline/full-pass pages
   by primary key (≤ 200), open attempts by Score-known ids (`IN` batches of 200), recently closed by ids touched by the
   last tail events. Each capture is **one read transaction** (v5.1 #2) returning rows + `sqlite_sequence` marks +
   min/max probes. zod-validate every row.
3. **History policy** (v5 §A, v4 §1): normal maintenance vs contradiction vs insufficient evidence; frozen evidence
   compared only non-null to non-null; paused state; Hermes legacy-shape migration ⇒ new history.
4. **Classification** (v5 §B, v4 §3): proven / partial / synthetic exactly as written, with `classification_basis`
   stored; never reclassify an attempt that was seen open.
5. **Coordinator** (v4 §7, v5 §D): one per source, serializes captures; capture ids (UUID) persisted in
   `kanban_pages` inside the page transaction; per-event dedupe via `kanban_seen_events`; revisions and hashes inside
   the writer transaction; baseline/sweep/full-pass observations submitted without an event-retirement floor.
   `kanban_pages` retention 7 days (v5.1 #3) in the hourly pass.
6. **Observation-loss boundaries** (v5 §C): set `observation_ended_at` atomically when an open attempt disappears,
   its source pauses/unreadable, or its history closes.
7. **Kanban projection writer** (v4 §4): own operation; same-terminal refresh, `ended_unknown` → known terminal,
   terminal → open refused (contradiction).
8. **Legacy upgrade** (v5 §E as narrowed by v5.1 #1): snapshot inputs into `kanban_upgrade_links` in the migration's
   follow-up step; resumable; maps only with the narrowed proof; everything else unresolved. Receipts are **not** touched
   in stage 1 (stage 2 changes response shapes).
9. **Association pass** (v5 §G) for review edges of newly linked tasks.
10. A read-only domain function `listAttempts({ since, until, taskId?, agentId? })` returning attempts with all fields;
    stage 2 consumers will use it. No HTTP route yet.

Wire the coordinator into the live adapter's existing Kanban polling next to (not replacing) today's task projection,
behind `SCORE_KANBAN_ATTEMPTS=1` (default off) so stage 1 can merge without changing behaviour.
