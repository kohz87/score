## Design decisions (from the lead; follow these)

- **App factory**: `buildApp(options)` in `apps/server/src/app.ts` takes `{ config, logger? }` and returns the Fastify
  instance without listening. `src/index.ts` loads config, builds the app, listens, and prints the pairing URL.
  Keep the existing `GET /api/health`.
- **Config** (`src/config.ts`), validated with zod: `SCORE_HOME` (default `~/.score`), `SCORE_HOST` (default
  `127.0.0.1`), `SCORE_PORT` (default 8740), `SCORE_WEB_ORIGIN` (default `http://127.0.0.1:5173`), `SCORE_MODE`
  (`fake` | `live`, default `fake`). A pure `loadConfig(env)` function so tests pass their own env.
- **Error shape** (`src/errors.ts`): every error response is `{ "error": { "code", "message", "details"? } }`. Map zod
  validation failures to 400 `bad_request`, unknown routes to 404 `not_found`, unexpected errors to 500 `internal`
  (no stack or internal message in the body). Export an `HttpError` class with `(status, code, message, details?)`.
- **CSRF guard** (`src/auth/csrf.ts`): for `POST`/`PUT`/`PATCH`/`DELETE` under `/api/`, require header
  `X-Score-Client: web`. If an `Origin` header is present it must be in the allowlist (`SCORE_WEB_ORIGIN` plus the
  server's own `http://<host>:<port>`). Otherwise 403 `forbidden`. `/bridge/*` is not covered by this guard
  (bridge auth arrives in a later task).
- **Pairing** (`src/auth/pairing.ts`, `src/http/session.ts`):
  - At startup, `index.ts` creates a one-time **pairing token** (32 random bytes, base64url), valid 15 minutes, and
    prints `Pair this browser: <SCORE_WEB_ORIGIN>/pair#<token>` to stdout. Use the URL fragment, so the token never
    reaches server logs via a request line.
  - The server keeps only a sha256 hash of the token and compares in constant time (`crypto.timingSafeEqual`).
  - Each successful pairing invalidates that token. A new token is printed on every server start.
  - `POST /api/session/pair { token }` (CSRF-guarded): on success, create a session ID (32 random bytes), store
    only its sha256 hash, and respond `204` with
    `Set-Cookie: score_session=<id>; HttpOnly; SameSite=Strict; Path=/; Max-Age=2592000` (no `Secure`: localhost
    http). A bad, expired or reused token → 401 `pairing_failed`.
  - `GET /api/session` → `{ "paired": boolean }`.
  - `DELETE /api/session` (CSRF-guarded) → `204`, revokes the session, clears the cookie (`Max-Age=0`).
  - Sessions live behind a `SessionStore` interface with an in-memory implementation for now (task 1.3 adds SQLite).
    Sessions are lost on restart; that's acceptable for this task.
  - Parse and serialize cookies with a small local helper (no new dependency).
- **Human-decision guard** (`src/auth/human.ts`): a reusable preHandler (or route option) that requires a valid
  `score_session` cookie and returns 401 `not_paired` otherwise. Add one internal test-only route to exercise it,
  or test the preHandler directly; don't add product routes that aren't in the contract.
- **`GET /api/system`** (`src/http/system.ts`): returns a fake `SystemStatus` (mode from config,
  `hermes.reachable: false`, `agentIsolation: 'same_user'`), validated with `SystemStatusSchema` before sending.
- **Logging**: Fastify logger on in non-test runs. Redact `req.headers.cookie`, `req.headers.authorization` and
  `res.headers["set-cookie"]`. Never log tokens.

## Contract conventions

Conventions

- Base path `/api`. JSON in and out, UTF-8. Times are ISO-8601 strings (UTC). IDs are opaque strings.
- Every mutating request (`POST`/`PUT`/`PATCH`/`DELETE`) must send `X-Score-Client: web` (CSRF guard) and may send
  `Idempotency-Key`. Replays with the same key return the first response.
- Endpoints marked **H** are _human decisions_: they also require the paired session cookie (`score_session`,
  HttpOnly, SameSite=Strict, see §3). Without it they return `401 not_paired`. (ARCHITECTURE D7.1)
- Errors: HTTP 4xx/5xx with `{ "error": { "code": string, "message": string, "details"?: unknown } }`.
  Common codes: `bad_request`, `not_found`, `conflict`, `not_paired`, `hermes_unavailable`, `hermes_unsupported`,
  `feature_disabled` (compatibility gate), `forbidden`.
- Snapshot endpoints (marked **S**) return `asOfSeq: number`, read in the same transaction as the data. Each
  cached query keeps its own `asOfSeq` and applies only stream events with `seq > asOfSeq` (resync rules in §2).
- Lists are cursor-paginated: `?limit=50&cursor=<opaque>` → `{ items: T[], nextCursor: string | null }`.

## ARCHITECTURE D7 (security posture)

### D7. Security posture (single user, local first)

- **Network.** The server binds `127.0.0.1`.
- **Browser.** Mutations require `X-Score-Client` + same-origin (CSRF).
- **D7.1 Human decisions** (approval decisions, grants, rule changes, credential actions) additionally require a
  **paired browser session**. On first run the server prints a one-time pairing URL **to its own terminal**. The
  browser exchanges it for an HttpOnly, SameSite=Strict session cookie. The server stores only a hash, never in a
  file the bridge uses.
  - **Threat-model limit (owner decision 2026-10-06: accepted, option a):** agents run as the same OS user, so a determined agent with
    shell access could still read browser cookie stores or `~/.score`. Pairing stops casual or accidental
    self-approval and CSRF, not a hostile same-user process.
  - Real isolation means running agents in Hermes's sandboxed terminal backend (docker/ssh) or as a different
    OS user. Score shows the current isolation level on the Settings page.
- **Bridge identity.** The bootstrap secret `~/.score/bridge.token` only allows `POST /bridge/v1/hello`. Each
  producer then gets a short-lived **producer token** scoped to its profile, process incarnation and
  `HERMES_KANBAN_TASK`. It can post only its own events, receive only decisions targeted at its own approvals,
  and redeem only grants for its own task. Bridge tokens can't call `/api/*`.
- **Secrets.** Score never reads `~/.hermes/.env`, `auth.json` or key files. Payloads are redacted per D6.
