## Part A: bridge plugin tools (Python, `hermes-plugin/`)

New module `hermes-plugin/score_bridge/exchanges.py`, registered from `score_bridge/__init__.py` exactly like
`_register_knowledge` (a separate `_register_exchanges(ctx)` called right after it; failures swallowed).

- Toolset `score_exchanges`. Six tools, registered with `ctx.register_tool(name=, toolset=, schema=, handler=,
  description=)`:

  | Tool | Required args | Optional | Sends `action` |
  |---|---|---|---|
  | `score_handoff` | `capability`, `to`, `note` | `command_id`, `replaces` | `{"action":"handoff","to","note"}` |
  | `score_ask` | `capability`, `to`, `question` | `command_id`, `replaces` | `{"action":"ask","to","question"}` |
  | `score_review` | `capability`, `to`, `note` | `command_id`, `replaces` | `{"action":"review","to","note"}` |
  | `score_approve` | `capability`, `note` | `command_id`, `replaces` | `{"action":"approve","note"}` |
  | `score_send_back` | `capability`, `note` | `command_id`, `replaces` | `{"action":"send_back","note"}` |
  | `score_reply` | `capability`, `text` | `command_id` | `{"action":"reply","text"}` |

  `replaces` goes into the action object when given. Limits as the contract: `note`/`question` 1–4000 bytes UTF-8,
  `text` 1–8000 bytes, `to` 1–64 chars, `command_id`/`replaces` 1–64 chars `[A-Za-z0-9._:-]`, `capability` matches
  `^xtc_[A-Za-z0-9_-]{43}$`. No NUL characters in any string. Unknown arguments are refused. Validate locally (like
  `_validate` in knowledge.py; extend it for the byte limits and patterns), the server validates again.
- **Descriptions** tell the model, plainly: the capability is in the turn's instructions from Score and must be
  copied exactly; the action takes effect **when the turn ends**, and only if the turn completes; one routing action
  per turn (handoff/ask/review/approve/send_back), a second one needs `replaces` with the first one's command id;
  `score_approve` and `score_send_back` are only for the reviewer of an open review; `score_reply` marks the answer to
  a question you were asked (otherwise the whole final reply is the answer). Never put the capability in a note.
- **command_id**: when the model omits it, derive it deterministically:
  `"x" + sha256(capability + "\n" + canonical_json(action)).hexdigest()[:40]` where `canonical_json` is
  `json.dumps(action, sort_keys=True, separators=(",", ":"), ensure_ascii=False)`. So an exact repeat is idempotent.
- **Transport**: `POST <base_url>/bridge/v1/exchanges/action` with the producer token, body
  `{"capability", "commandId", "action"}` (camelCase `commandId`). Reuse the client logic of `KnowledgeClient.call`
  (hello, token refresh on 401, one process-wide client, `_allow_decisions = False`). Prefer a small generalisation
  (a shared base class or a `path` parameter) over copying it; `knowledge.py`'s behaviour and its tests must not
  change.
- **Result**: every handler returns a JSON string and never raises. A 200 answer is the `ExchangeReceipt`
  (`{status, commandId, action, code?, message}`); return it as `{"success": status == "staged", ...receipt}`.
  HTTP errors, Score not set up (`NotReady`) and unreachable Score map to `{"success": false, "error": "..."}` like
  knowledge.py does (wording: "Score is not reachable right now; the action was not sent.").
- **Tests** `hermes-plugin/tests/test_exchange_tools.py` (pytest, the fake transport in `tests/helpers.py`): six tools
  registered through the public `register_tool` with toolset `score_exchanges`; each tool's body on the wire (exact
  JSON, camelCase, `replaces` included only when given); derived command_id is stable for the same input and differs
  when any field differs; explicit `command_id` is sent as given; every validation refusal (missing arg, unknown arg,
  bad capability, byte limits with multi-byte text, NUL, bad command_id pattern) makes no HTTP call; receipt
  `staged` → `success: true`, `refused` → `success: false` with `code`; 401 → re-hello and retry once; Score down →
  error JSON, no raise; `register` in `__init__` still registers knowledge tools when exchange registration fails and
  vice versa. Run with `cd hermes-plugin && uv run pytest -q`.

## Part B: `score-action` block parser (TypeScript, `apps/server/`)

New file `apps/server/src/domain/exchanges/action-block.ts`:

```ts
export type ScoreActionBlock =
  | { kind: 'none' }
  | { kind: 'action'; action: ExchangeAction }
  | { kind: 'invalid'; notice: string }
export function parseScoreAction(sanitizedReply: string): ScoreActionBlock
```

- Same rule as `parseVerdict`: count opening markers ```` ```score-action ```` (an extra marker counts even when it is
  unterminated or malformed). Zero markers → `none`. Exactly one marker and exactly one complete block
  (```` ```score-action ```` + optional spaces/tabs + newline + body + newline + ```` ``` ````) whose body is JSON that
  passes `ExchangeActionSchema` from `@score/contract` → `action`. Anything else → `invalid` with a short, plain notice
  the thread will show, e.g. "Score ignored this reply's action: it had 2 score-action blocks." / "…: the
  score-action block wasn't valid JSON." / "…: the action wasn't valid (note is required)." The notice must never quote
  the block's content (it may contain anything).
- A pure function: no database, no imports from `hermes/`.
- Tests `apps/server/test/domain/action-block.test.ts` (Vitest): each of the six actions parses; `replaces` kept;
  zero blocks; two blocks; one complete block plus a stray opening marker; unterminated block; invalid JSON; unknown
  action; extra key (schemas are strict); byte limits with multi-byte text; CRLF line endings; a block inside other
  text before and after; a `score-verdict` block is not an action.
