## Design (from the lead; follow it)

`apps/server/src/hermes/live/fingerprint.ts`:

- `computeFingerprint(inputs)` → `{ id: string (sha256 hex, first 16 chars), parts }`, where `parts` is:
  - `codeVersion`, `codeSha`: from `<hermesHome>/gateway_state.json` (`code_version`, `code_sha`; zod-validated,
    read-only; the file holds no secrets);
  - `capabilities`: the sorted feature names that are `true` in `GET /v1/capabilities` `features` (via the existing
    gateway client);
  - `schemas`: `kanban` and `state` = sha256 of the **normalised schema SQL** of each DB (`SELECT type, name, sql FROM
sqlite_master WHERE sql IS NOT NULL ORDER BY type, name`, whitespace collapsed), read through `openReadOnly`.
    For `state.db` use the default profile's;
  - `bridge`: `null` for now (the bridge plugin handshake arrives in 1.13a; leave the field and a TODO);
  - `cli`: the output of `hermes --version` first line, via `execFile('hermes', ['--version'])` with a 5 s timeout
    (an argument array, never a shell); `null` if unavailable.
    Missing inputs become `null` parts, never throw.
- `apps/server/src/hermes/tested-fingerprints.json`: a list of `{ id, parts, testedAt, notes }`. Seed it with **one**
  entry: the fingerprint of the owner's live install as computed by a small script you add,
  `apps/server/scripts/print-fingerprint.ts` (prints JSON for the current machine; the lead runs it and pastes the
  result, since your sandbox may not see `~/.hermes`). Until then, put a placeholder entry with `"id": "unseeded"` and
  a note.
- `evaluateCompatibility(fingerprint, tested)` → `SystemStatus['compatibility']`:
  - exact `id` match → `{ fingerprint: id, tested: true, disabled: [] }`;
  - otherwise `tested: false`, plus `disabled` derived from which parts differ from the **closest** tested entry (most
    matching parts):
    - `codeSha`/`codeVersion` or `schemas` differ → disable `gateway-approvals` and `kanban-grants` (private-API and
      schema-dependent features);
    - a capability the adapter needs is missing (`run_submission`, `run_events_sse`, `run_status`, `run_stop`,
      `run_approval_response`) → also disable `score-runs`;
    - only `cli` differs → nothing disabled (informational).
  - Reads always stay enabled (degraded mode, D2.2).
- `LivePort.status()` computes the fingerprint on start and every 10 minutes (and when the gateway reconnects), and
  reports `compatibility` from `evaluateCompatibility`. Add a degraded reason
  `"Untested Hermes build: <codeVersion> (<codeSha first 8>)"` when untested.
- `HttpError(403, 'feature_disabled', …)`: export a helper `assertFeature(status, feature)` the routes will use later.
  `LivePort.startRun` uses it for `score-runs`.

## ARCHITECTURE D2.2

**D2.2 Compatibility gate (fingerprints, not semver).** All of Hermes 0.x shares major 0, so semver can't gate
anything. A **compatibility fingerprint** is: Hermes `code_version` + `code_sha` (from `gateway_state.json`),
`/v1/capabilities` features, a hash of the `kanban.db` / `state.db` schemas, the bridge handshake (plugin version,
`plugins.isolation` mode, which private functions resolved), and the CLI version. Score keeps a list of
**tested fingerprints** (recorded with fixtures). If the fingerprint is unknown, Score runs in a degraded mode:

- reads still work;
- Score-started runs are still controlled through the public Runs API;
- bridge-dependent actions (gateway approval answers, Kanban grants) are **disabled** and shown as such;
- a banner explains it.

Under `plugins.isolation: host` the bridge runs outside the gateway process, so in-process approval actions are
impossible. The handshake reports it and those features stay off. `translate.ts` is keyed by fingerprint.
Capabilities are not a complete inventory (e.g. `/api/jobs` exists despite `jobs_admin: false`), so endpoints are
also probed directly.
