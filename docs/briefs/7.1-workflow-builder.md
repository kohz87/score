# 7.1 Workflow builder — design v2 (2026-10-09)

v1 was not approved (`docs/reviews/2026-10-09-7.1-workflow-builder-codex.md`: 12 high, 7 medium). v2 replaces v1's
execution model and narrows v1 scope so every promise is one Score can keep. v1 text below is history.

## Scope of 7.1 v1 (what ships first)
- Steps are **Score-started room runs** of Hermes agents only (coding agents join after 7.2 ships and passes the
  runtime capability matrix below). **No Kanban-task steps** (Hermes can't stop one attempt; `--max-runtime` requeues).
- Results are **text** (the run's final assistant text, redacted, ≤ 32 KB). **No file artifacts** in v1: instructions
  may mention paths, but successors get only the text; the editor says so.
- No loops; `retry` counts per node (≤ 3).

## Runtime capability matrix
A step mode is allowed only if its runtime has all of: Score-started admission with a receipt, Stop by run id with
terminal evidence, a final-text source, spend per run (or "unknown" handled below). Hermes room runs: yes. Claude
Code / Codex (7.2): decided per CLI after 7.2's tests; until then not selectable.

## Executor (server-owned, single writer)
- The workflow executor in `domain/workflows/` is the **only** authority that admits work for a workflow run; it never
  uses Hermes task dependencies, brief Start plan, or room routing to start steps.
- State machine per step attempt: `blocked → ready → admitting → running → (succeeded | failed | cancelled | unknown)`;
  per run: `running | paused(reason) | stopping | finished(outcome)`. Every transition is one transaction through the
  ingest single writer (D1) with a revision; observations carry the attempt id and are rejected when stale.
- **Durable intents:** before an external call the executor commits `{run, node, attempt, payloadHash, frozenPayload}`
  with state `admitting`; the call uses the existing durable admission (intents/receipts). Crash boundaries enumerated
  in the test list: before intent, after intent before call, call accepted but receipt lost (→ reconcile by receipt; if
  unprovable → `unknown`, which pauses the run with "Step state unknown — check the agent, then mark done/failed"), after
  accept before running, completion observed twice / out of order (revision guard), result accepted but successors not
  activated (same transaction — can't happen).
- **Dispatch retry ≠ execution retry:** re-sending the same frozen admission after a lost response uses the same
  idempotency key; a node `retry` is a new attempt with a new key. Score never promises exactly-once agent side effects
  (the UI says "an agent may have acted before a failure").
- **Typed dispatch:** workflow steps go through a workflow-only path with a fixed recipient: implicit hand-offs and
  @mentions in workflow turns are not routed (a hand-off inside a step is shown as text and ignored); rendered inputs
  and previous outputs are inserted as quoted data blocks, never parsed for commands.
- **Stop fence:** Stop first commits `stopping` (fence) — no new admissions after it — then cancels pending admissions,
  records owed stops durably (the batch E stop-intent mechanism), and requires terminal evidence before the run is
  `finished(stopped)`; until then the run shows "stopping (waiting for <agent>)".

## Control flow (precise)
- **Tokens:** a node becomes `ready` when all incoming edges carry a token. Branch nodes emit exactly one token on the
  first matching rule in order, else on their `default` edge (required). Untaken edges carry `skip`; a node whose inputs
  are all `skip` is `skipped` and propagates `skip`. Joins: `all` (ready when every input has a token or skip, success if
  ≥ 1 token and no failure) or `first` (ready on the first token; it records the winning attempt; the other branches'
  running steps are stopped with the stop fence, their later results ignored).
- **Template dependencies** are validated against control dependencies: a template may reference only nodes that are
  guaranteed ancestors on every path to it, or must use `{{nodes.N.output|default:"…"}}`.
- **Result envelope:** `{ attempt, status: succeeded|failed|cancelled|unknown, verdict?: passed|changes_requested (only
  from a review verdict Score validated, e.g. a reviewer's structured reply), output (sanitized), truncated, source }`.
  Branch rules may test `status`, `verdict`, or "output contains" — the last is labelled advisory in the editor and can
  never stand in for a gate.

## Gates
A gate creates a workflow-local decision target `{run, node, attempt, revision, evidenceHash}` showing the exact
evidence (the predecessor outputs it was opened with). Exactly one paired-human decision is accepted atomically
(approve → token; reject → `failed` path or run stop). Gate, budget, manual, agent and team holds are independent
(a run resumes only when none applies). A gate decision never grants tool permissions.

## Budgets and deadlines
- **Soft budgets only in v1:** the executor checks spend (session accounting, attributed per attempt by the run's
  session window) **between steps**: if known spend ≥ budget, the run pauses with a budget gate before admitting the next
  step. Parallel admissions reserve the node's `estimateUsd` (author-given) so two branches can't both pass a nearly
  exhausted budget. Unknown spend: a budgeted run requires a policy chosen at start — "pause when spend is unknown"
  (default) or "continue". The editor says budgets are checked between steps and a running step may overshoot.
- **Deadlines** are absolute timestamps persisted at admission; paused time counts (wall clock); on startup overdue runs
  are reconciled (fenced, overdue steps stopped) before any admission; the timeout reason is kept separately from the
  runtime's eventual termination.

## Projection, API and stream
New tables `workflow_definitions` (immutable versions, hash), `workflow_runs`, `workflow_steps` (attempts),
`workflow_gates`; stream events `workflow.run.updated`, `workflow.step.updated` (D1 transactional snapshots + resync);
`GET /api/workflows`, `/api/workflow-runs/:id` (snapshot with `asOfSeq`); mutations (create/version, import, start,
rerun, stop, pause/resume, gate decision, budget change) all need a paired session. A workflow run has its own brief
for Now/Flow/Reports; Flow shows the run graph from the workflow projection (not the brief's step list). The pause
contract mismatch (`block` vs task holds' `scheduled`) is resolved in the contract doc before building.

## Reruns, replay, limits, export
- **Rerun** = new run with frozen inputs (edit allowed), same definition version, fresh gates, fresh sessions (each run
  uses its own room and per-step sessions; same-agent parallel steps in one run use separate sessions).
- **Replay:** Watch scope per step attempt (frames associated by run id), bounded pages; retention gaps shown.
- **Limits:** definition ≤ 50 nodes, ≤ 100 edges, instruction ≤ 8 KB, total definition ≤ 256 KB; ≤ 5 running workflow
  runs, ≤ 4 concurrent steps per run, ≤ 2 per agent; attempts per run ≤ 200; outputs ≤ 32 KB (truncated, flagged).
- **Export:** portable schema `{ format: 'score.workflow/1', name, inputs, nodes (agent by portable descriptor: name +
  role, never internal ids), edges }`; instruction text passed through `redact()` with a visible diff if anything
  changed; no run data, no credential references.
- **Import:** new local identity; the person reviews the full definition and maps every descriptor to a local agent;
  approval binds to the definition hash + mapping revision and is invalidated by any change; admission re-checks the
  mapped agents exist and are served.

## Acceptance tests (before the editor)
Recorded Hermes fixtures and the fake adapter, no model calls: every crash boundary above; uncertain admission →
unknown; duplicate and out-of-order completions; Stop during admission and with late admission; competing gate
decisions; overlapping holds; skipped branches and skip propagation; first-join losers stopped and ignored; stale
mappings after import; unknown and parallel spending with reservations; restart with overdue deadlines; replay after
retention.

# Design v1 (2026-10-09, not approved)

**Goal (PLAN 7.1):** reusable multi-agent pipelines drawn on a canvas that extends Flow: a node per agent step (Hermes or
coding agent, 7.2), branches, human approval gates, budgets and deadlines, pause/resume/stop, replay, JSON export/import.

## Model
- **Workflow definition** (Score DB, versioned, immutable once used): `{ id, name, version, inputs: [{ name, label,
  required }], nodes, edges }`. Node kinds:
  - `agent` — `{ agentId, instruction (template with {{inputs.x}} and {{nodes.N.output}}), room?: 'new'|'input',
    budgetUsd?, deadlineMin?, mode: 'message'|'task' }`;
  - `gate` — a human approval (`{ question }`) that must be answered in Score;
  - `branch` — routes on the previous node's outcome: `passed`/`changes_requested` (review verdicts), `completed`/
    `failed`, or "output contains <text>" (case-insensitive, no code execution);
  - `parallel` / `join` — fan out, wait for all (or any);
  - `end`.
  Validation: DAG (no cycles in v1; retries are explicit `retry` counts on a node), every path ends, templates reference
  existing nodes/inputs, size limits (≤ 50 nodes).
- **Workflow run**: a durable state machine in Score DB (`workflow_runs`, `workflow_steps`), built on the existing brief
  and durable-operation patterns: each `agent` step is a brief turn (message or Kanban task) so Now/Flow/Reports/Watch
  show it unchanged; the run links to its brief. Steps are recorded before acting (crash-safe like 5.14), idempotent per
  (run, node, attempt).

## Control
- Pause/resume/stop reuse the pause holds (5.13): pausing a workflow run holds its brief; Stop stops active steps.
- **Budgets:** per node and per run, from session accounting (spend per day split, 5.15); exceeded → the run pauses with
  a "budget reached" gate the person can raise or stop. Unknown cost (coding agents without cost) counts as unknown and
  can't satisfy a budget silently: the gate says "spend unknown".
- **Deadlines:** per node and per run; on expiry the step is stopped and the branch `failed` path taken (or the run
  pauses if none).
- **Replay:** a finished run can be re-run with the same or edited inputs (new run, same definition version); Watch
  replays each step's events.

## UI
Flow gains an editor mode: drag nodes from a palette (agents with glyphs, gate, branch, parallel/join, end), connect,
edit node details in the inspector, validate live, save as a new version. A run view reuses the Flow canvas with live
step state. Workflows list under Flow › Workflows; start from there or `/run <workflow>` in chat.

## Import/export
`GET /api/workflows/:id/export` → JSON (definition only, no run data, no secrets); `POST /api/workflows/import` validates
with the same zod schema and limits, maps agent ids by name with a confirmation step when an agent is missing.

## Security
Templates are plain text substitution (no expressions); branch conditions are a fixed set; imported workflows can't run
until the person reviews the agent mapping; gates are human decisions (paired session, D7.1).

## Open questions for review
- Loops (iterate until review passes) beyond `retry` counts — v2.
- Whether a workflow run may create rooms automatically (default: yes, one per run, archived on finish).
