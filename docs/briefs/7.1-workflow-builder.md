# 7.1 Workflow builder — design v8.1 (2026-10-10, amends v8 below)

v8 review (`docs/reviews/2026-10-10-7.1-workflow-builder-v8-codex.md`): not approved — 2 high (both in fix batch H / the
shared executor: legacy recovered completions, manual Pause lost under a budget pause; added to fix batch H as items 4–5)
and 5 medium, amended here. Executor-level items apply to orchestrations too.

1. **Remapping existing assignments.** A remap decision moves every affected step into `remapping`: steps that are
   provably unsent (no `send_started` in DB or journal) are retired with disposition `remapped` and re-created for the
   new incarnation — their old gate is withdrawn and, under `every-step`, the new frozen payload needs its own approval;
   under `gates-only` the remap card shows the new payload and the remap decision is that approval. Possibly-sent work
   keeps its attempt, obligations and unknown state; the remap applies only to later work. Remap re-creations don't use a
   logical retry but count against `maxSteps` (planner caps remaps at 2 per node). Runs from before 0049 get their mapping
   backfilled from their attempts' recorded incarnations (journaled); runs with no attempt get the incarnation at
   migration time. Tests: remap after approval, crash around the remap transaction, legacy run.
2. **Durable wakes for waiting work.** A global `admission_revision` (orc_global) increments on every change that can make
   waiting work admissible — limits raised, Resume (run/agent/team), fence lift, waiver, capacity released by any run,
   quota released — in the same transaction as the change; each run with waiting work records the revision it last
   evaluated, and the executor re-evaluates runs whose revision is behind (also at startup, after recovery). A workflow
   node `ready` + waiting counts as a wake source, so a workflow never pauses with `no_wake_source` while it has waiting
   nodes. Tests: capacity freed by another run, each hold/fence release, restart between the change and the pass.
3. **Payload bound = the dispatched bytes.** Rendering never clips: the final dispatched payload (wrappers, quoting,
   consumed results) is rendered and validated (≤ 32 KB UTF-8 bytes) **before** the assignment is frozen and its gate
   shown; an oversized payload is refused (orchestrations: `payload_too_large` receipt; workflows: node fails validation at
   readiness with the reason). The gate shows the exact rendered text; the dispatched payload's hash equals the approved
   payload hash. Internal workflow assign schema allows 32 KB instructions; the MCP `orch.assign` schema keeps 8 KB.
   Tests: multibyte text, quoting expansion, hash equality.
4. **No settlement claims.** The spend reader is replaced by an adapter evidence contract `{attributed, lineageComplete,
   fresh, costScope}`. Today's Hermes adapter cannot prove `lineageComplete`, so live Hermes spend is **never settled**:
   it stays provisional, reservations stay held until the run ends, and the run's summary says "spend not settled —
   Hermes doesn't report complete costs". Unknown-spend acceptance stays a risk decision, never evidence. The fake adapter
   can report full evidence (tests). Tests: missing continuation, delayed cost, the real token-only payload fixture.
5. **Complete storage inventory.** The per-run charge covers orchestration/workflow rows, receipts, owned intents, the
   run room's messages and message_runs, its attempts' `runs`/tool rows and control history; retained definition
   versions are charged globally (≤ 200 definitions × ≤ 20 versions × ≤ 256 KB). Unsent-failure churn is bounded: a node's
   provably unsent attempt is reused for the next try (no new rows); after 5 consecutive unsent failures the node waits
   with "Hermes unavailable". Control history ≤ 200 records per run, older ones compacted into counters (journaled
   transitions are kept). 64 KB per run is protected for Stop/obligation evidence. Charges are released only when every
   associated row is deleted (pruning deletes them together, tombstone kept). Tests: prolonged adapter outage, 500
   Pause/Resume, quota saturation during result acceptance and Stop, associated-row cleanup.

# 7.1 Workflow builder — design v8 (2026-10-10)

v7 review (`docs/reviews/2026-10-10-7.1-workflow-builder-v7-codex.md`): not approved — 6 high, 5 medium. Three highs were
defects in the **shipped 7.5 executor** (recovered text as termination evidence, unjournaled authorization changes,
assignments rebinding a replaced agent); they are fixed for orchestrations first in fix batch H
(`docs/briefs/fix-h-orchestrator.md`, migration 0049) and workflows inherit the fixes. v8 amends v7 for the rest, following
the review's "design I would approve". Where v8 and v7 differ, v8 wins.

## A separate workflow control projection
- Workflow graph state is its own durable projection (migration 0050): `wf_runs` (run ↔ orchestration, definition id +
  version, frozen inputs, planner generation), `wf_nodes` (node state `waiting|ready|gate_open|running|succeeded|failed|
  skipped|cancelled|unresolved`, logical attempts used, verdict), `wf_tokens` (edge, kind `ok|failed|rejected|skip|branch`,
  produced by, consumed by), `wf_consumed` (consuming node attempt → producing node attempt + output revision).
- The executor's `after` dependencies are **not** used for workflows: an agent node is handed to the executor only once
  the planner has established graph readiness from tokens (routed failures, skips, joins, rejected-gate routes all
  resolved), as a step with no `after`. Consumed results (including routed failures and template defaults) are frozen
  in `wf_consumed` in the same transaction.

## Planner principal and command identity
- The planner is a **server-only principal** (no capability, no MCP). Its commands use run-scoped identities
  `(run, node, logical attempt, verb, generation)` stored in `wf_commands` with tool, payload hash, receipt and
  outcome; node→step mapping, token transitions and the receipt commit **atomically**. A crash before or after a pass
  re-derives the same commands; a stored identity returns its receipt.
- **Waiting vs failing:** admission conditions that can change (budget, reservations, capacity, deadline not yet passed,
  fences, holds, quota) never produce a stored refusal: the node stays `ready` with a `waitingFor` reason and the planner
  re-evaluates on the next wake cause with a **new generation** (e.g. after the person raises the budget). Only
  permanent refusals (validation, mapping mismatch without remap, limits that cannot change) fail the node with a
  recorded reason. Planner commands per pass ≤ node count; passes are triggered only by wake causes (7.5 cursor).

## Gates are local graph nodes
- A `gate` node opens a **workflow gate** (`kind: node`): payload frozen (question, consumed ancestor results with
  revisions, node + run revision). The decision transaction (paired, revision-bound): approve → `ok` token; reject →
  `rejected` token if the edge exists, else the run stops (Stop semantics). It never queues or rejects an executor
  assignment. Contract: `POST /api/workflow-runs/:id/gates/:gateId/decision` (§15).
- Under `every-step`, each agent node additionally gets the executor's assignment gate (7.5 semantics, unchanged).

## End and Finish
Reaching `end` records an end token only. The planner issues Finish only when the graph is terminal: no node in
`waiting|ready|gate_open|running|unresolved`, no queued or admitted step, no planner command without a receipt, and every
produced token consumed or at an `end`. Outcome `succeeded` iff an end token exists and no node failed unrouted; else
`failed`. A pending gate on another branch therefore always blocks Finish.

## Retries, abandonment and parameters
- Logical attempts per node: `retries + 1` (max 3), counted across replacement lineage. A failed attempt with attempts
  left becomes a new executor step `replaces` the old (new session). **Abandonment** is administrative: it never
  produces a `failed` token; the node becomes `unresolved` and offers **Retry** (paired decision, only with attempts left)
  or Stop the run.
- Node parameters actually transported: `agentId`, rendered instruction (≤ 32 KB), `estimateUsd` (per-step reservation;
  executor gains a per-step estimate field). **Per-node deadlines are removed from v8** (run deadline only).
  Validation and reservations use the true maximum: Σ nodes × (retries + 1) steps ≤ 30.
- Agent mapping: the run's frozen mapping from fix batch H; a replaced agent blocks its node until a remap decision.

## Verdicts and results
The verdict is parsed from the **complete sanitized final reply before truncation** (runtime-terminal attempts only);
the stored record is bounded: verdict, reason (≤ 500 chars), source (`runtime`), and whether the stored output was
truncated. Recovered or incomplete observation ⇒ no verdict (and, per fix H, no success). "Output contains" rules match
the stored sanitized output and say so in the editor. Tests: duplicate blocks beyond the cap, a block crossing the
truncation boundary, recovered text.

## Spend, Watch, storage
- **Spend:** stated plainly — Hermes reports tokens, often not dollars; unknown cost is shown as unknown, never zero.
  Spend is settled only for runtime-terminated attempts whose session lineage is closed with qualifying facts;
  otherwise provisional with reservations kept. Budgets with unknown spend pause as in 7.5.
- **Watch: per-attempt filtering is out of 7.1.** A node's "Watch" link opens the agent's Watch at the attempt's time
  window, labelled "agent-wide: may include other work". No association is implied.
- **Storage:** the per-run reserve covers step outputs (≤ 64 KB × max attempts), receipts, workflow projection rows and
  control history (≤ 8 KB per transition); Watch/media stay under their existing global retention (not charged per
  run, stated in the UI); definitions ≤ 256 KB each, ≤ 200 definitions; charges released only when the covered rows are
  pruned (90 days after quiescence, tombstones kept).

## Contract first
7.1a's first commit is API-CONTRACT §15 + `packages/contract/src/workflows.ts` (definitions, validation errors, runs,
nodes, tokens, gate decisions, Retry/remap decisions, events `workflow.run.upserted`, revisions, ownership transitions
added to §14's table); the lead reviews it before the engine is built.

## Tests added
Every v7 counterexample: failure route `A --failed→ B`, rejected-gate route, mixed join with a skipped input, early end
beside a pending gate and beside work waiting for capacity, budget refusal then raise (new generation), crash around an
accepted assignment, replacement after Start before assignment, recovered text on a node, retry lineage and abandonment.

# Design v7 (2026-10-10; amended by v8 above)

Codex design rounds and a Codex code review, and proven in a live run. **v7 replaces the separate workflow executor with
that one:** a workflow run is an orchestration whose planner is a fixed graph instead of a model. v1–v6 stay as history;
where they differ, v7 wins; their scope cuts and node semantics (v3 "Node and edge semantics", "Results and verdicts")
still hold unless restated here.

## One executor
- `orchestrations.planner = 'lead' | 'workflow'` (migration 0049). A workflow run has **no lead attempts, no
  capabilities and no MCP calls**: where 7.5 wakes a lead, the executor runs the **graph planner**, a pure function
  `(frozen definition, node states, accepted results) → commands`. Its commands go through the same command path as
  `orch.*` calls (`orch.assign`, `orch.cancel`, `orch.finish`), with deterministic `commandId`s
  (`wf:<node>:<attempt>:<verb>`), the same receipts, limits and refusals. A crash before or after a planner pass
  re-derives the same commands; receipts make them idempotent.
- Everything below the planner is 7.5 unchanged: single admission authority with claim/send transactions and journaled
  `send_started`; typed dispatch with a fresh session per attempt (`orc-<run>-<step>-<attempt>`); termination evidence
  (`completed`/`failed` only; anything else → unknown, which fences the run); Stop / Finish / cancel barriers; owed
  stops; abandonment; budgets with reservations and provisional vs complete spend; deadlines (expiry acts as Stop);
  storage reserve; global capacity (workflow runs count toward the 5 runs / 6 steps / 3 per run / 2 per agent).

## v6 findings
- **H1 restore witness:** replaced by 7.5's execution journal outside `$SCORE_HOME` with permanent tombstones and
  journaled authority-restoring transitions, `scripts/score restore` (fence + untrusted history), and the documented
  limit (a manual same-host, same-boot whole-home restore can't be detected). Workflow runs are covered because they are
  orchestrations. Tests: v3.2's restore tests run once more with a workflow run.
- **H2 frozen toolset ≠ no background work:** the acknowledgement stays for workflows exactly as for orchestrations
  (same text). `run_tool_policy` (the Hermes proposal) is described only as tool restriction; the proposal is amended to
  also ask for auto-review / async work exclusion, and removing the acknowledgement needs its own design review.
- **M human resolution:** an unknown node attempt offers 7.5's actions only — Stop the run, or Abandon (capacity and
  reservations released, owed stop kept, late result recorded but never consumed) followed by **Retry as a new attempt**
  (allowed only when the node has retries left; the new attempt is a `replaces` lineage step). No "mark done/failed".
- **M settled spend:** 7.5's rule — complete only when the attempt is terminated and its session's sibling runs all
  ended `completed`/`failed`; otherwise provisional, reservations held.
- **M replay scope:** this stage adds **session ownership on Watch frames** (shared with orchestrations, closing 7.5's
  open item): frames are tagged at ingest with the attempt whose session they belong to (exact session id; compression

- **M control matrix:** 7.5's ownership transition table (API-CONTRACT §14) applies to workflow-owned rooms, briefs and
  messages unchanged; workflow-specific actions (definition edit, run start, gate decision) are added to it.
- **M reservations and growth:** 7.5's per-run storage reserve formula, with steps = node count × (retries + 1).

## Definitions
- `workflow_definitions` (id, name, version, created_at, used: bool) — immutable once a run used the version; editing
  saves a new version. `{ inputs: [{ name, label, required, maxChars ≤ 4 KB }], nodes ≤ 30, edges }`.
- **Node kinds (v7):** `agent` `{ agentId, instruction template, retries 0–2, estimateUsd?, deadlineMin? }` (Hermes
  agents only; coding agents and Kanban later), `gate` `{ question }`, `branch` (rules on the previous agent node:
  verdict `passed|changes_requested`, outcome `succeeded|failed`, or output contains text; `default` required),
  `join` (all only), `end`. DAG only; validation exactly as v3 (every agent/gate failure routed or "fail the run";
  join reachability; template ancestry).
- **Planner semantics:** v3's transition table. An `agent` node becomes an `orch.assign` with `after` = its resolved
  inputs; a `gate` node becomes a **workflow gate** (7.5 gate record, kind `node`, payload frozen: question, consumed
  ancestor results with revisions) — approve/reject route its edges; skipped branches record disposition `skipped`
  on their nodes; reaching `end` with nothing running issues `orch.finish`.
- **Gate policy per run:** `every-step` (each agent node also gets 7.5's assignment gate), or `gates-only` (only gate
  nodes stop for the person; default for workflows). Start screen states which.
- **Agent mapping** bound to incarnation; a replaced agent blocks start until the person re-confirms the mapping.
- **Export** only (scrubbed with `redact()`, diff shown); no import in v7.

## UI
- **Flow › Workflows:** list; editor mode on the Flow canvas (palette, connect, inspector, live validation, save as new
  version); start dialog (inputs, budget, deadline, gate policy, 7.5 acknowledgement and preflight minus MCP checks).
- **Run view:** the 7.5 live diagram, log and replay, laid out from the definition graph (branches and skipped nodes

- **Re-run** a finished run with the same or edited inputs (new run, same version).

# Design v6 (2026-10-10; replaced by v7 above)

v5 review (`docs/reviews/2026-10-10-7.1-workflow-builder-v5-codex.md`): not approved — 3 high, 4 medium, all needing
guarantees Hermes does not give today. v6 states exactly which guarantees exist, degrades honestly where they don't,
and moves the missing ones into `docs/proposals/hermes-run-execution-policy.md`. Where v6 and v5 differ, v6 wins.

## Restore quarantine
`sendStarted` is mirrored by a monotonic counter in a file outside the database (`$SCORE_HOME/workflow-epoch`, fsync'd
before each POST). On startup, if the database's highest counter is below the file's (a restored or rolled-back
database), every workflow run with a non-terminal attempt becomes `quarantined`: no automatic admission or retry for
any workflow until the person reviews each quarantined run (Stop it, or mark it "I checked: nothing is running" — a
recorded human decision that never counts as termination evidence). A missing or unreadable epoch file also
quarantines.

## Tool policy binding
- **Capability `run_tool_policy`:** Hermes builds the agent with a toolset list given per run. Today only Hermes's hosted
  room dispatch (`room_execution_policy`) does that, and it is tied to Hermes room grants, so Score does **not** have the
  capability; the proposal asks for it on `/v1/runs`.
- **Without the capability (now):** the editor and every start screen say "Score can't stop this agent from starting
  background work (delegation, background processes); a step may keep working after its run ends". Starting such a run
  needs the person's explicit acknowledgement, recorded on the run. Unreadable tool inventory counts as "can't be
  excluded".
- **With the capability (later):** each attempt freezes `enabledToolsets` without delegation or background-process tools,
  sends it with the run, and the acknowledgement is no longer needed.

## Termination evidence
Accepted as "terminated", per Hermes run outcome: `completed` or `failed` reported by the run's own agent loop through
`GET /v1/runs/{id}` (the status is set when the agent call returns). **Not** accepted: `cancelled` from a gateway
shutdown or interrupt, a forgotten/expired run, a 404, a lost handle — these keep the attempt `unknown` with its
obligations (owed stop, reservations, capacity) until a later `completed`/`failed` is observed or the person resolves
it. Background OS processes started by tools are outside the evidence (see tool policy) and the UI says so.

## Mediums
- **Attribution settles** when the attempt is terminated and its compression lineage has no open session; until then
  spend is provisional and budgets use the provisional value plus reservations.
- **Watch replay** shows frames whose producer session id equals the attempt's session id (exact); frames without a
  session id are listed as "unassociated" next to the run, never inside an attempt.
- **Controls:** the contract lists every workflow-owned object (brief, room, tasks it creates) with allowed actions and
  the `409 workflow_owned` code; human actions on a run (gate decision, quarantine resolution, acknowledgement, Stop)
  each carry the expected revision.
- **Quota:** admission reserves storage per attempt (64 KB) against the 200 MB quota; when the remaining quota cannot
  cover a run's maximum attempts, the run can't start; evidence of unresolved attempts is never pruned.

# Design v5 (2026-10-10; amended by v6 above)

v4 review (`docs/reviews/2026-10-10-7.1-workflow-builder-v4-codex.md`): not approved — 3 high, 4 medium. v5 amends v4;
where they differ, v5 wins.

## "Not dispatched" needs proof
The executor commits `sendStarted` (same transaction as nothing else external) **before** the POST that creates the
run, and the POST happens only in the process that committed it. `not_dispatched` is concluded only when `sendStarted`
was never committed (the crash happened before; nothing could have been sent). In every other uncertain case the
attempt is `unknown` — no time horizon, no inference from an absent session, and an unreadable/changed/restored Hermes
database also means `unknown`.

## A run handle is never inferred
The only handle Score uses to observe or stop a run is the `run_id` Hermes returned (persisted in the same transaction
that records the response). Hermes's Runs API has no listing/lookup by session (only `POST /v1/runs` and
`GET /v1/runs/{id}`), so a lost `run_id` cannot be recovered: the attempt stays `unknown`, Stop is shown as "can't be
confirmed — the agent may still be working", and transcript rows are shown as evidence but never promoted to a runtime
status. (If Hermes later offers a lookup by session or idempotency key, it becomes a capability-gated reconciliation.)

## No detached children
Workflow steps may only use agents whose `delegation` toolset is **disabled** (Score already reads toolsets for Team ›
Tools): `delegate_task` — including its `background` mode — is then unavailable, so a step's work can't outlive its run.
Admission re-checks this per attempt; an agent that re-enables delegation is not admitted ("disable delegation to use
this agent in workflows"). Session lineage (compression) is followed for spend; anything not provable is `unknown`.

## Mediums
- **Attribution:** spend is the per-attempt session plus its compression lineage; any other child is unprovable →
  `unknown` (and budgets treat unknown per the run's policy).
- **Controls:** every control path that could act on a workflow-owned brief, room or task is listed and guarded:
  brief Pause/Resume/Stop and Flow node Stop → executor; Start plan, `/assign`, routing hand-offs, task holds, Kanban
  actions, rewind/edit/delete of workflow-room messages, and room archive → 409 `workflow_owned` while the run is not
  finished. The room is read-only for the person except the run's gate/budget decisions.
- **Retention and quotas:** workflow data has a 200 MB quota and 90-day retention for finished runs; pruning never
  removes a run with an owed stop, an unconfirmed attempt, or a pending gate; when the quota is reached new runs are
  refused (no silent deletion of live data).
- **Verdict reason** ≤ 1 KB (longer → no verdict); attempt data limit counts it.

# Design v4 (2026-10-10; amended by v5 above)

v3 review (`docs/reviews/2026-10-09-7.1-workflow-builder-v3-codex.md`): not approved — 4 high, 4 medium left. v4
amends v3; where they differ, v4 wins.

## No replay at all; reconciliation by the attempt's own session
The executor never re-sends an admission whose outcome is uncertain. Each attempt has a unique Hermes session id
(`wf-<run>-<node>-<attempt>`), so after any uncertainty (crash after intent, lost response, gateway restart) it
reconciles by reading Hermes's own session records read-only (the adapter's existing `state.db` readers): a user row in
that session ⇒ dispatched (attach and observe it); no session after the horizon (intent time + 10 min, covering queued
admission) ⇒ not dispatched (attempt `failed: not_dispatched`, retry allowed); anything in between ⇒ `unknown`. No
receipt/idempotency window is relied on.

## Quiescence before replacement
Per attempt the executor tracks three separate facts: `retired` (Score will never admit or consume it), `stopRequested`
/ `stopAcknowledged`, and `terminated` (canonical runtime terminal evidence or "never dispatched" proof). A **retry**
is admitted only when the previous attempt is `terminated`. An `unknown` attempt offers only **Stop the run** (no retry,
no continue). A run is `succeeded` only if every attempt ever admitted is `terminated`; otherwise it ends `stopped` /
`failed` with "1 attempt not confirmed ended" shown until evidence arrives (owed stops keep being retried).

## Graph protocol
- **Initialization:** at start, every node with no incoming edges gets one token (validation requires ≥ 1 such root
  and that all are `agent` or `gate` nodes).
- **Local nodes** (gate, branch, join, end) resolve by committed local evidence in the same transaction as the event
  that makes them ready: gate → the exact decision; branch → its rule evaluation on the frozen input; join → its inputs;
  end → receiving a token. Only `agent` nodes have external attempts and termination requirements.
- **Fan-out:** an outgoing port may connect to several targets; each target gets its own token (parallel work).
  Exclusive branches reconverging through an `all`-join are valid: untaken paths deliver `skip`, so the join resolves.
- Tests: the smallest graph (agent → end), a branch reconverging through a join, fan-out to two agents joined.

## Fences and timeouts
- **Attempt fence (node timeout):** stop that attempt; after its termination evidence, the node takes its `failed`
  edge (or fails the run). Other branches continue.
- **Run fence (run deadline, Stop, unrouted failure, gate rejection without a reject edge):** no further admissions;
  stop every running attempt; drain until all are terminated (or reported "not confirmed ended"); outcome
  `failed(timeout)` / `stopped` / `failed(unrouted failure)` / `stopped(rejected)`.
- **Ordering:** the single writer serializes events; whichever commits first wins (a completion committed before the
  deadline check counts; after a run fence commits, later completions are recorded but not consumed).

## Mediums
- **Spend/replay scope:** per-attempt sessions are the attribution unit; Hermes child sessions spawned by an attempt
  (compression lineage, subagents) are followed through the existing lineage reader; unprovable children make spend
  `unknown`.
- **Brief controls:** workflow-owned briefs route Pause/Resume/Stop and the Flow node Stop to the executor; Start plan,
  holds and Kanban actions are refused (409) on workflow-owned briefs; the contract types gain `owner: 'workflow'` on
  briefs.
- **Retention:** only `finished` runs older than 90 days are pruned, and never while an owed stop or unconfirmed attempt
  exists.
- **Verdicts:** the verdict block is parsed from the full reply before truncation; truncation never applies to the
  verdict.

# Design v3 (2026-10-09; amended by v4 above)

v2 review (`docs/reviews/2026-10-09-7.1-workflow-builder-v2-codex.md`): not approved — 7 of 19 v1 findings resolved,
12 partly, 7 new high. v3 amends v2 (below); where they differ, v3 wins. Scope cuts first, then precise rules.

## Scope cuts for v1 (each can return later with its own design)
- **No first-joins.** Joins are `all` only. (Removes the shared-cancellation / winner barrier problem.)
- **No import.** Export only (scrubbed). Import returns with incarnation-bound mappings later.
- **No human "mark done/failed".** An `unknown` step offers exactly two actions: **Stop the run**, or **Retry as a new
  attempt** — both retire the old admission permanently (it can never be admitted again) and record an owed stop for it.
- **One session per attempt:** every step attempt uses its own Hermes session id `wf-<run>-<node>-<attempt>`; no session
  reuse across attempts or runs. Watch association is by that session id (exact), not by run id.

## One admission authority
- `command_intents` gain an `owner` column: `room` (today) | `workflow`. Workflow-owned intents are **never** recovered by
  the generic intent recovery; on startup the order is fixed: (1) generic recovery skips `owner='workflow'`, (2) the
  workflow executor scans its unfinished transitions and its intents, applies fences (stop, deadline, pause) **before**
  any re-admission, (3) only then do new admissions start. Late admission evidence for a fenced or retired attempt
  attaches the external run to the attempt and records an owed stop; its result is stored but never consumed.
- **Receipt durability:** Hermes's Runs API idempotency is per profile, in memory with a TTL
  (`api_server_run_idempotency`). The executor records at admission the profile, gateway incarnation and the receipt
  window end (`admittedAt + receiptTTL − 30 s`). A same-key replay is allowed only inside that window **and** with the
  same gateway incarnation; otherwise the attempt reconciles without creating work (run lookup by the frozen session id)
  or becomes `unknown`. Test: receipt lost across a gateway restart inside the window → unknown, no duplicate.

## Node and edge semantics (transition table)
| Node | Ready when | Succeeds → | Fails → | Cancelled/skipped → |
|---|---|---|---|---|
| agent | all inputs resolved and ≥ 1 token | token on `ok` edge | token on `failed` edge if present, else run fails | skip on all out edges |
| gate | same | approve → token | reject → `rejected` edge if present, else run stops | skip |
| branch | same | one token on the first matching rule, else `default` (required) | — | skip |
| join (all) | every input resolved | token if ≥ 1 input token and no input failed-unrouted | — | skip if all inputs skipped |
| end | any token | run may finish | — | — |
- **Node state vs attempt state:** a node is `waiting | ready | running | succeeded | failed | skipped | cancelled`; it
  has 1..(retry+1) attempts. A failed attempt with retries left creates the next attempt (new session, new key); retry
  exhaustion makes the node `failed`. A node is resolved only when its last attempt is terminal **with termination
  evidence** (see results).
- **Run finishes** when no node is `waiting/ready/running` and every reached `end` has its token; outcome `succeeded`
  if any `end` got a token and no node failed unrouted, else `failed`. Validation rejects graphs where an `agent`/`gate`
  failure has neither a failure edge nor an explicit "fail the run" setting, and graphs where a join can receive
  inputs from mutually exclusive branches without a `default` (deadlock check by path analysis).
- **Templates** may reference only ancestors that are resolved before the node is admitted on **every** path; a
  conditional ancestor needs `|default:"…"`; forward and self references are rejected. The exact consumed attempt and
  output revision are frozen on the consuming attempt.

## Results and verdicts
Adapter facts per attempt: `terminated` (canonical runtime terminal status with source), `text` (final assistant text:
`live` from the run stream or `recovered` from Hermes records — 5.16), `observationLost` (bool). **Success requires
`terminated: completed` from the runtime**, never recovered text alone; recovered text is shown and, if the run's
termination can't be proven, the attempt is `unknown`. One authoritative output is frozen with source and truncation.
**Verdicts** come only from a structured reply: the reviewer's final text must contain exactly one fenced block
```` ```score-verdict\n{"verdict":"passed"|"changes_requested","reason":"…"}\n``` ```` parsed with a strict schema;
malformed, missing or multiple blocks → no verdict (branch rules on verdict then take `default`).

## Budgets, deadlines, limits
- Spend at admission boundaries uses a **fresh reconciliation** of the attempt's own session costs (sessions are per
  attempt, so attribution is exact); evidence older than 60 s or incomplete counts as unknown. Reservations (node
  `estimateUsd`) persist with the attempt and are released only when the attempt is terminal with evidence.
- Deadlines: run deadline set at start (absolute); node deadline set at each attempt's admission (retries get a fresh
  node deadline but never beyond the run deadline); paused and waiting time count. Expiry is checked inside every
  admission transaction; on expiry the executor fences, stops, waits for termination evidence, then routes `failed`.
  Precedence: Stop > run deadline > node deadline > budget > gate.
- Limits add: start inputs ≤ 16 KB total, rendered instruction ≤ 32 KB UTF-8 after expansion, stored attempt data
  ≤ 64 KB, ≤ 20 waiting (paused) runs; capacity counts unresolved external work (incl. paused runs and owed stops) until
  quiescent; run data retained 90 days (definitions forever), then pruned with a visible "history removed" marker.

## Projection, human actions, export
- A workflow run **owns** its brief: brief status is derived from the run (running/paused/finished); the existing brief
  controls (Pause/Resume/Stop) call the workflow executor for workflow-owned briefs. Gates and budget pauses appear in
  Now's "Needs you" with their exact targets. Every mutation carries the expected run revision (409 on conflict);
  snapshots have `asOfSeq` watermarks; transitions are kept as durable history (`workflow_transitions`).
- Agent mapping (definitions reference local agent ids) is bound to the agent's **incarnation**; admission revalidates
  incarnation and capabilities; a replaced or recreated agent invalidates the definition's mapping until the person
  confirms it again.
- **Export** scrubs every free-text field (name, labels, instructions, gate questions, branch texts, input labels) with
  `redact()`, shows the complete diff, lets the person remove fields, revalidates, and is described as "scrubbed", not
  "guaranteed secret-free".

## Acceptance tests (added to v2's list)
Generic recovery skipping workflow intents; startup fence ordering; late admission after Stop/retire → owed stop, result
ignored; receipt loss inside/outside the window and across gateway restart; every transition-table row incl. mixed
inputs into a join, retry then success, retry exhaustion, deadlock-shaped graphs rejected; verdict parser
(valid/malformed/multiple); recovered text without termination → unknown; stale spend → unknown; deadline precedence;
incarnation replacement invalidating mappings; export scrubbing of every field; retention marker.

# Design v2 (2026-10-09; amended by v3 above)

v1 was not approved (`docs/reviews/2026-10-09-7.1-workflow-builder-codex.md`: 12 high, 7 medium). v2 replaces v1's
execution model and narrows v1 scope so every promise is one Score can keep. v1 text below is history.

## Scope of 7.1 v1 (what ships first)
- Steps are **Score-started room runs** of Hermes agents only (coding agents join after 7.2 ships and passes the
  runtime capability matrix below). **No Kanban-task steps** (Hermes can't stop one attempt; `--max-runtime` requeues).
- Results are **text** (the run's final assistant text, redacted, ≤ 32 KB). **No file artifacts** in v1: instructions
  may mention paths, but successors get only the text; the editor says so.
- No loops; `retry` counts per node (≤ 3).

## Runtime capability matrix
A step mode is allowed only if its runtime has all of: Score-started admission with a receipt, Stop by run id with
terminal evidence, a final-text source, spend per run (or "unknown" handled below). Hermes room runs: yes. Claude
Code / Codex (7.2): decided per CLI after 7.2's tests; until then not selectable.

## Executor (server-owned, single writer)
- The workflow executor in `domain/workflows/` is the **only** authority that admits work for a workflow run; it never
  uses Hermes task dependencies, brief Start plan, or room routing to start steps.
- State machine per step attempt: `blocked → ready → admitting → running → (succeeded | failed | cancelled | unknown)`;
  per run: `running | paused(reason) | stopping | finished(outcome)`. Every transition is one transaction through the
  ingest single writer (D1) with a revision; observations carry the attempt id and are rejected when stale.
- **Durable intents:** before an external call the executor commits `{run, node, attempt, payloadHash, frozenPayload}`
  with state `admitting`; the call uses the existing durable admission (intents/receipts). Crash boundaries enumerated
  in the test list: before intent, after intent before call, call accepted but receipt lost (→ reconcile by receipt; if
  unprovable → `unknown`, which pauses the run with "Step state unknown — check the agent, then mark done/failed"), after
  accept before running, completion observed twice / out of order (revision guard), result accepted but successors not
  activated (same transaction — can't happen).
- **Dispatch retry ≠ execution retry:** re-sending the same frozen admission after a lost response uses the same
  idempotency key; a node `retry` is a new attempt with a new key. Score never promises exactly-once agent side effects
  (the UI says "an agent may have acted before a failure").
- **Typed dispatch:** workflow steps go through a workflow-only path with a fixed recipient: implicit hand-offs and
  @mentions in workflow turns are not routed (a hand-off inside a step is shown as text and ignored); rendered inputs
  and previous outputs are inserted as quoted data blocks, never parsed for commands.
- **Stop fence:** Stop first commits `stopping` (fence) — no new admissions after it — then cancels pending admissions,
  records owed stops durably (the batch E stop-intent mechanism), and requires terminal evidence before the run is
  `finished(stopped)`; until then the run shows "stopping (waiting for <agent>)".

## Control flow (precise)
- **Tokens:** a node becomes `ready` when all incoming edges carry a token. Branch nodes emit exactly one token on the
  first matching rule in order, else on their `default` edge (required). Untaken edges carry `skip`; a node whose inputs
  are all `skip` is `skipped` and propagates `skip`. Joins: `all` (ready when every input has a token or skip, success if
  ≥ 1 token and no failure) or `first` (ready on the first token; it records the winning attempt; the other branches'
  running steps are stopped with the stop fence, their later results ignored).
- **Template dependencies** are validated against control dependencies: a template may reference only nodes that are
  guaranteed ancestors on every path to it, or must use `{{nodes.N.output|default:"…"}}`.
- **Result envelope:** `{ attempt, status: succeeded|failed|cancelled|unknown, verdict?: passed|changes_requested (only
  from a review verdict Score validated, e.g. a reviewer's structured reply), output (sanitized), truncated, source }`.
  Branch rules may test `status`, `verdict`, or "output contains" — the last is labelled advisory in the editor and can
  never stand in for a gate.

## Gates
A gate creates a workflow-local decision target `{run, node, attempt, revision, evidenceHash}` showing the exact
evidence (the predecessor outputs it was opened with). Exactly one paired-human decision is accepted atomically
(approve → token; reject → `failed` path or run stop). Gate, budget, manual, agent and team holds are independent
(a run resumes only when none applies). A gate decision never grants tool permissions.

## Budgets and deadlines
- **Soft budgets only in v1:** the executor checks spend (session accounting, attributed per attempt by the run's
  session window) **between steps**: if known spend ≥ budget, the run pauses with a budget gate before admitting the next
  step. Parallel admissions reserve the node's `estimateUsd` (author-given) so two branches can't both pass a nearly
  exhausted budget. Unknown spend: a budgeted run requires a policy chosen at start — "pause when spend is unknown"
  (default) or "continue". The editor says budgets are checked between steps and a running step may overshoot.
- **Deadlines** are absolute timestamps persisted at admission; paused time counts (wall clock); on startup overdue runs
  are reconciled (fenced, overdue steps stopped) before any admission; the timeout reason is kept separately from the
  runtime's eventual termination.

## Projection, API and stream
New tables `workflow_definitions` (immutable versions, hash), `workflow_runs`, `workflow_steps` (attempts),
`workflow_gates`; stream events `workflow.run.updated`, `workflow.step.updated` (D1 transactional snapshots + resync);
`GET /api/workflows`, `/api/workflow-runs/:id` (snapshot with `asOfSeq`); mutations (create/version, import, start,
rerun, stop, pause/resume, gate decision, budget change) all need a paired session. A workflow run has its own brief
for Now/Flow/Reports; Flow shows the run graph from the workflow projection (not the brief's step list). The pause
contract mismatch (`block` vs task holds' `scheduled`) is resolved in the contract doc before building.

## Reruns, replay, limits, export
- **Rerun** = new run with frozen inputs (edit allowed), same definition version, fresh gates, fresh sessions (each run
  uses its own room and per-step sessions; same-agent parallel steps in one run use separate sessions).
- **Replay:** Watch scope per step attempt (frames associated by run id), bounded pages; retention gaps shown.
- **Limits:** definition ≤ 50 nodes, ≤ 100 edges, instruction ≤ 8 KB, total definition ≤ 256 KB; ≤ 5 running workflow
  runs, ≤ 4 concurrent steps per run, ≤ 2 per agent; attempts per run ≤ 200; outputs ≤ 32 KB (truncated, flagged).
- **Export:** portable schema `{ format: 'score.workflow/1', name, inputs, nodes (agent by portable descriptor: name +
  role, never internal ids), edges }`; instruction text passed through `redact()` with a visible diff if anything
  changed; no run data, no credential references.
- **Import:** new local identity; the person reviews the full definition and maps every descriptor to a local agent;
  approval binds to the definition hash + mapping revision and is invalidated by any change; admission re-checks the
  mapped agents exist and are served.

## Acceptance tests (before the editor)
Recorded Hermes fixtures and the fake adapter, no model calls: every crash boundary above; uncertain admission →
unknown; duplicate and out-of-order completions; Stop during admission and with late admission; competing gate
decisions; overlapping holds; skipped branches and skip propagation; first-join losers stopped and ignored; stale
mappings after import; unknown and parallel spending with reservations; restart with overdue deadlines; replay after
retention.

# Design v1 (2026-10-09, not approved)

**Goal (PLAN 7.1):** reusable multi-agent pipelines drawn on a canvas that extends Flow: a node per agent step (Hermes or
coding agent, 7.2), branches, human approval gates, budgets and deadlines, pause/resume/stop, replay, JSON export/import.

## Model
- **Workflow definition** (Score DB, versioned, immutable once used): `{ id, name, version, inputs: [{ name, label,
  required }], nodes, edges }`. Node kinds:
  - `agent` — `{ agentId, instruction (template with {{inputs.x}} and {{nodes.N.output}}), room?: 'new'|'input',
    budgetUsd?, deadlineMin?, mode: 'message'|'task' }`;
  - `gate` — a human approval (`{ question }`) that must be answered in Score;
  - `branch` — routes on the previous node's outcome: `passed`/`changes_requested` (review verdicts), `completed`/
    `failed`, or "output contains <text>" (case-insensitive, no code execution);
  - `parallel` / `join` — fan out, wait for all (or any);
  - `end`.
  Validation: DAG (no cycles in v1; retries are explicit `retry` counts on a node), every path ends, templates reference
  existing nodes/inputs, size limits (≤ 50 nodes).
- **Workflow run**: a durable state machine in Score DB (`workflow_runs`, `workflow_steps`), built on the existing brief
  and durable-operation patterns: each `agent` step is a brief turn (message or Kanban task) so Now/Flow/Reports/Watch
  show it unchanged; the run links to its brief. Steps are recorded before acting (crash-safe like 5.14), idempotent per
  (run, node, attempt).

## Control
- Pause/resume/stop reuse the pause holds (5.13): pausing a workflow run holds its brief; Stop stops active steps.
- **Budgets:** per node and per run, from session accounting (spend per day split, 5.15); exceeded → the run pauses with
  a "budget reached" gate the person can raise or stop. Unknown cost (coding agents without cost) counts as unknown and
  can't satisfy a budget silently: the gate says "spend unknown".
- **Deadlines:** per node and per run; on expiry the step is stopped and the branch `failed` path taken (or the run
  pauses if none).
- **Replay:** a finished run can be re-run with the same or edited inputs (new run, same definition version); Watch
  replays each step's events.

## UI
Flow gains an editor mode: drag nodes from a palette (agents with glyphs, gate, branch, parallel/join, end), connect,
edit node details in the inspector, validate live, save as a new version. A run view reuses the Flow canvas with live
step state. Workflows list under Flow › Workflows; start from there or `/run <workflow>` in chat.

## Import/export
`GET /api/workflows/:id/export` → JSON (definition only, no run data, no secrets); `POST /api/workflows/import` validates
with the same zod schema and limits, maps agent ids by name with a confirmation step when an agent is missing.

## Security
Templates are plain text substitution (no expressions); branch conditions are a fixed set; imported workflows can't run
until the person reviews the agent mapping; gates are human decisions (paired session, D7.1).

## Open questions for review
- Loops (iterate until review passes) beyond `retry` counts — v2.
- Whether a workflow run may create rooms automatically (default: yes, one per run, archived on finish).
