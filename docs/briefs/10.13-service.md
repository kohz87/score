# 10.13 — Score as a service

Owner (2026-10-20): Score should be installable as a service as part of setup. Today a VM reboot or a crash leaves
Score down until someone runs `scripts/score start`. The Hermes gateway already runs as a systemd **user** service
(`hermes-gateway.service`), linger is on, and coding runs already use transient user units (PLAN 7.7a). SETUP.md §9 only
has a manual recipe (`docs/score.service.example`) that the launcher knows nothing about.

## Done when (PLAN 10.13)
1. **`scripts/score run`** (new, foreground): does exactly the preparation `cmd_start` does today — `use_local_tls`,
   `use_named_tls`, log rotation past 10 MB, `SCORE_HOME`, `SCORE_LOG_FILE`, `SCORE_SERVE_WEB=1`, the "not built yet"
   check, refuse if another Score already runs on this home (`running_pid`) — writes its own pid to `score.pid`, then
   `exec node scripts/start.mjs` (no nohup, no background), so systemd supervises the node process itself. Share the
   preparation with `cmd_start` (one function), don't copy it.
2. **`scripts/score service install`**:
   - writes `~/.config/systemd/user/score.service` (`Type=simple`, `WorkingDirectory=<repo root>`,
     `ExecStart=<repo>/scripts/score run`, `EnvironmentFile=%h/.config/score/score.env`, `Restart=on-failure`,
     `RestartSec=5`, `StartLimitIntervalSec=300`, `StartLimitBurst=5`, `KillSignal=SIGTERM`, `TimeoutStopSec=60` (a clean
     stop drains for up to ~45 s), `WantedBy=default.target`; stdout/stderr appended to `$SCORE_HOME/score.log` so
     `score logs` and `score pair` keep working);
   - writes `~/.config/score/score.env` (folder 0700, file 0600, atomic temp + rename) with: every `SCORE_*` variable
     set in the shell that runs `install` (that is how the owner passes remote mode, host, public origins, terminal,
     Kanban attempts), `SCORE_HOME` resolved absolute, and `PATH` as it is at install time (systemd has no shell PATH,
     and the server runs `hermes`, `git`, `tmux` and the coding CLIs from PATH). Values are written quoted for systemd's
     EnvironmentFile syntax; refuse values containing a newline. Never write anything else from the environment;
   - `daemon-reload`, `enable --now score`, then waits for the server's ready line in the log like `cmd_start` and prints
     the address and the pairing link the same way;
   - refuses with a clear message if a launcher-started Score is running (say: run `scripts/score stop` first), if the
     user manager isn't reachable, or if not built; warns (doesn't fail) when linger is off, with the exact command
     `loginctl enable-linger $USER` and why (starts at boot without a login).
   - Re-running `install` updates the unit and env file (prints what changed) and restarts.
3. **`service status`** (systemctl state, enabled, MainPID, the URL from `score.url`, linger) and **`service uninstall`**
   (`disable --now`, remove the unit, `daemon-reload`; keep `score.env` unless `--purge`).
4. **Launcher defers to the service when the unit is installed**: `start`, `stop`, `restart` (new), `status` use
   `systemctl --user start|stop|restart|status score` and report as today (start/restart wait for the ready line and
   show the pairing link). `pair` and `logs` work unchanged. `start` without the unit behaves exactly as today. A
   launcher-started copy can never run beside the service (both directions are refused with the reason).
5. **Docs**: SETUP.md gets "Run Score as a service" as a numbered setup step (install, check, update after a release
   with `scripts/score restart`, logs, uninstall, linger), replacing the manual recipe; `docs/score.service.example`
   is removed (the launcher writes the unit); README's quick start mentions `scripts/score service install`.

## Tests (failing first) — never touch the real systemd or `~/.config`
Add overrides used only by tests: `SCORE_SYSTEMD_USER_DIR` (unit folder), `SCORE_CONFIG_DIR` (env file folder) and
`SCORE_SYSTEMCTL` / `SCORE_LOGINCTL` (paths to fake commands). Tests run the real `scripts/score` (bash) against a temp
home with fake `systemctl`/`loginctl` scripts that record their arguments and simulate state (and, for start, launch
`scripts/score run` in the background like systemd would, against fake mode). Cover: unit and env file contents and
modes; SCORE_* passthrough, PATH captured, newline refusal, nothing else leaked (e.g. a `SECRET_X` env var never
appears); install refuses when a launcher copy runs; start/stop/restart/status route to systemctl when installed;
`run` refuses a second copy; reinstall updates; uninstall keeps vs `--purge` removes the env file; linger warning. Put
them with the existing launcher tests (`apps/server/test/index-process.test.ts` and siblings show how the launcher is
exercised). The server suite's HOME is already a temp folder (see `test/helpers/tmp-root.ts`); keep it that way.

## Rules
Follow AGENTS.md. No new dependencies. Bash stays `set -euo pipefail`, argv-safe (quote everything). Don't edit
docs/API-CONTRACT.md or docs/ARCHITECTURE.md. Commit per step (`git add <paths>`, never `-A`, never `git stash`). Never
pkill or killall; never touch ports 8740/8741, `~/.score`, `~/.config/systemd`, `~/.config/score`, `~/score-vault`,
`~/.hermes`, and never run the real `systemctl --user` or `loginctl` (tests use the fakes). Targeted tests while
building; one full `pnpm check` and one full `pnpm e2e` (`SCORE_WEB_PORT=5904`) at the end. Report: what changed,
failing-first evidence, test counts, the exact unit file and env file your install writes for a sample environment.
