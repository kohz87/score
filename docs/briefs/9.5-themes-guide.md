# 9.5 Built-in themes and the theme author guide (PLAN 9.5; design docs/briefs/9-themes.md §9; decision 90)

Goal: three new built-in themes that look clearly different from Score/Paper/Night shift/Dense, a guide for writing a
theme, and an example theme package — all using only what the manifest supports (9.3 merged).

1. **Themes** (built-in, ids reserved in `BUILTIN_THEME_IDS` — add them to the contract constant and the server's
   built-in list in the same change):
   - **Harbour** — glass surfaces over a soft gradient background image (shipped asset, generated in-repo, no stock
     art), left rail navigation, chat bubbles, round radius, comfortable.
   - **Ledger** — flat, sharp corners, hairline borders, compact density, launcher navigation, full width, a monospace
     accent font (OFL, from an already-installed @fontsource package where possible; any new font is a dependency the
     lead adds — report it, don't add it).
   - **Studio** — airy density, serif headings, right rail navigation, narrow content, a custom Now arrangement.
   Each passes the existing WCAG AA contrast test for light and dark, and the hostile-theme guarantees.
2. **Guide** `docs/THEMES.md`: what a theme is (and isn't: no scripts), the package layout, every manifest field with
   its allowed values (generated or checked against the contract so it can't drift — a test compares the documented
   field list with the schema), the public colour token list with what each colours, custom CSS rules (what the
   sanitiser drops and why), protected surfaces, how to get back (`?look=safe`, Ctrl+Shift+0, palette, host command),
   and a step-by-step example.
3. **Example package** `docs/themes/example-theme/` (theme.json, style.css, one image) + a test that zips it and imports
   it through the real import route successfully.
Done when: visual baselines (light, dark, phone; Now, Chat, Settings, user view) for each new theme; contrast and
hostile tests cover them; the guide's field list test passes; `pnpm check` + full e2e.
