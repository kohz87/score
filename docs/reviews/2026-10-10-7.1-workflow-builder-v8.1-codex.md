### [high] The send barrier can discover unknown execution and still dispatch

**Where:** [Initial fence checks](/home/raven/score/apps/server/src/domain/orchestration/executor.ts:1208), [fresh reconciliation](/home/raven/score/apps/server/src/domain/orchestration/executor.ts:1253), [recovered-to-unknown transition](/home/raven/score/apps/server/src/domain/orchestration/executor.ts:1483).

**What happens:** Attempt A still has executor state `running`, while its observed run has become recovered `completed`. Attempt B is already `created`. B’s send barrier checks for unknown attempts, then reconciliation changes A to `unknown`, and nevertheless records B’s `send_started`. An in-memory probe confirmed both resulting states.

**Why:** The unknown/cancel fences are checked **before** reconciliation. Afterwards, the barrier rechecks spend and deadline, but not the newly established execution fence. This can occur between sequential dispatches while an earlier admission awaits its response.

**Change:** Reconcile before the final authorization check, then recompute run status, independent holds and unknown/cancel fences immediately before journaling the send. Test a recovered or interrupted sibling arriving between dispatches.

### [high] Legacy recovered success becomes consumable after Abandon

**Where:** [Upgrade downgrade](/home/raven/score/apps/server/migrations/0049_fix_h_orchestrator.sql:30), [upgrade test retaining success](/home/raven/score/apps/server/test/orchestration/fix-h.test.ts:531), [abandonment handling](/home/raven/score/apps/server/src/domain/orchestration/decisions.ts:323).

**What happens:** Migration 0049 changes an already accepted recovered attempt to `unknown`, but leaves its step `succeeded` with the old result. Abandon only changes steps already marked `unknown`. After Abandon and Resume, a queued dependent is admitted using that synthetic result. The probe confirmed this. Previously finished orchestrations also retain their old run status.

**Why:** The temporary unknown fence does not revoke the result’s execution eligibility. “Stays visible” currently also means “still satisfies dependencies and supplies input.”

**Change:** Preserve historical text separately from authoritative result eligibility. Downgrade affected step/run outcomes, invalidate dependent approvals and record affected consumers. Abandon must not restore synthetic success. Add upgrade tests through Abandon → Resume, including previously finished runs and already-created consumers.

### [high] Lead remapping bypasses a manual Pause

**Where:** [Independent manual hold](/home/raven/score/apps/server/src/domain/orchestration/decisions.ts:175), [remap resumes the run](/home/raven/score/apps/server/src/domain/orchestration/decisions.ts:387), [admission checks run status](/home/raven/score/apps/server/src/domain/orchestration/executor.ts:918).

**What happens:** Lead replacement pauses a run as `agent_unavailable`. The person presses Pause, adding `manual_paused_at` while preserving that reason. Remapping then sets the run to `running`. Admission creates another lead attempt despite the manual hold; the in-memory probe confirmed this.

**Why:** Remap clears status without considering `manual_paused_at`. Neither admission nor the send barrier independently checks that hold. The journal can preserve its existence while execution ignores it.

**Change:** Remap must clear only the replacement condition. Derive admissibility from every independent hold, and check the manual hold directly at claim and send. Test replacement pause → manual Pause → remap, including queued steps and restoration.

### [medium] Unsent-attempt reuse conflicts with permanent send records

**Where:** [v8.1 reuse rule](/home/raven/score/docs/briefs/7.1-workflow-builder.md:34), [journal-first send](/home/raven/score/apps/server/src/domain/orchestration/executor.ts:1294), [adapter’s proven-unsent refusal](/home/raven/score/apps/server/src/hermes/live/live-port.ts:690), [journal replay barrier](/home/raven/score/apps/server/src/domain/orchestration/executor.ts:1180).

**What happens:** The executor journals `send_started` before calling the adapter. An unavailable profile then returns a proven `not_dispatched` refusal. Reusing that attempt as `created`, as v8.1 proposes, causes its next send to become `unknown: journal_records_send`. A probe reproduced this.

**Why:** One attempt identity currently permits one journaled send. A certified unsent outcome does not supersede that record. Removing the record would weaken restore protection.

**Change:** Define qualified dispatch generations and journaled unsent evidence, or another bounded protocol compatible with restore verification. Preserve logical attempt counts and never reuse possibly sent dispatches. Specify the availability wake/reset after five failures. Test outage → recovery and crashes/restores around the unsent proof.

### [medium] Workflow success must preserve the executor’s unresolved outcome

**Where:** [Graph outcome predicate](/home/raven/score/docs/briefs/7.1-workflow-builder.md:80), [Abandon → Retry](/home/raven/score/docs/briefs/7.1-workflow-builder.md:85), [executor Finish settlement](/home/raven/score/apps/server/src/domain/orchestration/executor.ts:869).

**What happens:** A is unknown and abandoned; its replacement B succeeds and reaches an end. All graph-terminal conditions can hold, so the workflow predicate says `succeeded`. The shared executor instead returns `finished_with_unresolved` because A remains abandoned. That behavior is implemented and was confirmed in memory.

**Why:** Logical graph completion and confirmed execution completion are different facts. V8.1 does not amend the graph-success wording or define their final projection.

**Change:** Treat graph success as the requested Finish outcome. Preserve the executor’s final unresolved status in workflow summaries, briefs, history and UI. If graph outcome is exposed separately, name it explicitly. Require Abandon → Retry → successful replacement tests while the old attempt remains unconfirmed.
