# 7.7b design review (Codex gpt-6.1-sol, max, read-only), 2026-10-13

Reviewed: docs/briefs/7.7b-coding-workers.md v1. Verdict: BLOCK (10 P1, 7 P2, 1 P3). Responses: design v2 (same file).

**BLOCK**

1. **P1 — Release omits admission rules (§5).** [ops.ts:68](apps/server/src/domain/orchestration/ops.ts:68) retires an attempt without changing `running`; [executor.ts:1940](apps/server/src/domain/orchestration/executor.ts:1940) checks independent holds, cancellation fences, mapping and dollar accounting. A lead cancels a queued worker, or the person lowers its budget: the listed authorization checks can still permit release. **Fix:** reuse a complete, pure admission predicate, including retirement, owed Stop, finishing, agent/team holds, withdrawn inputs and fresh spend.

2. **P1 — Comparing the current agent does not freeze the invocation (§§3,5).** [service.ts:865](apps/server/src/runtimes/coding/service.ts:865) captures settings before awaits; [service.ts:973](apps/server/src/runtimes/coding/service.ts:973) subsequently builds argv from that capture. Capture `full`, then restore the approved permission before authorization: the row comparison passes while prepared argv grants full access. Ambient CLI configuration also remains mutable through [env.ts:15](apps/server/src/runtimes/coding/env.ts:15). **Fix:** construct owned invocations from frozen policy; authorize their actual hash, executable/workspace identity and effective noncredential configuration. Unverifiable reach blocks readiness.

3. **P1 — Dispatch generations have no safe coding identity protocol (§§0,5,10).** The turn ID is per logical attempt, **not per generation** ([executor.ts:1788](apps/server/src/domain/orchestration/executor.ts:1788)). [recordRefusal](apps/server/src/domain/orchestration/ops.ts:347) retains its old run/turn linkage; [service.ts:457](apps/server/src/runtimes/coding/service.ts:457) returns the old accepted handle. Revoked turns also satisfy `turnWitnessed`. Additionally, [beginSend’s returned attempt](apps/server/src/domain/orchestration/executor.ts:2051) contains the previous generation. **Scenario:** queued refusal followed by redispatch reattaches the failed run or authorizes with the wrong generation. **Fix:** specify durable generation-specific turn/run/launch identities, linkage replacement and generation-qualified callbacks; return the committed generation.

4. **P1 — A refusal is not automatically proof of no execution (§§0,5,10,11).** [release](apps/server/src/domain/orchestration/coding-journal.ts:177) returns `not_authorised` without writing a revoke; revocation happens separately. A projection failure already leaves `mayHaveExecuted=true`, yet [unit-backend.ts:1129](apps/server/src/runtimes/coding/unit-backend.ts:1129) returns a refusal. Its [outer exception handler](apps/server/src/runtimes/coding/unit-backend.ts:631) also manufactures refusals without execution proof. Treating these as `send_refused` permits another execution. **Fix:** require a durable, generation-bound no-release proof; classify releasing/projection-failed/uncertain launches conservatively. Consult folded `mayHaveExecuted`, including tombstones.

5. **P1 — Transaction-aware authorization does not make release transaction-safe (§5).** [codingProjection](apps/server/src/domain/orchestration/coding-checkpoint.ts:217) unconditionally starts a transaction; the production [blocked callback](apps/server/src/start-server.ts:392) starts a read transaction. Inside a caller’s transaction, release journals `releasing` and then fails with “Nested transactions are not supported.” Simply reusing that transaction would allow `go` before its eventual rollback. **Fix:** define transaction ownership across the entire release path, preserve journal→database ordering, and send `go` only after the owning commit succeeds.

6. **P1 — Coding accounting lacks an admission/release/settlement protocol (§9).** The executor must debit before `startRun`, but [unit-backend.ts:629](apps/server/src/runtimes/coding/unit-backend.ts:629) creates the launch ID internally. [Journal state](apps/server/src/domain/orchestration/coding-records.ts:42) carries no allocation or settlement amounts; [usage](apps/server/src/runtimes/coding/translate.ts:301) remains transient until terminal persistence. Refusals can exhaust limits without executing; restore cannot reconstruct missing charges; supervisor death can leave no measured end time. **Fix:** preallocate identities, journal allocation and settlement data, define proof-qualified refunds, persist observed usage, and retain conservative charges when duration is uncertain.

7. **P1 — §0’s late-evidence guarantee is false (§§0,7,11).** [executor.ts:2252](apps/server/src/domain/orchestration/executor.ts:2252) accepts evidence from `unknown`; only abandoned attempts receive the nonconsumable late-result treatment. Meanwhile, [unit reaping](apps/server/src/runtimes/coding/unit-backend.ts:1716) updates launch proof without publishing executor reconciliation evidence. After late proof, either obligations remain forever or a normal terminal promotion consumes old output. **Fix:** separate monotonic end proof, disposition and result eligibility; permanently disqualify unconfirmed results while closing obligations and settling accounting. Add a coding-specific proven-cancellation transition.

8. **P1 — Held successes do not survive restart as claimed (§§0,7,11).** [service.ts:811](apps/server/src/runtimes/coding/service.ts:811) deliberately downgrades pending successes to `interrupted`, clearing the eligible reply; this is enforced by [the restart test](apps/server/test/runtimes/coding-runtime.test.ts:1396). Following §11 literally requires removing that safety rule without specifying replacement evidence. Released work whose end is proven but whose final reply was lost also has no defined disposition. **Fix:** retain stage 1’s interruption rule, or explicitly design a durable complete-result envelope bound to proof and generation; provide an exhaustive recovery matrix.

9. **P1 — Frozen workers can ignore Stop and the orchestration deadline (§§5,8,9).** [executor.ts:2393](apps/server/src/domain/orchestration/executor.ts:2393) suppresses every owed Stop while frozen. The runtime’s [deadline](apps/server/src/runtimes/coding/service.ts:928) is its turn allowance, potentially thirty minutes. Freeze a worker with a five-minute orchestration deadline: person Stop and deadline expiry cannot reach it. **Fix:** apply decision 74 to executor-owned live connections, preserving the ban on recovered/inherited signals; pass the minimum of the run deadline and coding reservation to the supervisor, and define deadline tightening.

10. **P1 — `recordRunResult` cannot supply the proposed orchestration result (§7).** [verdict.ts:93](apps/server/src/domain/workflows/verdict.ts:93) records workflow steps only; [executor.ts:2351](apps/server/src/domain/orchestration/executor.ts:2351) reads those facts only for workflows. Orchestrations receive the 8 KiB run output, which can also contain [Score’s cleanup annotation](apps/server/src/runtimes/coding/service.ts:1196). A worker’s accepted result therefore differs from its complete CLI final answer. **Fix:** add authoritative result storage and consumption for orchestration attempts, sourced exclusively from the eligible reply before display cuts or annotations, with explicit size/truncation semantics.

11. **P2 — Consent and remap lack a policy identity (§§3,4,13; contract changes).** The proposed POST contains an acknowledgement boolean without the policy hash the person viewed. Configuration can change between dialog and creation, silently binding consent to different reach. Furthermore, [coding PATCH](apps/server/src/http/coding-agents.ts:168) does not change lifecycle incarnation; [remap](apps/server/src/domain/orchestration/decisions.ts:387) rejects unchanged or `untracked` incarnations. **Fix:** return a versioned policy/reach description from preflight, require its identity at creation and reapproval, and extend remap, gates and history to that identity.

12. **P2 — Every authorization “no” must not count as a readiness refusal (§§5,10).** [recordRefusal](apps/server/src/domain/orchestration/ops.ts:317) increments consecutive/lifetime refusal counters and eventually fails an orchestration step. Repeated Pause/Resume or policy changes while queued can exhaust those counters despite no CLI failure. **Fix:** distinguish temporary waiting, Stop cancellation, policy-remap blockage, readiness refusal, execution failure and uncertainty; specify accounting for each transition.

13. **P2 — Runtime-scoped unknown-cost acceptance cannot use today’s budget model (§9).** [budget.ts:124](apps/server/src/domain/orchestration/budget.ts:124) collapses uncertainty to one boolean; [executor.ts:1998](apps/server/src/domain/orchestration/executor.ts:1998) pauses only with a dollar budget. Mapping accepted Codex uncertainty to the global acceptance also exempts Hermes; retaining it blocks Codex, and unbudgeted coding runs bypass the proposed pause. **Fix:** preserve uncertainty provenance, evaluate accepted scopes independently, and journal scoped acceptance/revocation consistently across assignment, admission and release.

14. **P2 — Stop delivery is sequential, and Hermes acknowledges with `void` (§§0,8).** [executor.ts:2411](apps/server/src/domain/orchestration/executor.ts:2411) awaits each Stop inside the pump; no tracked Stop-job shutdown barrier exists. [HermesPort](apps/server/src/hermes/port.ts:335) permits `void`, which today counts as acknowledgement. One slow Stop blocks others; implementing “only stopped/not_running” literally leaves Hermes Stops owed indefinitely. **Fix:** design tracked asynchronous jobs and shutdown draining, retain ingest until receipts commit, and normalize Hermes acknowledgements separately from coding proof.

15. **P2 — Removing an unresolved worker loses Stop routing (§§2,8,11).** [Deletion](apps/server/src/http/coding-agents.ts:216) checks active statuses only, so an unconfirmed terminal run permits removal. The [composite port](apps/server/src/runtimes/coding/port.ts:84) then routes its Stop to Hermes because the agent is no longer recognized as coding. **Fix:** route controls by durable run/launch runtime identity; retain removed-agent routing or prohibit removal while execution remains unresolved.

16. **P2 — Replacing the shared guard enables stage 3 accidentally (§§1,2).** `assertHermesOnly` also guards [workflow save](apps/server/src/http/workflows.ts:77) and [workflow preflight/start](apps/server/src/domain/orchestration/executor.ts:1008). Replacing all calls with worker support admits workflows whose contracts contain none of this stage’s consent or coding-policy fields. **Fix:** make support explicitly planner/stage-specific; keep workflow coding rejection and its existing tests until 7.7c.

17. **P2 — Storage charging omits the new retained inventory (§§7,9,12).** [Acceptance charging](apps/server/src/domain/orchestration/executor.ts:2372) covers existing result/message/run copies; [pruning](apps/server/src/domain/orchestration/prune.ts:60) does not cover coding launches or pending terminals. New result, policy, refusal and accounting records escape the reserve calculation. **Fix:** inventory and charge every retained copy, reserve proof/Stop/accounting capacity, and prune associated records atomically while retaining required journal tombstones.

18. **P3 — Stage 1 does not guarantee one launch per turn (§§0,6).** [service.ts:930](apps/server/src/runtimes/coding/service.ts:930) permits two launches for Chat’s qualified resume fallback. Treating §0’s statement as a global invariant would break that behavior. **Fix:** correct the claim and enforce the proposed restriction specifically for owned workers. The other §0 basics—signature, phase journal, tombstones, external receipts, dispatch ordering and recovered/unconfirmed exclusions—are present.

Read-only probes reproduced the transaction, generation, result-storage and late-proof issues using in-memory SQLite. No files changed.
