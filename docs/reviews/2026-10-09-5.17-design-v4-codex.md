### [high] History detection needs separate persisted allocation watermarks

**Where:** [V4 §1](/home/raven/score/docs/briefs/5.17.md:13), [current task checkpoint](/home/raven/score/apps/server/src/hermes/live/tasks.ts:98), [Hermes event GC](/home/raven/.hermes/hermes-agent/hermes_cli/kanban_db.py:4370).

**What happens:** V4 compares two independent allocation sequences to “Score’s checkpoint,” without defining separate saved watermarks. The current checkpoint is a `task_events.id`: comparing `task_runs.seq` against it would create false histories on an ordinary board.

Comparing only against processed cursors also misses detectable restores. If Score reads allocation mark 1,000 while processing events through 500, a restore to allocation mark 900 passes the stated checkpoint test. It has caught up past the checkpoint, but remains detectably below the previously observed allocation mark.

**Why:** Allocation history, event-processing progress and baseline progress are different facts. The GC correction is sound, but the replacement comparison and persistence rules remain incomplete.

**Change:** Persist separate event and attempt allocation watermarks, alongside separate processing cursors, atomically with each accepted observation. Scope the “undetectable restore” disclaimer to restores preserving both saved watermarks and all checked evidence. Define missing sequence entries and empty tables explicitly.

Also distinguish frozen claim evidence from current nullable fields: Hermes’s [invariant-recovery writer clears `claim_lock`](/home/raven/.hermes/hermes-agent/hermes_cli/kanban_db.py:3707). Cleanup or enrichment from unknown to known must not become an immutable-tuple contradiction.

### [high] Synthetic writer shape does not uniquely establish synthetic provenance

**Where:** [V4 §3](/home/raven/score/docs/briefs/5.17.md:40), [legacy backfill](/home/raven/.hermes/hermes-agent/hermes_cli/kanban_db_connect.py:950), [synthetic writer](/home/raven/.hermes/hermes-agent/hermes_cli/kanban_db.py:2109).

**What happens:** A legacy running task with no lock, PID or start time is backfilled with `started_at=now`. Closing it as blocked in that same second produces precisely the row that the synthetic blocked writer produces.

Executing those extracted Hermes functions against in-memory tables produced **identical rows across every column**. Both have equal start/end times, null claim/process evidence, status/outcome `blocked`, and the supplied reason as summary. A blocked transition event cannot distinguish them either.

A previously observed partial open row can therefore become “synthetic” under the stated predicate when it closes.

**Why:** Positive-evidence precedence fixes ordinary claimed rows, including pruned claims with retained locks. Negative evidence plus a compatible writer shape cannot distinguish every supported writer.

**Change:** Preserve indistinguishable rows as partial. Persist “previously observed open” and the provenance supporting classification; closure must not erase an established partial attempt. Permit synthetic exclusion only where evidence actually distinguishes the synthetic path.

Fixtures must cover legacy backfill with copied positive evidence, without evidence, and followed by same-second closure. Include `edit_task` synthesis, dangling-run recovery and dispatcher closure branches, rather than treating one fixture per named operation as complete writer coverage.

### [high] Observation loss remains unbounded for deletion and ambiguity pauses

**Where:** [V4 §1](/home/raven/score/docs/briefs/5.17.md:17), [Hermes task deletion](/home/raven/.hermes/hermes-agent/hermes_cli/kanban_db.py:4003), [Reports interval end](/home/raven/score/apps/server/src/domain/reports.ts:335), [Now interval construction](/home/raven/score/apps/server/src/domain/lanes.ts:75).

**What happens:** Score observes a running attempt; Hermes archives and deletes the task before the next poll. The attempt and its closing events disappear. V4 correctly preserves the history and records deletion, but applies `observation_ended_at` only when the history closes. The retained attempt consequently remains open indefinitely.

An ambiguity pause has the same problem. It pauses projection without bounding existing open observations or explicitly making task controls and hold recovery inert. Existing hold recovery can still [read and mutate tasks by bare task ID](/home/raven/score/apps/server/src/http/task-holds.ts:109).

**Why:** Deletion and paused verification both end reliable observation without ending the logical history or proving worker termination.

**Change:** Define an observation-loss boundary for disappearing open attempts and paused/unreadable sources. Publish it atomically with the gap and source state; consumers must stop extending those intervals. Suspend routing, parking and release operations that depend on unverified source/history qualification. Define how subsequent confirmed evidence reconciles the boundary while retaining any unresolved gap.

The deletion fixture must assert finite time and inactive controls, not merely “same history, deleted upstream.”

### [high] Baseline page identities can collide before revisions are allocated

**Where:** [V4 §7](/home/raven/score/docs/briefs/5.17.md:81), [ingest key gate](/home/raven/score/apps/server/src/hub/ingest.ts:189).

**What happens:** The page identity contains an event range and `sweepTick`, but no baseline attempt range. Two attempt-only baseline pages processed during one tick have the same empty event range and can share the same wrapper key. An ordinary tick counter can also repeat after restart.

The current ingest layer then returns `duplicate` **before invoking `apply`**. Transactional hashes, revisions and `kanban_seen_events` cannot recover that page. The in-memory reproduction left the first page’s durable content unchanged after submitting the second under the same wrapper.

**Why:** Internal dedupe protects only observations that reach the writer. V4 never defines the uniqueness or restart semantics of `sweepTick`.

**Change:** Give each captured page observation a restart-safe identity, distinguish baseline/tail/sweep work, and include the relevant page boundaries. Reusing an identity must mean retrying the same captured observation; a new read needs a new identity.

Explicitly retain the durable baseline cursor from v3. Baseline and sweep observations must avoid event retirement floors; reconciliation’s separate identity alone does not bypass the [checkpoint-floor gate](/home/raven/score/apps/server/src/hub/ingest.ts:178).

Test multiple eventless baseline pages in one tick and a restart that repeats the initial tick value.

### [high] Legacy-link matching still lacks a minimum affirmative proof

**Where:** [V4 §8](/home/raven/score/docs/briefs/5.17.md:97), [legacy activity representation](/home/raven/score/apps/server/src/hermes/live/task-model.ts:45), [numeric links](/home/raven/score/apps/server/src/hermes/live/task-model.ts:160).

**What happens:** An old projection contains task `T` and numeric attempt `7`, but its 50-item activity window no longer contains claim information. A restored board contains a different attempt `7` for the same task.

“All retained evidence agrees,” with profile/start checked only _when recorded_, permits this match unless missing evidence explicitly disqualifies it. No retained immutable fingerprint has actually connected the old reference to the new attempt.

**Why:** Absence of contradiction is weaker than affirmative identity evidence. Current activity items omit event and attempt IDs; ordinary claim payloads also do not supply the profile consumed by `eventActivity`.

**Change:** Define a minimum matching predicate. Task ID plus numeric ID alone must yield unresolved, even on the same inode. Specify which retained evidence can establish the match and test each allowed case.

The durable snapshot and resumable work are improvements. Receipt invalidation must preserve the original execution barrier: invalidate or replace the response without permitting the mutation to run again, including compressed receipts.

### [high] History qualification does not yet reach public references and existing associations

**Where:** [V4 §2](/home/raven/score/docs/briefs/5.17.md:31), [AttemptSummary](/home/raven/score/docs/briefs/5.17.md:62), [task detail route](/home/raven/score/apps/server/src/http/tasks.ts:85), [history task links](/home/raven/score/apps/server/src/http/agent-history.ts:139).

**What happens:** An earlier-history attempt can still expose bare `taskId=T`. Opening `/api/tasks/T` resolves the current projection, potentially belonging to a replacement history. Internal qualified joins cannot make that public reference inert because the reference carries no qualification.

Adding columns also leaves the upgrade policy for existing room, brief, review and hold associations unspecified. Assigning them all to the newly observed history can attach old ownership to reused IDs.

Existing Kanban denial references need an explicit policy too: [approval matching uses bare task IDs](/home/raven/score/apps/server/src/domain/tasks.ts:73), and [denial uniqueness uses numeric attempt IDs without history](/home/raven/score/apps/server/src/domain/kanban-denials.ts:23).

**Why:** Qualification must survive storage upgrades, response serialization, navigation and action recovery. The current projection’s upstream-ID primary key also does not preserve an earlier task detail after replacement.

**Change:** Define qualified public references or make historical/unresolved references explicitly non-navigable and non-actionable. Preserve historical detail where promised, or disclose its absence. Upgrade legacy ownership conservatively; unresolved associations stay inert.

Until 5.17a-2 establishes bridge provenance, unqualified denial evidence must not resolve through replacement task projections or authorize task actions.

### [medium] Event dedupe cannot replace late relationship backfill

**Where:** [V4 page dedupe](/home/raven/score/docs/briefs/5.17.md:84), [newly linked task backfill](/home/raven/score/apps/server/src/hermes/live/tasks.ts:43), [per-brief review identities](/home/raven/score/apps/server/src/hermes/live/flow-history.ts:44).

**What happens:** Score consumes a review event while its task is unlinked. A brief later links that task. If the event’s presence in `kanban_seen_events` suppresses all processing, the new brief never receives its review edge.

**Why:** Canonical event ingestion and creation of a relationship have different identities. The current implementation deliberately rereads historical review events for newly linked tasks.

**Change:** Define a separately idempotent association pass keyed by source/history, brief and event. It may process an already-seen canonical event without re-emitting task activity. Commit the relationship and its stream updates together, with durable backfill progress. Add a late-link fixture with a crash during backfill.

### [medium] The bounded-query claim conflicts with the actual schema

**Where:** [V4 polling evidence](/home/raven/score/docs/briefs/5.17.md:13), [V4 source queries](/home/raven/score/docs/briefs/5.17.md:92), [Hermes indexes](/home/raven/.hermes/hermes-agent/hermes_cli/kanban_db.py:1149).

**What happens:** Baseline queries are bounded and use the integer primary key. The open and recently closed queries have no page limit and no supporting `ended_at` index. In-memory query plans against the recorded schema reported `SCAN task_runs` for both.

Checking every known attempt’s immutable tuple every poll is also unbounded, and conflicts with paging old closed rows through a daily pass.

**Why:** Limiting baseline result size does not bound the remaining reads or their scan cost. Score cannot add indexes to Hermes’s database.

**Change:** Use bounded primary-key batches and targeted reads of Score’s known open/touched attempt IDs. Specify scheduling, durable full-pass progress and the detection latency for old closed-row contradictions. Remove the old per-task all-attempt read from the polling path.

Extend the acceptance oracles with query bounds, eventless pages, legacy writer ambiguity, paused/deleted interval boundaries, reused-ID ownership, late relationship backfill and client rendering. The current scenario list does not establish those coupled invariants.
