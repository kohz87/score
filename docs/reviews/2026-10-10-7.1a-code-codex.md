### [high] Pruning deletes messages added after ownership was released

**Where:** [executor.ts:2454](/home/raven/score-worktrees/7.1a/apps/server/src/domain/orchestration/executor.ts:2454)

**What happens:** After a finished run’s room becomes an ordinary room, maintenance deletes subsequent messages along with the run’s replies. If those messages have briefs or other FK references, pruning instead fails and rolls back.

**Why:** Cleanup deletes every room message except the original goal, regardless of whether the run owned it. A probe confirmed that a later human message disappeared.

**Fix:** Delete only messages associated with the pruned run’s attempts. Preserve subsequent conversation data and its references. This affects live orchestrations too.

### [high] Withdrawn graph evidence leaves gates and consumers authorized

**Where:** [payload.ts:54](/home/raven/score-worktrees/7.1a/apps/server/src/domain/workflows/payload.ts:54), [decisions.ts:63](/home/raven/score-worktrees/7.1a/apps/server/src/domain/workflows/decisions.ts:63), [executor.ts:210](/home/raven/score-worktrees/7.1a/apps/server/src/domain/orchestration/executor.ts:210)

**What happens:** After A’s result is withdrawn, an already-created successor B can still send if its instruction contains no template references. A local gate displaying A’s withdrawn output also remains approvable. Both cases were reproduced while A’s graph node was `unresolved`.

**Why:** `wf_consumed` records template substitutions, but omits evidence establishing control readiness. Node-gate decisions check the gate node’s revision without checking the producers and revisions frozen in its payload. Existing tokens remain usable.

**Fix:** Persist and validate readiness provenance as well as substituted text. Withdraw affected local gates, approvals and unsent consumers when their supporting evidence changes; recheck this provenance before sending.

### [medium] Restore verification misses a refusal lost within the same generation

**Where:** [fence.ts:172](/home/raven/score-worktrees/7.1a/apps/server/src/domain/orchestration/fence.ts:172), [fence.ts:296](/home/raven/score-worktrees/7.1a/apps/server/src/domain/orchestration/fence.ts:296)

**What happens:** A crash after journaling `send_refused(g)` but before committing its database transaction leaves the database at `send_started(g)`. Verification reports no mismatch, and journal reconciliation leaves that state untouched. Recovery then treats proven-unsent work as unknown.

**Why:** Verification compares generation numbers but does not verify the database’s committed refusal state. `applyJournalEvidence` handles refused generations only for attempts already `created`. A probe returned an empty mismatch list for this exact boundary.

**Fix:** Persist generation-qualified refusal state and verify it against full entries and witnesses. Reconcile proven refusal evidence conservatively, preserving refusal counters and the human-required lifetime limit.

### [medium] Unknown-spend “continue” policy is ignored by admission

**Where:** [executor.ts:1593](/home/raven/score-worktrees/7.1a/apps/server/src/domain/orchestration/executor.ts:1593), [executor.ts:1960](/home/raven/score-worktrees/7.1a/apps/server/src/domain/orchestration/executor.ts:1960)

**What happens:** A budgeted workflow started with `unknownSpend: 'continue'` pauses after its first unknown-cost result. Its successor requires another human acceptance.

**Why:** The planner respects the workflow policy, but claim and send check only `accepted_unknown_spend`. The initial continue choice never sets that flag. This was reproduced.

**Fix:** Apply one consistent unknown-spend authorization rule at planning, claim and send, including subsequent revocation decisions.

### [medium] Defaults for skipped nodes produce invalid snapshots

**Where:** [payload.ts:51](/home/raven/score-worktrees/7.1a/apps/server/src/domain/workflows/payload.ts:51), [workflows.ts:491](/home/raven/score-worktrees/7.1a/packages/contract/src/workflows.ts:491)

**What happens:** A valid branch/join workflow using `{{nodes.rework.output|default:"no rework"}}` records `producerAttempt: 0` when `rework` was skipped. Its snapshot fails `WorkflowRunDetailSchema`.

**Why:** Skipped nodes have no attempt, while `ConsumedViewSchema` requires every producer attempt to be positive. The branch/default probe reproduced the schema failure.

**Fix:** Represent an absent producer attempt explicitly for defaults, or allow zero only for that consumption kind. Update §15 and add the skipped-default integration case.

### [medium] Valid workflows containing only gates cannot start

### [medium] Large definition saves commit but return 500 with idempotency keys

**Where:** [workflows.ts:56](/home/raven/score-worktrees/7.1a/apps/server/src/http/workflows.ts:56)

**What happens:** Saving a valid approximately 75 KB definition with an `Idempotency-Key` commits the definition, then returns 500. Retrying the same request returns `409 idempotency_pending`.

**Why:** These routes use the middleware’s default 64 KB response limit, although their responses contain definitions allowed up to 256 KiB. Fastify injection reproduced both responses and the committed row.

**Fix:** Provide a response bound and receipt representation that support the complete allowed definition response before committing the save.

### [medium] Keyed deletion returns 500 after deleting the definition

**Where:** [workflows.ts:85](/home/raven/score-worktrees/7.1a/apps/server/src/http/workflows.ts:85)

**What happens:** `DELETE /api/workflows/:id` with an idempotency key deletes the definition, then returns 500.

**Why:** The handler sends an empty 204 response through receipt middleware that requires a JSON string. Injection confirmed the error and successful deletion.

**Fix:** Teach the middleware to record and replay bodyless 204 responses correctly.

### [medium] Storage accounting still permits growth beyond the reserved inventory

**Where:** [views.ts:386](/home/raven/score-worktrees/7.1a/apps/server/src/domain/workflows/views.ts:386), [translate.ts:294](/home/raven/score-worktrees/7.1a/apps/server/src/hermes/live/translate.ts:294), [executor.ts:2537](/home/raven/score-worktrees/7.1a/apps/server/src/domain/orchestration/executor.ts:2537)

**What happens:** Observed tool and thinking rows grow without consuming the run’s charge. A probe retained 3,072,000 bytes against a 1,073,152-byte reserve while `stored_bytes` stayed unchanged. Pruning also releases the reserve while retaining all `orc_history` rows.

**Why:** Inventory reporting does not enforce charging; thinking rows are omitted altogether. Cleanup preserves complete history rather than only the necessary tombstone.

**Fix:** Charge and bound retained observation data at its writers, include thinking in the inventory, and delete or separately account for retained history when releasing a run’s reserve.

### [medium] Pruning erases the definition’s permanent “used” protection

**Where:** [definitions.ts:40](/home/raven/score-worktrees/7.1a/apps/server/src/domain/workflows/definitions.ts:40), [executor.ts:2544](/home/raven/score-worktrees/7.1a/apps/server/src/domain/orchestration/executor.ts:2544)

**What happens:** After the last run is pruned, its definition changes from `used: true` to `false`; deletion succeeds despite §15’s “any run ever used a version” rule. This was reproduced.

**Why:** Usage is derived exclusively from retained `wf_runs`, which pruning deletes.

**Fix:** Persist an irreversible used marker per version or retain usage references in the pruning tombstone.
