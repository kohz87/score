1. **P1 — ORDINARY PATH — The new Codex notice exemption still hides fatal output loss.**  
   [codex.ts:54](apps/server/src/runtimes/coding/codex.ts:54), [codex.ts:179](apps/server/src/runtimes/coding/codex.ts:179).

   `RETRY_NOTICE` accepts any message containing “reconnecting”, “retrying” or “stream disconnected”. This is a keyword test, not an exact harmless-notice schema.

   A parser probe supplied a validated answer, then:

   ```json
   {"type":"error","message":"stream disconnected: fatal output loss; no retries remain"}
   ```

   followed by `turn.completed`. The verdict remained eligible and `lossReason()` returned `null`. The service’s new final loss check therefore cannot disqualify it.

   **Fix:** allow only the complete, known retry-notice forms for the pinned CLI, with validated fields and position. Every other error envelope must produce sticky loss.

2. **P1 — ORDINARY PATH — A failed final-receipt publication can still certify successful completion.**  
   [supervisor.mjs:691](apps/server/src/runtimes/coding/supervisor.mjs:691), [supervisor.mjs:699](apps/server/src/runtimes/coding/supervisor.mjs:699), [unit-backend.ts:917](apps/server/src/runtimes/coding/unit-backend.ts:917).

   The replacement containing `durable: true` becomes readable **before its directory fsync succeeds**. Cleanup assumes that an unsuccessful publication can be removed, but removal can fail too.

   A filesystem-boundary probe failed the replacement’s directory fsync and its cleanup unlink. The supervisor returned **exit 1**, while `parseReceipt()` returned **present, `durable: true`**. After manager replacement removes the failed unit’s exit metadata, the backend’s absent-unit branch accepts precisely that receipt.

   **Fix:** after manager replacement, missing exit metadata must remain ineligible unless a clean supervisor exit was independently captured. A durability flag cannot replace exit evidence. Test failure of the second directory sync and cleanup—not only the initial publication.

3. **P1 — FROZEN STATE — Outgoing Hermes operations bypass the freeze.**  
   [intents.ts:106](apps/server/src/hermes/live/intents.ts:106), [intents.ts:198](apps/server/src/hermes/live/intents.ts:198), [live-port.ts:745](apps/server/src/hermes/live/live-port.ts:745).

   Only `recoverIntents()` checks `frozen`. Normal `startRunIntent()` dispatch and cancellation Stop delivery do not. The Chat dispatcher continues pumping pending replies, and direct message/Flow Stops reach `LivePort.stopRun()` without checking the freeze.

   Probes with `frozen: () => 'frozen copy'` observed both a gateway start and an inherited cancellation Stop. A browser Stop can likewise stop a source run through the copied handle.

   Approval delivery has the same missing boundary check at [live-port.ts:867](apps/server/src/hermes/live/live-port.ts:867).

   **Fix:** enforce the shared freeze predicate at every outgoing Hermes execution/control boundary, including normal dispatch, cancellation Stops, direct Stops and approval delivery. Preserve ordinary admission-fence Stop behavior.

4. **P1 — FROZEN STATE — Reset does not retire all unfinished work, and late evidence can resurrect retired steps.**  
   [history-reset.ts:122](apps/server/src/history-reset.ts:122), [history-reset.ts:133](apps/server/src/history-reset.ts:133), [executor.ts:2252](apps/server/src/domain/orchestration/executor.ts:2252).

   Reset leaves `message_runs` untouched. An inherited pending reply without a command intent survives reset and is dispatched afterward. A probe through the real `RoutingDispatcher` observed **one start after reset**.

   Reset also changes an admitted step to `unknown` while leaving `retired = 0` and retaining its run handle. A second probe supplied late source-run completion: reconciliation changed the supposedly retired step from **`unknown/history_reset` to `succeeded`**, cleared its disposition and accepted the source output. That can release dependent work or wake the lead.

   **Fix:** retire pending replies, queued/gated/admitted steps and their attempts; invalidate inherited handles and capabilities; and exclude reset dispositions from result consumption and further scheduling. Reset must neither send nor Stop this work.

5. **P1 — FROZEN STATE — Reset retirement is not bound to the database that actually committed it.**  
   [history-reset.ts:73](apps/server/src/history-reset.ts:73), [scripts/installation.mjs:101](scripts/installation.mjs:101), [fence.ts:705](apps/server/src/domain/orchestration/fence.ts:705).

   The fresh external `history-reset` record contains an archive name and count, but no database generation or retirement checkpoint. It is published before the database reset. Startup treats its existence as sufficient reset authority.

   Restore a database backup predating reset: retired pending intents, handles and process rows return, while the fresh journal contains no corresponding witnesses. A copied-home probe returned **`fenced: false`, `frozen: null`**; its restored source process row then reached the recovery Stop boundary. Restored coding intents whose launch rows disappeared can similarly become sendable again.

   **Fix:** bind reset to a durable installation history generation stored in both the namespace and database. Incomplete or mismatched generations must freeze. Hold the home lock across reset and make the retirement commit durable before publishing completion.

6. **P1 — FROZEN STATE — A source installation’s reset is mistaken for a reset performed in its copy.**  
   [installation.ts:471](apps/server/src/installation.ts:471), [fence.ts:705](apps/server/src/domain/orchestration/fence.ts:705).

   `inheritedJournal()` copies source `history-reset` records and rewrites their scope to the new installation. The copy gate accepts **any** such record.

   Copy a source that previously reset its history. The first startup freezes because of the copy marker and consumes that marker. Restore the copy’s pre-freeze database: the inherited reset now suppresses the registry-derived copy freeze, even though nobody reset this copy.

   The startup probe returned **no fence and no freeze**.

   **Fix:** inherited reset records must not authorize a local reset. Bind reset authority to this installation’s confirmation/generation, or exclude source reset markers during inheritance.

7. **P1 — FROZEN STATE — Lost-journal freezes are neither completely detected nor durably reconstructed.**  
   [fence.ts:475](apps/server/src/domain/orchestration/fence.ts:475), [fence.ts:269](apps/server/src/domain/orchestration/fence.ts:269), [fence.ts:737](apps/server/src/domain/orchestration/fence.ts:737).

   `lost` detection covers coding launches/checkpoints and launch folders. Orchestration-only history has no equivalent reverse comparison: a surviving empty/older journal can return **no freeze**, despite database execution history. The unreadable-journal branch also raises an admission fence without setting the execution freeze.

   Separately, `executionFrozen()` reads only SQLite’s `frozen_reason`. Restore a database predating a detected journal loss while retaining the durable external `global_fence(reason='execution_frozen')` record: startup reconstructs an ordinary mismatch fence, but `executionFrozen()` returns `null`.

   A probe then successfully performed an **ordinary fence lift without reset-history**.

   **Fix:** reconstruct frozen status from durable external evidence until a matching completed reset supersedes it. Detect lost orchestration witnesses/high-water state as well as coding state; unreadable evidence must not permit external recovery actions.

8. **P2 — ORDINARY PATH — Retention accounting still omits commentary and diagnostics.**  
   [service.ts:994](apps/server/src/runtimes/coding/service.ts:994), [unit-backend.ts:971](apps/server/src/runtimes/coding/unit-backend.ts:971).

   The callback charges parser and translator retention, but excludes `CappedText`’s retained raw commentary and the backend’s `BoundedDiagnostics`. Once measured retention exceeds the reservation floor, those additional buffers remain outside the installation budget. Charging overflow debt fixes the previous accounting rollback, but not these omissions.

   **Fix:** include both accumulators in actual retention accounting and update the charge when stderr/commentary changes. Test aggregate retention near the installation limit.
