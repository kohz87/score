I would not approve [the draft](/home/raven/score-worktrees/3.13-remote-access/docs/briefs/3.13.md) yet. Plain HTTP permits browser takeover, and bridge isolation and session revocation need concrete designs.

I checked Hermes source at `e97923c38acba2066aff9c45e35fe1584a2155b2`. The draft makes no assertions about Hermes profile, plugin, or gateway commands, so there are no incorrect upstream command claims to identify. Its baseline does need these corrections:

- **“Score listens on 127.0.0.1 only” is wrong as an enforced restriction.** That is the default; `SCORE_HOST` already accepts LAN addresses, wildcard addresses, IPv6 and hostnames. Startup uses it directly. [Configuration](/home/raven/score-worktrees/3.13-remote-access/apps/server/src/config.ts:19), [listener](/home/raven/score-worktrees/3.13-remote-access/apps/server/src/start-server.ts:119).
- **GETs and SSE being unpaired is correct.** However, some POSTs are also unpaired, including file and configuration previews. [File preview](/home/raven/score-worktrees/3.13-remote-access/apps/server/src/http/agents.ts:113), [configuration preview](/home/raven/score-worktrees/3.13-remote-access/apps/server/src/http/settings.ts:66).
- **Console delivery, single use, a 15-minute pairing TTL, and the loopback Vite proxy are correct.** Current sessions last 30 days; Settings browser management and pairing rate limits are proposed additions.
- **“Bridge endpoints stay loopback-only” requires new enforcement.** Bridge handlers check bearer credentials but do not check the connecting address. The plugin defaults to `http://127.0.0.1:8740`, while `SCORE_URL` can override that destination. [Bridge guards](/home/raven/score-worktrees/3.13-remote-access/apps/server/src/hermes/bridge/routes.ts:76), [plugin transport](/home/raven/score-worktrees/3.13-remote-access/hermes-plugin/score_bridge/client.py:46).
- Hermes’s native API uses bearer keys, selects credentials per profile, and scopes run ownership by profile/key. Score cookies do not protect it. Native health is public. [Authentication](/home/raven/reference/hermes-agent/gateway/platforms/api_server.py:1562), [run scope](/home/raven/reference/hermes-agent/gateway/platforms/api_server_runs.py:360), [health](/home/raven/reference/hermes-agent/gateway/platforms/api_server.py:2452).

The findings below distinguish existing behavior from gaps in the proposed design.

1. **Critical — HTTP defeats both confidentiality and human confirmation.**  
   **Rule:** The review’s privacy bar and D7.1 human authority.  
   **Scenario:** A LAN attacker intercepts the pairing POST or session cookie, or replaces the downloaded JavaScript. They can then read conversations, send agent instructions and approve commands. `HttpOnly`, SameSite, rate limits and short sessions do not prevent this. Binding the cookie to an IP cannot authenticate the browser or protect page contents.  
   **Minimal change:** Require trusted TLS for LAN access. HTTP over an explicitly selected encrypted tunnel can be a separate supported case. If unrestricted LAN HTTP remains, require explicit acceptance of this takeover risk; a banner alone is insufficient. This conflicts with PLAN 3.13’s optional-TLS requirement and needs a recorded owner decision.

2. **High — Remote-off behavior can accidentally expose unauthenticated reads.**  
   **Rule:** D7 network posture and the draft’s opt-in guarantee.  
   **Scenario:** An existing environment contains `SCORE_HOST=0.0.0.0`; the new implementation enables read authentication only when `SCORE_REMOTE=1`. The server remains externally reachable with open reads. The draft also names only the IPv4 wildcard, leaving `::` unspecified.  
   **Minimal change:** Reject non-loopback bindings when remote mode is off. Require the wildcard opt-in for both `0.0.0.0` and `::`. Prefer numeric listen addresses; never silently fall back after an invalid address or TLS configuration.

3. **High — The listener change can disconnect or expose the bridge.**  
   **Rule:** D2.4 recovery, D7 bridge identity, and the draft’s loopback requirement.  
   **Scenario:** Binding only `192.168.x.x` removes the plugin’s default loopback destination. Making port 8740 HTTPS rejects its default HTTP connection. Binding a wildcard preserves connectivity but exposes bridge routes unless an additional restriction exists. Event capture and gateway decision delivery can fail while the browser appears operational.  
   **Minimal change:** Provide a dedicated loopback HTTP bridge listener and an external browser listener. Register no bridge routes on the external listener, including behind a proxy. Preserve producer authentication, compatibility gating and spool recovery. Validate both listeners before declaring startup successful.

4. **High — Public exceptions are too loosely defined.**  
   **Rule:** D7 privacy and API-contract access rules.  
   **Scenario:** An implementer treats `/api/system` as “minimal status”; it reveals served profiles, capabilities and compatibility details. Alternatively, “pairing endpoints” becomes a broad prefix exemption that later exposes browser-management routes. Future screenshots or exports could bypass protection through static serving.  
   **Minimal change:** List exact public method/path pairs: pairing redemption, boolean session status, and a deliberately minimal health response. Require authentication before handlers, adapter calls, stream headers and protected file delivery. Cover previews, HEAD, range requests and future media/export endpoints. Public static delivery must contain only the built application assets; private responses need `Cache-Control: no-store`.

5. **High — Revocation would leave existing streams authorized.**  
   **Rule:** The promised session revocation and D7 privacy.  
   **Scenario:** A browser opens SSE, then its session is revoked in Settings. An initial authentication hook blocks its next connection but the existing stream continues receiving messages. Current streaming code has no session association or expiry check. [Stream handler](/home/raven/score-worktrees/3.13-remote-access/apps/server/src/http/stream.ts:18).  
   **Minimal change:** Associate connections with their session and close them on revocation and expiry, including during replay. Enforce server-side idle and absolute expiration; stream heartbeats must not renew authority. Clear browser query caches on logout. State that revocation cannot retract previously downloaded data.

6. **Medium — Host, public origin and bind address need separate definitions.**  
   **Rule:** D7 CSRF protection and the proposed rebinding defense.  
   **Scenario:** With a wildcard bind, deriving allowed hosts or the pairing URL from `0.0.0.0` is unusable. With TLS, the existing `serverOrigin()` still constructs HTTP. Automatically trusting forwarded headers lets a caller influence the security decision. [Origin construction](/home/raven/score-worktrees/3.13-remote-access/apps/server/src/config.ts:58).  
   **Minimal change:** Configure exact browser authorities and origins independently of the listen address, including scheme and port. Support explicitly named certificate hostnames. Reject malformed authorities and missing, `null` or disallowed mutation origins in remote mode; retain `X-Score-Client`. Keep CORS disabled for same-origin serving and proxy trust disabled unless explicitly configured.

7. **Medium — Pairing does not explicitly explain the authority being granted.**  
   **Rule:** The review’s explicit-confirmation bar.  
   **Scenario:** The existing pairing loader redeems the fragment automatically before displaying the page. A shared browser opening a forwarded link receives access without a screen explaining that it can read all conversations and control every profile. [Pairing loader](/home/raven/score-worktrees/3.13-remote-access/apps/web/src/routes/pair/PairPage.tsx:5).  
   **Minimal change:** In remote mode, show that scope and require a Pair button before redemption. Keep the token only in memory after removing the fragment. Bound token input and limiter state; limit attempts globally and per peer without permanent lockout. Provide console-side token regeneration so adding another browser does not require restarting Score.

8. **Medium — The browser-management interface and acceptance tests are absent.**  
   **Rule:** AGENTS.md requires contract-first changes and task acceptance tests.  
   **Scenario:** Settings adds undocumented endpoints, or returns session credentials as browser identifiers. A route-by-route guard implementation passes happy-path tests while missing encoded routes, previews or existing streams.  
   **Minimal change:** Specify listing and revocation schemas, using management IDs distinct from credentials. Update API-CONTRACT, `packages/contract`, D7 and SETUP together. Define negative tests before implementation.

The implementer should follow this corrected design:

1. Record the LAN transport decision; require TLS for the secure LAN mode and preserve the accepted local-only mode.
2. Validate remote flags, IPv4/IPv6 bindings, certificates, public authorities and origins before starting listeners or adapter work.
3. Separate the external browser listener from the loopback bridge listener, sharing existing services and state.
4. Install authentication that denies access by default, with exact public exceptions and no generic Hermes proxy. Serve only the built web assets; keep Vite on loopback.
5. Add explicit remote pairing consent, bounded redemption attempts, fresh server-generated sessions, host-only cookies with `HttpOnly`, SameSite=Strict and Secure for TLS, plus shorter server-enforced session lifetimes.
6. Add authenticated browser listing/revocation and disconnect revoked or expired streams. Stop unauthorized reconnects and clear client caches.
7. Keep Hermes access inside both adapters. Enabling remote access must not adopt profiles, rotate keys, install plugins, restart gateways or edit Hermes configuration. Preserve D2.6’s file exception and D6 redaction.
8. Test unpaired reads/previews/streams/media, authentication before adapter calls, wildcard opt-in, Host/Origin rejection, bridge separation, token replay, expiry/revocation during SSE, and failure cleanup. Use fake adapters and recorded fixtures; finish implementation with `pnpm check`.

The opt-in approach, pairing loopback clients when remote mode is active, bundled same-origin serving, and separate browser/producer credentials are sound. Existing pairing already generates fresh 256-bit session IDs, stores hashes and rejects duplicate session cookies; I found no existing session-fixation flaw.
