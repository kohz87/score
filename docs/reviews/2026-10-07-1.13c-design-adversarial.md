**Do not enable this design yet.** At Hermes `e97923c3`, it cannot guarantee consent for exactly one execution or reliable removal. The central problem is converting call-scoped consent into profile-wide policy.

1. **Critical — Tool IDs cannot identify grant ownership.**  
   **Rule:** [D4.4](/home/raven/score/docs/ARCHITECTURE.md:265) explicitly says `tool_call_id` is nonunique; the brief nevertheless keys in-flight tracking, revocation and cleanup on it.  
   **Scenario:** Two concurrent terminal calls reuse ID `x`. A receives a grant. B has a different command with the same dangerous pattern. B’s pre hook sees the pattern already approved and, because its ID equals A’s, does not revoke it. Both guards can allow execution. A set also collapses their lifetimes.  
   **Minimum change:** Introduce a runtime occurrence identity propagated through dispatch, guard and completion. Reject ambiguous occurrences. Neither IDs alone nor thread-local state supplies this guarantee.

2. **High — Checking “no calls in flight” does not reserve exclusivity.**  
   **Rule:** Plugin steps 3–4 require exclusive execution and revocation before another call proceeds.  
   **Scenario:** A checks an empty set and waits for redeem. B passes its pre hook before A installs the grant. A then adds the pattern while B approaches its guard. Hermes’s authorization locks are per executor/batch, not process-wide.  
   **Minimum change:** Atomically reserve the occurrence before redeem, register every entering call, and serialize reservation, installation and revocation. Include pending redemption, nested dispatch and abandoned workers; capacity overflow must permanently disable granting until safely reconciled.

3. **Critical — The digest does not bind the executed command.**  
   **Rule:** D4.3 promises “this exact command.”  
   **Scenario:** Score hashes command A during `pre_tool_call`; another plugin returns `action: modify` replacing it with command B sharing the pattern. Hermes [merges modifications after invoking the callbacks](/home/raven/reference/hermes-agent/hermes_cli/plugins.py:1988), then executes B using A’s temporary permission. Changing `workdir` can also target another repository with identical command bytes.  
   **Minimum change:** Validate and consume consent at the final guard/execution boundary, after every rewrite. Bind final command plus effective execution context, including working directory and backend.

4. **High — One tool dispatch can execute four times.**  
   **Rule:** Approve once permits one execution.  
   **Scenario:** [`_run_foreground`](/home/raven/reference/hermes-agent/tools/terminal_tool.py:1240) retries `env.execute()` up to three times after the initial attempt, beneath the approval guard and without new pre hooks. A backend exception after launch can cause another execution.  
   **Minimum change:** Disable launch retries for granted calls unless the backend proves the previous attempt never launched. An uncertain launch consumes permission and requires human reconciliation. Hermes’s protection against replaying middleware continuations does not cover these retries.

5. **Critical — Cleanup failures can leave standing permission.**  
   **Rule:** The pattern must disappear after the call; uncertainty must fail closed.  
   **Scenario:** Removal times out and returns control before the sender retries; another guard acquires Hermes’s lock first and observes the permission. Missing/suppressed post hooks leave it indefinitely. Worse, a pre callback can be abandoned, receive its cleanup post, then resume and install permission afterward.  
   **Evidence:** [Plugin callbacks run on bounded daemon threads](/home/raven/reference/hermes-agent/hermes_cli/plugins_dispatch.py:274); timeout abandons rather than terminates them. Tool timeouts also synthesize posts while workers may remain alive.  
   **Minimum change:** Use an expiring, occurrence-scoped capability consumed inside Hermes’s guard, with cancellation fencing. Server-side `unknown`, sender retries and exit handlers cannot make this ambient-set mechanism fail closed.

6. **High — Removal can address the wrong profile set.**  
   **Rule:** Remove exactly the permission installed.  
   **Scenario:** A routed profile’s hook adds to its set. Another profile’s hook revokes it, or a sender retries removal without the original context. [`_permanent_set()`](/home/raven/reference/hermes-agent/tools/approval.py:329) selects the caller’s active home, so removal touches another set and silently succeeds.  
   **Minimum change:** Capture the exact governing set/home during installation and preserve ownership through every cleanup path. An ordinary `HERMES_HOME` environment value selects the launch set; context-local overrides select separate sets. Cron/webhook sessions using the same governing home share permission regardless of session.

7. **High — Score avoiding persistence does not prevent Hermes persisting it.**  
   **Rule:** Nothing reaches `command_allowlist`.  
   **Scenario:** During the temporary window, another same-home approval chooses “always.” Hermes’s [`_persist_choice`](/home/raven/reference/hermes-agent/tools/approval.py:382) snapshots the entire permanent set and saves it. The temporary entry can therefore reach config even though Score never calls the saver; an already-captured snapshot can outlive removal.  
   **Minimum change:** Keep temporary authority outside the permanent set and persistence snapshots. Testing only that Score never calls `save_permanent_allowlist` is insufficient.

8. **High — Fork cleanup discards bookkeeping, not inherited authority.**  
   **Rule:** “The child never inherits a grant.”  
   **Scenario:** Fork copies the permanent set containing the pattern. Clearing `activeGrant` and in-flight tracking leaves that pattern approved and removes the information needed to clean it up. A copied lock may also remain locked by a vanished thread.  
   **Minimum change:** Explicitly remove temporary authority from child policy before clearing ownership, with fork-safe synchronization. Prefer noninheritable scoped capabilities. The body’s “clear” instruction conflicts with its acceptance criterion requiring actual discard.

9. **High — Redemption accepts unrelated later attempts.**  
   **Rule:** D4.3 binds profile, board, task and **the next attempt**; triage/re-promotion invalidates grants.  
   **Scenario:** Run 10 receives consent; run 11 never uses it and enters triage; the specifier promotes the task before the sweep observes triage. Run 12 redeems because `12 > 10`. Redemption also specifies no grant-profile/current-assignee check, no current worker/run verification, and no feature-gate recheck.  
   **Minimum change:** Bind to the first authorized successor run, verify producer profile and worker identity against that live run, and fence invalidating events synchronously. Scope lookup/deduplication to board and profile. `HERMES_KANBAN_RUN_ID` is valid worker metadata, not server-verified attempt ownership.

10. **High — Revalidation and unblock are separate operations.**  
    **Rule:** Consent must apply to the revalidated task generation; delivery attribution requires confirmation.  
    **Scenario:** After Score’s read, Hermes changes the assignee or produces a newer blocked attempt. [`unblock_task`](/home/raven/reference/hermes-agent/hermes_cli/kanban_db.py:3724) accepts whichever blocked/scheduled generation exists then. A CLI error followed by “no longer blocked” can also mean triage, archive or someone else’s unblock—not Score success.  
    **Minimum change:** Add a Hermes conditional unblock accepting expected run/event version, assignee and board. Confirm that operation’s event; revoke grants on definite failure and fence ambiguous delivery. Read-only rechecks cannot eliminate this race. Also capture the baseline after the blocking transition: the denial hook can precede that event.

11. **Medium — Two advertised Hermes facts are wrong.**  
    **Rule:** Compatibility decisions and acceptance tests require accurate source facts.  
    **Scenario:** Implementers build detectors or exclusions around the stated behavior.  
    **Corrections:** `_unattended_deny` includes `pattern_key`/`description`, but [`_run_approval_guards`](/home/raven/reference/hermes-agent/tools/terminal_tool.py:1018) drops them when constructing the terminal denial. The hook envelope has `status: error`; its `result` is JSON text decoding directly to `status: blocked`. Batch preparation occurs **after** that slot’s pre hook, through [`_dispatch_authorized_once`](/home/raven/reference/hermes-agent/agent/tool_executor.py:747). Moreover, terminal approval batching requires desktop source plus a gateway notifier; ordinary Kanban `-q` workers have source `kanban`.  
    **Minimum change:** Correct both facts and fixtures before implementation.

**Things that are fine**

Worker argv/environment, instant deny-mode rejection without approval hooks, the plain lock, alias lookup, separate persistence and CLI syntax are verified. Adding/discarding one canonical key is sufficient when alias-aware absence was established and ownership is preserved. Tirith still runs after the unattended pattern check.

Normal sequential and concurrent dispatch run pre hooks before terminal guards; delegated agents use those paths. Deny-mode `execute_code` is rejected before permanent approval lookup; its terminal RPC dispatch otherwise uses hooks. Background starts are guarded, but posts indicate launch/handoff rather than process exit. Normal reissue after successful cleanup cannot reuse a redeemed grant.

Atomic redeem prevents two redemption winners. A full process crash destroys memory; `unknown` without automatic regrant is appropriate. L5 proves isolated-worker permission works, but does not establish these one-shot guarantees.
