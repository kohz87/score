New findings:

1. **N1 · P1 — The release predicate rejects an ordinarily queued worker (§§5–6).**  
   [beginSend checks `created`](apps/server/src/domain/orchestration/executor.ts:1876), while [recordHandle changes `send_started` to `running`](apps/server/src/domain/orchestration/executor.ts:2061). Coding [returns a handle while waiting behind another turn](apps/server/src/runtimes/coding/service.ts:558). That worker later fails §6’s mandatory `send_started` check. The same predicate cannot literally serve admission and release with these states. **Fix:** define a committed queued/armed handshake and phase-specific guards sharing the common admission rules. Release must validate its existing allocation, including the last available step, without debiting again.

2. **N2 · P1 — Generation identity stops at `recordHandle` (§5).**  
   [Message mapping uses the logical turn](apps/server/src/domain/orchestration/executor.ts:1816); [attachment requires that exact turn](apps/server/src/domain/message-runs.ts:178). Sending `turn:g1` therefore loses the room/owner join, including observation charging. Separately, [`run_handle` has no generation](apps/server/src/domain/orchestration/journal.ts:74): [verification checks every old handle](apps/server/src/domain/orchestration/fence.ts:214), and [replay attaches the first handle](apps/server/src/domain/orchestration/fence.ts:367). After g1’s refusal and g2’s admission, restart fences or attaches g1. **Fix:** bind messages, intents, handles, observations, callbacks and recovery to `(attempt, generation, launch, run)`. Fold and replay only the applicable generation while retaining old execution/accounting evidence.

3. **N3 · P1 — The policy hash does not fully bind effective configuration (§3).**  
   An environment allow-list does not specify its values; argv containing `--settings /same/path` does not bind that file’s contents. [Current environment construction](apps/server/src/runtimes/coding/env.ts:39) admits configuration homes and proxies. Changing those values across restart can preserve the proposed hash while changing the invocation. Also, Codex’s `--strict-config` rejects unknown keys; it does not exclude configuration sources. Verified against 0.160.1 and the [official OpenAI CLI reference](https://learn.chatgpt.com/docs/developer-commands?surface=cli). **Fix:** freeze noncredential environment values and settings bytes, and specify/test exclusion of hooks, rules, plugins and managed configuration for each pinned CLI. Unverifiable sources must prevent readiness.

4. **N4 · P1 — Admission-time duration does not enforce an execution-time deadline (§§8–9).**  
   [The runtime starts its duration clock after waiting/preparation](apps/server/src/runtimes/coding/service.ts:928). Reserve five minutes at admission against a deadline five minutes away; wait four minutes behind Chat; release passes because the deadline remains future. Passing only `maxTurnMs=5m` gives the supervisor another five minutes. **Fix:** carry the absolute orchestration deadline, set the supervisor expiry to `min(release-time + reservation, current deadline)`, and validate that prepared expiry at release. Define tightening while queued and while arming as well as while running.

5. **N5 · P1 — Wall-time accounting does not preserve dollar spend, and compaction can erase allocations (§8).**  
   [Usage observations update memory only](apps/server/src/runtimes/coding/translate.ts:301); a crash before terminal persistence loses a reported cost. With that source’s unknown cost accepted, subsequent budget checks can undercount it. Meanwhile, [send tombstones omit allocation data](apps/server/src/domain/orchestration/journal.ts:755), and [coding compaction keeps only the final full state](apps/server/src/domain/orchestration/journal.ts:914). §8 does not define retained accounting state. **Fix:** durably record observed USD totals/source and complete launch accounting—allocation, refund, charged duration and settlement identity—and preserve sufficient cumulative state through compaction. Replay must be idempotent.

6. **N6 · P1 — Normal pruning becomes a restore mismatch (§11).**  
   [verifyCoding requires a projection row for every journal launch](apps/server/src/domain/orchestration/coding-checkpoint.ts:252), including settled tombstones; [applyCodingEvidence recreates missing rows](apps/server/src/domain/orchestration/coding-checkpoint.ts:339). Prune a finished orchestration as proposed, restart, and Score fences admission and recreates the deleted launches. **Fix:** design a durable pruning witness and teach verification/replay to distinguish intentional deletion from lost projections, preserving execution witnesses and any outstanding obligations.

7. **N7 · P2 — Queued refusals never accumulate the intended consecutive streak (§§5–6).**  
   [recordHandle resets `refused_streak`](apps/server/src/domain/orchestration/executor.ts:2061), while [recordRefusal increments it](apps/server/src/domain/orchestration/ops.ts:317). A CLI repeatedly becoming unavailable after handle admission produces streak 1, then resets on the next queued handle. The five-refusal wait never occurs. [recordSendFailure also ignores post-handle failures](apps/server/src/domain/orchestration/executor.ts:2078). **Fix:** specify a durable, generation-qualified asynchronous refusal receipt and reset the streak only on qualified release.

8. **N8 · P2 — The restart matrix is incomplete and contradicts refund authority (§§6,8,10).**  
   §§6/8 permit refunds only with a revoke tombstone; §10 refunds “no launch record.” [Readiness can fail before any launch exists](apps/server/src/runtimes/coding/service.ts:467), while [recovery explicitly encounters requested/armed launches](apps/server/src/runtimes/coding/unit-backend.ts:1874). Neither requested/armed nor ended/settled and already-committed-result combinations have complete rows. **Fix:** define one authoritative no-launch protocol, persist its typed cause, and enumerate these states plus missing handles. Proven no execution must carry known-zero execution spend and consistent refund/try semantics.

9. **N9 · P2 — The proposed measured-time receipts do not exist (§8).**  
   [`released.json`](apps/server/src/runtimes/coding/supervisor.mjs:449) and [`ended.json`](apps/server/src/runtimes/coding/supervisor.mjs:558) contain wall-clock `at`; [receipt validation accepts them without monotonic stamps](apps/server/src/runtimes/coding/supervisor.mjs:162). Using these as the proposed measurements can mischarge clock changes or old receipts. **Fix:** explicitly extend/version the receipt format with validated paired monotonic stamps and clock/boot identity. Define whether cleanup time counts. Missing or incomparable measurements retain the conservative charge.

10. **N10 · P2 — Promised recovery controls lack contract and authorization semantics (§§3–4,8,12; Contract changes).**  
    [LimitsDecision accepts only dollar budget, deadline and global unknown-spend acceptance](packages/contract/src/orchestration.ts:425); [its journal record remains global](apps/server/src/domain/orchestration/decisions.ts:165). The proposed “raise coding limit” action therefore has no defined request. Remap’s new policy also needs renewed reach consent rather than inheriting the old acknowledged IDs. **Fix:** specify paired limits, scoped acceptance/revocation, remap/reapproval and gate contracts, with full resulting authorization journaled and verified after restore. Define the disposition for withdrawn inputs and unaccepted unknown spend.

11. **N11 · P2 — “Drain with the existing barrier” does not define shutdown (§9).**  
    [Executor close currently awaits only its pump](apps/server/src/domain/orchestration/executor.ts:316); [startup closes the executor before coding](apps/server/src/start-server.ts:188). A tracked Stop job that retries until proof can remain pending forever on `unconfirmed`, preventing coding shutdown and resource closure. **Fix:** stop scheduling retries, initiate queue cancellation/runtime shutdown, drain bounded in-flight deliveries, and leave unresolved Stops durably owed. Keep ingest/database available until receipts commit; explicitly connect the job registry to shutdown.

12. **N12 · P2 — Charging the new inventory does not reserve room for it (§11).**  
    [reserveFor remains 72 KiB per item plus the shared control reserve](apps/server/src/domain/orchestration/ops.ts:31). One 64 KiB `result_text`, plus existing step/message/run copies, already exceeds that item allowance; observations may have consumed the ordinary pool before completion. Repeated temporary revocations also create generations without refusal-counter bounds. **Fix:** give concrete reserve formulas and record-size/generation bounds for the new inventory. Preserve terminal, proof, accounting and Stop capacity independently of ordinary observations.

13. **N13 · P3 — §0 still misdescribes `turnWitnessed`; §2 names the wrong runtime column.**  
    [`turnWitnessed`](apps/server/src/domain/orchestration/coding-checkpoint.ts:194) checks projected `unsendable=1` rows. Requested/armed launches return false; revoked launches return true. It is not a direct test for any journaled launch. [`runs.origin` is `score`](apps/server/src/runtimes/coding/service.ts:511); runtime routing needs `runs.runtime` or launch metadata. §0’s result description also needs qualification: [acceptance falls back to message text and adds failure errors](apps/server/src/domain/orchestration/executor.ts:2352). **Fix:** correct these descriptions. All other §0 claims checked match current code, with the terminal-source exclusions applying to `completed`/`failed` statuses.

Read-only probes reproduced the lifecycle, generation attachment/replay, refusal-streak, usage persistence and pruning issues using in-memory SQLite. No files changed.
