**Do not approve yet.** V2 resolves **7** of the 19 v1 findings and **partly resolves 12**. The narrower scope, fixed recipients, exact human gates, and fresh sessions are substantial improvements. The remaining blockers concern admission recovery, receipt durability, executable control-flow rules, cancellation barriers, and result provenance. These need explicit design changes before implementation. This was a read-only review of v2 and the repository mechanisms it references; no files were modified or live Hermes operations invoked.

### [high] Existing intent recovery remains another admission authority

**Where:** [Executor and durable admission](/home/raven/score/docs/briefs/7.1-workflow-builder.md:18), [adapter startup](/home/raven/score/apps/server/src/hermes/live/live-port.ts:197), [intent recovery](/home/raven/score/apps/server/src/hermes/live/intents.ts:259).

**What happens:** Reusing the existing recovery path unchanged can send a workflow admission after Stop or after its deadline, before the workflow executor reconciles that run.

**Why:** `LiveHermesPort.start()` automatically recovers all pending, sent, and unknown `start_run` intents. Its dispatcher checks agent lifecycle and replay age, but has no workflow ownership, cancellation, hold, or deadline check. This conflicts with v2’s sole-admission-authority rule and its requirement to reconcile overdue runs before admission.

**Change:** Give intents an explicit owner. Workflow-owned intents must recover through the workflow executor’s persisted authorization and fences. Define startup ordering and a durable scan for unfinished transitions. Late admission evidence must still attach the external run and create an owed stop, even when its execution result would be stale.

### [high] Same-key replay is unsafe without verified receipt durability

**Where:** [Capability matrix](/home/raven/score/docs/briefs/7.1-workflow-builder.md:13), [23-hour replay rule](/home/raven/score/apps/server/src/hermes/live/intents.ts:72), [capability projection](/home/raven/score/apps/server/src/hermes/live/live-port.ts:276).

**What happens:** An accepted request loses its response, the runtime loses its receipt, and recovery resubmits the same key within 23 hours. The runtime can then create another run.

**Why:** A receipt’s existence does not establish durable deduplication across restarts. The current capability projection keeps boolean features and discards structured receipt properties. The [fake gateway](/home/raven/score/apps/server/test/hermes/live/gateway/fake-gateway.ts:82) exposes durability and retention explicitly, but admission recovery uses a fixed age cutoff without that evidence. Reposting cannot safely discover receipt loss: it may create work while checking.

**Change:** Preserve per-profile receipt capabilities, retention, and relevant runtime identity. Freeze them with the attempt and calculate a conservative replay deadline. When durable deduplication is unproven or its backing state changed, reconcile without creating work or remain unknown. Test receipt loss during a restart **inside** the current replay window.

### [high] Token rules still permit deadlocks and undefined failure routing

**Where:** [Control-flow rules](/home/raven/score/docs/briefs/7.1-workflow-builder.md:40), [attempt state machine](/home/raven/score/docs/briefs/7.1-workflow-builder.md:21).

**What happens:** An exclusive branch reconverging directly into an agent node can leave that node with one token and one skip. It satisfies neither ordinary readiness nor all-skip propagation. Failed predecessors can also strand failure branches—or activate successors before retries finish.

**Why:** Ordinary nodes require all tokens; only explicit `all` joins accept mixed token/skip inputs. Validation does not prohibit other convergence. Failure is mentioned in join success conditions, but its edge representation and propagation are absent. Attempt failure is not distinguished from exhausted node failure. Entry and end-node behavior are also unspecified.

**Change:** Provide a transition and edge-resolution table for every node kind. Require explicit joins where necessary, define failure/cancellation propagation and retry exhaustion, distinguish node state from attempt state, and specify when multiple ends permit a run to finish. Test mixed-input convergence and failed attempts followed by retries.

### [high] First joins lack a safe cancellation scope and completion barrier

**Where:** [First-join behavior](/home/raven/score/docs/briefs/7.1-workflow-builder.md:43), [run Stop fence](/home/raven/score/docs/briefs/7.1-workflow-builder.md:36), [existing owed-stop mechanism](/home/raven/score/apps/server/src/hermes/live/intents.ts:166).

**What happens:** Applying the described run-wide fence to a losing branch prevents the winning continuation from starting. Interpreting it as a branch fence instead can launch successors while losing agents still act.

**Why:** The only defined fence moves the whole run to `stopping`. First joins become ready immediately, without a loser-draining state or a definition of which nodes belong exclusively to a losing branch. The referenced stop mechanism marks `stop_state = 'done'` after a successful Stop response, including `stopping`; that marker does not prove termination.

**Change:** Define branch/attempt cancellation separately from run cancellation, including ownership of shared nodes and pending admissions. Persist the winner, drain exclusively losing work, and retain its capacity/spend reservations until terminal evidence arrives. Specify which successors require that barrier. Separate Stop acknowledgement from proven termination, or defer first joins.

### [high] “Mark done/failed” can leave an old admission executable

**Where:** [Unknown-state recovery](/home/raven/score/docs/briefs/7.1-workflow-builder.md:24), [automatic unknown-intent replay](/home/raven/score/apps/server/src/hermes/live/intents.ts:265).

**What happens:** A person marks an uncertain step failed and a retry starts, while its original admission remains replayable or its original agent continues running. Marking it done can similarly release successors alongside unresolved work.

**Why:** V2 supplies the UI instruction but no resolution protocol. It does not say how the old intent is permanently retired, what evidence/output is frozen, how late acceptance is handled, or whether human classification proves termination. The existing adapter explicitly revisits unknown intents.

**Change:** Define a paired, revision-bound resolution command. Permanently retire the original admission, preserve execution uncertainty separately from the human-selected outcome, freeze supplied evidence, and specify late-admission stops. Continuing with unresolved execution must require an explicit recorded decision; ordinary Resume must not silently release it.

### [high] Existing recovered results do not prove runtime success

**Where:** [Result envelope](/home/raven/score/docs/briefs/7.1-workflow-builder.md:48), [forgotten-run recovery](/home/raven/score/apps/server/src/hermes/live/runs.ts:85), [synthetic completion](/home/raven/score/apps/server/src/hermes/live/translate.ts:481).

**What happens:** Recovered assistant text becomes workflow success without canonical terminal evidence. A locally synthesized terminal row can also be mistaken for confirmation that cancellation finished.

**Why:** Existing recovery finds a plain assistant reply and synthesizes `completed`; absent text produces `interrupted`. Those are recovery conclusions, not necessarily observed runtime terminal states. Normal result storage also [clips output to 8 KiB](/home/raven/score/apps/server/src/hermes/live/translate.ts:335) without a truncation flag. A workflow reading that projection cannot construct v2’s promised provenance and truncation information reliably.

**Change:** Define adapter facts that distinguish canonical runtime termination, recovered text, and lost observation. Keep text recovery separate from success and termination proof. Freeze one authoritative, sanitized output with source identity and truncation metadata. Specify the exact structured-review schema and parser; reject malformed or incomplete verdicts instead of inferring approval.

### [high] Import approval does not bind the agent incarnation

**Where:** [Import admission checks](/home/raven/score/docs/briefs/7.1-workflow-builder.md:86), [agent incarnation identity](/home/raven/score/apps/server/src/domain/agent-lifecycle.ts:6).

**What happens:** An approved mapping names `builder`. That profile is deleted and recreated under the same ID with different configuration. It still exists and is served, so v2’s admission checks accept a different agent without invalidating the review.

**Why:** Definition hash and mapping revision bind the mapping record, but not the identity behind its agent ID. Score already tracks `incarnation_id`; the proposed admission checks omit it.

**Change:** Bind local mappings to incarnation and required runtime capabilities. Revalidate them at every admission and invalidate approval on replacement or incompatible capability changes. Freeze incarnation and the adapter’s credential-generation/runtime identity with each attempt. Test deletion and recreation under the same name.

### [medium] Budget checks can mistake stale spend for current known spend

**Where:** [Budget accounting](/home/raven/score/docs/briefs/7.1-workflow-builder.md:59), [window calculations](/home/raven/score/apps/server/src/domain/spend.ts:47), [sampling interval](/home/raven/score/apps/server/src/start-server.ts:375).

**What happens:** A step finishes after the latest cost sample. Its successor is admitted using an older, apparently known balance even though actual spend has already reached the budget.

**Why:** Existing session accounting samples every ten minutes, overwrites quarter-hour readings, and can use a preceding reading when the window has no new sample. V2 does not define a freshness requirement, compression-lineage attribution, or reservation settlement after cancellation and uncertain admission. Soft-budget overshoot during a running step does not justify stale checks between steps.

**Change:** Use attempt-owned cost readings or fresh reconciliation at admission boundaries. Persist attribution, observation time, estimated/actual status, and reservations. Treat insufficiently fresh evidence as unknown. Define settlement and retain reservations while admission or termination remains unresolved.

### [medium] Absolute deadlines still need origins and precedence rules

**Where:** [Deadlines](/home/raven/score/docs/briefs/7.1-workflow-builder.md:65).

**What happens:** A workflow waiting before admission may escape its intended deadline; execution retries may reset node deadlines; simultaneous completion and expiry can produce different outcomes across recovery paths.

**Why:** “Persisted at admission” does not distinguish workflow start, node readiness, first attempt, and subsequent attempts. Paused time is defined, but gate/queue waiting, retry inheritance, and completion-versus-expiry precedence are not.

**Change:** Define each deadline’s origin and scope. Persist the run deadline at start, specify retry inheritance and waiting-time treatment, and check expiry inside every admission transaction. Define deterministic precedence and keep timeout routing behind the required termination barrier.

### [medium] Defaults permit unordered template dependencies

**Where:** [Template validation](/home/raven/score/docs/briefs/7.1-workflow-builder.md:46).

**What happens:** Parallel node A references B with a default. A receives B’s output if B finishes first and the default otherwise. A descendant or self-reference can also pass the literal fallback exception.

**Why:** The fallback clause removes the guaranteed-ancestor requirement without imposing another ordering requirement. A default solves unavailable output on a skipped path; it does not establish when an unrelated node’s output becomes eligible.

**Change:** Restrict references to ordered ancestors whose availability is settled before admission. Allow defaults for skipped conditional ancestors, forbid forward/self references, and define whether discarded first-join results are available. Freeze the exact consumed attempt/output revisions.

### [medium] Workflow projections do not yet define brief and human-action behavior

**Where:** [Projection/API proposal](/home/raven/score/docs/briefs/7.1-workflow-builder.md:69), [brief status derivation](/home/raven/score/apps/server/src/domain/briefs.ts:192), [Now’s human-action selection](/home/raven/score/apps/server/src/domain/now.ts:118).

**What happens:** A workflow’s brief appears done between agent steps while the workflow waits at a gate. Workflow-local gates do not reach Now’s existing “Needs you” selection. Generic brief controls may apply different hold semantics.

**Why:** Brief status derives from turns, tasks, and one pause flag. Now selects the existing approvals ledger. Adding workflow tables and a separate Flow graph does not define how these consumers change. Mutation names and event names also leave request schemas, conflict responses, gate snapshots, and historical transitions unspecified.

**Change:** Define workflow ownership of brief status, gate/budget visibility in Now, and how existing controls operate on workflow-owned objects. Specify the complete API and stream payloads, expected revisions, conflicts, snapshot watermarks, and durable history. Complete the contract extension before implementation.

### [medium] Limits omit expanded payloads and nonterminal resource accounting

**Where:** [Limits](/home/raven/score/docs/briefs/7.1-workflow-builder.md:81), [admission input schema](/home/raven/score/apps/server/src/hermes/live/gateway.ts:53).

**What happens:** An 8 KiB template repeats a 32 KiB predecessor output many times and produces a much larger prompt. Paused runs with active steps can fall outside the “five running runs” count. Repeated completed or gate-waiting runs accumulate rooms, sessions, and retained payloads indefinitely.

**Why:** Definition and output limits do not bound inputs or rendered admission size. Run-state limits do not necessarily count admitting, stopping, or unknown work. Retention and storage quotas are absent.

**Change:** Bound start inputs, expanded UTF-8 payloads, and stored attempt data. Claim capacity atomically and count unresolved external work until quiescent, including work in paused runs. Specify retry-session policy, waiting-run limits, retention, cleanup, and quota behavior.

### [medium] Run-ID filtering alone cannot establish exact replay association

**Where:** [Replay promise](/home/raven/score/docs/briefs/7.1-workflow-builder.md:80), [session-to-run lookup](/home/raven/score/apps/server/src/domain/watch-frames.ts:363), [frame association](/home/raven/score/apps/server/src/domain/watch-frames.ts:415).

**What happens:** Frames arriving before a session association is recorded are stored without a run ID. Compression changes the session ID; reused sessions can attribute delayed frames to another attempt. Filtering by run ID then omits or misattributes evidence.

**Why:** Current association chooses the newest run matching the currently projected session ID. It has no durable attempt/session-lineage ownership proof. Markers and gaps also use agent-wide queries.

**Change:** Persist attempt-owned session lineage and proven frame associations, preferably with a unique session per execution attempt. Preserve uncertain associations explicitly. Scope frames, markers, gaps, live state, and pagination consistently; record retention boundaries so missing history remains visible after deletion.

### [medium] Export redaction covers only instruction text

**Where:** [Portable export](/home/raven/score/docs/briefs/7.1-workflow-builder.md:83), [redaction behavior](/home/raven/score/apps/server/src/redact.ts:35).

**What happens:** A secret pasted into a gate question, input label, branch operand, or other exportable text leaves the repository in the exported JSON despite instructions being scrubbed.

**Why:** These fields are arbitrary text, while v2 applies `redact()` only to instructions. Pattern redaction also cannot establish that every arbitrary secret has been removed.

**Change:** Define scrubbing for every exportable free-text field, show a complete diff, and revalidate the transformed definition. Provide full-definition review and manual removal; describe the export as scrubbed rather than guaranteed secret-free. Test secret-bearing fields beyond instructions.

## The design I would approve

- Keep initial scope to Hermes room runs and text results. Specify complete node, edge, retry, and termination semantics; defer first joins unless their cancellation ownership and barriers are defined.
- Make workflow-owned admission and recovery obey one persisted authority, with startup fences and verified per-profile receipt durability and expiry.
- Separate runtime termination evidence, recovered text, and human assertions. Define unknown resolution, late admissions, scoped stops, and immutable result/verdict provenance.
- Bind mappings to agent incarnation and capabilities; freeze consumed output revisions and use explicit attempt/session-lineage ownership.
- Enforce fresh soft-budget checks, durable reservations, precise deadline rules, expanded-payload limits, nonterminal capacity limits, and retention quotas.
- Complete workflow status and human-action integration in the contract, including exact replay scope and all exportable text.
- Extend the fixture suite with the counterexamples above before building the editor.
