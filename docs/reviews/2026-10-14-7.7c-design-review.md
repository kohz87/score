# 7.7c design review (Codex gpt-6.1-sol, max, read-only), 2026-10-14

Reviewed: docs/briefs/7.7c-coding-workflows.md v1. Verdict: BLOCK (1 P1, 7 P2, 2 P3). #9 was a live 7.7b bug (owned runs wrote Chat's session cache): fixed in v1.2.1. Responses: design v2.

**BLOCK — 1 P1, 7 P2, 2 P3.** Reviewed design v1 against current commit `18e17fd0`.

1. **P1 — Suspended coding work can be recreated and run twice (§§0,4).**  
   [workflows/planner.ts:298](apps/server/src/domain/workflows/planner.ts:298) clears a blocked node’s `step_id`; [orchestration/decisions.ts:206](apps/server/src/domain/orchestration/decisions.ts:206) resumes its original suspended step when the limit rises. The planner can then assign a replacement. **Scenario:** a coding-limit block followed by “Raise the limit” leaves both steps dispatchable. An in-memory probe produced two Codex attempts whose release checks both returned `allowed: true`, and `attempts_used = 2` despite `attempts_max = 1`. **Fix:** preserve the node→step→suspended-attempt association through policy and limit decisions; re-admit that same attempt. Test concurrency one and two, fan-out, tight budgets and restart.

2. **P2 — §4 binds the wrong kind of gate (§4).**  
   [executor.ts:1307](apps/server/src/domain/orchestration/executor.ts:1307) routes assignment gates to `decideGate`, while `decideNodeGate` handles separate graph gates. Assignment payloads created at [workflows/planner.ts:598](apps/server/src/domain/workflows/planner.ts:598) omit `policyId`; [coding-policy.ts:120](apps/server/src/domain/orchestration/coding-policy.ts:120) requires it. **Scenario:** an approved `every-step` coding assignment immediately blocks as `agent_changed`. **Fix:** explicitly bind assignment gates at creation, re-approval, admission and release. Define graph-gate bindings separately: a `kind: 'gate'` node has no agent.

3. **P2 — Policy remap and agent substitution lack workflow contracts (§4; Contract changes).**  
   [WorkflowRemapDecisionSchema:861](packages/contract/src/workflows.ts:861) rejects policy/consent fields; [workflows/decisions.ts:231](apps/server/src/domain/workflows/decisions.ts:231) rejects unchanged incarnations. The existing policy-remap entry point explicitly requires a lead orchestration at [executor.ts:1077](apps/server/src/domain/orchestration/executor.ts:1077). **Scenario:** changing a bound CLI configuration blocks a node, but neither workflow remap nor the orchestration endpoint can repair it. **Fix:** specify a revision-bound workflow node policy-remap API, current-policy report, per-step mapping and renewed consent. Also define an explicit target-agent mapping for “to/from coding,” or remove that promise; current remap replaces the incarnation of the same agent ID.

4. **P2 — “Try again” cannot continue after twenty coding refusals (§4; Done when).**  
   [workflows/decisions.ts:195](apps/server/src/domain/workflows/decisions.ts:195) resets refusal counters on the existing attempt. [executor.ts:2333](apps/server/src/domain/orchestration/executor.ts:2333) independently rejects generation 21. **Scenario:** twenty readiness refusals → Try again → immediate `held_back_too_often`; the probe reproduced this. **Fix:** define a fresh, durable dispatch identity/allocation for this decision, with bounded storage and unchanged logical-retry semantics. Never reset or reuse generation identities.

5. **P2 — Storage must be reserved per retained coding attempt, not drawn node (§7).**  
   [workflows/runs.ts:30](apps/server/src/domain/workflows/runs.ts:30) budgets retries and remap recreations; [ops.ts:70](apps/server/src/domain/orchestration/ops.ts:70) defines the protected coding allocation. **Scenario:** one coding node, two retries and `codingSteps = 3` retains three items, but §7 adds only one item’s allocation. Ordinary observations can exhaust the remaining room before results arrive. **Fix:** give a concrete formula covering permitted coding attempts and every retained workflow copy, including `wf_results` and node output. Set the protected partition at creation and keep limit-growth accounting consistent with it.

6. **P2 — Live workflow views cannot support the promised recovery and scoped cost controls (§§2,6; Contract changes).**  
   [WorkflowNeedsYouSchema:571](packages/contract/src/workflows.ts:571) has no coding-limit or policy-change item. [workflows/views.ts:576](apps/server/src/domain/workflows/views.ts:576) reports the frozen start-time `unknownSpend`, and supplies no coding authorization state; shared scoped-cost buttons require `run.coding` at [RunDecisions.tsx:294](apps/web/src/routes/orchestrations/RunDecisions.tsx:294). **Scenario:** later limits revoke global acceptance or a coding step blocks, but the snapshot cannot represent the effective acceptance or promised card. **Fix:** extend workflow summary/detail/decision contracts with current authorization, accepted sources, coding limit and actionable blocked-node items.

7. **P2 — Definition validation has no runtime validation path (§§1,6).**  
   [http/workflows.ts:65](apps/server/src/http/workflows.ts:65) calls the graph-only [validateDefinition:131](apps/server/src/domain/workflows/definition.ts:131), without team or host facts. **Scenario:** Validate reports an Antigravity or `full` agent definition as valid, then save rejects it; replacing the existing save guards does not change this. **Fix:** specify runtime validation and structured issue codes alongside graph validation, consistently across Validate, initial save, new versions and start. Keep volatile readiness outside immutable definition hashes.

8. **P2 — The default coding limit needs a zero-worker rule (§2).**  
   The proposed default is zero for Hermes-only and gate-only graphs; 7.7b’s request limit starts at one at [orchestration.ts:187](packages/contract/src/orchestration.ts:187). **Scenario:** computing and submitting that default through reused validation rejects an existing Hermes-only workflow. **Fix:** explicitly omit coding authorization/limits when there are no coding workers, preserving the existing path and reserve. Add Hermes-only and gate-only regression cases.

9. **P3 — §0’s cache claim needs a Hermes-only qualification (§§0,5).**  
   §0’s guard locations, create fields, result join and decision names match current code. Cache isolation is not inherited from the coding worker path: [service.ts:698](apps/server/src/runtimes/coding/service.ts:698) avoids reading Chat’s cache for owned runs, but [translate.ts:221](apps/server/src/runtimes/coding/translate.ts:221) still writes it. **Scenario:** a workflow session overwrites the cache; subsequent Chat resumes that session. The translator probe confirmed the overwrite. **Fix:** describe §5 as new work and propagate ownership to suppress cache writes while retaining the run’s session identity. Do not clear Chat’s cache on release.

10. **P3 — The claimed verdict-input limit does not exist (§3).**  
    [verdict.ts:58](apps/server/src/domain/workflows/verdict.ts:58) parses the complete reply before limiting stored output; `result_text` comes from an already capped copy at [coding/translate.ts:377](apps/server/src/runtimes/coding/translate.ts:377). **Scenario:** two verdict blocks separated beyond 32 KiB yield no verdict from the full answer, but `passed` from the retained prefix; the probe confirmed this. **Fix:** name raw `TerminalInfo.reply` as the parsing input, before storage cuts. Define any input bound explicitly and never parse a truncated prefix or coding display fallback.

Read-only review with in-memory probes; no files changed or live CLIs invoked. The full suite was not run.
