The remaining findings are:

1. **P1 — ORDINARY PATH — A valid failure can be overwritten by a later success.**  
   [codex.ts:174](apps/server/src/runtimes/coding/codex.ts:174), [claude.ts:243](apps/server/src/runtimes/coding/claude.ts:243), [service.ts:978](apps/server/src/runtimes/coding/service.ts:978).

   Valid failed terminals neither close the parser’s terminal state nor invalidate subsequent success. The service replaces `result` on every result event.

   A probe supplied `turn.failed → agent_message → turn.completed`, with a mocked clean unit exit and ended proof. The real parser and `CodingRuntime` stored **`status: completed`, `error: null`, eligibility `eligible`**. Claude likewise accepts an error result followed by an explicit success result, with `lossReason() === null`.

   **Fix:** enforce one terminal per attempt. A duplicate or contradictory terminal must make the attempt ineligible; a failed terminal cannot be replaced. A permitted resume retry must use its existing proof checks and a fresh parser/launch.

2. **P1 — ORDINARY PATH — A same-home restore can adopt the reset generation while retaining executable replies.**  
   [fence.ts:826](apps/server/src/domain/orchestration/fence.ts:826), [fence.ts:846](apps/server/src/domain/orchestration/fence.ts:846).

   `databaseHoldsExecutionHistory()` checks only `orc_attempts`, `coding_launches` and `command_intents`. A backup containing a queued chat reply, taken before intent creation, passes its “brand new database” exception.

   With a completed external reset and that older database, the startup probe returned **`fenced: false`, freeze `null`**, adopted the new generation, and left the old reply **`pending`**. That reply can dispatch again. This directly defeats decision 72(b), including for ordinary restores of the same home.

   **Fix:** restrict adoption to a demonstrably fresh database, or include every surviving executable state in the check—particularly replies, runs and approval deliveries. A pre-reset backup must freeze before any dispatcher starts.

3. **P1 — FROZEN STATE — Reset preserves active replies, usable run handles and unfinished approvals.**  
   [history-reset.ts:274](apps/server/src/history-reset.ts:274), [history-reset.ts:285](apps/server/src/history-reset.ts:285), [message-runs.ts:558](apps/server/src/domain/message-runs.ts:558).

   Reset retires an active reply only when `run_id IS NULL`. An accepted start with an existing run survives, as does the live run row. `approval_deliveries` is untouched.

   The probe retained **active reply + accepted intent + running source handle** after reset. A late completion containing `@builder` created a pending hand-off; the real `RoutingDispatcher` then dispatched **builder**. Another probe renewed the same bridge approval lease after reset.

   In a copied home, surviving handles also remain usable by direct Stop and approval routes once reset clears the freeze.

   **Fix:** retire every unfinished reply, invalidate old control handles and approval deliveries, and prevent follow/recovery from giving retired runs routing or control authority. Late evidence may be displayed historically but must not create work.

4. **P1 — FROZEN STATE — Bridge approvals and routine execution bypass the freeze.**  
   [approval-outbox.ts:288](apps/server/src/domain/approval-outbox.ts:288), [live-port.ts:412](apps/server/src/hermes/live/live-port.ts:412).

   `claimBridge()` never checks the shared hold. It leases decisions directly to the plugin, bypassing guarded `LivePort.deliverDecision()`. With `frozen_reason` set and the port reporting a hold, the probe still returned an actionable **`once` approval** for the old session/request.

   `runRoutine()` similarly calls the Hermes routine runner without `assertThawed()`, allowing an agent turn while frozen.

   **Fix:** guard bridge leasing inside its claim transaction and guard routine execution at the outgoing adapter boundary. Apply the same check to execution-enabling routine/task actions.

5. **P2 — FROZEN STATE — Live coding Stops use unguarded control paths.**  
   [service.ts:608](apps/server/src/runtimes/coding/service.ts:608), [unit-backend.ts:749](apps/server/src/runtimes/coding/unit-backend.ts:749), [coding-socket.ts:228](apps/server/src/runtimes/coding/coding-socket.ts:228).

   Recovery signaling checks the freeze, but a live `CodingRuntime.stopRun()` invokes its process handle directly. `sendStop()` checks whether the session is connected, without checking the hold. Socket shutdown also sends a Stop unconditionally.

   With `frozen: () => 'freeze'`, the direct backend probe still sent **`stop('user')`**. Thus decision 72(a)’s “every outgoing coding boundary” requirement remains incomplete.

   **Fix:** enforce the shared predicate on live control paths and immediately before outgoing Stop/cancel frames and signals. Preserve the supervisor’s independent disconnect/watchdog containment.

6. **P1 — FROZEN STATE — Reset takes a different home lock from the running server.**  
   [history-reset.ts:150](apps/server/src/history-reset.ts:150), [db/lock.ts:81](apps/server/src/db/lock.ts:81), [scripts/installation.mjs:64](scripts/installation.mjs:64).

   Reset locks **`<home>/lock.sqlite`**. `startServer()` holds **`<home>/score.lock`**. These exclude neither process from the other. The earlier `score.pid` check also misses direct server starts and races a restart during confirmation.

   Reset can consequently publish completion while a live runtime retains its queues and handles. With a simulated in-flight unit boundary, the runtime probe dispatched **`queued-before-reset` after retirement committed**, and subsequently marked it completed.

   **Fix:** use the actual shared home lock across identity resolution, archive, database retirement and completion publication. If replacing it with an OS sidecar lock, switch both server and reset together. PID checks cannot provide this exclusion.

7. **P2 — FROZEN STATE — Loss detection still accepts missing or shorter journals.**  
   [journal.ts:493](apps/server/src/domain/orchestration/journal.ts:493), [fence.ts:519](apps/server/src/domain/orchestration/fence.ts:519), [fence.ts:397](apps/server/src/domain/orchestration/fence.ts:397).

   Two single-loss cases remain:

   - During an existing server incarnation, journal disappearance becomes an **empty, readable history**. Even with database launch evidence, `executionFrozen()` returned **null**, and the outgoing Hermes guard allowed dispatch. Missing-history detection runs only at startup.
   - Truncate an orchestration attempt from generation 2 back to its surviving generation-1 refusal. `unjournaledAttempts()` checks only whether the ID exists; forward verification accepts the database being ahead. The startup probe returned **no fence and no freeze**.

   **Fix:** treat disappearance of established history as a hold before decisions/appends, and compare orchestration generations and high-water state in both directions. Matching an attempt ID does not establish complete evidence.
