1. **High — Identifier casing can bypass the terminal guard.**

   **Evidence:** [projections.ts:76](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/projections.ts:76) compares column names case-sensitively, while SQLite treats `ID` and `id` as the same identifier. The subsequent SELECT and UPSERT can consequently target different rows.

   Reproduced with an existing `terminal/completed` row:

   ```ts
   key: { ID: 'different-row' },
   values: { id: 'terminal', state: 'running' }
   ```

   This returned `'applied'` and changed `terminal` to `running`.

   **Fix:** Canonicalize column identifiers before checking key conflicts, merging values, and constructing updates. Reject conflicting aliases. Test casing variants for simple and composite keys.

2. **High — A listener can change what later listeners receive.**

   **Evidence:** [ingest.ts:100](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/ingest.ts:100) passes the same mutable batch and envelopes to every listener. `readonly StreamEvent[]` leaves envelope properties mutable.

   Reproduced: listener A changed `seq` to `99` and `messageId` to `"mutated"`. Listener B received those values, while SQLite contained seq `1`, message `"one"`, and `submit()` returned `seqs: [1]`. Clearing the batch also suppressed delivery to later listeners.

   **Fix:** Deep-freeze the envelopes, nested payloads, and batch before fan-out; expose deeply readonly types. Test mutation attempts followed by an independent listener.

3. **High — Single-writer ownership is not enforced.**

   **Evidence:** Every [createIngest call at ingest.ts:57](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/ingest.ts:57) creates an independent queue and listener registry. The [restart test at ingest.test.ts:166](/home/raven/score-worktrees/1.4a-ingest/apps/server/test/hub/ingest.test.ts:166) actually leaves two instances alive.

   Reproduced by submitting `A.one`, `A.two`, then `B.three` against one `ScoreDb`:

   ```text
   committed order: one, three, two
   A notifications: [1, 3]
   B notifications: [2]
   ```

   SQLite still serializes transactions, but it does not merge publication queues. Another process has the same notification problem. A subscription fence using only one instance’s notifications cannot capture foreign commits during replay.

   **Fix:** Have one hub owner per database, with explicit shutdown/release semantics. Enforce process ownership of the canonical database path at startup. Test rejection of a second active owner and successful ownership transfer after shutdown.

4. **High — Checkpoints can regress or advance past a failed observation.**

   **Evidence:** [ingest.ts:35](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/ingest.ts:35) unconditionally replaces the cursor and incarnation. The queue continues after failures at [ingest.ts:114](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/ingest.ts:114).

   Two reproductions:

   - Cursor `10`, then `20`, then duplicate `10` left checkpoint `10`. Omitting incarnation also replaced the previous incarnation with `NULL`.
   - Observation `10` failed; queued observation `11` succeeded. Only ingest key `11` existed, but checkpoint `11` was committed. A tailer resuming above that checkpoint skips observation `10`.

   The latter also follows from a transient busy failure followed by a successful submission.

   **Fix:** Define source-specific checkpoint advancement: preserve monotonic progress within an incarnation and advance only through acknowledged observations. Hold a source’s checkpoint at a failure until retry or an explicit gap record; keep unrelated sources moving. Make incarnation reset explicit. Do not compare opaque cursor strings lexically.

5. **Medium — Lazy snapshot results escape the read transaction.**

   **Evidence:** [snapshot.ts:18](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/snapshot.ts:18) rejects promises but accepts SQLite iterators and returns them after COMMIT.

   Reproduced:

   ```ts
   snapshot(db, sqlite =>
     sqlite.prepare('SELECT id FROM runs ORDER BY id').iterate(),
   )
   ```

   After another observation committed, consuming the returned iterator produced `["one", "two"]` with `asOfSeq: 1`.

   **Fix:** Require materialized snapshot data. Reject lazy iterators/functions and perform `.all()` plus contract parsing inside the read transaction. Add this exact regression case.

6. **Medium — Async listeners can complete delivery out of sequence.**

   **Evidence:** Promise-returning listeners are supported, but [ingest.ts:100](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/ingest.ts:100) invokes later batches without waiting for earlier listener work.

   Reproduced with a listener awaiting a gate for seq `1`: `drain()` returned after seq `2` was delivered; releasing the gate produced delivery order `[2, 1]`. Callback invocation itself remained ordered.

   **Fix:** Use a separate ordered promise chain per listener without blocking the writer, or require synchronous callbacks that enqueue into an ordered subscriber queue. Test delayed delivery of the first batch.

7. **Medium — Rejecting an async apply does not stop its writes.**

   **Evidence:** [ingest.ts:78](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/ingest.ts:78) invokes `apply` before discovering that its result is not iterable. The [async-apply test at ingest.test.ts:214](/home/raven/score-worktrees/1.4a-ingest/apps/server/test/hub/ingest.test.ts:214) merely returns `Promise.resolve([])`.

   With an actual async callback, I reproduced:

   ```text
   submit: rejected
   write before await: rolled back
   write after await: persisted outside a transaction
   events, ingest_keys, checkpoints: empty
   ```

   This violates the synchronous callback contract, but the runtime rejection currently provides misleading protection. A later rejection can also remain unhandled.

   **Fix:** Reject native async callbacks before invoking them, handle unexpected returned promises, and make transaction-scoped SQLite access unusable after rollback. Test a callback that writes after an awaited gate.

8. **Medium — The post-commit acceptance test can swallow its own failures.**

   **Evidence:** Assertions in [ingest.test.ts:293](/home/raven/score-worktrees/1.4a-ingest/apps/server/test/hub/ingest.test.ts:293) execute inside a committed listener. Ingest catches assertion failures, logs them, and returns successfully. The test’s external check only verifies that the listener was called.

   An intentionally false listener assertion reproduced exactly that outcome: logged failure, successful submission, one callback invocation.

   Also, the [zero-event test at ingest.test.ts:176](/home/raven/score-worktrees/1.4a-ingest/apps/server/test/hub/ingest.test.ts:176) claims to prove projection persistence but replaces `apply` with `() => []`, which writes no projection.

   **Fix:** Capture listener observations and assert outside the callback; assert that no listener error was logged. Make the zero-event callback actually write a projection and verify its persistence.

9. **Medium — Terminal rows discard enrichment when their state stays unchanged.**

   **Evidence:** [projections.ts:95](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/projections.ts:95) returns `'ignored_terminal'` by default even when `current === nextState`. This differs from `canTransition()` and the same-state allowance in [the brief at line 55](/home/raven/score-worktrees/1.4a-ingest/docs/briefs/1.4a.md:55).

   Reproduced: updating a completed row’s detail was ignored; the same update succeeded with `refreshTerminal: true`. Consumers can therefore discard later metrics or reconciliation data unless they know about this added flag.

   **Fix:** Restore the brief’s allowance for unchanged terminal states, with source-version checks to prevent stale enrichment. Add a test for legitimate enrichment after completion.

10. **Medium — D2.3’s entity identities need a separate observation-version policy.**

    **Evidence:** [ingest.ts:71](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/ingest.ts:71) drops a matching key without inspecting the new payload. Reproduced: `"original"` followed by `"edited"` under the same key returned `'duplicate'` and retained `"original"`.

    This matches the brief, but [D2.3’s identity table](/home/raven/score-worktrees/1.4a-ingest/docs/ARCHITECTURE.md:115) mixes immutable observation identities and mutable entity identities:

    - Bridge incarnation/counter, run SSE run/seq, and append-only task-event IDs work for immutable redelivery.
    - Tool-call lifecycle IDs, run IDs used for status polling, approval request IDs, mutable task-run rows, and message IDs/UIDs require distinct observation revisions.
    - `task_events.id` and `task_runs.id` can collide if both become plain numeric identities under source `"kanban"`.

    **Fix:** Explicitly distinguish projection entity keys from observation dedupe keys. Namespace table/event kinds and include a revision or content version for mutable observations. Detect conflicting immutable redelivery at the producer edge.

11. **Low — Ingest keys form an indefinitely growing second log.**

    **Evidence:** Keys are inserted at [ingest.ts:67](/home/raven/score-worktrees/1.4a-ingest/apps/server/src/hub/ingest.ts:67), including observations that emit nothing. There is no retirement mechanism. After 1,000 observations and deletion of every event, all 1,000 keys remained.

    **Fix:** Define source-aware retirement or compaction using durable acknowledged floors and producer lifetimes. Retain enough information to reject old redelivery. Deleting keys solely because their events were pruned would re-enable duplicate application.

**Things that are fine**

- For synchronous applies, throwing after projection writes, failing validation on the second event, and failing checkpoint insertion rolled back projections, events, keys, and checkpoints together. Later submissions succeeded. Injected busy failures at BEGIN and COMMIT also preserved atomicity; actual cross-process contention was not exercised.
- One ingest instance preserves FIFO, including reentrant submissions behind already queued work. Ordinary fan-out starts after COMMIT, and listener failures do not reject the committed submission.
- Zod normalization happens before persistence. Without listener mutation, stored JSON exactly matched serialized live data, including removal of unknown fields.
- `(source, identity)` correctly isolates distinct sources. Duplicate checkpoint updates and intentional zero-event observations follow the brief.
- Eager snapshot reads obtain head and projections in one transaction. Reading head first establishes the WAL snapshot before the callback. [SQLite isolation documentation](https://www.sqlite.org/isolation.html).
- `sqlite_sequence` is a suitable committed insertion high-water mark here. Pruning and in-memory VACUUM preserved it; rolled-back assignments may be reused. A restored backup carries its older head, so restoration must regenerate the epoch before serving clients. [AUTOINCREMENT](https://www.sqlite.org/autoinc.html), [VACUUM](https://www.sqlite.org/lang_vacuum.html).
- Identifier validation and bound values prevent ordinary SQL injection. NULL keys are rejected, invalid/NULL states fail closed, and consistently named composite keys work. `BEGIN IMMEDIATE` protects the guard’s read/write pair from competing writers.
- `ignored_*` guards protect SQL only. Callers must suppress drafts using the exact `'applied'` check shown in the tests; unconditionally returned drafts are still persisted.
- A process crash between COMMIT and fan-out leaves committed events available for task 1.4b’s replay. The persistence format does not make recovery impossible.
