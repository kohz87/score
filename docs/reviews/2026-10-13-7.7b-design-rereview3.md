I verified every §0 “what exists” claim against the code. **No remaining §0 misdescription found.** Decision 75’s simplifications are accepted.

1. **P1 — External policy identities become stale during arming (§§3,6).**  
   V4 re-reads identities before arming, then authorizes the prepared policy hash. The runtime [prepares the spec before asynchronous arming](apps/server/src/runtimes/coding/unit-backend.ts:985); the supervisor later [executes its command by pathname](apps/server/src/runtimes/coding/supervisor.mjs:477). **Scenario:** replace the CLI or edit a bound configuration file while the supervisor starts. The authenticated spec remains unchanged, so authorization passes although execution reads a different binary/configuration. This can change reach after consent. **Fix:** revalidate executable, workspace and every bound source inside the release critical section immediately before `releasing`; mismatch ⇒ typed `agent_changed` revocation. Ensure generated settings consumed by the CLI remain the hashed bytes. Test changes between preparation and release.

2. **P2 — Re-approval leaves an executable attempt behind the new gate (§§6,12a).**  
   `agent_changed` leaves the attempt `created`, while re-approval returns its step to `pending_gate`. Current [dispatch selection ignores step status](apps/server/src/domain/orchestration/executor.ts:1614), and [fresh admission counts the existing attempt against capacity](apps/server/src/domain/orchestration/executor.ts:1725). **Scenario:** with concurrency one, approval moves the step to `queued`, but its old attempt occupies the only slot, preventing re-admission. Reusing that attempt through current dispatch also permits sending while the gate remains pending. **Fix:** explicitly suspend and re-admit the same attempt after approval, or durably retire it before creating a replacement. Require the current gate, payload and policy at admission and release; retain exactly one active attempt for the step.

3. **P2 — Readiness refusals do not normally transition to `refused` (§6 cause table).**  
   [ `recordRefusal` returns ordinary refusals to `created`](apps/server/src/domain/orchestration/ops.ts:347); terminal `refused` is the orchestration lifetime-limit outcome. [Readiness waiting examines only `created` attempts](apps/server/src/domain/orchestration/executor.ts:359). **Scenario:** implement the table’s literal `send_refused ⇒ refused` after one missing-CLI receipt: neither normal backoff nor redispatch wakes it. **Fix:** specify `created` with the existing retry/wait fields until the lifetime limit, then the existing terminal failure outcome. Keep readiness counters separate from `send_closed`.

4. **P2 — Launch-based routing does not fix Stop when the run row is missing (§§2,9,10).**  
   [Coding Stop returns `not_running` before consulting launch evidence when its run lookup fails](apps/server/src/runtimes/coding/service.ts:633). **Scenario:** restore a database that lacks the run row but has a recoverable, unproven launch. The composite port correctly routes to coding, yet Stop is acknowledged without reaching that launch. **Fix:** resolve launch evidence before the missing-run return; stop through the qualified launch identity and return `unconfirmed` until no-execution/end proof exists. Add the missing-run-row recovery case to acceptance tests.

5. **P3 — “Environment values are never stored” contradicts the retained launch protocol (§3).**  
   The spec contains [environment values](apps/server/src/runtimes/coding/unit-backend.ts:994) and is [written to `spec.json`](apps/server/src/runtimes/coding/unit-backend.ts:1035). **Scenario:** ordinary preparation writes those values to the private transient file despite the absolute promise. **Fix:** scope the promise to policy snapshots, journal, history and UI; document the private transient spec exception and preserve current credential filtering.
