These are the remaining failures and new regressions:

1. **P1 — An existing capability marker is mistaken for a durably published marker.**  
   [unit-backend.ts:554](apps/server/src/runtimes/coding/unit-backend.ts:554), [supervisor.mjs:77](apps/server/src/runtimes/coding/supervisor.mjs:77).

   `writeReceipt()` links the final name before syncing its directory. If that fsync fails, the first check correctly pauses. The next retry hits `EEXIST`, returns success, and lifts the pause without retrying the failed sync.

   A filesystem-boundary probe returned `usable: true` after only the failed directory-sync attempt. Losing that undurable name before any owned launch history exists, then failing the host check on restart, selected unrestricted fallback.

   **Fix:** on `EEXIST`, validate and fsync the existing marker and its directory. Keep admission paused until those operations succeed.

2. **P1 — Missing-journal retirement can falsely establish a copied process row’s ownership.**  
   [coding-checkpoint.ts:241](apps/server/src/domain/orchestration/coding-checkpoint.ts:241), [fence.ts:599](apps/server/src/domain/orchestration/fence.ts:599).

   The copy gate requires *any* `inherited-retired` record. The new missing-journal lift writes that same kind for surviving coding launch folders.

   Lose a copy’s original confirmation roster and restore inherited process rows. Initially, ownership is correctly refused. Lift the missing-journal fence: the replacement record names only surviving unit launches, yet the unrelated source fallback row now passes ownership checking.

   The probe changed `ownsProcessRow('source-fallback-run', true)` from **false to true** solely through this lift.

   **Fix:** distinguish confirmation rosters from journal-loss retirements, bind the roster to `copiedFrom`, and prohibit signaling when that specific roster is unavailable.

3. **P1 — Confirmed copies still deliver inherited cancellation Stops through accepted Hermes intents.**  
   [installation.ts:521](apps/server/src/installation.ts:521), [coding-checkpoint.ts:276](apps/server/src/domain/orchestration/coding-checkpoint.ts:276), [intents.ts:281](apps/server/src/hermes/live/intents.ts:281).

   An accepted `start_run` intent can still have `stop_state='pending'`. Confirmation excludes it because its admission state is `accepted`. Even explicitly adding its key to a retirement record does nothing: application preserves accepted rows with results.

   Hermes recovery subsequently dispatches the accepted intent and calls [gateway Stop](apps/server/src/hermes/live/intents.ts:196) for the source run. This happens while the copy’s admission fence is still up.

   The probe captured no retirement key and observed a Stop for `source-live-run`.

   **Fix:** durably retire pending Stop obligations and inherited handles independently of admission state. Recovery and direct Stop routes must consult that disposition.

4. **P1 — An unresolved home can still deliver inherited orchestration Stops.**  
   [start-server.ts:540](apps/server/src/start-server.ts:540), [executor.ts:2396](apps/server/src/domain/orchestration/executor.ts:2396).

   The executor starts despite unresolved installation ownership. `serviceStops()` excludes attempts already marked `inherited_retired`, but unconfirmed copies have not received that disposition. The installation hard block gates admission, not Stop delivery.

   With the hard block set to an unconfirmed copied installation, the probe still called `port.stopRun()` for its inherited source handle.

   **Fix:** apply a resolved-installation ownership gate at every external Stop boundary, including executor and Hermes-intent recovery. Preserve legitimate Stops during ordinary admission fences.

5. **P1 — A truncated journal still loses permanent turn retirement after fence lift.**  
   [fence.ts:581](apps/server/src/domain/orchestration/fence.ts:581), [fence.ts:397](apps/server/src/domain/orchestration/fence.ts:397).

   Retirement runs only for the `journal-missing` item. Restore SQLite before execution and truncate the journal to an empty file or valid older prefix while retaining receipts/routing. Startup raises `journal_mismatch`; lift skips retirement, then the lift timestamp suppresses the unowned launch folder.

   The probe left the witnessed turn **pending**, wrote no retirement record, and removed its folder mismatch after lift.

   **Fix:** reconcile every unaccounted launch folder before any applicable lift, regardless of whether the journal file is absent or truncated. Remove timestamp-only acceptance of execution evidence.

6. **P1 — ACK-receipt fsync failure can still become successful completion after manager replacement.**  
   [supervisor.mjs:633](apps/server/src/runtimes/coding/supervisor.mjs:633), [unit-backend.ts:874](apps/server/src/runtimes/coding/unit-backend.ts:874).

   An ACK receipt’s final name can exist when its directory fsync fails. The supervisor then exits unsuccessfully. If the manager loses that exit metadata, Score accepts `exit === 'absent'` plus the readable receipt.

   The writer probe threw `EIO` while the receipt reader returned `present`; the backend’s absent-unit path returned `complete: true`. ACK consumption is established, but successful supervisor completion and receipt durability are not.

   **Fix:** require positive clean-exit evidence when metadata disappears. A readable `acked.json` alone cannot certify normal completion, particularly after publication failure.

7. **P1 — Unvalidated “ignorable” records can contradict success without invalidating it.**  
   [codex.ts:51](apps/server/src/runtimes/coding/codex.ts:51), [codex.ts:168](apps/server/src/runtimes/coding/codex.ts:168), [claude.ts:273](apps/server/src/runtimes/coding/claude.ts:273).

   Codex ignores every `error` envelope without validating its payload or position. Claude similarly exempts every non-init `system` envelope.

   A validated Codex answer and `turn.completed`, followed by an error record claiming fatal output loss, retained an eligible verdict with `lossReason() === null`. Claude also retained no loss after an unknown system error record.

   **Fix:** validate exact ignorable notice schemas and permitted positions. Errors, rejected notice shapes and unknown system subtypes must produce sticky loss when they can affect authority.

8. **P1 — A valid adopted stop cause does not disqualify live completion.**  
   [unit-backend.ts:864](apps/server/src/runtimes/coding/unit-backend.ts:864), [unit-backend.ts:1431](apps/server/src/runtimes/coding/unit-backend.ts:1431), [service.ts:1147](apps/server/src/runtimes/coding/service.ts:1147).

   Receipt adoption now preserves the cause in journal and SQLite. The returned outcome nevertheless takes its stop state from the control/session view. Eligibility checks neither the adopted journal cause nor the resulting database cause.

   The live backend probe returned **`complete: true`, `stopped: null`** while its journal recorded `deadline`. A valid candidate then meets the service’s success condition.

   **Fix:** derive eligibility from the authoritative first stop cause after adoption. Any cause must prevent completion; contradictory evidence must remain visible.

9. **P1 — Resume retry happens before sticky parser loss is checked.**  
   [service.ts:1073](apps/server/src/runtimes/coding/service.ts:1073), [service.ts:1095](apps/server/src/runtimes/coding/service.ts:1095).

   A rejected tool record produces no event, so `worked` remains false. If the attempt subsequently reports the recognized resume-refusal text, the service launches again before consulting `lossReason()`.

   Through the real execution method with fake launch boundaries, a rejected command record followed by resume refusal produced **two launches and a completed result**. The first attempt’s loss was discarded.

   **Fix:** require no parser loss before retrying. Lost records mean Score cannot establish that the first attempt performed no work.

10. **P1 — Raw commentary truncation still leaks credential prefixes into terminal storage.**  
    [note.ts:32](apps/server/src/runtimes/coding/note.ts:32), [service.ts:965](apps/server/src/runtimes/coding/service.ts:965), [service.ts:1116](apps/server/src/runtimes/coding/service.ts:1116).

    `CappedText` clips raw commentary before failure output is sanitized. Exact-secret replacement can no longer recognize a credential cut at that boundary.

    A normal **70-byte registered key** preceded by text that redaction substantially shortened left its recognizable prefix in the bounded stored output. A separate execution-path probe confirmed truncated credential text reaching `coding_pending_terminals.info`.

    **Fix:** retain redaction context across commentary chunks and cap sanitized output. Discard uncertain truncated suffixes rather than persisting them.

11. **P2 — Memory overflow stops the run but stops charging its retained data.**  
    [coding-socket.ts:493](apps/server/src/runtimes/coding/coding-socket.ts:493), [unit-backend.ts:971](apps/server/src/runtimes/coding/unit-backend.ts:971).

    When actual retention exceeds the budget, `chargeRetained()` records a violation and returns without updating the reservation. The parser/translator still owns that data while termination and delivery proceed. The new timed reservation release also substitutes elapsed time for clearing retained state.

    The accounting probe reported **100 charged bytes for 2,500 retained bytes**, with another reservation still fitting.

    **Fix:** charge retained overflow debt until the state is cleared, or immediately discard that state safely. Release reservations and cancel retention timers when their referenced state is actually gone.
