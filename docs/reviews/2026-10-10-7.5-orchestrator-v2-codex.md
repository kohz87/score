### [high] Restore detection still misses whole-home rollback and lost Stop fences

**Where:** [Global admission fence](/home/raven/score/docs/briefs/7.5-orchestrator.md:45), [workflow restore witness](/home/raven/score/docs/briefs/7.1-workflow-builder.md:7), [7.1 v6 counterexamples](/home/raven/score/docs/reviews/2026-10-10-7.1-workflow-builder-v6-codex.md:39).

**What happens:** Restore `$SCORE_HOME` on the same machine, during the same boot. The database, witness, and `instance-id` all return to their earlier values; the machine identity stays unchanged. No mismatch appears, although externally accepted work may remain active. Separately, restoring a database snapshot taken before Stop can erase that fence without changing the dispatch counter.

**Why:** The inherited witness advances before POSTs, not authorization changes. Neither a restored home identity nor a stable machine identity proves that history was preserved. A counter also cannot identify “every run/attempt whose state may be missing”; today’s Hermes exposes no run listing or lookup by session to reconstruct those missing handles. This is the same unresolved problem identified by the workflow review.

**Change:** Require a restore protocol that marks execution history untrusted and globally fences admission before startup. If automatic detection is required, maintain a journal outside the rollback scope containing admissions **and authorization fences**, with qualified attempt identities and returned handles. Otherwise explicitly require operator reconciliation of unidentified missing work. Test same-host, same-boot restoration and restoration after Stop with an unchanged dispatch counter.

### [high] MCP request IDs cannot deduplicate logical commands

**Where:** [Command identity](/home/raven/score/docs/briefs/7.5-orchestrator.md:35), [stateless MCP transport](/home/raven/score/apps/server/src/mcp/routes.ts:15), [Hermes tool invocation](/home/raven/.hermes/hermes-agent/tools/mcp_tool_handlers.py:394).

**What happens:** An assignment commits, but its reply disappears. Reinvoking the tool receives a different JSON-RPC request ID and creates another assignment. Conversely, reconnecting during the same lead attempt can reuse an earlier request ID, causing an unrelated command to collide with a stored receipt.

**Why:** Request IDs correlate transport requests and responses. Hermes passes the tool name and arguments to `ClientSession.call_tool()`; it does not preserve a logical command identity. The installed SDK allocates IDs within each dispatcher and resets its counter for a new dispatcher. Hermes also returns an [uncertain outcome for ambiguous write failures](/home/raven/.hermes/hermes-agent/tools/mcp_tool_handlers.py:227), leaving subsequent verification or reinvocation to the caller.

**Change:** Require an explicit, bounded `commandId` argument, scoped to the orchestration and lead attempt. Persist the tool name, canonical payload hash, mutation, reservations, and receipt atomically. Reuse returns the receipt; reuse with different content conflicts. Provide receipt verification after uncertain outcomes and define how admission-not-yet-recorded `retry` responses remain retryable. Do not substitute provider tool-call IDs, which the architecture already identifies as nonunique.

### [high] Finish and cancellation still do not establish admission barriers

**Where:** [Finish and cancel](/home/raven/score/docs/briefs/7.5-orchestrator.md:54), [assignment schema](/home/raven/score/docs/briefs/7.5-orchestrator.md:113).

**What happens:** A lead queues a step and calls `finish`. Sealing further tool commands does not explicitly prohibit the scheduler from admitting that already-queued step. The success predicate examines admitted attempts, so it can also overlook queued work. After cancellation, the lead can submit a reworded assignment under a new step ID while the cancelled execution continues.

**Why:** “Seals further commands” is different from fencing admissions. “For the same purpose counts” is neither an admission predicate nor a server-verifiable identity: `assign` has no replacement lineage, and arbitrary instruction text cannot establish semantic equivalence. These leave gaps in the termination barriers established by 7.1.

**Change:** Make Finish atomically fence admissions and either reject outstanding queued work or permanently retire it with recorded dispositions. Specify gate/inquiry closure and the treatment of active attempts, including the requesting lead. Introduce explicit replacement lineage for retries. If cancellation promises protection against arbitrary reassignment, fence **all new admissions** until cancelled work is terminated or a separate human waiver permits continuation. Test Finish with queued work and cancellation followed by a differently worded replacement.

### [medium] `lead-asks` has no enforceable approval operation

**Where:** [Gate policies](/home/raven/score/docs/briefs/7.5-orchestrator.md:27).

**What happens:** The lead asks the person about a step and also assigns it. The inquiry does not authorize anything, but no specified operation binds that assignment to a requested gate. An implementation may admit the step before the answer or incorrectly treat an affirmative answer as permission.

**Why:** V2 correctly separates inquiries from authorization, but only defines assignment gating for `every-step` and `none`. It also leaves rejection disposition unspecified. Quoted step results can still induce valid tool calls; the default assignment gate addresses that risk, while an inquiry does not.

**Change:** Initially offer `every-step` and `none`, keeping `orch.ask` available solely for information. Alternatively, add an explicit gate request to `assign`, creating the frozen assignment and gate atomically. Define rejection as a committed step disposition, propagate blocked dependencies, and record its wake cause in the same transaction.

### [medium] Hash-only capabilities conflict with durable rendered inputs unless dispatch changes

**Where:** [Capability handling](/home/raven/score/docs/briefs/7.5-orchestrator.md:7), [frozen input](/home/raven/score/docs/briefs/7.5-orchestrator.md:15), [current intent persistence](/home/raven/score/apps/server/src/hermes/live/intents.ts:238).

**What happens:** Reusing the current admission-intent implementation stores the capability inside the plaintext input payload. Redacting that payload instead prevents dispatching the required capability. “Redacted everywhere” also exceeds what adding a pattern to Score’s redactor can guarantee upstream.

**Why:** Current intents persist the complete input. Hermes separately [persists user content and tool calls](/home/raven/.hermes/hermes-agent/agent/session_persistence.py:204); Score’s redactor cannot alter those records. The bridge also requires its own redaction pass before serialization, as D6 mandates.

**Change:** Specify a capability-free durable snapshot and a narrowly controlled outbound render that injects the volatile capability. Define recovery when that volatile value is lost, retaining the prohibition on uncertain admission replay. State that hash-only storage applies to Score and document Hermes transcript exposure under the accepted threat model. Cover both redaction layers, stream fragments, errors, receipts, and step-input scanning before redaction/truncation.

### [medium] Fresh accounting still lacks completeness and settlement evidence

**Where:** [Budget rules](/home/raven/score/docs/briefs/7.5-orchestrator.md:64), [lineage reader](/home/raven/score/apps/server/src/hermes/live/recover.ts:40), [7.1 settlement finding](/home/raven/score/docs/reviews/2026-10-10-7.1-workflow-builder-v6-codex.md:71).

**What happens:** A fresh reading of an incomplete compression lineage becomes apparently known spend. Alternatively, a completed attempt retains reservations indefinitely because “lineage closure” is interpreted as session closure.

**Why:** The existing reader silently stops on forks, errors, and traversal limits without reporting completeness. Turn completion does not establish session closure. V2’s auxiliary exclusions are appropriate, but freshness and “closure” still do not define the facts needed to settle observed spend.

**Change:** Specify adapter facts for qualified session ownership, lineage completeness and failure reasons, observation time, cost scope, and settlement. Define reservation-to-cost reconciliation without gaps or double counting. Incomplete evidence remains unknown; an auxiliary exclusion must not make an incomplete main-loop total known. Test missing continuations, forks, delayed accounting, and completed turns with open sessions.

### [medium] Ownership controls and abandonment still need an actual transition contract

**Where:** [Controls matrix](/home/raven/score/docs/briefs/7.5-orchestrator.md:68), [abandonment](/home/raven/score/docs/briefs/7.5-orchestrator.md:60), [current Team Resume](/home/raven/score/apps/server/src/http/team-pause.ts:96).

**What happens:** Legacy controls clear the wrong holds or admit ordinary work. Abandonment releases capacity and reservations while owed stops remain, but the design does not determine whether the run can resume, whether replacements become eligible, or when ownership guards lift.

**Why:** “Delegate or reject” defers the behavioral decision for every route. Current Team Resume directly edits brief flags, summaries reserve ordinary runs, and brief status still [derives from turns/tasks](/home/raven/score/apps/server/src/domain/briefs.ts:192). Normal Hermes Stop can permanently leave `cancelled`, so abandonment is a routine operational path, not an exceptional footnote.

**Change:** Supply the matrix and typed lifecycle/status mappings before approval. Define abandonment as a paired, revision-bound transition that permanently retires admission authority, ignores late results, retains owed stops and tombstones, and distinguishes released reservations from unknown actual spend. Explicitly define ownership guards afterward. Any continuation alongside unconfirmed execution needs a separately recorded waiver; ordinary Resume must not provide it.

### [medium] The quota and capacity rules do not yet describe compatible bounds

**Where:** [New limits](/home/raven/score/docs/briefs/7.5-orchestrator.md:76), [retained 2 MB allowance](/home/raven/score/docs/briefs/7.5-orchestrator.md:138).

**What happens:** Forty permitted 64 KiB frozen lead inputs alone exceed the retained 2 MB allowance, before step inputs, results, gates, receipts, and history. Many waiting orchestrations can also consume resources despite each respecting its per-run limits.

**Why:** V2 identifies states that count against capacity, but provides no global/per-agent ceilings. It reserves storage for obligations without specifying the accounting scope, amount, or refusal behavior for already-running work. This leaves the associated-growth issue from 7.1 unresolved.

**Change:** Choose compatible prompt, snapshot, and run-storage limits. Define shared capacity ceilings and atomic claims across orchestrations and workflows. Account for owned rooms, messages, intents, receipts, transitions, and associations; explicitly budget or separately cap replay data. Reserve protected space for results, fences, and Stop records. Specify deterministic behavior when ordinary writes exhaust their allowance.

### [medium] Attempt ownership alone does not scope the complete Watch response

**Where:** [Watch requirement](/home/raven/score/docs/briefs/7.5-orchestrator.md:80), [Watch response assembly](/home/raven/score/apps/server/src/http/watch.ts:82), [frame and marker queries](/home/raven/score/apps/server/src/domain/watch-frames.ts:453).

**What happens:** Frames belong to the correct attempt, but replay still displays another concurrent session’s markers, approval positions, browser context, gaps, latest session, or live state.

**Why:** Those fields currently use agent-wide queries. V2 repairs ownership and includes continuations, but does not require every response field and stream update to use the same attempt scope.

**Change:** Define one qualified attempt/lineage scope for frames, markers, approvals, browser context, gaps, pagination, live state, and updates. Unassociated evidence belongs in an explicitly unassociated feed. Specify retention floors and coordinate cleanup with protected unresolved evidence.

## The design I would approve

- Retain short lead turns, immediate-return tools, per-turn capabilities, typed dispatch, and the acknowledgement covering unrestricted lead and step execution.
- Use explicit logical command IDs and atomic receipts; persist every wake-producing transition and claim one immutable lead snapshot.
- Never replay an uncertain Hermes admission. Lost handles and insufficient termination evidence remain unknown.
- Make restore reconciliation globally mandatory when execution history is untrusted, including missing runs and lost fences.
- Define Finish, cancellation, replacement, Stop, and abandonment as admission and termination protocols with explicit human waivers.
- Keep default immutable assignment gates; specify or defer `lead-asks`.
- Complete accounting facts, the ownership/API matrix, compatible quotas, and consistent Watch scope.
- Require fixture tests for reconnecting command retries, same-boot restoration, Finish with queued work, reworded replacements, abandonment, incomplete accounting, and concurrent replay.
