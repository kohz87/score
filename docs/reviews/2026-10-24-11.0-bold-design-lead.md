# 11.0 bold rework design: adversarial review by the lead (2026-10-24)

Codex has no ChatGPT credits (owner, 2026-10-24), so under CLAUDE.md the lead did the design review. Reviewed: the
proposal's agent-to-agent model and data sketch (`docs/proposals/ui-rework-bold.md` §3, §4, §8, §9), the parity list,
and the lead's first-pass design for 11.0, against Score at `f39322e4`. The aim was to break the design: find where
it would lose work, leak data, stall, run away or change the owner's live Score unannounced. The answers are folded
into `docs/briefs/11.0-bold.md` v1.1. A Codex max review runs again before 11.1a merges if Codex has quota by then.

**Verdict: approved for 11.1a with v1.1.** No finding needs the owner except where §12 of the brief lists a decision.

## Checked premises (code, 2026-10-24)
- `mcp/access.ts`, contract §13: MCP access and writes are **off by default** per agent; turning them on needs the
  owner to run `hermes --profile <id> mcp add score …` and paste a token. Score never writes that config.
- 7.7b brief: coding CLIs run with `--strict-mcp-config` and no MCP servers.
- `hermes-plugin/score_bridge/knowledge.py`: the plugin already registers model-callable tools with
  `ctx.register_tool`, identified by the producer token (profile), not by an argument.
- MCP and bridge identity are per agent/profile. The orchestrator binds tool calls to one lead attempt with a per-turn
  `orc_` capability in the turn input (contract §14), which is the proven pattern.
- `routing.ts`: `HANDOFF_HOP_LIMIT = 4`, reverse-edge refusal, hand-offs from any parsed `@mention`
  (`message-runs.ts` `completeRunMessage`); ARCHITECTURE D3.2 says 6 and "a pair at most 2 times".
- `roomRunInput` sends the last 10 room messages (or summary + later ones), not "messages since that agent's last
  turn" as D3.1 says.
- `score-<room>-<agent>` is built in `routing-dispatch.ts`, `versions.ts`, `hermes/live/runs.ts`,
  `http/conversations.ts`, `http/session-compaction.ts` and `runtimes/coding/service.ts`; `outside-sessions.ts`
  substitutes a continued session.
- `room-summaries.ts`: summary runs go through the room's lead agent.
- `watch_frames` carry `run_id`, so frames can be joined to a job through `message_runs`.
- `RoutingDispatcher`: one active turn per (room, agent).

## Rejected or deferred
- **Parallel fan-out from one turn** (lead asks builder and designer at once). Deferred: one routing action per turn
  keeps budgets and reply-back simple; parallel plans already run through the orchestrator recipe. Revisit after 11.4.
- **Apply actions at call time** so the target starts sooner. Rejected: a turn that then fails or is stopped would leave
  orphan hand-offs; staging costs at most the rest of one turn.
- **A separate one-to-one conversation table.** Rejected: jobs in the agent's direct room reuse sessions, summaries,
  search, unread and the job menu (§6.1).
- **Per-job concurrency for throughput.** Rejected for workspace safety (F11).
- **MCP mirror of the action tools in v1.** Deferred: no user needs it yet, and it adds a second auth path.
