**Do not approve.** This brief leaves core execution and authorization rules undefined and promises controls that the existing runtimes cannot provide. The main blockers are cancellation, recovery after uncertain dispatch, gate enforcement, result provenance, and budget accounting. These need a revised execution design before implementation. I checked Score’s code, the local Hermes source, and installed CLI help; the repository is unchanged and no CLI received a prompt.

### [high] The advertised step modes and controls are unsupported

**Where:** [Agent nodes and Control](/home/raven/score/docs/briefs/7.1-workflow-builder.md:9), [existing Stop contract](/home/raven/score/docs/API-CONTRACT.md:472), [7.2 task restriction](/home/raven/score/docs/briefs/7.2-coding-agents.md:38).

**What happens:** A workflow accepts a coding agent in task mode, or promises to stop a running Kanban step, then cannot perform the operation.

**Why:** 7.2 explicitly limits coding agents to room work. Score rejects stopping Kanban attempts because Hermes has no public stop targeting one attempt. Hermes’s `--max-runtime` terminates and **requeues** workers; that does not implement the promised deadline failure transition.

**Change:** Define a capability matrix for each runtime and mode. Reject unsupported combinations before saving or starting. Limit initial execution to controllable Score-started room runs unless a separately reviewed task executor supplies the missing guarantees.

### [high] Reusing Start plan can dispatch work past a human gate

**Where:** [Brief-turn reuse](/home/raven/score/docs/briefs/7.1-workflow-builder.md:18), [plan materialization](/home/raven/score/apps/server/src/http/plan-start.ts:60), [Hermes task creation](/home/raven/.hermes/hermes-agent/hermes_cli/kanban_db.py:1342).

**What happens:** In `build → gate → publish`, eagerly creating tasks using the existing plan pattern can let Hermes dispatch `publish` when its task parents finish, before Score’s gate is answered. This can happen while Score is down.

**Why:** Start plan creates the whole task sequence. Hermes schedules ready tasks independently; it has no knowledge of Score’s workflow gates. Arrival holds act after creation and leave already-started work running.

**Change:** Make the workflow scheduler the sole authority for node admission. Create external work only after its control and data dependencies, gates, and limits are satisfied. Never use Hermes task dependencies as a substitute for a Score gate.

### [high] Stop has no durable fence against pending or late-admitted work

**Where:** [Pause/resume/stop](/home/raven/score/docs/briefs/7.1-workflow-builder.md:24), [current pause semantics](/home/raven/score/apps/server/src/http/brief-control.ts:20), [Hermes Stop response](/home/raven/.hermes/hermes-agent/gateway/platforms/api_server_runs.py:1253).

**What happens:** Stop targets active steps, but pending nodes, an admission already in flight, or a late completion can still launch work. A deadline’s failure branch can start while the timed-out agent continues acting.

**Why:** Brief pause allows running work to finish. Hermes Stop returns `stopping`, not confirmed termination. The brief defines neither a terminal workflow cancellation state nor precedence between Stop, completion, timeout, retry, and resume.

**Change:** Persist a cancellation fence before external calls. Cancel pending admissions, track owed stops durably, and stop work admitted after the fence. Require terminal evidence before conflicting successors run; expose unresolved cancellation explicitly.

### [high] “Recorded before acting” does not establish crash-safe execution

**Where:** [Durability claim](/home/raven/score/docs/briefs/7.1-workflow-builder.md:18), [ingest transaction and listeners](/home/raven/score/apps/server/src/hub/ingest.ts:33), [existing recovery setup](/home/raven/score/apps/server/src/start-server.ts:304).

**What happens:** A crash after recording a completion but before scheduling its successor strands the workflow. A crash after scheduling but before recording the association can cause duplicate activation or orphaned work.

**Why:** The brief specifies durable step rows but no transition table, atomic activation protocol, revision fencing, or recovery algorithm. `onCommitted` callbacks are asynchronous notifications, not durable jobs.

**Change:** Commit result acceptance, step transition, branch selection, successor eligibility, and command intent through the single writer. Recover by scanning durable state, with terminal guards and revisions that reject stale observations. Enumerate every crash boundary.

### [high] External idempotency has limits the design ignores

**Where:** [Attempt idempotency](/home/raven/score/docs/briefs/7.1-workflow-builder.md:20), [Score’s replay cutoff](/home/raven/score/apps/server/src/hermes/live/intents.ts:72), [Hermes run receipt retention](/home/raven/.hermes/hermes-agent/gateway/platforms/api_server_run_idempotency.py:53), [Kanban deduplication](/home/raven/.hermes/hermes-agent/hermes_cli/kanban_db.py:1395).

**What happens:** Recovery repeats work whose acceptance is unknown. That can create another task or repeat an agent’s external side effects.

**Why:** Hermes run receipts have finite retention and can fall back to process memory. Score already refuses uncertain replay after 23 hours. Kanban deduplication excludes archived tasks. Installed `codex exec resume --help` describes sending another prompt; resuming a session is not an admission receipt.

**Change:** Separate dispatch retry from execution retry. Freeze each attempt’s payload and runtime identity, record receipt capabilities and expiry, and reconcile before repeating. Unprovable acceptance must become an explicit unknown state. Do not promise exactly-once agent side effects.

### [high] Human gates lack an exact decision target

**Where:** [Gate model and Security](/home/raven/score/docs/briefs/7.1-workflow-builder.md:11), [current approval schema](/home/raven/score/packages/contract/src/types.ts:113), [decision delivery](/home/raven/score/apps/server/src/http/approvals.ts:115).

**What happens:** A stale browser approves an earlier attempt or artifact, or ordinary Resume releases work still blocked by a gate or budget decision.

**Why:** `{ question }` defines no choices, rejection behavior, occurrence identity, expiry, or reviewed payload. Existing approvals target Hermes actions and offer `once/session/always/deny`; they have no workflow-local target. Brief pause is one flag that Resume clears.

**Change:** Introduce a workflow-local gate target bound to run, node, attempt, revision, and the exact reviewed evidence. Atomically accept one paired-human decision and activate successors. Gate, budget, manual, agent, and team holds must remain independent. A workflow decision must never grant runtime tool permission.

### [high] Ordinary room routing escapes the declared DAG

**Where:** [Reuse of message turns](/home/raven/score/docs/briefs/7.1-workflow-builder.md:19), [automatic hand-offs](/home/raven/score/apps/server/src/domain/message-runs.ts:496), [message routing](/home/raven/score/apps/server/src/domain/routing.ts:25).

**What happens:** An untrusted agent emits `@reviewer` and starts an undeclared turn, potentially bypassing the next gate. Posting a rendered instruction through ordinary room routing can also interpret mentions or slash commands as control.

**Why:** Successful ordinary turns automatically reserve hand-offs. Human message routing combines explicit recipients with parsed mentions. Neither mechanism understands workflow edges or per-node limits.

**Change:** Dispatch workflow instructions through a typed workflow path with fixed recipients. Disable implicit hand-offs for workflow turns, or explicitly admit and account for them through the workflow scheduler. Rendered inputs and agent outputs must remain data.

### [high] DAG validation does not define executable branches and joins

**Where:** [Branch, join, and validation rules](/home/raven/score/docs/briefs/7.1-workflow-builder.md:12).

**What happens:** An all-join waits forever for an unselected branch. An any-join proceeds after a failed predecessor while another keeps spending or modifying shared files. A valid control DAG deadlocks because A references B’s output while B depends on A.

**Why:** “Previous node,” “all,” and “any” have no precise semantics. Existing-node template validation does not establish output availability. Entry nodes, edge conditions, default routes, skipped states, multiple matches, and end behavior are undefined.

**Change:** Specify control tokens, branch precedence/defaults, skip propagation, and join success conditions. Validate template dependencies alongside control dependencies, including conditional availability. Persist an any-join’s winning evidence and define the disposition of remaining work.

### [high] Completion and review outcomes have no canonical source

**Where:** [Branch outcomes](/home/raven/score/docs/briefs/7.1-workflow-builder.md:12), [message completion](/home/raven/score/apps/server/src/domain/message-runs.ts:425), [task disposition](/home/raven/score/apps/server/src/domain/briefs.ts:124), [Hermes review transition](/home/raven/.hermes/hermes-agent/hermes_cli/kanban_db.py:3575).

**What happens:** A failed message run advances as completed, or a finished worker attempt advances while its task is still waiting for retry or review. Substring matching accepts “not passed” or a quoted verdict.

**Why:** Message mappings become `completed` after terminal runs, including failures; the run status carries the distinction. Hermes task disposition differs from attempt completion, and `changes_requested` can immediately return work to the implementer. Ordinary message runs have no typed `passed` verdict.

**Change:** Define a normalized result envelope with exact provenance, terminal status, optional validated verdict, output, and unknown/truncated indicators. Specify canonical sources by mode. Treat text matching as advisory routing, never evidence of human authorization or independently verified success.

### [high] Session accounting cannot enforce the promised budgets

**Where:** [Budgets](/home/raven/score/docs/briefs/7.1-workflow-builder.md:25), [sampling interval](/home/raven/score/apps/server/src/start-server.ts:375), [snapshot bucketing](/home/raven/score/apps/server/src/domain/spend.ts:13), [terminal usage ingestion](/home/raven/score/apps/server/src/hermes/live/translate.ts:321).

**What happens:** Parallel steps exceed the run budget before detection. Shared-session spending is attributed to the wrong node. Pausing the brief after detecting overspend leaves active work spending.

**Why:** Reports sample cumulative session costs every ten minutes and overwrite readings within quarter-hour buckets. These are unsuitable per-attempt baselines. Run usage is generally recorded at completion. Unknown cost also affects Hermes/Kanban work, not just coding agents.

**Change:** Distinguish hard runtime-enforced caps from soft spending alarms. Define attempt attribution, reservations for parallel admissions, estimated versus actual costs, freshness, and overshoot behavior. Budgeted work with unknown cost needs an explicit pre-admission policy. Claude help advertises a print-mode budget option; other runtimes require their own verified capabilities.

### [high] Task outputs can disappear before successors receive them

**Where:** [Task steps and output templates](/home/raven/score/docs/briefs/7.1-workflow-builder.md:9), [current task creation arguments](/home/raven/score/apps/server/src/hermes/live/task-writes.ts:74), [Hermes workspace cleanup](/home/raven/.hermes/hermes-agent/hermes_cli/kanban_db_workspace.py:353).

**What happens:** A task produces files in its default scratch workspace, completes, and loses files needed by a later workflow step.

**Why:** Score currently supplies no workspace policy when creating tasks. Hermes removes managed scratch directories on completion, with exceptions for existing dependents/shared use and preserved artifacts. A successor created after a gate may not exist when cleanup runs.

**Change:** Define workspace ownership, artifact publication and preservation before task completion, successor access, retention, and cleanup. File hand-offs need durable artifact references; a path embedded in output text does not preserve the file.

### [high] Import review is neither portable nor bound to what will execute

**Where:** [Definition, import, and Security](/home/raven/score/docs/briefs/7.1-workflow-builder.md:7), [agent incarnation identity](/home/raven/score/apps/server/src/domain/agent-lifecycle.ts:6).

**What happens:** Name mapping selects an agent with different capabilities, or a reviewed definition/mapping changes before its first run without invalidating approval.

**Why:** Nodes contain only `agentId`; no portable agent descriptors are specified for name mapping. Display names are mutable. The import section requests confirmation when an agent is missing, while Security requires review of every mapping. Definitions remain mutable until first use.

**Change:** Import into a new local identity with explicit portable descriptors. Require review of the complete definition and every resolved runtime mapping. Bind review to a definition hash and mapping revision; invalidate it on changes. Revalidate incarnation and capabilities at admission. Definition mutations, imports, starts, reruns, and budget changes must require paired-human authority.

### [medium] Deadline semantics do not survive pauses, retries, and downtime

**Where:** [Deadlines](/home/raven/score/docs/briefs/7.1-workflow-builder.md:28).

**What happens:** Restart resets a timer, retries extend execution indefinitely, or an expired run launches a failure branch that starts more work after the run-wide deadline.

**Why:** There is no deadline origin, persisted absolute expiry, pause policy, queue/gate treatment, retry policy, or precedence rule for simultaneous completion.

**Change:** Persist absolute deadlines and define their clock semantics. Specify whether waiting and pauses count. Reconcile overdue runs before new admission on startup. Run-wide expiry must fence further work; retain the timeout reason separately from eventual runtime termination.

### [medium] Briefs and Flow cannot show this workflow “unchanged”

**Where:** [Integration promise](/home/raven/score/docs/briefs/7.1-workflow-builder.md:18), [derived brief status](/home/raven/score/apps/server/src/domain/briefs.ts:192), [Flow schemas](/home/raven/score/packages/contract/src/briefs.ts:28), [stream contract](/home/raven/score/docs/API-CONTRACT.md:238).

**What happens:** Between agent steps, a brief becomes `done` although its workflow is waiting at a gate. Gate, branch, skipped, stopping, and unknown states cannot appear correctly in the current graph.

**Why:** Brief status derives solely from turns, tasks, and a pause flag. Flow has only `brief` and `step` nodes. The brief defines only import/export endpoints, with no lifecycle API, snapshots, events, revisions, or conflict responses.

**Change:** Add an explicit workflow projection and its relationship to brief status. Specify the complete API and stream extension, following D1’s transactional snapshots and resync rules. Reconcile the existing pause contract too: it says `block`, while task holds currently use `scheduled`.

### [medium] Reruns have no frozen input or session policy

**Where:** [Rooms and reruns](/home/raven/score/docs/briefs/7.1-workflow-builder.md:9), [session selection](/home/raven/score/apps/server/src/domain/routing-dispatch.ts:139), [room context construction](/home/raven/score/apps/server/src/domain/message-runs.ts:541).

**What happens:** Rerunning identical inputs in an input room includes intervening messages and previous tool history. Two parallel nodes for the same agent serialize through a shared session. Reading mutable messages later changes the evidence used by downstream nodes.

**Why:** Existing turns share a session per room/agent and append recent room context at admission. “One room per run” conflicts with node-level `room: 'new'|'input'`, whose scope is undefined.

**Change:** Specify session reuse versus isolation and same-agent parallel behavior. Freeze run inputs, rendered attempt instructions, consumed output revisions, and relevant context. Rerun must create fresh execution and fresh gates; historical playback must remain read-only.

### [medium] Watch cannot currently replay an exact workflow step

**Where:** [Replay promise](/home/raven/score/docs/briefs/7.1-workflow-builder.md:30), [Watch endpoint](/home/raven/score/apps/server/src/http/watch.ts:73), [frame filtering](/home/raven/score/apps/server/src/domain/watch-frames.ts:453), [session attribution](/home/raven/score/apps/server/src/domain/watch-frames.ts:363).

**What happens:** Opening a step’s replay includes unrelated work by the same agent or misattributes a delayed frame to a later run.

**Why:** Watch filters by agent and starting frame sequence, with no exact run boundary. Some attribution selects the newest run for a session. Frame sequences are per agent and frames are updated in place. The seven-day SSE log cannot supply durable workflow history.

**Change:** Add exact step/attempt replay scope, proven frame associations, bounded pagination, and retained transition history. Keep unprovable associations unknown. Specify retention and visible gaps instead of promising complete replay.

### [medium] Fifty nodes is not an execution or storage limit

**Where:** [Validation limits](/home/raven/score/docs/briefs/7.1-workflow-builder.md:16).

**What happens:** A small imported graph causes excessive retries, concurrent runs, expanded prompts, rooms, or retained output. Expansion succeeds in the editor but exceeds the execution endpoint’s limits.

**Why:** Edge count, inputs, template expansion, output size, retry count, concurrent runs, and storage growth are unbounded. Existing paths already differ: room messages are limited to 16 KiB, task bodies to 32,000 characters, and stored run output is clipped.

**Change:** Specify byte and cardinality limits throughout import, validation, rendering, dispatch, and storage. Bound total attempts and concurrency globally and per runtime. Validate numeric limits and define deterministic oversized-output handling.

### [medium] Definition-only export does not mean secret-free export

**Where:** [Export claim](/home/raven/score/docs/briefs/7.1-workflow-builder.md:39), [D6 redaction](/home/raven/score/docs/ARCHITECTURE.md:325).

**What happens:** Instructions, questions, or labels containing pasted secrets are exported. Newly stored step outputs or rendered instructions bypass existing redaction paths.

**Why:** Definitions contain arbitrary text. Excluding run data and credential stores cannot guarantee that text contains no secrets. Redacting templates silently can also change their meaning.

**Change:** Define a portable export schema and a precise sensitive-text policy. Explicitly exclude execution data and credential references, show any redaction changes, and enforce D6 before storing agent-derived results. Branch evaluation and downstream consumption must use the same sanitized result.

### [medium] Acceptance tests do not cover the claimed guarantees

**Where:** [Brief](/home/raven/score/docs/briefs/7.1-workflow-builder.md:1), [PLAN 7.1](/home/raven/score/docs/PLAN.md:357), [existing recovery tests](/home/raven/score/apps/server/test/http/arrival-holds.test.ts:186).

**What happens:** A happy-path fake workflow passes while production duplicates work, bypasses a gate, or remains stuck after restart.

**Why:** Neither the brief nor PLAN defines acceptance criteria for these invariants. Existing plan recovery tests cover a materially simpler operation. CLI help establishes available options, not event shapes or recovery guarantees.

**Change:** Require deterministic tests for crash boundaries, uncertain admission, duplicate/out-of-order completion, Stop during admission, competing gate decisions, overlapping holds, skipped branches, any-join losers, stale mappings, unknown/parallel spending, restart deadlines, artifact preservation, and replay after retention. Use recorded Hermes/CLI fixtures and fake adapters without model calls.

## The design I would approve

- A server-owned DAG executor with explicit transitions, dependency semantics, transactional activation, durable command intents, and recoverable unknown states.
- Initially, controllable Score-started room runs; additional modes admitted only through a tested runtime capability matrix.
- Exact paired-human gates bound to immutable evidence, with independent holds and cancellation fences.
- Frozen inputs and results, deliberate session/workspace policies, and durable artifact hand-offs.
- Honest budget guarantees, persisted deadlines, bounded retries/concurrency/storage, and exact replay scope.
- A complete contract extension and failure-focused acceptance suite before building the editor.
