**Do not approve v1.** Event-driven lead turns and nonblocking MCP tools are implementable with today’s Hermes, but the proposed agent token cannot authorize one particular lead turn, ordinary Hermes runs retain ways to bypass the orchestrator, and the gate, wake-up, cancellation, and completion protocols remain incomplete. Several unresolved 7.1 findings also carry over, including restore safety and administrative resolution of unknown execution. I reviewed the requested documents, all six available 7.1 reviews, Score’s implementation, and local Hermes revision `e97923c38a`. I made no changes or live model calls.

### [high] The agent token does not identify the calling lead turn

**Where:** [Identity and scope](/home/raven/score/docs/briefs/7.5-orchestrator.md:27).

**What happens:** Another session of the lead profile—or a delayed request from an earlier turn—can assign, cancel, or finish whichever orchestration currently has a running lead turn. A step assigned to the lead profile would possess the same profile credential, contradicting “a step can’t call orchestrator tools.”

**Why:** [MCP authentication](/home/raven/score/apps/server/src/mcp/access.ts:118) returns only `agentId`; the server is stateless. Hermes invokes MCP with [the tool name and arguments](/home/raven/.hermes/hermes-agent/tools/mcp_tool_handlers.py:394), without authenticated run identity. Holding Score room queues cannot prevent CLI, cron, gateway, or detached execution from using that credential.

**Change:** Require authorization bound to the orchestration, lead attempt, turn generation, and agent incarnation. A feasible current-Hermes option is an unguessable turn capability supplied only to that turn and required by every `orch.*` call. Treat it as bearer authority, redact it everywhere, never forward it to steps, and reject expired generations. An asserted session ID or “this agent currently has a turn” is insufficient.

### [high] Ordinary Hermes lead runs can bypass Score’s referee

**Where:** [Normal lead runs](/home/raven/score/docs/briefs/7.5-orchestrator.md:12), [injection protection](/home/raven/score/docs/briefs/7.5-orchestrator.md:43).

**What happens:** An injected result persuades the lead to use terminal, delegation, another MCP server, or existing Score write tools directly. That activity bypasses step limits, orchestration gates, reservations, and run scoping.

**Why:** Hermes constructs ordinary Runs agents with [the profile’s API-server toolsets](/home/raven/.hermes/hermes-agent/gateway/platforms/api_server.py:2400). Score cannot currently bind an orchestration-specific tool policy. Quoting results does not prevent the model from acting on them. Automatic [memory/skill reviews](/home/raven/.hermes/hermes-agent/agent/turn_finalizer.py:769) can also run after the main loop returns.

**Change:** Distinguish restricted conductor execution from acknowledged unrestricted execution. Today’s acknowledgement must cover **both lead and steps**, explaining that Score controls its admitted work rather than every agent action. Stronger claims require tested restrictions on other tools and asynchronous runtime activity; a future toolset filter alone does not establish execution quiescence.

### [high] Human gates are not bound to the steps they authorize

**Where:** [Tool definitions](/home/raven/score/docs/briefs/7.5-orchestrator.md:22), [gate policies](/home/raven/score/docs/briefs/7.5-orchestrator.md:49).

**What happens:** Under “ask before each step,” an assignment can enter the queue without a specified approval target. Alternatively, the person approves a visible plan and the lead changes the actual instruction afterward. An injected result can induce a perfectly valid `orch.assign` despite remaining quoted data.

**Why:** `assign` accepts step dependencies, but no gate binding; `ask` contains only a question. The brief does not define the reviewed payload, decision occurrence, rejection behavior, or independent holds. Agent membership and instruction length do not establish authorization for the instruction’s effects.

**Change:** Automatically create the required step gate when accepting an assignment. Freeze the agent incarnation, instruction, dependencies, estimate, and reviewed evidence; accept one paired, revision-bound decision for that exact payload. Inquiry answers remain data and cannot change permissions. Define “never ask” behavior separately from budget uncertainty and runtime approvals. Gate, budget, manual, team, and agent holds must remain independent.

### [high] POST intents do not make MCP commands or wake-ups crash-safe

**Where:** [Wake-up batching](/home/raven/score/docs/briefs/7.5-orchestrator.md:15), [durability rules](/home/raven/score/docs/briefs/7.5-orchestrator.md:37).

**What happens:** A completion commits, Score crashes before recording its wake-up, and the orchestration stalls. A lost `orch.assign` response causes the same logical command to create another step. Competing notifications can claim duplicate lead turns.

**Why:** External admission intents cover the Hermes POST, not the preceding MCP mutation or event-consumption protocol. Existing [committed listeners](/home/raven/score/apps/server/src/hub/ingest.ts:266) execute asynchronously after commit. There is no specified durable command receipt, wake cursor, or lead-turn claim.

**Change:** Commit command identity, payload hash, mutation, reservations, and returned receipt together. Commit result acceptance and pending wake state together. Atomically claim one lead attempt against a durable cause cursor and freeze its input. Define calls arriving before the admission response is recorded. Recover both lead and step intents exclusively through the orchestration executor; [generic recovery](/home/raven/score/apps/server/src/hermes/live/intents.ts:259) currently resends uncertain admissions and must exclude them.

### [high] The inherited epoch counter does not reliably detect restoration

**Where:** [Restore safety](/home/raven/score/docs/briefs/7.5-orchestrator.md:37), [7.1 restore quarantine](/home/raven/score/docs/briefs/7.1-workflow-builder.md:7).

**What happens:** Restoring `$SCORE_HOME` rolls back both the database and epoch file, so accepted work appears unsent. A database-only restore can erase a later Stop without changing the dispatch counter. Entire externally active orchestrations may be absent from the restored database.

**Why:** The witness lives inside the [documented backup location](/home/raven/score/docs/SETUP.md:238). It witnesses POSTs, not subsequent authorization fences. The [v6 review](/home/raven/score/docs/reviews/2026-10-10-7.1-workflow-builder-v6-codex.md:39) identifies these same counterexamples.

**Change:** Define a mandatory restore protocol imposing a persistent **global admission fence**, even when no quarantinable runs remain in the database. Document the witness’s rollback assumptions. Preserve independent admission/fence history or require explicit operator reconciliation of potentially missing work. A human assertion must remain distinct from termination evidence.

### [high] Finish, cancel, and unknown execution lack termination barriers

**Where:** [Cancel and finish](/home/raven/score/docs/briefs/7.5-orchestrator.md:23), [termination and Stop](/home/raven/score/docs/briefs/7.5-orchestrator.md:39).

**What happens:** The lead cancels a step, assigns its replacement, or calls `finish` while old work remains active or unknown. `finish` itself necessarily arrives before the requesting lead loop has ended. Waking a new lead on an unknown step can also bypass 7.1’s retained restriction on continuing unresolved execution.

**Why:** There are no explicit finish predicates or attempt-local cancellation semantics. Current [Stop bookkeeping](/home/raven/score/apps/server/src/hermes/live/intents.ts:166) treats a successful response or 404 as done, while [transcript recovery](/home/raven/score/apps/server/src/hermes/live/translate.ts:491) synthesizes `completed`. Neither supplies the inherited termination evidence. Normal Hermes interruption produces [`cancelled`](/home/raven/.hermes/hermes-agent/gateway/platforms/api_server_runs.py:181), which may never later become `completed` or `failed`.

**Change:** Separate retirement, Stop request, acknowledgement, and proven termination. Make `finish` a durable finish request that seals further commands; report success only after the requesting lead and all admitted attempts are accounted for, with no unresolved steps or gates. Unknown execution fences continuation. Specify administrative abandonment separately, including capacity, reservations, owed stops, late results, ownership guards, and any explicit risk waiver.

### [high] Lead turns also need the workflow-only dispatch path

**Where:** [Lead versus step dispatch](/home/raven/score/docs/briefs/7.5-orchestrator.md:12).

**What happens:** A lead’s ordinary final reply containing `@reviewer` creates undeclared work. Ordinary room context or summary text enters later controller turns outside the frozen orchestration snapshot.

**Why:** Routing and hand-offs are disabled explicitly for **steps**, but not lead turns. Current [completion handling](/home/raven/score/apps/server/src/domain/message-runs.ts:535) reserves hand-offs, and [ordinary dispatch](/home/raven/score/apps/server/src/domain/routing-dispatch.ts:112) appends room context and chooses a shared room/agent session.

**Change:** Use typed, fixed-recipient orchestration dispatch for both kinds of run. Disable mention routing, plan materialization, ordinary context assembly, and autonomous summaries. Give each lead attempt a fresh session, or specify an equally rigorous history and accounting policy. Freeze controller input and consumed result revisions; revalidate agent incarnation and capabilities at admission.

### [medium] Budget reservations and accounting remain underspecified

**Where:** [Per-call reservations](/home/raven/score/docs/briefs/7.5-orchestrator.md:31), [admission budgets](/home/raven/score/docs/briefs/7.5-orchestrator.md:41).

**What happens:** Queued assignments reserve twice, reservations disappear before accounting settles, or apparently known spend omits compression continuations and auxiliary activity. A live lead’s unavailable cost can also make assignment handling pause without a defined recovery path.

**Why:** Neither tool schemas nor the run model define estimates, reservation transfer, or settlement. Existing [cost sampling](/home/raven/score/apps/server/src/start-server.ts:407) is periodic; [lineage traversal](/home/raven/score/apps/server/src/hermes/live/recover.ts:40) lacks completeness facts. Hermes records background-review usage [outside the session cost row](/home/raven/.hermes/hermes-agent/agent/background_review.py:797).

**Change:** Define owner/server-controlled estimates for lead turns and steps, reserve once, and transfer reservations through queue/admission states. Reconcile fresh, qualified accounting at actual admission, with explicit completeness and settlement. Include auxiliary usage or label it outside the observed spend scope. Missing evidence remains unknown; session closure alone is insufficient.

### [medium] Existing controls can bypass or strand orchestration ownership

**Where:** [Owned brief and controls](/home/raven/score/docs/briefs/7.5-orchestrator.md:10), [product controls](/home/raven/score/docs/briefs/7.5-orchestrator.md:51).

**What happens:** Message Retry or summary generation admits ordinary work outside the executor. Team Resume clears legacy flags without releasing the correct orchestration hold. A brief appears done between turns while its orchestration waits at a gate.

**Why:** Current [brief status](/home/raven/score/apps/server/src/domain/briefs.ts:192) derives from ordinary turns/tasks. [Team Resume](/home/raven/score/apps/server/src/http/team-pause.ts:96) edits brief flags directly; [summaries](/home/raven/score/apps/server/src/domain/room-summaries.ts:155) reserve normal runs. Existing MCP room posts provide another mutation path.

**Change:** Supply the ownership/control matrix required by 7.1: delegate or reject every relevant room, message, summary, MCP, Flow, brief, team, and agent action. Keep guards while obligations remain unresolved. Define orchestration-owned status, typed Now decisions, expected revisions, snapshot watermarks, events, and history in the API contract before implementation.

### [medium] Failed dependencies and unproductive lead turns have no disposition

**Where:** [Wake conditions](/home/raven/score/docs/briefs/7.5-orchestrator.md:15), [assignment dependencies](/home/raven/score/docs/briefs/7.5-orchestrator.md:22).

**What happens:** Step A fails and B waits forever for A to succeed. A lead returns prose without assigning, asking, or finishing, leaving no future wake source. The last permitted lead turn creates work whose completion cannot be processed.

**Why:** There is no transition table for failed/cancelled dependencies, lead failures, no-op turns, or exhausted limits. Budget/deadline events also cannot always wake a lead because admission is already fenced.

**Change:** Validate dependency IDs as existing, earlier steps in the same run. Define failure/skip propagation, cancellation of blocked descendants, and explicit dispositions for every lead outcome. Specify deterministic behavior at turn exhaustion and when no wake source remains. Budget and deadline handling must work without spending another lead turn.

### [medium] The limits do not bound prompts, commands, or retained growth

**Where:** [Full lead snapshots](/home/raven/score/docs/briefs/7.5-orchestrator.md:12), [storage limit](/home/raven/score/docs/briefs/7.5-orchestrator.md:46).

**What happens:** Thirty 8 KiB results already produce roughly 240 KiB before other context. Repeated frozen snapshots exceed the 2 MB run allowance. Plan replacements, notes, questions, refusals, waiting runs, and unresolved attempts have no specified aggregate limits.

**Why:** Step and turn counts do not bound total rendered input or command traffic. The brief omits global/per-agent capacity accounting, storage reservation scope, control-record headroom, and protected retention eligibility.

**Change:** Bound every text/array field, total rendered UTF-8 input, and command count. Define bounded result selection for controller context. Count admitting, stopping, paused-active, and unknown work against shared capacity. Reserve storage for admitted obligations and Stop records. Prune from a persisted quiescence/abandonment boundary, preserving unresolved evidence and tombstones.

### [medium] Existing Watch cannot provide the inherited attempt scope

**Where:** [Watch reuse](/home/raven/score/docs/briefs/7.5-orchestrator.md:18).

**What happens:** Early frames remain unassociated, compression continuations disappear, and replay includes another attempt’s markers, browser context, or live state.

**Why:** [Frame storage](/home/raven/score/apps/server/src/domain/watch-frames.ts:283) lacks durable producer-session ownership; association chooses the newest matching run. [Watch queries](/home/raven/score/apps/server/src/domain/watch-frames.ts:453) remain agent-scoped, and [cleanup](/home/raven/score/apps/server/src/hub/retire.ts:96) independently removes seven-day-old frames.

**Change:** Persist qualified attempt/session ownership before dispatch and include proven compression continuations. Apply that scope consistently to every replay field and update. Keep uncertain associations explicit and expose actual retention floors separately from ninety-day orchestration history.

### [medium] MCP is unavailable in Score’s default local mode

**Where:** [Reuse of the 7.4d MCP server](/home/raven/score/docs/briefs/7.5-orchestrator.md:21).

**What happens:** A normally configured local Score installation starts an orchestration whose lead cannot reach its tools.

**Why:** [Startup](/home/raven/score/apps/server/src/start-server.ts:303) creates the MCP listener only in remote mode, and [configuration](/home/raven/score/apps/server/src/config.ts:156) rejects `SCORE_BRIDGE_PORT` without that mode. Access switches and tokens are also off or absent by default; provisioning is currently an owner-run command.

**Change:** Specify a separate loopback MCP listener for local mode, or explicitly constrain initial availability. Preflight listener availability, lead access, required write authorization, and tool readiness before starting. Preserve the current owner-controlled provisioning boundary.

## The design I would approve

- Keep short, event-driven Hermes lead runs and immediate-return tools.
- Require a per-turn capability and typed orchestration dispatch for both lead and steps.
- Make step authorization, command receipts, reservations, wake causes, and lead claims durable transactions.
- Bind human approval to immutable assignments, independently of what the lead requests.
- Define finish/drain, cancellation, unknown execution, abandonment, and restoration as explicit protocols.
- Support acknowledged unrestricted Hermes execution today, with controls and accounting accurately scoped to observed work.
- Complete the control/API matrix, accounting facts, limits, storage, and replay rules. Require fixture tests for cross-session calls, delayed calls, lost command replies, wake-up crashes, competing gates, cancel/replacement overlap, whole-home restore, lost Stop fences, and quota exhaustion.
