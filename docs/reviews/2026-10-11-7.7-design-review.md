# 7.7 design review (Codex gpt-6.1-sol, max, read-only), 2026-10-11

Reviewed: docs/briefs/7.7-coding-workers.md (design v1). Prompt: ~/.score/codex/7.7-design-review.prompt.md. Verdict: block v1.

**I would block v1 on the P1 findings below.** P1 means must fix before building. Read-only probes reproduced the access escalation, early Stop return, false termination evidence, and signaling of a reused process ID. No files changed.

1. **P1 — `completed`/`failed` does not prove the process group is gone.**  
   Locations: [process.ts:191](apps/server/src/runtimes/coding/process.ts:191), [service.ts:657](apps/server/src/runtimes/coding/service.ts:657), [executor.ts:140](apps/server/src/domain/orchestration/executor.ts:140).  
   The reaper returns `false` after its hard deadline. The runtime merely appends an error and still records `completed` or `failed`; `isEvidence` accepts both because `terminal_source` is NULL. Capacity is released and workflow success or retry becomes possible while a tool survives. The brief’s §6 and “facts” are false.  
   **Design fix:** require explicit, durable termination evidence for coding runs. A surviving or unobservable group remains unresolved, retains its process record and obligations, and supplies no consumable result.

2. **P1 — Recovery does not prove termination before deleting the process record.**  
   Locations: [proc.ts:58](apps/server/src/runtimes/coding/proc.ts:58), [service.ts:696](apps/server/src/runtimes/coding/service.ts:696).  
   `killRecordedGroup()` returns whether anything **was alive**, not whether everything stopped. It returns `true` even after the final wait expires with survivors. Unreadable `/proc` can instead produce an empty target list. `recover()` ignores the return value and deletes the record unconditionally. Changing the run to evidence-bearing `failed`, as §6 proposes, would authorize retry alongside surviving work.  
   **Design fix:** return `gone | alive | unobservable` with identity-qualified evidence. Only `gone` permits terminal failure; the other outcomes retain records and fence admission.

3. **P1 — “No process row” cannot mean “never spawned.”**  
   Locations: [process.ts:172](apps/server/src/runtimes/coding/process.ts:172), [process.ts:260](apps/server/src/runtimes/coding/process.ts:260), [service.ts:609](apps/server/src/runtimes/coding/service.ts:609).  
   The child exists and receives its prompt before `onSpawn` persists its identity. A crash in that interval leaves launched work without a row. Conversely, successful reaping deletes the row before terminal persistence, so a crash there loses the result of work that certainly ran. An `onSpawn` failure requests SIGKILL and throws without awaiting termination.  
   **Design fix:** replace §6’s inference with a durable launch phase and a supervisor release barrier before CLI execution. Delete the process record atomically with termination proof. Missing records after `send_started` remain ambiguous unless an explicit no-launch receipt proves otherwise.

4. **P1 — Recovery can kill an unrelated replacement process.**  
   Location: [proc.ts:63](apps/server/src/runtimes/coding/proc.ts:63).  
   When the recorded PID’s start time differs, recovery falls back to `groupMembers(pgid, originalStart)`. A new group leader reusing that PID/PGID has a later start time and therefore passes the filter. My mocked `/proc` probe confirmed that it receives SIGTERM despite failing the identity check.  
   **Design fix:** never treat a matching PGID plus a later birth time as ownership. Persist boot identity and use a stable supervised job identity, or individually verified member identities. A replacement leader must never be signaled.

5. **P1 — Queued workers can acquire forbidden full access after approval.**  
   Locations: [coding-agents.ts:147](apps/server/src/http/coding-agents.ts:147), [service.ts:500](apps/server/src/runtimes/coding/service.ts:500), [workflow decisions.ts:224](apps/server/src/domain/workflows/decisions.ts:224).  
   Permission and workspace PATCHes are allowed while busy. A queued turn re-reads those values at execution and passes the current permission to the driver. Approve `workspace-write`, queue behind Chat, then raise the agent to `full`: the unattended turn launches with full access. The configuration password authorizes changing the agent, not upgrading this run’s approval. Coding updates also create no lifecycle incarnation change; workflow remap rejects `untracked`.  
   **Design fix:** freeze a versioned worker policy containing runtime/version, permission, resolved workspace and effective reach. Bind approval and consent to it; revalidate immediately before launch. Always reject `full` for owned workers, and require remap/reapproval for changed unsent work.

6. **P1 — Run Stop does not revoke the coding queue’s launch authority.**  
   Locations: [orchestration decisions.ts:268](apps/server/src/domain/orchestration/decisions.ts:268), [ops.ts:67](apps/server/src/domain/orchestration/ops.ts:67), [service.ts:414](apps/server/src/runtimes/coding/service.ts:414), [service.ts:542](apps/server/src/runtimes/coding/service.ts:542).  
   Stop retires the executor attempt and records an owed Stop. It does not set the runtime’s `stopBeforeStart`. When the preceding Chat turn finishes, the queue can launch before `serviceStops()` delivers that owed request. The runtime’s final check examines only its own flag, not the durable attempt retirement or run stop fence. Batch R does not establish §5’s run-level guarantee.  
   **Design fix:** make queued launches carry an executor-owned, revocable launch authorization. The final synchronous launch check must reject stopped/cancelled attempts and expired run deadlines. Alternatively, acquire the coding slot before the executor’s final dispatch barrier.

7. **P1 — Stop acknowledgment currently means neither successful delivery nor group termination.**  
   Locations: [service.ts:442](apps/server/src/runtimes/coding/service.ts:442), [executor.ts:2405](apps/server/src/domain/orchestration/executor.ts:2405), [start-server.ts:173](apps/server/src/start-server.ts:173).  
   `CodingRuntime.stopRun()` returns immediately after requesting a signal, and returns success without doing anything when its in-memory entry is missing. The executor then stamps `stop_acknowledged_at`. An abandoned attempt can lose its remaining stop obligation despite surviving work. Simply changing this method to await the queued turn is also hazardous: Stop delivery is sequential in the executor pump, and shutdown waits for that pump before calling `coding.close()`.  
   **Design fix:** distinguish delivery acknowledgment from observed termination. Missing entries require durable reconciliation, not successful no-op acknowledgment. Cancel queued turns immediately with a no-launch proof; observe running termination asynchronously so one Stop cannot stall all reconciliation and other Stops.

8. **P1 — A session per `(run, agent)` violates fresh-attempt and workflow evidence boundaries.**  
   Locations: [executor.ts:1800](apps/server/src/domain/orchestration/executor.ts:1800), [service.ts:367](apps/server/src/runtimes/coding/service.ts:367), [coding store.ts:129](apps/server/src/runtimes/coding/store.ts:129), [planner.ts:620](apps/server/src/domain/workflows/planner.ts:620).  
   7.5 requires fresh sessions per attempt; 7.1 explicitly requires a new session on retry. Reusing one worker session silently imports previous failed, abandoned or unrelated-branch instructions and results that are absent from the approved payload and `wf_consumed`. The current runtime ignores the requested session key and resumes by room/agent. A released workflow room becomes ordinary Chat, which can then resume that same cached worker session.  
   **Design fix:** namespace sessions by owner and **attempt**, separate from Chat’s room cache. Retries, replacements and remaps get fresh CLI sessions. Cross-attempt memory would require a separate lineage/evidence design.

9. **P1 — The runtime already performs an unjournaled second execution.**  
   Location: [service.ts:612](apps/server/src/runtimes/coding/service.ts:612).  
   A resumed invocation with no observed text/tool-start and an error containing generic `"not found"` causes a fresh CLI invocation under the same run, turn and executor admission. Missing, malformed or unfamiliar events do not prove absence of side effects. The fallback also does not require `groupGone`; its next spawn can overwrite the sole process record while the first group survives. Each invocation receives a fresh 30-minute timer.  
   **Design fix:** disable this fallback for executor-owned turns. Only an authoritative pre-execution session refusal may permit another dispatch generation. Any execution retry must be separately identified, journaled, charged and preceded by qualifying termination evidence.

10. **P1 — Workflow results can be incomplete or preliminary text masquerading as final evidence.**  
    Locations: [service.ts:634](apps/server/src/runtimes/coding/service.ts:634), [translate.ts:315](apps/server/src/runtimes/coding/translate.ts:315), [planner.ts:211](apps/server/src/domain/workflows/planner.ts:211), [verdict.ts:81](apps/server/src/domain/workflows/verdict.ts:81).  
    Coding terminal ingestion never calls `recordRunResult`; it cuts output to 8 KiB. Workflows therefore lose verdicts beyond that cap instead of parsing the complete reply before truncation. More dangerously, exit 0 plus any text is accepted without a result event, and the workflow fallback treats a short string as complete. Codex concatenates assistant messages; Antigravity ignores its final response when streamed text exists. A preliminary verdict can become a branch decision.  
    **Design fix:** drivers must distinguish streaming commentary from an authoritative complete final reply. Record complete sanitized workflow facts atomically with qualifying termination, before truncation. Missing final-reply evidence produces no verdict.

11. **P1 — Unknown cost is not evidence of subscription-only billing.**  
    Locations: [budget.ts:124](apps/server/src/domain/orchestration/budget.ts:124), [translate.ts:281](apps/server/src/runtimes/coding/translate.ts:281), [env.ts:20](apps/server/src/runtimes/coding/env.ts:20).  
    No code establishes billing mode; the CLI inherits its own configuration. Usage exists only in translation memory until termination, so restart also turns potentially incurred charges into unknown cost. §9 exempts these failures automatically and labels them “quota, not money.” If billing is metered, step/minute limits cannot establish a dollar ceiling.  
    **Design fix:** preserve unknown-cost pausing by default. Any exemption needs explicit paired acceptance, scoped to the relevant coding runtime and distinguishing unmetered evidence from missing accounting. Keep Hermes uncertainty independent. Also correct the “Claude reported” fact: coding currently records `estimated`, and the live spend reader never settles costs merely because they are reported.

12. **P1 — Coding limits lack admission, lifetime and restore semantics.**  
    Locations: [service.ts:556](apps/server/src/runtimes/coding/service.ts:556), [service.ts:593](apps/server/src/runtimes/coding/service.ts:593), [journal.ts:94](apps/server/src/domain/orchestration/journal.ts:94), [fence.ts:105](apps/server/src/domain/orchestration/fence.ts:105).  
    The brief does not define whether minutes mean elapsed run time or summed worker time, when steps are debited, or how interrupted attempts retain usage. Admission-only checks can admit several long turns against the same remaining allowance; runtime fallback resets the timer. Existing journal authorization knows only dollar budget, deadline and unknown-spend acceptance. The promised “step deadline” also does not exist—7.1 explicitly removed per-node deadlines.  
    **Design fix:** specify durable debits and reservations keyed by execution identity, retain ambiguous usage, and enforce remaining time during execution and at queued launch. Reconstruct counters across restart without charging reconciliation twice. Journal any mutable coding limits and consent revocation; remove the step-deadline promise or introduce it contract-first.

13. **P2 — Keeping `cancelled` “as today” defeats the proposed stronger Stop evidence.**  
    Locations: [service.ts:511](apps/server/src/runtimes/coding/service.ts:511), [executor.ts:2249](apps/server/src/domain/orchestration/executor.ts:2249), [service.ts:709](apps/server/src/runtimes/coding/service.ts:709).  
    Every clean user Stop still records `cancelled`, which becomes `unknown` even when the group is provably gone. The run continues draining and cancellation fences remain until human abandonment. Recovery skips already-cancelled rows; terminal ingestion also refuses to update them. “Abandon should rarely be needed” is therefore false.  
    **Design fix:** separate termination proof from result disposition. Proven coding cancellation should close execution obligations without generating a success or an automatically retryable model-failure token.

14. **P2 — CLI readiness failures consume logical workflow retries instead of dispatch-refusal generations.**  
    Locations: [service.ts:154](apps/server/src/runtimes/coding/service.ts:154), [service.ts:259](apps/server/src/runtimes/coding/service.ts:259), [executor.ts:2076](apps/server/src/domain/orchestration/executor.ts:2076), [planner.ts:229](apps/server/src/domain/workflows/planner.ts:229).  
    `served` includes unconfirmed untested versions and does not express verified permission readiness. A CLI disappearing or changing after preflight produces a 422 or queued-run failure. That burns a logical attempt and can exhaust workflow retries without launching any CLI, bypassing 7.1’s reusable, journaled no-dispatch generation protocol.  
    **Design fix:** expose typed worker readiness and distinguish recoverable, proven no-launch refusals from permanent validation errors and uncertain launches. Route genuine no-dispatch cases through the bounded refusal-generation machinery.

15. **P2 — The requested recovery owner is not durable in coding intents.**  
    Locations: [hermes/port.ts:322](apps/server/src/hermes/port.ts:322), [service.ts:310](apps/server/src/runtimes/coding/service.ts:310), [service.ts:357](apps/server/src/runtimes/coding/service.ts:357).  
    The port currently permits only `owner: 'orchestration'`; workflows use that same executor owner. Coding drops owner entirely and inserts intents with owner NULL. Merely carrying the proposed argument cannot support §6’s Chat-versus-executor recovery split, particularly before `recordHandle` commits.  
    **Design fix:** persist canonical executor ownership and attempt identity before launch, including planner kind where needed. Define recovery using durable joins/metadata and preserve exclusive executor recovery authority.

16. **P2 — Moving the wrapper into startup can duplicate every coding agent.**  
    Locations: [app.ts:145](apps/server/src/app.ts:145), [coding/port.ts:47](apps/server/src/runtimes/coding/port.ts:47), [executor.ts:1506](apps/server/src/domain/orchestration/executor.ts:1506).  
    Passing the proposed shared wrapped port into `buildApp` while retaining `coding` wraps it again. Both wrappers append coding agents to team lists. Also, the brief’s separate “workflow executor” does not exist: workflow planning runs transactionally inside the one `Orchestrator`.  
    **Design fix:** construct the composite port exactly once and share it with routes and the existing executor. Preserve one admission authority and the current atomic workflow planner transactions.

17. **P2 — The consent predicate understates tool reach, and redaction cannot contain prompt injection.**  
    Locations: [claude.ts:239](apps/server/src/runtimes/coding/claude.ts:239), [claude.ts:262](apps/server/src/runtimes/coding/claude.ts:262), [antigravity.ts:279](apps/server/src/runtimes/coding/antigravity.ts:279), [redact.ts:36](apps/server/src/redact.ts:36).  
    Claude requires no read acknowledgment, but its deny rules cover selected paths and only `Read`/`Edit`, while read-only mode enables `Grep`/`Glob`. The code does not establish general secret exclusion. Antigravity explicitly advertises scheduling and subagents, which group termination cannot establish as stopped. A lead can request secret extraction; provider disclosure precedes Score’s output redaction, and encoded/unlabelled values can survive it.  
    **Design fix:** base consent on verified effective reach, including allowed tools and inherited configuration. Cover secret disclosure and background work, retain 7.5’s existing acknowledgment, and close tool-specific deny gaps. D7.1 accepts same-user risk; describe consent as accepting that risk, not proving confinement.

18. **P2 — Coding observations bypass the protected orchestration storage allowance.**  
    Locations: [translate.ts:209](apps/server/src/runtimes/coding/translate.ts:209), [translate.ts:222](apps/server/src/runtimes/coding/translate.ts:222), [ops.ts:290](apps/server/src/domain/orchestration/ops.ts:290).  
    Coding writes thinking and tool rows without `chargeObservation`, unlike the Hermes translator. Many small events can grow retained storage far beyond the run’s allowance while `stored_bytes` remains low. Bounding the final reply and allowing 32 MiB stdout does not preserve the storage/control reserve invariant.  
    **Design fix:** charge retained coding thinking/tool observations at their transactional writer and drop ordinary observations when allowance is exhausted, preserving Stop and obligation evidence.

- Keeping one shared executor and journaling `send_started` before dispatch is right; existing reconciliation already avoids accepting an ended attempt twice.
- Hermes-only leads, no worker capability, full-access refusal and explicit per-run consent are sound boundaries when enforced against frozen worker policy.
