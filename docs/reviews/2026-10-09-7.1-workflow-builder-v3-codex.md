### [high] Gateway incarnation checks do not make replay safe

**Where:** [V3 receipt rule](/home/raven/score/docs/briefs/7.1-workflow-builder.md:20), [gateway capabilities](/home/raven/score/apps/server/src/hermes/live/gateway.ts:77), [capability projection](/home/raven/score/apps/server/src/hermes/live/live-port.ts:280).

**What happens:** A request is accepted and its response disappears. Recovery observes the original gateway incarnation, but the gateway restarts before the replay POST arrives. With memory-backed receipts, the new process admits another run using the same key.

**Why:** Checking incarnation and submitting admission are separate operations; the current admission API has no incarnation precondition or replay-only operation. The premise is also inaccurate: the inspected [receipt implementation](/home/raven/.hermes/hermes-agent/gateway/platforms/api_server_run_idempotency.py:65) defaults to persistent storage and falls back to memory. Its [capability response](/home/raven/.hermes/hermes-agent/gateway/platforms/api_server_runs.py:243) reports durability and retention explicitly. Score currently discards that structured information.

**Change:** Preserve typed per-profile receipt capabilities and credential scope. Calculate recovery horizons from the first possible dispatch, including uncertain dispatch. Require proven durable reconciliation or an upstream operation that atomically refuses creation when the expected receipt/incarnation is absent. Otherwise remain `unknown`. Test a restart **between the identity check and replay POST**, not only before recovery begins.

### [high] Retiring an unknown admission does not establish execution quiescence

**Where:** [Unknown actions](/home/raven/score/docs/briefs/7.1-workflow-builder.md:9), [last-attempt resolution and run completion](/home/raven/score/docs/briefs/7.1-workflow-builder.md:34), [existing owed-stop implementation](/home/raven/score/apps/server/src/hermes/live/intents.ts:166).

**What happens:** Attempt A was accepted but is `unknown`. The person retries; attempt B succeeds and reaches an end while A remains active or unobserved. The stated completion predicate permits a successful run because it checks node state and the **last** attempt.

**Why:** Permanent retirement prevents another admission of A; it cannot terminate work already admitted. Recording an owed stop is likewise insufficient. The referenced mechanism marks Stop done after a successful response—including a stopping acknowledgement—and treats 404 as completion. V3 correctly requires terminal evidence elsewhere, but does not apply that barrier to unknown retries or successful run completion across **all** attempts.

**Change:** Track admission retirement, Stop acknowledgement, and proven termination separately. Require older attempts to become quiescent before admitting a replacement and require every admitted attempt, including retired ones, to be accounted for before reporting success. Any deliberate continuation with unresolved execution needs separately defined, recorded semantics. Test B finishing before A’s late admission or termination evidence.

### [high] The transition table cannot initialize roots or resolve local nodes

**Where:** [Transition table and node resolution](/home/raven/score/docs/briefs/7.1-workflow-builder.md:26), [termination facts](/home/raven/score/docs/briefs/7.1-workflow-builder.md:47).

**What happens:** A simple `agent → gate → end` graph never starts under the literal readiness rule: its root has no incoming token. If implementation seeds the agent informally, the gate still cannot satisfy the universal requirement that its last attempt have runtime termination evidence.

**Why:** No start node, virtual start token, or root-seeding transaction is defined. The document assigns attempts and runtime termination requirements to every node, although gates, branches, joins, and ends execute locally. The join-validation rule also refers to a `default` without defining whether that belongs to the join or its upstream branch.

**Change:** Define graph initialization explicitly. Restrict external attempts and runtime termination requirements to agent nodes; resolve local nodes through committed local evidence, such as the exact gate decision. Specify outgoing-edge resolution, fan-out cardinality, and end-node transitions in the same protocol. Test the smallest successful graph and a normal exclusive branch reconverging through an all-join.

### [high] Timeout routing conflicts with the only defined cancellation fence

**Where:** [Deadline behavior](/home/raven/score/docs/briefs/7.1-workflow-builder.md:59), [retained run-wide Stop fence](/home/raven/score/docs/briefs/7.1-workflow-builder.md:123), [run completion](/home/raven/score/docs/briefs/7.1-workflow-builder.md:38).

**What happens:** In `build → failed:repair`, a node timeout applies the defined fence, putting the whole run into `stopping`; the promised repair step cannot be admitted. An unrouted failure in one parallel branch also lacks a rule for cancelling and draining the other branch and unresolved descendants.

**Why:** V3 says expiry “fences” and then routes `failed`, but only a run-wide admission fence is defined. Node timeout and run timeout require different scopes. The precedence list does not place canonical completion relative to expiry, so arrival order can change the outcome after recovery.

**Change:** Define attempt-local timeout fences and run-wide terminal fences separately. A node timeout may release its failure handler after termination evidence; run expiry must prohibit further execution. Define cancellation/draining for unrouted failures and gate rejection. Specify deterministic completion-versus-expiry precedence and the final outcome after draining.

### [medium] Fresh session roots do not establish exact spend or replay scope

**Where:** [Session identity](/home/raven/score/docs/briefs/7.1-workflow-builder.md:11), [cost attribution](/home/raven/score/docs/briefs/7.1-workflow-builder.md:56), [compression recovery](/home/raven/score/apps/server/src/hermes/live/recover.ts:40), [frame storage](/home/raven/score/apps/server/src/domain/watch-frames.ts:283).

**What happens:** Hermes compresses an attempt’s `wf-…` session and continues in a child session. Exact-root filtering omits subsequent frames and costs. Frames arriving before the run association can still lose their attempt association.

**Why:** A unique starting session does not guarantee an immutable session ID throughout execution. Existing recovery already follows compression continuations. Existing Watch rows store `run_id`, not a durable session/attempt identity; the session is only embedded in some opaque call keys. Markers, live state, and gaps remain agent-scoped. Session cost readings likewise have no attempt-lineage ownership.

**Change:** Persist attempt-owned session lineage through the adapter, including profile and incarnation qualifications, before relying on it for attribution. Preserve uncertain associations explicitly. Scope frames, markers, gaps, pagination, and live state together. Define verified cost aggregation and final settlement across compression continuations before releasing reservations.

### [medium] Brief ownership does not cover the existing control paths or contract types

**Where:** [Projection promise](/home/raven/score/docs/briefs/7.1-workflow-builder.md:68), [Team Resume](/home/raven/score/apps/server/src/http/team-pause.ts:96), [Flow Stop](/home/raven/score/apps/server/src/http/briefs.ts:85), [current Now contract](/home/raven/score/docs/API-CONTRACT.md:394).

**What happens:** Team Pause calls the delegated brief control, but Team Resume directly clears legacy brief flags and never resumes the workflow executor’s hold. A workflow can remain paused after Resume everyone. Generic Flow/message Stop and message Retry also have no stated workflow-ownership behavior.

**Why:** Delegating brief buttons does not integrate every route touching their underlying objects. The proposed brief states `running/paused/finished` do not match the current `running/paused/done/failed` schema. Now’s `focusApproval` only accepts existing runtime approvals and their permission choices. API names and “expected run revision” do not define creation requests, gate payloads, replay scope, or historical responses.

**Change:** Enumerate all existing controls affecting workflow-owned objects and delegate or reject them explicitly. Keep team, agent, and manual holds distinct. Define run-to-brief status mapping and a typed workflow human-action target. Complete request, response, stream, conflict, and history schemas in the contract before implementation.

### [medium] Ninety-day retention can discard unfinished execution state

**Where:** [Retention and limits](/home/raven/score/docs/briefs/7.1-workflow-builder.md:63), [existing frame pruning](/home/raven/score/apps/server/src/hub/retire.ts:96).

**What happens:** A run waits at a gate or remains stopping/unknown for more than 90 days. Pruning its data can remove frozen inputs, decision evidence, unresolved stop obligations, or permanently retired admission records while they are still needed. A history marker cannot reconstruct those obligations.

**Why:** Retention has no stated origin or eligibility predicate. Deadlines are not mandatory, so unfinished runs can outlive it. It also does not explain cleanup of associated rooms, messages, intents, and frames, or reconcile the existing seven-day frame retention. Definitions retained forever and admission throughput remain outside a storage quota.

**Change:** Prune execution data only after the whole run is quiescent, using an explicit retention origin. Pin unfinished evidence and keep required admission/cancellation tombstones. Define associated-data cleanup and actual Watch retention boundaries. Add storage quotas and deterministic behavior when they are reached.

### [medium] Truncation can turn an invalid reply into a valid verdict

**Where:** [Verdict parser](/home/raven/score/docs/briefs/7.1-workflow-builder.md:50), [output bound](/home/raven/score/docs/briefs/7.1-workflow-builder.md:169), [existing output clipping](/home/raven/score/apps/server/src/hermes/live/translate.ts:335).

**What happens:** A long final reply contains a `passed` block near the beginning and a second verdict block beyond the retained output limit. Parsing the clipped text finds exactly one block and accepts a verdict that the complete reply should reject.

**Why:** V3 records truncation but does not specify parser ordering or whether truncated source text is eligible for a verdict. The current projection clips output to 8 KiB, so parsing that projection cannot establish the complete reply’s block count.

**Change:** Validate the complete sanitized final reply before presentation truncation, with an independently bounded verdict representation. If the source itself is incomplete or truncated, produce no verdict. Add tests with a second block beyond the output limit, a block crossing the truncation boundary, and unavailable final text.

## The design I would approve

- Retain the narrower Hermes-room, text-only scope and the three explicit scope cuts.
- Specify initialization, local-node evidence, edge resolution, failure draining, and terminal outcomes as one executable protocol.
- Permit uncertain replay only through proven receipt guarantees; retain unknown execution and retired attempts until accounted for.
- Separate attempt timeout fences from run termination, with deterministic completion precedence and termination barriers.
- Persist attempt/session lineage for results, spend, and every part of Watch.
- Complete the contract and all legacy-control integration; define safe pruning, quotas, and truncation-aware verdicts.
- Extend the existing fixture suite with these counterexamples before building the editor.
